### Шаг 05 закрыт: браузерная проверка и логи

**Логи не теряются.** Прежняя запись «`vite preview` не выводит `console.log`
SSR» неверна: вывод идёт в stdout процесса. Проверено на пустой БД —
`grep -n "\[user\]\|\[db\]" /tmp/preview.log` даёт

```text
3:[db] схема: применено 50, конфликтов 0, ждут решения 0
4:[user] администратор создан
5:[user]   seed (в базе):        VIWpYLpTAND_-HV3QkkElHzaIkFsNyKMwAP3OOumaD4
6:[user]   ключ взят из ADMIN_SEED — в поле «Seed» вставляется значение этой переменной
```

Причина, по которой строк в начале не было: БД открывается лениво, на первом
запросе, поэтому до первого `GET` в логе пусто. Как только первый запрос
приходит, `dbHandle` разворачивает схему и администратора и печатает отчёт
целиком. Настоящая причина неудобства была не в логе, а в том, что ключ
генерировался случайно — отсюда `ADMIN_SEED` (коммит `430f27e`): при заданной
переменной `ensureSeedAdmin` берёт её, генерирует только когда переменной нет,
а `announceSeedAdmin` различает `env` и `generated`. Оговорка: в постоянной БД
уже созданный администратор не перезаписывается — новая переменная подействует
на пустой базе.

**Ключи фильтров забронированы.** Нажатие «Выбрать пользователей» падало на
`запись: ключ «scope» никем не забронирован`: модалки фильтров писали `from`-
параметры через кодек маршрута, а маршруты `/users/filters` и `/blocks/filters`
не объявляли их в `keys`. Оба маршрута получили `search: querySchema(...)` с
разбором `from` через `localPath` и брони `from`/`scope`/`uid`. Один литерал
`from` нельзя отдать двум владельцам (реестр бросает «уже забронирован»),
поэтому оба маршрута объявляют одного владельца `user.filters`; `scope`
сохранён, потому что `BlocksFiltersModal` по нему достаёт область стора.
