## Найденные факты (важные)

- `close()` в `src/lib/modals/create.ts:504` только усекает цепочку;
  `clearMemory` при закрытии не вызывается; runtime чистится лишь
  аргумент-less `clearMemory()`. Поэтому LRU-кеш загрузчика переживает
  закрытие и повторное открытие переиспользует тот же `ck` — тезис
  «переоткрытие грузит заново» сегодня сломан.
- `releaseLayers` (`create.ts:249`) откладывает освобождение до конца
  анимации: содержимое выхода и «Вперёд» читают освобождённое. Синхронно
  чистить кеш безопасно — `ModalContent` рисует из `rt`, не из кеша.
- `commit` (`create.ts:199`) — единственная воронка изменений цепочки,
  рядом с `fireLifecycle` и `releaseLayers`.
- `store.registerMemoryCleaner` (`store.ts:108`) — точка подписки;
  `clearLoaderCache(name, params?)` (`loader.ts:372`).
- `component.svelte.ts`: `inflight` — `WeakMap<object, Promise>` (`:39`),
  `resolvedByName` — `$state` (`:42`).
- `viewGate` (`loader.ts:223`) ставит `loading` безусловно, даже когда
  данные уже в кеше.
- Глобальные обходчики стора пагинатора: `filters/FiltersPanel.svelte:122,127,133`,
  `search.svelte.ts:116`, `BlocksFiltersModal.svelte:69-81`,
  `SeedUsersFiltersModal.svelte:56-71`.
- БД открывается лениво, на первом запросе; SSR-логи (`console.log` из
  `*.server.ts`) идут в stdout процесса сразу, но до первого запроса его пусто —
  это не потеря логов, а порядок событий.
- `ensureSeedAdmin` (`admin-bootstrap.server.ts`) берёт `ADMIN_SEED` из `src/env.ts`,
  генерирует ключ только без переменной; в постоянной БД уже созданный
  администратор не перезаписывается.
- Литерал ключа адреса нельзя забронировать двум владельцам: реестр бросает
  `ключ «X» уже забронирован «A» (претендент: «B»)`, поэтому `/users/filters`
  и `/blocks/filters` объявляют одного владельца `user.filters`.

## Этапы, критерии проверки

Каждый этап — отдельный локальный коммит после зелёных гейтов

  вернулся промис; тип `ensureView` → `Promise<void> | void`;
  `setRuntime` не пишет, если `status`+`data`(+`error`) не изменились.

  `showSkeleton = hasLoader && !hasData && rt.status !== 'error'`;
  ветка ошибки и `wasPending` под `!hasData`; `loading` несёт `prev.data`.
- **03'**: `dropForClosed(prev, next)` рядом с `fireLifecycle`/`releaseLayers`:
  для каждой записи, отсутствующей в `next`, `clearLoaderCache(name, params)`
  и новый `forgetRuntime(key)`. Отдельный коммит.
- **04**: `initial` из `useLoader().data` + `invalidateLoader` в
  `onChange`/`onDone` у `ProfileModal`, `SeedUsersModal`, `BlocksModal` и
  модалок правки/удаления/создания.
- **05**: изоляция пагинатора по ключу записи, снятому на монтировании;
  владелец регистрирует/удаляет стор на mount/unmount; модалки фильтров
  читают через `modal.params`; чистка `extra.ids` переезжает в dispose стора.

### Шаг 05 закрыт: браузерная проверка и логи

**Логи не теряются.** Прежняя запись «`vite preview` не выводит `console.log`
SSR» неверна: вывод идёт в stdout процесса. Проверено на пустой БД —
`grep -n "\[user\]\|\[db\]" /tmp/preview.log` даёт

```text
3:[db] схема: применено 50, конфликтов 0, ждут решения 0
4:[user] администратор создан
5:[user]   seed (в базе):        VIWpYLpTAND_-HV3QkkElHzaIkFsNyKMwAP3OOumaD4
6:[user]   ключ взят из ADMIN_SEED — в поле «Seed» вставляется значение этой переменной
```

Причина, по которой строк в начале не было: БД открывается лениво, на первом
запросе, поэтому до первого `GET` в логе пусто. Как только первый запрос
приходит, `dbHandle` разворачивает схему и администратора и печатает отчёт
целиком. Настоящая причина неудобства была не в логе, а в том, что ключ
генерировался случайно — отсюда `ADMIN_SEED` (коммит `430f27e`): при заданной
переменной `ensureSeedAdmin` берёт её, генерирует только когда переменной нет,
а `announceSeedAdmin` различает `env` и `generated`. Оговорка: в постоянной БД
уже созданный администратор не перезаписывается — новая переменная подействует
на пустой базе.

**Ключи фильтров забронированы.** Нажатие «Выбрать пользователей» падало на
`запись: ключ «scope» никем не забронирован`: модалки фильтров писали `from`-
параметры через кодек маршрута, а маршруты `/users/filters` и `/blocks/filters`
не объявляли их в `keys`. Оба маршрута получили `search: querySchema(...)` с
разбором `from` через `localPath` и брони `from`/`scope`/`uid`. Один литерал
`from` нельзя отдать двум владельцам (реестр бросает «уже забронирован»),
поэтому оба маршрута объявляют одного владельца `user.filters`; `scope`
сохранён, потому что `BlocksFiltersModal` по нему достаёт область стора.
