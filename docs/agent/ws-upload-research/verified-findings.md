## 9. Платформа Vercel — первоисточники (доступ 2026-11-03)

`https://vercel.com/kb/guide/do-vercel-serverless-functions-support-websocket-connections`
и `https://vercel.com/docs/fluid-compute` (доступ 2026-11-03):

- «A single WebSocket connection is pinned to one Vercel Function instance» —
  соединение привязано к одному инстансу на всё время жизни.
- «WebSocket connections close when a Vercel Function reaches its maximum duration» —
  закрытие происходит по максимальной длительности функции, а не по TTL сокета.
- «New WebSocket connections are not guaranteed to reach the same Vercel Function
  instance. If a client reconnects, it may connect to a different instance» —
  переподключение может попасть на другой инстанс (проблема in-memory состояния).
- «WebSockets require Fluid compute to be enabled» — требуется Fluid compute.
- Максимальная длительность (таблица на /docs/fluid-compute): Hobby — 300 с;
  Pro/Enterprise — 300 с по умолчанию, до 800 с; расширенный максимум 1800 с (бета).
  Для значений выше 800 с требуется отдельная настройка.

Вывод: `WS_UPLOAD_MAX_DURATION` в проекте не задаёт платформенный лимит — он лишь
участвует в прогнозе. Реальный потолок задаёт платформа, и он одинаков для всех
соединений инстанса.

## 10. Понятие «паузы» в коде отсутствует в нужном смысле

`resumeGraceMs` (стр. 667–672) — это НЕ пауза между всплесками данных. Это окно
перепривязки сокета после аномального обрыва (код 1006), в течение которого
удерживается открытый `storage.put`. Комментарий стр. 664–665 прямо говорит:
«паркуем сессию на resumeGraceMs, удерживая открытый storage.put в паузе с 0% CPU».

Признака «между всплесками прогресса прошло N секунд» в коде нет: `touchActivity`
(стр. 533) продлевает единый таймер простоя независимо от того, пришли ли байты
данных или пустой `pong`. Разделения «ожидание данных» и «пауза по замыслу»
не существует — это и есть предмет проектирования.

## 11. Платформа Cloudflare — первоисточник (доступ 2026-11-03)

`https://developers.cloudflare.com/workers/runtime-apis/websockets/`
(страница помечена «Last updated Oct 12, 2026»), раздел **Connection lifetime**:

> «During routine Workers runtime updates, existing WebSocket connections to Workers
> can remain open until the process running the previous version of the Workers
> runtime exits. Connections still open when the grace period for runtime updates
> ends are disconnected. Crashes and shutdowns can disconnect clients earlier.»
> «Design clients to reconnect after a disconnection and restore application state.»

Что из этого следует практически:

- «Без потолка» в документации проекта НЕ означает бесконечное время жизни
  соединения. Соединение живёт до выхода процесса со старой версией рантайма;
  на границе grace-периода обновления рантайма оно разрывается, и это происходит
  без участия приложения.
- Cloudflare сам предписывает проектировать клиента с переподключением и
  восстановлением состояния — то есть разрыв считается штатным событием.
- Страница относится к Workers. Семантику Durable Objects (hibernation, отдельные
  правила CPU) переносить на обычный Worker нельзя; в проекте ветка `WebSocketPair`
  есть, но это не доказывает ни hibernation, ни наличие включённого DO.
- Официально рекомендуется DO, когда нужно координировать несколько соединений
  и хранить состояние между ними: «Durable Objects provide a single-point-of-
  coordination for Cloudflare Workers».

## 12. Критическая находка: единый таймер простоя обходится `pong`

Механика (проверено по коду):

- `WS_IDLE_TIMEOUT_MS = 90_000` (стр. 61) — единственный таймер простоя.
- `touchActivity()` (стр. 532–545) сбрасывает его при ЛЮБОМ входящем кадре.
- `handleTextFrame` (стр. 693–698): `touchActivity()` вызывается ДО разбора
  типа кадра, и только затем идёт `if (ctrl?.type === 'pong') return`.
- `WS_HEARTBEAT_MS = 25_000` (стр. 64): сервер сам каждые 25 с шлёт
  `{type:'ping', ts}` (стр. 551–556).

Следствие: клиент отвечает `pong` каждые 25 с → таймер 90 с сбрасывается и
НИКОГДА не срабатывает. Сокет удерживается неограниченно долго, при этом не
передано ни одного байта файловых данных и не выполнено ни одной проверки прав:
admission control (128/8 сессий, бюджет 256 МБ) срабатывает позже, внутри `init`.

Это ровно тот сценарий, против которого сформулировано требование владельца
(«сокеты не должны висеть вечно, если клиент лишь поддерживает их жизнь»).
Обновляемый (reset-on-activity) таймер не является ограничением: он ограничивает
только пассивный простой, но не активное удержание.

## 13. Чего в проекте НЕТ

- Нет HTTP-предвалидации перед открытием сокета: ни в
  `src/hooks/component-form/*`, ни в `src/routes/api/form-upload/+server.ts`.
  Вариант владельца («поля + метаданные по HTTP, затем разрешение на WS»)
  требует новой точки входа, а не настройки существующей.
- Нет понятия «пауза между всплесками прогресса»: `resumeGraceMs` — про
  перепривязку сокета, а не про темп данных.
- Нет нерасширяемого общего TTL: `WS_UPLOAD_MAX_DURATION` (src/env.ts стр. 163–168)
  описан как лимит «для прогноза успеваемости», а не как ограничитель соединения;
  дефолт для Node/Cloudflare — «без потолка».

## 14. Окно до `init` тоже без ограничения

`ws-session.server.ts` стр. 1207–1212: сразу после accept вызываются
`bindActiveSocketListeners(initialSocket)`, `attachControlFrameHandler(initialSocket)`,
`touchActivity()` и `startHeartbeat()`. То есть таймер 90 с и heartbeat 25 с
запускаются ДО того, как придёт `init` с полями и метаданными.

Поскольку `pong` продлевает таймер (п. 12), окно «сокет открыт, `init` не прислан»
не ограничено ничем, кроме платформенного потолка времени жизни функции. Ни одна
проверка (права, лимиты, бюджет, admission control 128/8) в этом окне не
выполняется: `startSessionFromInit` ещё не вызван.

## 16. Существующий фундамент политики времени: `upload-eta.ts`

В проекте УЖЕ есть модуль прогноза (`src/hooks/component-form/upload-eta.ts`),
и он ближе всего к тому, что просит владелец:

- `etaSeconds = ceil(remainingBytes / bytesPerSecond)` (стр. 179) — оценка по
  измеренной скорости, а не по догадке.
- `requiredBytesPerSecond = ceil(remainingBytes / (remainingBudgetMs / 1000))`
  (стр. 200–203) — сколько скорости ТРЕБУЕТСЯ, чтобы уложиться в остаток бюджета.
  При исчерпанном бюджете — `Number.POSITIVE_INFINITY`, то есть строгая
  невозможность, а не оценка.
- Резерв на фиксацию файла в хранилище (стр. 198) — время на `storage.put`
  вычитается из бюджета заранее, а не обнаруживается в момент отсечки.
- Защита от ложной тревоги на прогреве сокета (стр. 205–207):
  `settledMeasurement = elapsedMs >= 600 || etaSeconds * 1000 > maxDurationMs * 1.1`.
  Это ровно то различение «доказанная невозможность против ненадёжной оценки»,
  которого требует владелец: на первых миллисекундах скорость ещё не показательна.
- `willExceedLimit` (стр. 208–210) → статус `risk-timeout` и текст
  `UPLOAD_LIMIT_WARNING_RU` (стр. 112–113).

ГЛАВНОЕ ОГРАНИЧЕНИЕ: `willExceedLimit` приводит только к предупреждению
(`warningTextRu`), а не к отмене. Серверная сессия сама этот прогноз для решения
о прекращении НЕ использует — то есть политика «предупредить или отменить»
сейчас нигде не замкнута. Это и есть точка, где владельцу нужно принять решение.

## 17. Отмена не откатывает уже принятое

`abortAllPending` (ws-session.server.ts стр. 519–530) делает: `sessionFinished = true`,
снятие с `activeUploadSessions`, `clearTimers()`, `abortController.abort(reason)`,
отклонение всех `pendingPulls`, `resolveRootSession?.()`.

Отката НЕТ: поиск по `delete|rollback|cleanup|remove|unlink|discard` в файле
находит только удаления из коллекций в памяти (`activeUploadSessions.delete`,
`pendingPulls.delete`, `inFlight.delete`) — ни одной операции удаления уже
записанных байтов из хранилища.

Значит «полная отмена» в текущей реализации = прекратить приём и разорвать поток
(`storage.put` прерывается через `abortController`), НО частично принятые файлы
остаются в хранилище в неполном виде. Владельцу нужно решить, входит ли в
«полную отмену» удаление частично записанного.

## 19. Уточнение к п. 12: admission control не покрывает сокет без файлов

Реестр активных сессий и лимиты 128/8 применяются ТОЛЬКО внутри ветки
`if (init.files.length > 0 && resumeGraceMs > 0)` (стр. 933). Там же живёт и
чистка записей старше 24 ч (стр. 936).

Следствие: сессия, которая открыла сокет и не прислала валидный `init` с файлами,
в реестр не попадает вообще. Лимитов на число таких сокетов нет. В сочетании с
п. 12 (пустой `pong` продлевает простой) это значит: удержание сокета возможно
без единого байта данных И без расхода квоты сессий.

Разрыв между «проверка лимитов» и «факт открытия сокета» — главный аргумент в
пользу того, чтобы ограничение времени жизни начиналось в момент accept, а не в
момент `init`.

## 20. Что защищено ДО апгрейда, а что только после `init`

`src/routes/api/form-upload/+server.ts` стр. 15–25: до `101 Switching Protocols`
выполняется ТОЛЬКО `originGuard(...)` с `description: undefined as never`.

`src/server/form-security.server.ts` стр. 56–74: `originGuard` сравнивает
`origin` (иначе `referer`) с собственным origin, затем с доверенными шаблонами
(`trusted()`), иначе `reject(403, 'origin.rejected')`. Описание формы этому слою
не нужно и он его не читает.

Отсюда точная граница:

| Проверка | До апгрейда | После `init` |
|---|---|---|
| Происхождение (Origin/Referer) | ДА | — |
| Метод, тело, имена полей | — | ДА (`SECURITY_LAYERS`) |
| Права на форму (`createAuthorizeGuards`) | НЕТ | ДА |
| Лимиты полей, бюджет, квоты 128/8 | НЕТ | ДА |

Именно поэтому довод «немедленный WS экономит круг» верен лишь формально:
содержательных проверок до апгрейда всё равно нет, они всё равно требуют данных
формы, а значит второго прохода по пайплайну не избежать. Синтез `RequestEvent`
из `init` (п. «re-synthesis» в отчёте) существует ровно потому, что проверки
живут после `init`.

## 21. Архитектурный вывод (черновик решения)

Вариант «HTTP-предвалидация → затем WS» НЕ даёт выигрыша в безопасности сам по
себе: те же проверки (права, лимиты, бюджет) уже выполняются внутри сессии после
`init`, а до апгрейда доступна только проверка происхождения. Выигрыш варианта —
в другом: он позволяет получить ОТКАЗ обычным HTTP-ответом до открытия сокета,
не расходуя сокет и не занимая сессию на заведомо негодный запрос.

Цена варианта: лишний круг RTT, необходимость где-то хранить «разрешение» между
HTTP-ответом и апгрейдом (подписанный токен или запись в хранилище), и риск
расхождения состояния между моментом проверки и моментом апгрейда. Плюс
появляется обязательность JS-предзапроса, что усложняет сценарий без JS.

Поэтому решающим аргументом должен быть не «безопасность», а СТОИМОСТЬ УДЕРЖАНИЯ
СОКЕТА на заведомо негодный запрос. Этот аргумент закрывается и более дешёвым
способом — жёстким дедлайном от момента accept (п. 12, 19).

## 22. §4.1 Инвентаризация: переменные окружения и таймеры

## 23. Northflank: закрытие открытого вопроса со стороны кода

Внешние доки Northflank получить не удалось (обе пробы вернули 404,
`web_search` недоступен из-за 401 на стороне API-ключа). Но вопрос закрывается
со стороны кода проекта, и это надёжнее догадок:

1. `detectWsUploadPlatform()` (`src/server/ws-upgrade.server.ts:18–33`) возвращает
   только `'vercel' | 'cloudflare' | 'node'`. Определение идёт по признакам
   рантайма: `globalThis.WebSocketPair` → cloudflare, символ
   `Symbol.for('@vercel/request-context')` с `upgradeWebSocket` → vercel, иначе
   `node`. Комментарий прямо говорит: «без чтения `process.env`».

2. Northflank — это обычный Node/контейнер, поэтому он попадёт в ветку `node`.

3. В ветке `node` потолок прогноза равен `UNBOUNDED_HANDLER_TIMEOUT_MS = 24 ч`
   (ws-session.server.ts:70), а по описанию `WS_UPLOAD_MAX_DURATION` в env.ts
   Node идёт как «без потолка».

4. Поиск по `src/` не находит НИ ОДНОГО упоминания `northflank`/`NORTHFLANK`, и
   в корне нет конфигурационных файлов деплоя Northflank — коммит `8c0d16b`
   добавил `adapter-node`, стартовый процесс и мост апгрейда, но не отдельную
   обработку платформы.

Следствие: на Northflank соединение не ограничено ничем со стороны приложения,
а единственный барьер — `WS_IDLE_TIMEOUT_MS`, который обходится `pong` (п. 12).
Это самый уязвимый из трёх таргетов, и именно он требует жёсткого TTL.

ОГРАНИЧЕНИЕ ДОСТОВЕРНОСТИ: внешние лимиты Northflank (таймаут прокси/балансировщика,
максимальная длительность соединения) первичным источником НЕ подтверждены.
Причина названа: доки вернули 404, веб-поиск недоступен (401 на ключе).
Это остаётся единственным непроверенным внешним фактом в отчёте.

## 24. UX при сбоях: что реально видит пользователь (проверено ведущим)

### 24.1. Кто и с какими статусами посылает `fault`

| Статус | Текст | Закрытие | Строки |
|---|---|---|---|
| `408` | «Превышен интервал ожидания данных загрузки» | `close(1008, 'Idle timeout')` | 536–548 |
| `429` | «Too many concurrent upload sessions» | `close(1013, 'Try again later')` | 950–961 |
| `500` | «Internal upload handler error» | `close(1011, 'Internal failure')` | 1183–1196 |
| `400` | «Malformed binary segment header» и др. | `close(1002, …)` | 569, 580, 742, 894 |
| `404` | «Unknown component form» | `close(1008, 'Unknown form')` | 920–922 |

Проверено лично: строки 536–548 и 950–961 совпадают дословно.

### 24.2. Расхождение 1: тексты `fault` уходят в UI нерусифицированными

`externalFailureResult` кладёт `msg.message` прямо в `errors[0].message` без
нормализации, а `applyResult` (`src/lib/form/svelte/bind.svelte.ts:332–346`)
показывает это общим пайплайном. Подписей нет, поэтому на экране появятся
английские «Too many concurrent upload sessions» и «Unknown component form»
рядом с русским `label` из снапшота прогресса. Это единственные два
англоязычных сообщения, доходящих до пользователя.

### 24.3. Расхождение 2: `ws.disconnected` всегда получает статус `502`

Ветка `close` (стр. 718–730) собирает `externalFailureResult(req.envelope, 502,
'ws.disconnected', …)` независимо от реального кода закрытия. То есть `1002`
(серверный `fault`) и `1008` (idle / unknown form) как отдельные коды до UI не
доходят: различие остаётся только в тексте `reason` в скобках. Исключение — если
сервер успел прислать `fault` до закрытия: тогда статус берётся из `msg.status`,
а ветка `close` не срабатывает из-за `settled`.

### 24.4. Расхождение 3: `outcome: 'unknown'` неотличим от нулевого статуса

`allBytesSent` вычисляется как `receivedBytes >= size`. `submit.ts:262–273`
мапит `kind: 'network'` → `outcome: 'unknown'` со `status: policy.status.unknown
= 0`, а `kind: 'abort'` → `status: policy.status.aborted = 0`
(`src/lib/form/policy.ts:85`). Транспортный сбой и «нулевой статус» выглядят для
UI одинаково — различает их только `outcome`, если потребитель его читает.

### 24.5. Состояние `error` в прогрессе не используется никогда

`FileUploadProgressEntry.state` допускает `'error'` (`ws-protocol.ts:182`),
`Attachment.svelte` умеет рисовать `mediaVariant === 'error'` и красный
`errorText` (стр. 264–265, 331–334), НО `ws-transport.ts` присваивает только
`'uploading'`, `'processing'`, `'done'` (строки 262, 483, 490, 545, 560; поиск
`'error'` в файле не находит ни одного присваивания).

Следствие: при `fault` или обрыве запись остаётся в `'uploading'`, красная
карточка не включается, и пользователь видит ошибку только в общем списке
`form.state.shown`, но не в карточке файла. Для политики «ранняя отмена» это
важно: отмена обязана переводить карточку в видимое терминальное состояние,
иначе интерфейс продолжит показывать прогресс как идущий.
