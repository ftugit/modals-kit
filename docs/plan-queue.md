## Зафиксированные решения владельца

1. Очередь делается **через `lib/cache`** (`sharedStore` → `pgStore`), **без новой таблицы и миграции**.
2. Токен клиенту **не возвращается**: состояние живёт в БД, клиент знает только `jobId` (или ничего — опрос по ключу пользователя).
3. «В работе» пишется в БД; результат записан → метка снимается; не записан → запись истекает и считается мёртвой.
4. **Перед записью** результата проверяется, что в кэше всё ещё ждут именно это задание.
5. Инстанс может смениться — работу выполняет тот, у кого есть байты; «не запишет — печально» принимается как допустимый исход.
6. Новый аватар вытесняет старый в очереди.
7. UI показывает «аватар конвертируется».
8. **Пока очередь не сделана, серверная конвертация запрещена.** Файл обязан уже совпадать со спекой.

## Предполагаемый сценарий

```
1. Отправка формы
   execute: ник сохраняем сразу → commit() → ставим задание → ответ ok/committed + jobId
   (ник уже записан; провал конвертации его не откатывает)

2. Клиент видит «Аватар конвертируется»
   опрос статуса: GET по адресу формы + task-параметр (механика `#hooks/component-form`)

3. Исполнитель
   а) тот же запрос после ответа (`waitUntil`) — быстро, не гарантированно;
   б) при опросе: если задание ждёт и аренда свободна — выполняет этот запрос.

4. Конвертация
   claim → decodeWithNode → frame(cover) → fit(≤ maxBytes, deadlineMs) → url

5. Перед записью — проверка «ждут ли ещё»
   get('user:<uid>').jobId === jobId ? пишем : выбрасываем результат

6. Запись
   updateProfile({ avatarUrl }) → set(status: 'done', url) → delete(lease)

7. Провал
   аренда истекает → задание считается мёртвым → UI: «не удалось, попробуйте снова»
```

## Модель данных: ключи в `scope('photo-job')`

| Ключ | Значение | TTL | Смысл |
|---|---|---|---|
| `user:<uid>` | `{ jobId, status: 'queued'\|'running'\|'done', url?, at }` | 30 мин | что показывать; один на пользователя ⇒ новый вытесняет старый |
| `lease:<jobId>` | `{ owner }` | 30 с | «в работе»; продлевается `set`, перехватывается `add` после истечения |

Аренда выражается TTL: `add` в `pgStore` (`cache-db.ts:156–172`) пишет через
`ON CONFLICT … DO UPDATE … WHERE expires_at <= now() RETURNING key` — вернул
`true` — владелец, `false` — держит кто-то живой, истёк — перехват.
`get` отдаёт только живое (`LIVE`), поэтому отдельного статуса «мертва» не
нужно: метка просто перестаёт существовать.

## Операции ядра (`src/lib/queue/`)

| Функция | Что делает |
|---|---|
| `enqueue(uid, meta)` | новый `jobId`, `set('user:'+uid, {status:'queued'})` |
| `claim(jobId)` | `add('lease:'+jobId)` → `'ok' \| 'busy' \| 'gone'` |
| `touch(jobId)` | продлить аренду (`set` с тем же TTL) |
| `stillWanted(uid, jobId)` | `get('user:'+uid)?.jobId === jobId` — **проверка перед записью** |
| `settle(uid, jobId, url)` | `set(done)` + `delete(lease)` — только после успешной записи |
| `cancel(uid)` | новый `jobId` или `delete` — старая работа увидит расхождение |

Всё — над `AtomicStore` из `lib/cache`. Реализация по умолчанию — `memoryStore`
(тесты), прод — `sharedStore` (`pgStore`).

## Камни (все, что обсуждены)

### 1. Таймер не защищает от насыщения
WASM-энкод блокирует event loop — `setTimeout` не сработает, пока он крутится.
`Limits.timeoutMs` и `deadlineMs` помогают от **ожидания**, но не от **счёта**.
Значит нужен admission control (сколько одновременно) и/или `queued`, а не таймер.

### 2. Убить работу нельзя, пока нет Worker
`Promise.race` прекращает ожидание, а не работу. `worker.terminate()` есть только
на Vercel Node; на Cloudflare `node:worker_threads` — нефункциональная заглушка.
Единственная универсальная отмена — `AbortSignal` в конвейере `#lib/image`
(проверки по строкам уже есть), и она не прерывает один `codec.encode`.

### 3. Байты не переезжают между инстансами
`File` живёт в памяти принявшего запроса. Умер инстанс — у другого нет исходника.
Пока нет `lib/storage`, «другой инстанс доделает» невозможно. Обходной путь на
будущее: положить исходник объектом, в кэше держать ключ.

### 4. Нет транзакции между записью аватара и меткой
`updateProfile` и `set(status:'done')` — два разных хранилища (БД домена и
cacheKv). Порядок: **сначала данные, потом метка**. Худший случай — «в профиле
новое, а в UI ещё конвертируется»; обратный порядок дал бы ложное «готово».
Полная атомарность потребовала бы таблицы в `lib/db` — отклонено владельцем.

### 5. Окно между проверкой и записью
`stillWanted` → `updateProfile` — один запрос к БД (миллисекунды против 4,5 с
конвертации). Полностью закрывается лишь транзакционной проверкой. При
необходимости: повторная проверка после записи + откат на `prevUrl`.

### 6. Проверка нужна дважды
Перед конвертацией (не тратить CPU, если уже сменили) и перед записью
(не перезаписать новое). Это разные проверки в разные моменты.

### 7. TTL аренды против длительности
Аренда короче конвертации → двое возьмут одно задание. Длиннее → мёртвая работа
блокирует ключ. Правило: `lease ≥ 2 × худшего времени` + `touch` между ступенями.

### 8. Опрос чужого задания
`jobId` — UUID v4 + сверка `user_id` из сессии. Иначе чужой читает чужой статус.

### 9. Нельзя хранить `File` в кэше
Значения кэша JSON-совместимы (и в `pgStore` сериализуются). Байты — нет.
Вес для лимитов считать по `size` + `w*h*4`, сами байты не кладём.

### 10. Память под несколько работ
Кадр 4000×3000 = 48 МБ RGBA. Пять одновременных — 240 МБ на инстанс. Нужен
`maxWeight` и отказ до декодирования, а не «попробуем».

### 11. Смерть после `claim` до `settle`
Метка `lease` истечёт, `user:<uid>` останется `running` до своего TTL (30 мин).
Либо учитывать: `running` + нет живой аренды = мёртвое (проверять при опросе).

### 12. Вытеснение должно быть явным
Новый аватар = `set` нового `jobId`. Старая аренда истечёт сама, а её результат
`stillWanted` отбросит. Удалять `lease` старого задания не нужно и нельзя —
ключ `jobId` мог быть уже переиспользован.

### 13. Опрос и без JS
`queued` по контракту обязан дать `statusUrl` — страницу, где видно состояние.
Иначе исход-тупик (`QueuedWithoutProtocolError`).

### 14. `pgStore` вычищает просроченное на записи
`DELETE … WHERE expires_at <= now()` не чаще периода на инстанс. Мёртвые
`lease`-ключи уедут сами; читать их всё равно нельзя из-за `LIVE`.

### 15. Насыщение — это арифметика
Одна конвертация = T секунд CPU. Инстанс с C ядрами держит не больше C/T
одновременно. Всё выше — очередь или быстрый отказ (`429`/`503` + `Retry-After`).
Счётчик одновременности — `incr` в кэше (образец: `hyperdrive.ts`, `active >= max`).

### 16. Запись «мёртвая» не должна врать
Мёртвым считается задание, чья аренда истекла и данные не записаны. UI в этот
момент говорит «не удалось», а не «конвертируется» — TTL `user`-ключа для этого
короткий, либо статус пересчитывается при опросе.
