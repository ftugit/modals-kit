# План ускорения и упрощения прогона тестов (`2026-10-30`)

## Контекст и проблема

Тестовый контур репозитория даёт отличное покрытие (юнит-тесты, PGlite, SSR, no-JS, курсоры, скролл, мобильный тач, доступность `axe-core`), но из-за накопившихся фиксированных пауз, ожиданий `networkidle`, искусственных задержек демо-источников и монолитных скриптов полный цикл верификации стал слишком медленным — особенно в однопоточных контейнерах с лимитом ~2 ГБ ОЗУ:

1. **`test/browser/db-demo.mjs` + `test/browser/paginate.mjs` занимают ~165 секунд**, хотя полезной работы браузера там на ~20–25 секунд:
   - В `test/browser/paginate.mjs` (860 строк) — более **25 вызовов `sleep(300..1500)`** (~22 секунды безусловного сна).
   - В `test/browser/db-demo.mjs` (525 строк) — **~13 секунд `waitForTimeout`**, включая одиночный `waitForTimeout(7000)` на строке 344 ради ожидания нескольких тиков live-опроса.
   - В двух этих файлах **34 вызова `page.goto(..., { waitUntil: 'networkidle' })`**: каждый ждёт минимум `500 мс` полной сетевой тишины после последнего ответа (ещё ~20–25 секунд на пустом месте, а при включённом опросе может затягиваться ещё сильнее).
   - В `src/content/demo-catalog/items/items.ts` зашита константа `DEMO_TRANSPORT_MS = 500`, которая усыпляет **каждый** клиентский запрос товаров и фото на полсекунды. Эта задержка нужна глазу человека в ручном демо и ровно двум секциям в `paginate.mjs` («Скелетоны подгрузки» и «Строка „Загрузка…“ без скелетонов»), но тормозит все остальные секции (персист настроек, якоря, селекты, мобильное касание и т.д.).
2. **Все `test/browser/*.mjs` (24 файла, ~11 200 строк) монолитны и не имеют фильтра секций**:
   - Чтобы проверить одну правку в конце `paginate.mjs` или `regressions.mjs` (1814 строк), приходится каждый раз ждать прогон всех предыдущих блоков.
   - `npm run test:browser` в `package.json` последовательно запускает 16 отдельных процессов Node — многие из них сами поднимают и гасят свой `vite preview` и свой экземпляр Chromium.
3. **`vitest run src/lib/db` занимает ~55–65 секунд**:
   - В `src/lib/db/test/{db-port-specific,db-sync,db-rules,db-exists,db-acl-grants,db-sync-admin}.test.ts` многократные вызовы `withTestDb` каждый раз с нуля инициализируют PGlite WASM и накатывают схему (~4–6 секунд на один холодный старт).
4. **Устаревший ручной пробник `test/http/db-demo-http.check.mjs`**:
   - Не включён в `package.json`, но лежит в `test/http/` со старым контрактом формы создания без чекбокса `agree=on` и старой разметкой `id` строки — при ручном запуске падает с ложными `422` и сбивает с толку.

## Цель и жёсткие инварианты

**Цель**: ускорить прогон браузерных и DB-тестов в **3–5 раз** и дать быстрый точечный запуск отдельных секций за **3–5 секунд**, **не удалив и не ослабив ни одной существующей проверки**.

### Обязательные ограничения (не нарушать)

1. **Покрытие 1-в-1**: все проверки в `db-demo.mjs`, `paginate.mjs` и остальных сьютах (SSR, no-JS, курсорные закладки `page.beg` / `page.after`, отложенный срез `page.asof` и все режимы `PageSlice`, покадровые замеры скелетонов `dur` и `delay >= 250 мс`, скролл хоста, мобильный Pixel 7, `axe-core` WCAG 2.2 AA) сохраняются полностью.
2. **Поведение демо для человека не меняется**: при обычном открытии `/paginator` и `/db-demo` в браузере пользователем задержка `DEMO_TRANSPORT_MS = 500` и штатный интервал live-опроса остаются прежними. Ускорение включается только явным тестовым сигналом (заголовок / кука / query-параметр / env).
3. **Чистота слоёв (`AGENTS.md` и `tooling/*.test.mjs`)**:
   - `src/lib/*` остаётся полностью независимым от фреймворка, маршрутов и демо-стендов (`npm run test:guard` — 146/146).
   - Никаких ручных маркер-классов мимо UnoCSS (`npm run test:classes` — 0 маркер-классов).
   - `npm run check` — `0 errors, 0 warnings`.

## Этапы работ

### Этап `T1` — Общая обвязка браузерных тестов и фильтр секций (`test/browser/_harness.mjs`)

Создать компактный общий модуль для `test/browser/*.mjs` без сторонних зависимостей:

- **Именованные секции и фильтр `TEST_FILTER`**:
  - Обёртка `await section('slice', 'PageSlice (src=db)', async () => { ... })`.
  - Если задан `TEST_FILTER` (например, `TEST_FILTER=slice node test/browser/paginate.mjs` или `TEST_FILTER=cursor,slice`), выполняются только совпадающие по ключу/названию секции, остальные помечаются как пропущенные в выводе. Без `TEST_FILTER` выполняются все секции в прежнем порядке.
- **Детерминированные хелперы вместо `sleep` и `networkidle`**:
  - `gotoReady(page, url, selector?)` — навигация с `waitUntil: 'domcontentloaded'` + ожидание целевого селектора (например, `[data-paginator-host]`, `form`, маркера гидрации) вместо ожидания 500 мс тишины `networkidle`.
  - Хелперы ожидания факта: смены `location.href` / `searchParams`, появления/исчезновения узла, изменения текста или атрибута.
- **Единое управление preview-сервером**:
  - Поддержка уже запущенного сервера (`MODALS_BASE` / `MODALS_PORT`, быстрая проверка порта) и корректная передача дефолтных тестовых секретов (`AUTH_SEAL_SECRET`, `DB_CURSOR_SECRET`), если они не заданы снаружи, с прогревом `/db-demo` одним запросом при необходимости.

### Этап `T2` — Управляемые задержки в демо-слое (`/paginator` и `/db-demo`)

2. **`src/routes/(site)/(app)/db-demo/live.svelte.ts` и `DbPostsList.svelte`**:

## Попутные заметки по окружению (чтобы не тратить время на разведку)

- Секреты для `vite preview`: `AUTH_SEAL_SECRET` (не короче 32 символов) и `DB_CURSOR_SECRET` (формат `k1:<не короче 32 символов>`). Порт по умолчанию `5173` входит в `PREVIEW_PORTS` (проверка `Origin` для POST экшенов форм).
- В `test/browser/forms-a11y.mjs` не следует переопределять `FORMS_BASE` на корень сайта — по умолчанию он сам указывает на `/form`.
- Для инъекции `axe-core` на страницах со строгим CSP в контексте Playwright нужен `bypassCSP: true`.
- В контейнерах с ~2 ГБ RAM для `npm run check` и `npm run build` рекомендуется `NODE_OPTIONS="--max-old-space-size=1536"`, а для `vitest` — `--maxWorkers=1` (при включённых PGlite-тестах), предварительно останавливая `vite preview`.
