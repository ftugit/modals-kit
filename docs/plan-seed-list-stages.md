### Исследование (2026-10-27): что поможет из существующего

- **Демо-данные готовы**: `demo-profile-seed-100` даёт никнеймы
  `demo-user-001…100` всем демо-аккаунтам, включая 20 удалённых, — столбец
  и поиск проверяются сразу, в т.ч. в связке с состоянием удалённости.
- **Схема профиля готова**: `nickname` объявлен `filters: ['eq',
  'icontains']`, `orderable: true`, `read: () => true` — слой умеет
  подстрочный поиск по никнейму из коробки (в отличие от `seed`, где
  подстрока делается адаптером вручную).
- **Право и флаг**: политика чтения профиля —
  `ownerOrRoles('auth_id', ['admin', 'profile.read', 'profile.edit'])`.
  `account.read` сам по себе чужие профили не открывает, поэтому зритель
  списка с только `account.read` никнеймов не увидит. Прецедент флага —
  `canSeeDeleted`: домен считает `canSeeNickname`, UI имён прав не знает.
- **Поиск**: нынешний `searchSeed` в адаптере `listPage` выбирает срез
  батчами по 100, режет подстроку в JS и считает `total` по совпавшим
  («таблица аккаунтов мала»). Никнейм
  ложится в тот же проход: карта `auth_id → nickname` по срезу, совпадение
  = seed ИЛИ никнейм. Транспорт не меняется: тот же `users.q`, тот же
  `load`; у `SearchBar` при флаге меняется только подпись/placeholder.
- **Проекция и строка**: `SeedUserView` + необязательный `nickname`,
  `SeedUsersPage` + `canSeeNickname` (оба — по образцу существующих
  полей); в `SeedUserRow` никнейм ляжет рядом со спанами прав/блокировок.

### Чего не хватает / блокеры

- **Join: связь есть, читающего join в нужную сторону нет** (уточнено
  2026-10-27 по возражению владельца). У модели связь объявлена:
  `profile.auth_id` → `db.references { resource: auth, chain: true }`.
  Но в слое это не read-join: `chain` строит цепочки удаления
  (`src/lib/db/chain.ts`), `access.link` — проверку прав через политику
  цели (`src/lib/db/access.ts`). Читающий join — отдельная декларация
  `relations` + `include` в select (`LEFT JOIN LATERAL`, политика цели
  внутри), и он односторонний: `foreignField` обязан быть PK цели,
  поэтому работает «ребёнок включает родителя» (профиль → аккаунт), а
  списку нужен обратный ход (аккаунт → профиль по `auth_id`, не PK) —
  слой отвечает `unsupported`. Два пути:
  - **A. Расширить слой**: разрешить `include` по уникальному полю цели
    (`auth_id` уже `unique: true`; LATERAL и так с `LIMIT 1`), объявить
    на `auth` связь `relations: { profile: … }` — никнейм одним запросом,
    как владелец и ожидает от `link`. Правка ядра `#lib/db` + тесты слоя.
  - **B. Батч-подгрузка без ядра**: новый метод порта профилей
    (`listByAuthIds`), gateway — один `select` ресурса профиля под
    контекстом вызывающего; карта `auth_id → nickname` в адаптере.
  Решение — за владельцем (вопрос 5 ниже).
- **Порт профилей точечный**: `ProfileStorePort.get(authId)` — по одному;
  при пути B нужен батч. У поля `auth_id` объявлен только фильтр `eq` —
  `in` слой может не пропустить; запасной путь прецедентом «таблица
  мала»: профили срезом + карта в JS.
- **Гейтинг обязателен дважды**: без прав параметр никнейма недоступен в
  фильтрах и игнорируется доменом даже из подделанного адреса; без прав
  поиск по никнейму молчит полностью (иначе `total` утекает существование
  никнеймов), в выдачу без флага `nickname` не кладём вообще.

### Решения владельца (2026-10-27)

1. **Право на никнейм** — то, что уже есть у модели (политика чтения
   профиля: `admin` / `profile.read` / `profile.edit`); флаг
   `canSeeNickname` её зеркалит. Параметр никнейма в фильтрах доступен
   только при этих правах.
2. **Параметр живёт в фильтрах**: при правах в форме фильтров доступен
   параметр никнейма (вкл/выкл). Включён — в списке появляется столбец
   никнейма и поиск работает также по никнейму. Выключен (или нет прав) —
   ни столбца, ни поиска по никнейму. Параметр — обычный ключ `extra`
   пагинатора (адрес `?users.nick=…`), домен без прав его игнорирует.
3. **Сортировка**: при включённом параметре в select порядка появляются
   варианты по никнейму (по возрастанию/убыванию); при выключенном — нет.
   Если опцию никнейма **выключают**, связанная сортировка **сбрасывается
   на умолчание поля** (у нашего поля порядка это `created-desc`; в общем
   механизме схемы — `defaultValue` того поля, чья опция скрылась), а не
   остаётся висеть скрытым значением
   (требование владельца 2026-10-27; механика сброса — п. 3 дизайна A,
   обобщённо для любого фильтра).
4. **Нет ника / нет профиля** — в столбце `NULL` (как в БД), не пусто и
   не текст-заглушка.
5. **Путь join — вариант A** (решение владельца 2026-10-27): расширить
   слой, описание — ниже. Вариант B (батч-порт) отклонён как обходной;
   вариант C (читать от модели профиля и связываться с auth) отклонён при
   обсуждении: аккаунты без профиля выпали бы из списка при включении
   опции, а фильтры этапа 1 (состояние удаления, даты, сортировки) — поля
   auth, которых у профиля нет.

### Вариант A — принятый дизайн (2026-10-27, повторный проход по коду)

Принцип владельца: приём делается **через схему**, чтобы его мог
использовать любой будущий фильтр, а не точечной логикой списка.
Три точки объявления — модель БД, форма, список; вся механика выводится
из объявлений.

**Что уже существует (проверено по коду):**

| Метод | Где | Статус |
|---|---|---|

| `include` в select: `LEFT JOIN LATERAL`, политика цели внутри, payload JSON | `src/lib/db/resource.ts` (`includes`), дубль в `raw.ts`; тесты: `db-sync.test.ts` (comments include post, оба варианта) | ✅ есть, направление «ребёнок → родитель» |
| Валидация `relations` (поля существуют, имя не поле) | `src/lib/db/validation.ts` | ✅ |
| `nickname`: `filters: ['eq','icontains']`, `orderable: true`, `read: () => true` | `src/content/user/schema.ts` | ✅ |
| `auth_id` профиля: `unique: true` + `references { auth, chain: true }` | там же | ✅ |
| `orderSQL`: всегда `NULLS LAST` дописывает PK tie-breaker | `src/lib/db/query/sql.ts` | ✅ конвенция под `NULL`-никнеймы готова |
| Флаг прав `canSeeDeleted` (домен → load → экран) | этап 1 | ✅ прецедент для `canSeeNickname` |
| Условные опции сортировки в форме фильтров (опции по удалению при `canSeeDeleted`) | `SeedUsersFiltersForm.svelte` | ✅ прецедент, но статично на момент открытия формы |
| `FieldCondition` / `visibleWhen` / `DisableRule` (условия от значений соседних полей, проверка на обеих сторонах) | `src/lib/form/describe.ts`, `spec.ts` | ✅ машина условий есть |
| Ключи `extra` + `extraField`-валидация, форма на два носителя (модалка + no-JS GET) | этап 1 | ✅ параметр `nick` ляжет так же |

**Чего не хватает (это и есть вариант A):**

1. **Слой БД: include по уникальному полю.** В `includes` (обе
   реализации — `resource.ts` и `raw.ts`) условие `foreignField =
   primaryKey` цели расширить до «PK **или поле с `unique: true`**»:
   LATERAL там и так с `LIMIT 1`, уникальность гарантирует не более
   одной строки. Объявить на модели аккаунта:
   `relations: { profile: { resource: profile, localField: 'id',
   foreignField: 'auth_id' } }` — и список получает `include:
   ['profile']` одним запросом, с политикой профиля внутри join.
2. **Слой БД: сортировка по связанному полю — через схему.** Ключ
   порядка — путь `profile.nickname`: слой проверяет по объявлениям
   (связь есть, поле цели `orderable` и читаемо), сам добавляет тот же
   LATERAL join и сортирует по `payload->>'nickname'` с конвенцией
   `NULLS LAST` и PK tie-breaker. Ограничение v1: путь — только по
   текстовым полям (`->>` — текст). Обобщённо: любая модель со связью
   получает include и сортировку по связанным `orderable`-полям без
   нового кода в доменах.
3. **Форма: условие на опции + сброс зависимого значения — через схему.**
   У `Option` нет условия (у полей есть `visibleWhen`); механизма сброса
   значения при недоступности выбранной опции в форме нет (проверено:
   `bind.svelte.ts`, `validate.ts` — невидимые поля лишь пропускаются
   валидацией). Добавить в `Option` — `when?: FieldCondition` (тот же
   тип и оценщик, что у `visibleWhen`): опции порядка по никнейму
   объявляются с `when: { field: 'users.nick', equals: '1' }`, `Field`
   показывает только опции, чьё условие выполнено по текущим значениям.
   **Семантика сброса (часть контракта `when`, не отдельный флаг):**
   скрытая условием опция не может оставаться значением — как только
   условие перестаёт выполняться, значение поля сбрасывается на его
   умолчание (`defaultValue`; у порядка — `created-desc`) в том же
   изменении, которым опцию выключили. На сервере то же значение не
   ошибка, а coercion к умолчанию (подделанный/устаревший адрес не
   роняет форму); домен дополнительно игнорирует порядок по никнейму
   при выключенной опции — три слоя говорят одно. После сброса порядок
   равен умолчанию и в счётчик активных фильтров не попадает (механика
   этапа 1/`bff262f`). Без JS сценарий недостижим из UI (опций нет в
   разметке), достижим только ручной правкой адреса — его и закрывает
   серверный coercion. Обобщённо: любой фильтр гейтит опции соседним
   параметром и получает корректный сброс зависимого значения даром.
4. **Список (без новой механики)**: ключ `extra` `nick`; форма рисует
   параметр только при `canSeeNickname` (прецедент блока удалённых);
   домен при правах+включённом параметре: `include: ['profile']`,
   `nickname` в проекцию (`null` — нет ника/профиля), поиск seed∪nickname,
   порядок `profile.nickname`; без прав параметр из адреса игнорируется.

### Дополнение к этапу 2 (2026-10-27, по обсуждению с владельцем)

Отдельный план — `docs/plan-seed-list-polish.md` (утверждён, push запрещён).
Зафиксированные в нём решения сверх исходного этапа 2:

- Параметр никнейма в форме фильтров — **чекбокс** (поддержка есть в схеме
  форм кита; `Option.when` гейтит порядок по никнейму boolean-значением).
- Поиск дополнительно совпадает **по id** (тот же серверный проход адаптера,
  что seed и никнейм, с честным `total`).
- В форме фильтров — поле размера порции (целое, **30–100**), «Порядок»
  первым пунктом; раскладка пар полей — flex-сегментами с переносом по
  образцу `HeaderRowView` шапки сайта.
- У списка нет разделителей страниц; скелетоны при подгрузке повторяют
  геометрию строки, и **сегмент никнейма у скелетона показывается только
  при включённом параметре никнейма**.
- `replaceLoading` к скелетонам отношения не имеет (только строка
  «Загрузка…» при replace) и в этой работе не меняется.
- «Это конец» показывается только после хотя бы одной догрузки
  (`loadedPages.length > 1` в общем `EndRow` пагинатора); зоны краёв
  подгрузки сверху и снизу явно зафиксированы на `40%`.

### Зафиксированная проблема (2026-10-27): носитель показывает компонент, а не решает за него

**Симптом (владелец).** Свой профиль создан и работает (меню/шапка свежие), а
через seed-список в той же вкладке без перезагрузки выглядел «не созданным»;
обновление страницы всё чинило.

**Что замерено (не гипотезы).** В цепочке два независимых снимка, их нельзя
смешивать:

1. **Экран профиля** — снимок загрузчика модалок: первый запрос `/user/<id>`
   (открытие до создания профиля или предзагрузка) запоминается по ключу
   `user.profile + id` на всю сессию вкладки; следующие открытия роут не
   переспрашивают. Модалка из меню и модалка из строки списка — одна запись
   с одним ключом, разойтись между собой не могут.
2. **Текст строки списка** (никнейм) — ячейка пагинатора: стор гидрируется
   снапшотом один раз за сессию и новые не принимает. К компоненту профиля
   пагинатор отношения не имеет: он отдаёт в модалку только `id` юзера,
   а `id` не устаревает.

«Профиль работает» владелец видел по меню/шапке — это `vault`, он обновляется
из ответа формы в ту же секунду. Серверные данные при этом всегда были верны;
редактированию снимок не мешает: форма профиля предзаполняется из `vault`
(свежий серверный ответ), а не из снимка экрана.

**Правило владельца (2026-10-27).** Модалка и роут — только носители:
максимум ACL-гейт («можно ли сюда»), дальше они показывают нужный компонент.
Рисовать UI на основе данных — дело самого компонента, а не промежуточного
звена-экрана. Профиль: один компонент, на входе только `id` юзера, данные —
запрос к `load` роута `/user/[id]`; «профиля нет» рисует сам компонент
профиля. Seed-список — не исключение: просит только то, что показывает
(нужен ник — только ник, проекция по `auth_id`; `id` профиля не нужен).
Свой ник/аватар в шапке и меню из `vault` — правильно, не трогаем (решение
владельца).

**Приёмка пилота.** Сценарий владельца без перезагрузки страницы, одна
вкладка: открыл свой профиль до создания (заглушка) → создал профиль →
открыл из меню и из строки seed-списка: везде одинаково свежий профиль.
Плюс гейты проекта и SSR-тест состояний компонента (`initial` с
`notCreated` — заглушка спеки, а не экран отказа).

**Карточка — просто вызов профиля; выбор юзера — режим списка
(уточнение владельца 2026-10-27).** `ProfileCard` не обрастает
режимами: это показ профиля по данным, и всё. Псевдо-`select` («выбор
пользователя между этапами» для админки на шагах и будущих шагов 5–8)
делается не карточкой, а списком: владелец не будет заново делать
пагинатор с фильтрами под каждый случай, когда нужен список юзеров.
Поэтому компонент списка — единственный переиспользуемый список юзеров
(пагинатор, поиск и фильтры живут внутри него один раз), а снаружи им
управляют режимом строк:

1. Режим `link` (сейчас): строка — переход в профиль (модалка/роут).
2. Режим `select`: строка — выбор. Выбор управляемый и живёт снаружи
   (хост шагов/форма): снаружи приходят выбранный `id` и обработчик
   выбора; список только рисует строки и состояние «выбрано». Выбор
   обязан переживать переходы между этапами — поэтому он не внутри
   списка и не внутри карточки. Семантика — одиночный выбор (радио).
3. Новый случай «нужен список юзеров» = тот же компонент списка в
   нужном режиме, а не новый пагинатор с фильтрами.

Приёмка: в демо-хосте шагов шаг выбора показывает список в режиме
`select`, выбор сохраняется при переходе на следующий шаг и обратно,
на следующем шаге карточка показывает выбранного; список в режиме
`link` работает как сейчас.

**Список — в том же шаге (добавлено владельцем 2026-10-27).** Список —
такой же конечный компонент для рендера в разных местах: кроме страницы
`/users` и модалки `user.list` владелец добавит его в админку, которая
рисуется через компонент шагов (`steps`). У хоста шагов маршрутного
`load` под список нет и быть не должно: шаги в этом проекте живут
самодостаточными компонентами. Следовательно, экран, которого кормят
данными носители, туда не встанет — список приводится к той же модели,
что и профиль:

1. Компонент списка сам запрашивает данные при показе через свой уже
   существующий источник (`preloadData` на `load` роута `/users` — одна
   точка доступа, как договаривались; первая порция тем же путём, что
   догрузка порций). На странице носитель может отдать SSR-снапшот
   первой порции как начальное значение (no-JS и первый рендер не
   теряем) — как компонент профиля принимает данные серверного `load`.
2. Компонент сам рисует всё своё: заголовок, поиск, фильтры, строки,
   скелетоны, пустую выдачу, ошибку догрузки. ACL сам не рисует:
   отказ источника (`fact`) сообщает носителю, а носитель показывает
   `Acl` — страница и модалка по своим данным, админка — своим гейтом
   шага.
3. Носители (страница, модалка, шаг админки) ничего, кроме ACL-гейта и
   показа компонента, не делают; регистрация модалки `user.list` теряет
   маршрутную загрузку по той же причине, что и `user.profile`
   (no-JS `href` ссылок становятся явными).
4. Ячейка пагинатора одна на все носители (`seed-users`) — страница,
   модалка и шаг админки показывают один срез; это свойство компонента,
   а не носителя. Следствие, без которого самозапрос бессмыслен: когда
   компонент при показе переспрашивает источник, стор пагинатора
   принимает свежую первую порцию вместо замороженной первой
   (поведение стора, одна правка в `lib/paginate` на все пагинаторы;
   накопленное окно при обычном mount/unmount без переспроса не
   страдает).
5. Свежесть текста строки при этом решается тем же переспросом при
   показе, без инвалидаций по мутациям: механизмов вида «форма должна
   не забыть дёрнуть» не заводим (решение владельца выше).

**Приёмка по списку.** Тот же сценарий владельца: список, открытый
страницей и модалкой после создания профиля, показывает свежий ник без
перезагрузки; один и тот же компонент без подачи данных носителем
рендерится в демо-хосте шагов (прототип админки) и показывает список;
гейты проекта зелёны.

**Механика строк (правка владельца, та же дата; заменяет режимы
строк).** Режимы `link`/`select` — неправильно: механика нажатия не
режим компонента и не живёт внутри карточки. Модель: карточка строки —
чистый рисунок юзера, существует только внутри списка (снаружи её
никто не рисует); список принимает механику снаружи фабрикой
атрибутов строки `rowAttrs(user) => LinkAttrs` и оформление выбора
`isSelected(id)`; каждая механика стоит на `href` (no-JS по
построению): профиль — `asModalLink('user.profile', { id })`; другой
компонент — та же фабрика с другой зарегистрированной парой
«модалка + роут» (например `user.remove`: модалка и страница
показывают один конечный компонент); выбор между этапами/страницами —
`asLink` с переключением id в параметре адреса (`?picked=id,id`),
выбор читается из адреса, состояния выбора в компонентах нет.

механикой, несколько выбранных, «Далее» несёт `?picked` на следующий
шаг, где тот же список показывает выбранных (срез источника по списку
id: ключ адреса `users.ids` — состояние пагинатора, домен отдаёт
список в порт, адаптер режет срез как подстроку поиска: поле `id`
вне объявленных фильтров модели). Регистрации `user.profile` и
`user.list` возвращают `route` — `asModalLink` сам строит `href`,
ручные `href` у ссылок списка убираются; показ от этого не страдает:
конечные компоненты по-прежнему сами берут свежие данные своего
роута при показе (ответ загрузчика при открытии — тот же ответ).
Приёмка дополняется no-JS пробой: браузер с отключённым JS — вход,
список страницей, строка — ссылка на роут профиля, листание
страниц списка.

**Механика строк (выполнено, та же дата).** `SeedUserCard` — чистый
рисунок внутри списка; `SeedUsersList` принимает `rowAttrs` /
`isSelected`, по умолчанию строка — `asModalLink('user.profile')`;
прототип шагов переведён на хост `url`-режима и параметрный
мультивыбор (`?picked` + срез `users.ids` на шаге подтверждения).
No-JS проба поймала два дефекта, исправленных по ходу: (1) стор
пагинатора на шаге подтверждения спорил с URL-адаптером за срез —
срез потому и живёт ключом адреса, а не пропом; (2) `asModalLink`
признавал битой живую ссылку динамического роута в SSR:
`resolve()` кита строит относительный адрес (`./user/…`), а проверка
существования роута его не нормализовала и срезала `href` у всех
таких ссылок в серверной разметке — нормализация добавлена в
`hooks/links` (по прецеденту `missingPath` у `asLink`), чинит все
динамические пары «модалка + роут», не только профиль. Пробы:
механика и шаги с JS — всё зелёно; no-JS — вход нативным POST,
строки `<a href>` на роут профиля, переход по строке, листание
`?users=2` другим срезом.

### Исследование: публичный профиль и полевые права (вопросы владельца)

- **Отдельные поля за правами — модель умеет уже сегодня.** Маска поля
  `read` в `defineResource` — `Grant`: список ролей или функция
  `(ctx) => boolean` (`ctx.principal = { id?, roles }`); `readable()`
  слоя БД отбирает в выдачу только разрешённые колонки. Сейчас у профиля
  все поля `read: () => true` — полевая видимость не используется.
- **«Ключи всем / владельцу / ролям» одним конфигом**: такого отдельного
  конфига в слое нет; конфиг — сами объявления полей (`read`-маски) +
  политика строк `policy.select`. Трёхъярусная схема «публично /
  владельцу / ролям» выражается так: публичное поле — `read: () => true`;
  ролевое — `read: ['admin', …]`; «только владельцу» маской поля НЕ
  выражается (маска видит `ctx`, но не строку) — ярус владельца даёт
  политика строк: без прав видны только свои строки. Если строки сделать
  публичными, владельческий ярус полей потребует расширения слоя
  (маска с доступом к строке) — отдельная задача, здесь не делаем.
- **Публичный профиль — возможен, в этом этапе НЕ включаем** (решение о
  публичности — владельца): нужно (а) `policy.select: policy.publicRows()`
  или отдельная публичная проекция-ресурс; (б) доменная функция чтения без
  `guard` с анонимным контекстом `{ roles: [] }`; (в) публичными
  осмысленны только `nickname` и `avatar_url` (введены юзером сами,
  никнейм неуникален), `created_at` — «на сайте с …»; id/auth_id/времена
  правок — не публиковать. До такого решения чтение — по текущим правам.

## Этап 6. Запреты удаления: спека блокировок и проверки — ГОТОВО (e85e89c)

Удаление профиля и/или seed должно блокироваться запретом из
`blocked` целевого аккаунта. Ответ на вопрос владельца: да, это дело
ACL — запрет входит в вычисление возможности по паре
«вызывающий + цель», поэтому кнопка при запрете не показывается
точно так же, как при отсутствии права; а серверная форма
перепроверяет запрет в момент отправки (его могли поставить между
показом и нажатием).

**Что уже есть.** `blocked: Blocked[]` у auth-строки
(`{scope, reason, at, until?}`), `activeBlocks()`/`fullBlock()` в
`auth.ts`; семантику имеет только `scope: 'auth'` (полный бан),
остальные сферы — свободные строки без единого списка: тексты и
состав сфер нигде не сведены.

**Работы.**

1. Единая точка сфер: `spec-block.ts` (образец — `spec-profile.ts`):
   каталог сфер с текстами — `auth` (вход закрыт), `profile.delete`
   (нельзя удалять профиль), `account.delete` (нельзя удалять seed);
   помощник «активный запрет по сфере» поверх `activeBlocks`. На
   каталоге потом строится select постановки запретов; тексты причин
   для экранов — тоже отсюда.
2. Доменное чтение профиля отдаёт возможности по цели:
   `canDeleteProfile` = (сам или `profile.edit`/`admin`) И нет
   активного `profile.delete`; `canDeleteSeed` = (сам или
   `account.edit`/`admin`) И нет активного `account.delete`. Запрет
   цели сильнее любого права, включая владельца и админа, до снятия.
3. Серверные проверки этапа 7 лягут на тот же каталог: форма
   удаления при активном запрете отвечает отдельным фактом
   (`profile.delete-blocked` / `account.delete-blocked`, тексты —
   `messages.ts` со ссылкой на спеку), а не «нет прав».

Постановка и снятие запретов (UI выдачи) в этапы 5–7 не входят:
запись `blocked` сегодня серверная (`update: []` у поля модели);
спека этого этапа — источник будущего select.

**Приёмка.** Тесты домена: запрет цели гасит флаг и у владельца, и у
админа; снятие/истечение (`until`) возвращает; чужие сферы друг на
друга не влияют. Гейты + README.

(строки умолчаний, юзерские переопределения, схемы прав ключа) НЕ
переносится: у блока нет умолчаний и бутстрап-строк, `auth_id` всегда
задан — NULL-проблем умолчаний конфига (частичные уникальные индексы)
здесь не возникает. Сидов этапа два, и оба не про данные-умолчания:
индекс и backfill (9.3).

Ресурс рядом с `user.config` в `schema.ts`, композиция — в
`db.server.ts` (ресурс в список + индекс SqlStep, по образцу
`user-config-*`):

- `id` — uuid, как везде (`createValue: crypto.randomUUID()`,
  `filters: ['eq']`);
- `auth_id` — цель, uuid, FK на auth **с цепочкой** (`chain: true`,
  как конфиг): мягкое удаление аккаунта (надгробие) историю хранит,
  жёсткая зачистка уносит её вместе с аккаунтом;
- `scope` — text 1..40: значение валидирует API каталогом
  `BLOCK_SCOPES`, схема держит строку (исторические сферы старше
  каталога читаются, `describeBlockScope` уже это умеет);
- `reason` — text 1..200 (потолок — спека раздела, не схемы формы);
- `until` — срок окончания, nullable (нет срока — бессрочно);
  `at` записи даёт `timestamps.createdAt`, снятие видно по
  `updatedAt` + `until = момент снятия`;
- `by` — uuid наложившего, без FK (история обязана пережить удаление
  аккаунта наложившего; показ терпит отсутствующего);
- исполнение — НАТИВНО моделью, контекстом актора (решение владельца:
  отдельного API не создаём). Поля: `create: ['account.block',
  'account.edit', 'admin']` у всех полей записи; `update: [...]` тот
  же круг — только у поля `until` (снятие), у остальных полей update
  закрыт всем, кроме `server` (история не правится); `read: () => true`
  при политике ниже;
- `policy`: `select: ownerOrRoles('auth_id', ['server', 'admin',
  'account.block', 'account.edit'])` (круг операции читает через
  модель сам — проверка edit⇒read из раздела выше), `insert:
  roles(['account.block', 'account.edit', 'admin'])`, `update` —
  фильтр того же круга по любым записям цели, `delete:
  roles(['server', 'admin'])` — операцией блокировки строки не
  удаляются вообще;
- `checks` ресурса (по образцу проверок моделей слоя): цель ≠ актор
  (`auth_id != ctx.principal.id`), сфера — ключ каталога, `until`
  в будущем или отсутствует. Причина (непустая, ≤200) — схема поля
  (`s.text({min: 1, max: 200})` + normalize trim в домене формы);
- `order: [['created_at', 'desc']]`; индекс SqlStep
  `user-block-ix-target` на `(auth_id, created_at)` — чтение цели
  одним select, как частичные индексы конфига.

Новое право **`account.block`** в каталоге `permissions.ts` (группа
«Аккаунты», название/описание для экрана выдачи; `ADMIN_BUNDLE`
подхватит автоматически, стражи `permissions.test.ts` проверят
полноту). Новой модели прав не создаётся — каталог единый. Круг
операции (решение владельца): держатели `account.block` (отдельная
роль — фактически модератор), `account.edit` и `admin`; права чтения
аккаунта или профиля для бана НЕ нужны ни накладывающему, ни разделу.

### Проверки, обязательные при реализации (указания владельца 2026-10-29)

1. **«Есть редактирование — есть чтение»**: владелец исходит из того,
   что право редактирования всегда идёт в комплекте с чтением.
   Проверка по коду на старте этапа: в профиле инвариант держится
   конструкцией (`schema.ts:78` — select-политика включает
   `profile.edit`; `profile.ts` — `canSeeNickname` так же), а вот
   select-политика аккаунтов (`schema.ts:173`) знает только
   `account.read` — `account.edit` там нет, его сила сегодня чисто
   доменная (удаление seed, `profile.ts:60,160`). Для блока из этого
   следует: политика чтения модели обязана включать весь круг
   операции (`account.block` и `account.edit`), а доменные признаки
   показа — не требовать `*.read` от держателя `*.edit`. Расхождения
   инварианта по ходу — фиксировать, а не обходить молча.
2. **Аналогия с конфигом — только каркас**: глобальный ключ конфига
   (строка без юзера) контролирует правила схемы, а не «значение по
   умолчанию» как таковое — умолчание значения даёт бутстрап кода,
   строка несёт схему прав. Строить рассуждения этапа на обратном
   («глобальная строка = значение для всех») нельзя; у блока
   глобальных строк нет вовсе.

### 9.2. Операции: нативно моделью, без отдельного API

Почему не как конфиг (разбор владельца записан, не переоткрывать):
политики слоя — функции только от контекста (id + роли актора),
строку-цель и соседние строки политика не видит. У конфига права
живут в данных (схема в json строки умолчания), а эффективное
значение и «значение = умолчание не хранится» — сравнение двух строк
при записи: нативно это не выражается, учить слой понятиям
«строка-умолчание» и «права из json» ради одной модели — костыль
хуже системной роли, поэтому конфиг своим API и остаётся. У блока
права статические (фиксированный круг ролей), и всё выражается
моделью: маски полей, политики, `checks`. Отдельный `block-api`
блоку не создаём.

Порт `BlockStorePort` в `ports.ts` исполняет контекстом АКТОРА
(`principalOfRow` наложившего, как профили), не системным:
`listByTarget(ctx, authId)`, `listByTargets(ctx, ids)` (батч для
списка), `insert(ctx, row)`, `update(ctx, id, {until})`. Домен
(`profile.ts`-сосед, новый `blocks.ts` в домене user):

- `blocksOf(ports, targetId): Promise<Blocked[]>` — внутреннее чтение
  для своих читателей (9.3): системным контекстом порта, строки — к
  форме `Blocked`; дальше существующие чистые функции каталога.
- `addBlock(ports, access, {targetId, scope, reason, forever, until?})`:
  guard → актор; круг операции проверяет модель (маски+политики),
  домен добавляет только то, чего модель не видит: цель существует
  (`auth.identity-unknown`), `forever`/будущий срок собран в `until`.
  Остальное (круг, не-себе, каталог сфер, причина) — модель и её
  `checks`; отказ слоя домен показывает существующими кодами.
- `liftBlock(ports, access, {targetId, blockId})`: update поля `until`
  той же записью контекстом актора; принадлежность цели и активность
  проверяет домен по чтению (истёкшую не трогаем — отказ
  `auth.forbidden`).
- `listBlocks(ports, access, targetId)`: доступ раздела домен
  проверяет кругом операции (модель владельцу цели чтение даёт —
  раздел уже, чем модель: владелец свои записи разделом не читает,
  ему факт показывает профиль); возврат — записи как есть,
  группировку делает показ через `blockActive`.

Новых кодов ошибок нет: используются `auth.forbidden`,
`auth.identity-unknown`, `permissions.unknown`, `auth.blocked`
и полевые отказы формы.

### 9.3. Перенос читателей и поля `blocked`

Порядок внутри этапа (каждый шаг — зелёные гейты):
1. Модель + порт + API + backfill (ниже); читатели ещё на массиве.
2. Читатели переключаются на `blocksOf`: вход и продление
   (`auth.ts` — 5 мест), профиль (`profile.ts`: запреты удалений,
   `longestFullBlock`, редакция причины — без изменения правил),
   список юзеров (`accounts.ts`: батч `listByTargets` по id страницы —
   без N+1; флаг бана в строке — из активных записей батча),
   `RestrictionsNotice` (источник — `auth.ts:400`, та же замена).
   Синхронные `activeBlocks`/`fullBlock` остаются чистыми функциями
   по уже загруженному списку — меняется только источник списка.
3. Поле `user_auth.blocked` снимается из модели (sync решает снятие
   колонки своим потоком решений) — после того, как backfill покрыт
   тестом, а читателей на поле не осталось (grep-страх в приёмке).

**Backfill**: SqlStep `user-block-backfill` в `db.server.ts` —
один проход `INSERT INTO public.user_block (...) SELECT ... FROM
user_auth, jsonb_array_elements(blocked)` по строкам с непустым
массивом; шаг выполняется sync-ом один раз (учёт шагов — как у
`user-config-seed-*`). Записи с неизвестной сферой переносятся как
есть (каталог — дело API записи, не истории).

### Уточнение семантики конфига (владелец, 2026-10-29) — применено к бану

Как устроен конфиг на самом деле: значение строки без юзера —
умолчание для всех, включая её схему; как только подставляется
юзер, схема работает (обрезается до упрощённой) только для этого
параметра. Перенос на бан: схема строки «без юзера» влияла бы на
тех, кто создаёт запись за юзером, — владелец опасается обратного:
чтобы, например, `account.edit` не заблокировал разделы сайта
(права записи, заданные схемой, сильнее каталога ролей). Этот риск
и закрывает нативная конструкция 9.1–9.2: у записей бана схемы в
данных нет, права — только каталог. Упрощение владельца (схема
прямо в поле значения, отдельное поле не заводить) бану не нужно:
причина бана — человеческий текст, а не машиночитаемая схема;
фиксируем, что идея рассмотрена и отклонена конструкцией, чтобы
не переоткрывать.

## Этап 10. Конфиг-модель и её API (записано 2026-10-28; ВЫПОЛНЕНО 2026-10-28)

Исполнение: ресурс `user.config.v1` (`schema.ts`), частичные уникальные
индексы `SqlStep` в `db.server.ts`, каталог ключей `spec-config.ts`,
домен `config-api.ts` (`getEffective`/`getUserKey`/`createUserKey`/
`setUserKey`/`removeUserKey`/`setDefault`/`deleteDefaultKey`), порт
`settings` + адаптер в gateway, право `config.read` в каталоге.
Тесты: `config-api.test.ts` (схемы, «умолчание не хранится», кэш,
`session.ipLock` сквозной на уровне домена), политика модели — в
`policy.test.ts`. Пересадка `createUserConfig` поверх модели — отдельным
шагом, как и было записано.

Обобщённая модель настроек «ключ — значение — юзер» с правами,
хранимыми в самой модели. Заменяет собой будущий переезд
`createUserConfig` («в БД переедут, когда появятся ACL и роли» —
ACL и роли появились). Первый потребитель — приватность профиля
(этап 8), второй известный — ключ автовыхода при смене IP
(`session.ipLock`: админ закрепляет за юзером, владелец только
читает).

### Модель (`schema.ts`, ресурс `user.config.v1`, таблица `user_config`)

- `id` — uuid.
- `auth_id` — владелец строки; `NULL` — строка умолчания (глобальный
  ключ). Уникальность пары `(auth_id, key)`: обычный `db.unique`
  NULL-дыру не закрывает (проверено пробой на PGlite: второй
  глобальный ряд с тем же ключом проходит), поэтому — **два частичных
  уникальных индекса ручным SQL** (`SqlStep` в `db.server.ts`, по
  одному разу на id): `(key) WHERE auth_id IS NULL` и
  `(auth_id, key) WHERE auth_id IS NOT NULL`. Проба подтвердила: дубли
  глобального и юзерского ключа отклоняются, один ключ мирно живёт
  глобально и за юзером, сверка схемы — `ok` без замечаний.
- `key` — имя ключа строкой (`profile.visibility`, `session.ipLock`, …).
- `value` — json; у строки умолчания может отсутствовать (тогда
  значение — бутстрап кода потребителя).
- `schema` — json, **схема хранится прямо в модели**:
  - у строки умолчания — полная схема ключа: кто меняет умолчание
    (`editDefault`), кто создаёт такой ключ за юзером (`assign`),
    кто меняет закреплённый (`editUser`), кто снимает (`deleteUser`);
    роли — из каталога `permissions.ts`, плюс специальное `owner`;
  - у строки юзера — **только упрощённая схема редактирования именно
    этого ключа** (кто может менять эту строку). Новую полную схему
    строка юзера не наследует: нет своей упрощённой — действуют
    `editUser`/`deleteUser` схемы умолчания.

### Защита (решения владельца)

1. **Новый ключ по умолчанию** создаёт только роль, закреплённая
   за `insert` политики модели (`policy.insert`, стартово —
   `admin`; создать ключ в отрыве от кода приложения бессмысленно,
   но раздел управления сможет).
2. **Ключ за юзером** создают те, кто подходит под `assign` схемы
   ключа умолчания.
3. **Значения, совпадающие с умолчанием, не хранятся**: запись
   значения = умолчание при существующей строке юзера — строка
   удаляется; при отсутствующей — молча ничего не сохраняется
   (успех без записи). Сравнение — по эффективному умолчанию
   (строка умолчания, иначе бутстрап кода).

### Конфиг-API (свой API, работа от системы)

Отдельный доменный API единственной точки доступа; операции
исполняет **от системы** (`SERVER`-контекст, как исполнитель
удаления), а права проверяет сам — по схеме ключа:

- `getEffective(userId, key)` — значение: строка юзера → строка
  умолчания → бутстрап кода. Умолчания (строки + схемы) кэшируются
  в RAM (`#lib/cache`), инвалидация — при записи умолчания через
  API; строки юзеров не кэшируются (точечное чтение по паре).
- `setUserKey(actor, userId, key, value)` / `removeUserKey(...)`:
  право — упрощённая схема строки, иначе `editUser`/`deleteUser`
  схемы умолчания; действует правило «не хранить умолчание».
- `createUserKey(actor, userId, key, value, simplifiedSchema?)`:
  право — `assign` схемы умолчания.
- `setDefault(actor, key, value?, schema?)` / `createDefaultKey(...)` /
  `deleteDefaultKey(...)`: право — `editDefault` схемы; нового ключа
  схемы ещё нет — право берётся из политики модели (`insert`).
- **Права модели — запасной уровень**: политики ресурса настроены
  консервативно (чтение — владелец своих строк и держатели
  `config.read`/`admin`; запись напрямую — `server`/`admin`) и
  работают для случаев без схемы; основной путь — только API,
  прямые записи в модель мимо API правами модели закрыты.

### Проверено по коду перед реализацией (2026-10-28, пробы на PGlite)

- **Модель**: `f.json` для `value`/`schema` — roundtrip значений и схем
  работает; `auth_id`/`key` — `immutable` без update-маски (слой иначе
  отклоняет объявление), `key` — `orderable`. Политика чтения
  «админ — всё; иначе свои строки и глобальные (`auth_id IS NULL`)»
  выражается одним `Filter` (`eq` со значением `null` слой рендерит
  как `IS NULL`). `insert: policy.roles(['admin', 'server'])` —
  не-админу новый ключ умолчания запрещён на уровне модели.
- **Связь со смертью аккаунта**: `auth_id` — `db.references` на `auth`
  с `chain: true` (как у сессии): юзерские строки уйдут цепочкой,
  глобальные (`NULL`) не тронутся.
- **Состав**: ресурс добавляется в `resources` в
  `src/server/db.server.ts` + два `SqlStep` частичных индексов; таблица
  развернётся сверкой схемы сама.
- **Порты**: `AuthPorts.config` уже есть (это `UserConfig` поверх
  кэша) — конфиг-API этапа ляжет новым портом/расширением; фейковые
  порты в тестах (`accounts`/`admin`/`emulate`) — механическая правка
  в том же коммите. Исполнение «от системы» — образец адаптеров
  gateway (`SYSTEM`-контекст, `byAuth`-паттерн профиля).
- **Кэш умолчаний**: `#lib/cache` `Store` — `set` требует срок
  (`Infinity` — явно), инвалидация — `delete`/`clear` области; под
  план ложится без доработок.
- **Для этапа 8**: узел `exists` в `Filter` реализован
  (`docs/plan-exists-filter.md`, этап 1 выполнен) — политика профиля
  по модели конфига выразима.

# Этап 1 — предложение на утверждение

## Что нашлось в коде (reuse, ничего нового не изобретаем)

- Домен: `listSeedUsers(ports, token, {page, pageSize})`
  (`src/content/user/accounts.ts`) → порт `auths.listPage(ctx, {page, pageSize})`
  → адаптер в `gateway.server.ts`: `api().select(ctx, {page, limit,
  includeDeleted: true})` + `api().count(...)`.
- Слой БД (`src/lib/db/resource.ts`) умеет серверные `filter` (DSL:
  `eq/gte/lte/isNull/icontains/…`), `order`, `includeDeleted`; счётчик
  строится на том же предикате. То есть фильтрация/сортировка/поиск
  делаются в SQL, а не на клиенте.
- Схема `user_auth` (`src/content/user/schema.ts`): у `seed` объявлены
  фильтры только `['eq']` — для подстрочного поиска надо добавить
  `'icontains'` (декларация приложения, миграция БД не нужна). `seed` и
  `created_at` сортируемы. Удалённые строки видны правам
  `readDeleted = ['server', 'admin', 'account.read']` — то есть обоим
  правам, дающим сам список; «если права позволяет» для состояния
  удалённости на сегодня всегда «да» у зрителя списка, но UI решение
  должен получать из данных `load` (флаг `canSeeDeleted`), а не хардкодить.
- Пагинатор: источник объявляет ключи фильтров (`defineSource.filters`,
  прецедент `DB_LIST_FILTER_KEYS` у постов), значения едут в
  `data(look, input)` и в URL адаптера (`?users.*`). Поисковая строка —
  `SearchBar` (`src/components/paginator/ui/SearchBar.svelte`).
  Каталожная `FiltersPanel` заточена под схемы внешних каталогов
  (Shikimori) — для нашего фиксированного набора полей она тяжела;
  берём из неё идею (форма `lib/form` + чипы применённого), не саму панель.
- Одна точка доступа к данным сохраняется: все параметры идут через
  `load` роута `/users` (SSR, модалка и догрузка `preloadData`).

## Дизайн

Над списком одна строка: слева `SearchBar`, справа кнопка «Фильтры»
(со счётчиком активных, если есть). Работает одинаково на странице
`/users` и в модалке `user.list` (экран один — `SeedUsersScreen`).

**Поиск.** Серверный, подстрочный по `seed` (`icontains`, без учёта
регистра), debounce; сброс пагинации на первую порцию. Не kit-fuzzy-скан:
тот тянет все страницы в браузер и врёт в totals; серверный поиск честно
пересчитывает `total` и готовит этап 2 (там к условию добавится nickname
через join с профилями — на клиенте это не сделать).

**Фильтры — модалка.** Новая регистрация `user.list.filters` в
`modals.ts` (ленивый компонент, как остальные `*Lazy`). Внутри — `<Form>`
кита (по AGENTS формы только так):
- select «Порядок»: сначала новые / сначала старые (по `created_at`);
  опционально — по дате удаления (имеет смысл при показе удалённых).
- «Создан: с / по» — два поля даты-времени (`created_at` виден всегда).
- «Удалён: с / по» — только если `canSeeDeleted`.
- select «Состояние» — только если `canSeeDeleted`: только действующие /
  включая удалённые / только удалённые.
- Кнопки «Применить» / «Сбросить». Применение пишет параметры в адрес
  (`?users.*`), модалка закрывается, список перезапрашивается с первой
  порции. Под списком/над ним — чипы активных фильтров с крестиками
  (или строка «Фильтры: …» с общим сбросом — минимально: счётчик на
  кнопке + «Сбросить» в модалке; чипы — если захотите).

**Транспорт и домен.** `load` читает из адреса: `users` (страница),
`users.size`, `users.q`, `users.ord`, `users.state`,
`users.created.from/to`, `users.deleted.from/to` — и отдаёт в
`listSeedUsers(..., {…, search, order, state, createdFrom, …})`.
Домен валидирует (даты, enum состояния/сортировки) и строит `Filter`:
`seed icontains`, `created_at gte/lte`, `deleted_at isNull/isNotNull`
и диапазон по `deleted_at`. Порт `listPage` расширяется необязательными
`filter/order/includeDeleted`; адаптер передаёт их в `select` и `count`
(один срез на строки и счётчик). Догрузка: источник пагинатора строит
тот же набор в href `preloadData` из текущих значений фильтров
(источник объявляет ключи, адаптер держит их в URL — механика кита).

**Права на поля времени** («к которым есть доступ»): `createdAt` в
проекции есть у всех зрителей списка; `deletedAt` и весь блок удалённых —
только с `readDeleted`. Это решает домен/`load` и отдаёт экрану флаги
(`canSeeDeleted`), экран просто не рисует недоступное.
