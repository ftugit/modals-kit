# Хранилище и раздел «Облако» (черновой план на поверхности)

Статус: **черновой набросок по идеям владельца** (зафиксировано на верхнем уровне без доведения до финальной низкоуровневой спецификации; реализация — по отдельной команде).

---

## 1. Что уже есть в коде

- Автономная библиотека `src/lib/storage`: драйверы S3, WebDAV и локального диска, потоковое шифрование `AES-256-GCM` блоками по `64 КиБ`, лимитеры скорости и параллелизма, планировщик нарезки `split`, карантин `cooldownMs`, клонирование реплик `@replica:…`, раздача `serve` с сильным `ETag` и `Range` / `If-Range` (`206 Partial Content`).
- Обезличенный технический реестр `pgStorageLedger(db)` в `src/hooks/storage-db.ts`: таблицы `storage_file` (метаданные файла, физический путь, раскладка частей по серверам) и `storage_reservation`, не привязанные ни к какому пользователю.
- Боевой пул серверов `src/server/app-storage.server.ts` и модуль `src/content/storage-servers/` (`STORAGE_ACL`: `storage.read`, `storage.edit`, `admin`, запечатывание DSN под `AUTH_SEAL_SECRET`, предпроверка с защитой от SSRF, раздача `/api/storage/[...path]` и аватары `/api/storage/avatars/…`).

---

## 2. Ключевые идеи на разработку

### 2.1. Одна самореферентная модель раздела «Облако»

Состав полей одной строки:
- `id` (`uuid`)
- `name` — отображаемое имя папки или файла
- `auth_id` (`user_id`) — владелец узла
- `cloud_id` (`uuid | null`) — родительская папка (`null` = корень)
- `file_id` (`uuid | null`) — ссылка на обезличенную строку `storage_file` (`null` = сам узел является папкой)
- `visibility` — уровень приватности по аналогии с профилем (`'all' | 'users' | 'nobody'`, либо `null` на вложенном узле для наследования от родительской папки)
- `access_uids` (`uuid[]`) — список конкретных пользователей, которым открыт персональный доступ (выбираются через готовый `user.picker`; сам механизм `schema` / `checkGrants` в `#lib/db` на `id` пользователей **не расширяем**)
- `password` (`text | null`) — опциональный хеш пароля для доступа, когда не пустили предыдущие уровни

Матрица состояний `cloud_id` × `file_id`:
- `cloud_id = null`, `file_id = null` — папка в корне;
- `cloud_id = null`, `file_id = <uuid>` — файл в корне;
- `cloud_id = <uuid>`, `file_id = null` — папка внутри папки (любая глубина вложенности);
- `cloud_id = <uuid>`, `file_id = <uuid>` — файл внутри папки.

Инвариант: `cloud_id` может ссылаться только на узел-папку (`file_id IS NULL`), без циклов на саму себя. Сама запись `storage_file` (`file_id`) никому не принадлежит и несёт только технические метаданные, физический путь и соль/отпечаток файла.

### 2.2. Трёхуровневая иерархия доступа к узлу «Облака»

Проверяется строго сверху вниз (первое сработавшее правило открывает доступ):

1. **Приватность (`visibility`) + схема самой модели (`defineAcl`)**:
   - владелец (`owner`), `admin` и обладатели служебного права чтения модели (например `storage.read`) проходят **безусловно в любом случае** — видят любые узлы и закрытые подпапки без запроса пароля;
   - для остальных проверяется эффективный `visibility` узла (`'all'` — всем, включая гостей; `'users'` — любому вошедшему; `'nobody'` — закрыто на этом уровне). Явный закрытый `visibility` на вложенной папке перебивает открытую родительскую папку и скрывает такую подпапку из списка родителя.
2. **Персональный список `access_uids` (`Uid`)**:
   - если Уровень 1 не пустил, проверяется вхождение `actor.id` в `access_uids` узла (или открывающей родительской ветки, если дочерний узел не закрыт отдельно); при совпадении узел виден и открывается без пароля.
3. **Пароль (`password`)**:
   - работает **только когда не пустили ни Уровень 1, ни Уровень 2**, но на узле (или родительской папке) установлен пароль;
   - подтверждение хранится в запечатанной `HttpOnly`-куке (одинаково работает с JS и нативным `POST` без JS): пока кука валидна и отпечаток хеша пароля совпадает — ветка открыта, иначе показывается форма ввода пароля.

### 2.3. Дедупликация в `lib/storage` по соли / отпечатку

- Обезличенный `storage_file` хранит детерминированную соль/отпечаток содержимого: если загружается файл, соль/хеш которого уже присутствует в `storage_file`, повторный физический экземпляр в облачные серверы не пишется — новый узел «Облака» получает ссылку на существующий `file_id`.
- Физическое удаление объекта из серверов пула выполняется только тогда, когда на этот `file_id` больше не ссылается ни одна живая запись.

### 2.4. Раздача с клонированных серверов сразу с нескольких узлов

- Расширить выбор сервера чтения в `lib/storage` (`readStrategy`), чтобы клонированные реплики (`@replica:…`) работали не только как аварийный резерв, а раздавали файлы параллельно с разных серверов (например по `round-robin` или шардированию), распределяя соседние посты и вложения по разным серверам пула.

### 2.5. Живучесть серверов: счётчик пропавших файлов, софт-удаление серверов и крон-реанимация

- **Счётчик фантомов («в БД числится — сервер отдаёт 404»)**: при отсутствии файла на сервере, где он записан в `storage_file`, увеличивать счётчик потерь сервера (отдавая данные с живой реплики, если она есть). При достижении порога сервер автоматически переводится в отключённое («мёртвое») состояние до ручной проверки и повторной активации.
- **Отключение и мягкое удаление серверов**: поддержать явное выключение сервера и мягкое удаление (`deleted_at`) для серверов, которые выводятся из работы, но за которыми ещё числятся файлы («до востребованности»), без разрушения исторических связей.
- **Периодический крон-опросник**: фоновая/периодическая задача перепроверяет файлы, ранее помеченные пропавшими или удалёнными на проблемных серверах; если файлы снова начинают отвечать на сервере — появляется возможность штатно восстановить их и вернуть сервер в строй.

## 3. Поверхностный план по этапам (крупными мазками)

1. **Этап 1 — Дедупликация и параллельная отдача реплик в `#lib/storage`**
   - Детерминированная соль/отпечаток в `storage_file` без повторной загрузки дубликатов и учёт ссылок перед физическим удалением.
   - Балансировка чтения между основным сервером и клонированными репликами (`readStrategy`), чтобы разные посты/файлы отдавались сразу с нескольких серверов.
2. **Этап 2 — Живучесть пула серверов и крон-проверка пропавших файлов**
   - Выключение и мягкое удаление (`deleted_at`) серверов хранения + показ реальной занятости/квот в `/storage-servers`.
   - Счётчик отсутствующих по факту файлов с авто-отключением «мёртвого» сервера до повторной активации и периодический крон-опросник для обнаружения и восстановления вернувшихся файлов.
3. **Этап 3 — Модель и серверное ядро раздела «Облако»**
   - Самореферентная модель узла (`name`, `auth_id`, `cloud_id`, `file_id`, `visibility`, `access_uids`, `password`) поверх обезличенного `storage_file`.
   - Проверка иерархии доступа (`ACL модели + visibility` → `access_uids` → `password` через запечатанную куку) и фильтрация скрытых вложенных папок.
4. **Этап 4 — Пользовательский интерфейс «Облака»**
   - Проводник папок и файлов в паре «модалка + маршрут» (работа с JS и без JS), потоковая загрузка в выбранную папку, настройка `visibility`, списка `access_uids` (через `user.picker`) и пароля, экран ввода пароля при входе по закрытой ссылке.
