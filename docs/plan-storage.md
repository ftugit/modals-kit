# Хранилище и раздел «Облако» — архитектурный и поэтапный план

Статус: **технический план до начала написания кода** (реализация — только по отдельной команде).

---

## 1. Базовая опора в текущем коде

- Автономная библиотека `src/lib/storage`:
  - драйверы S3, WebDAV, локального диска и памяти; потоковое шифрование `AES-256-GCM` блоками по `64 КиБ`; лимитеры `rate` и `concurrency`; планировщик нарезки `split`; карантин `cooldownMs` на сетевые ошибки `5xx` / обрывы; раздача `serve` с сильным `ETag` и `Range` / `If-Range` (`206 Partial Content`);
  - интерфейс реестра `StorageLedger` (`StoredFileRecord`: `path`, `name`, `size`, `storedBytes`, `type`, `lastModified`, `createdAt`, `parts`).
- Прикладной реестр и модели в БД:
  - `pgStorageLedger(db)` в `src/hooks/storage-db.ts` — обезличенные таблицы `storage_file` и `storage_reservation`, не привязанные ни к какому пользователю;
  - `storageServer` в `src/hooks/storage-schema.ts`, `src/server/app-storage.server.ts` и модуль `src/content/storage-servers/` (`STORAGE_ACL`: `storage.read`, `storage.edit`, `admin`, запечатывание DSN под `AUTH_SEAL_SECRET`, предпроверка с защитой от SSRF).

Что сейчас в коде **отсутствует или требует переработки** под новый функционал:
1. В `StoredFileRecord` нет опционального контентного хеша: `ws-integrity.ts` считает только транспортный `HMAC-SHA-256` на одноразовой сессионной соли, поэтому не даёт воспроизводимого отпечатка файла между разными загрузками.
2. При перезаписи и `storage.del(path)` код удаляет физические `parts` безусловно — без проверки, не ссылается ли на те же `(server, path)` другая запись в `storage_file`.
3. `resolveReadCandidates` в `src/lib/storage/index.ts` на каждое чтение делает цикл `ledger.getFile('@replica:' + server + ':' + path)` по всем серверам пула (`N+1` запросов к БД), всегда ставит основной сервер первым (реплики работают только как аварийный резерв), а ветка `cdn: true` зовёт `resolveReadSlot` и реплики вообще не видит.
4. Карантин `cooldownMs` реагирует только на выброшенные сетевые ошибки/`5xx`. Если запись в `ledger` есть, а драйвер вернул `null` (`404` на облаке — файл пропал), это молча игнорируется: счётчик потерь не растёт, сервер продолжает принимать новые загрузки, а запись не помечается для последующей перепроверки.

## 2. Детальная закладка механизмов Г, Д, Е

### Г. Дедупликация по включаемому хешу отдельных файлов

Ключевое правило: **хеш не считается поголовно для всех файлов в системе**. Он включается точечно (`hash: true`) на уровне конкретного вызова загрузки (`put` / `upload`), конкретного поля формы или политики сервера, и в дедупликации участвуют **только те файлы, у которых этот хеш включён**.

#### Г.1. Контракты в `#lib/storage` и схема `storage_file`
- В `StorageServerPolicy`, `StorageCallOverrides` (`StoragePutInput`, `StorageUploadOptions`) добавляется флаг:
  - `hash?: boolean` (по умолчанию `false`) — считать ли потоковый `SHA-256` по открытым (до шифрования) байтам файла и сверять ли его по реестру;
  - `expectedHash?: string` — опциональный заранее известный `sha256` (например, посчитанный на клиенте или переданный формой), который всё равно верифицируется потоком при чтении, но позволяет проверить наличие дубликата ещё **до** открытия соединения к облачному серверу.
- В `StoredFileRecord` добавляется опциональное поле `hash?: string` (`64` hex-символа `SHA-256`). Если файл загружался с `hash: false`, поле `hash` равно `undefined` (`NULL` в БД) — такой файл никогда не склеивается с другими и ни с кем не сравнивается.
- В таблицу `storage_file` (`src/hooks/storage-db.ts`) добавляется колонка `hash text` и частичный индекс `CREATE INDEX ... ON storage_file (hash, size) WHERE hash IS NOT NULL` — быстрый поиск за `O(log N)` без раздувания индекса файлами, где хеш выключен.
- В `StorageLedgerSpec` / `StorageLedger` добавляется метод:
  - `findByHash(hash: string, size: number): MaybePromise<StoredFileRecord | null>` — возвращает живую запись (не в статусе `missing`), у которой совпадают `hash` и точный `size`, и чьи `parts` находятся на не удалённых серверах.

#### Г.2. Как именно работает `put` / `upload` при `hash: true` (три сценария потока)
Потоковый хешер (`TransformStream` / чанковый `SHA-256` блоками по `64 КиБ`, `0` лишних полноразмерных буферов в памяти) встраивается прямо в конвейер `put`:

1. **Повторно читаемый источник (`File`, `Blob`, `Uint8Array`, `ArrayBuffer`) или включён `stageToDisk: true`**:
   - До создания брони `ledger.reserve(...)` и до обращения к S3/WebDAV поток один раз прокачивается через потоковый `SHA-256` (для дискового спула — прямо во время записи `.spool`-файла).
   - Вызывается `ledger.findByHash(hash, size)`.
   - **Если совпадение найдено**: сетевой вызов `driver.put` в облако **не выполняется вообще (`0` байт в S3/WebDAV)** и квота сервера повторно не расходуется. Новая логическая запись `StoredFileRecord` сохраняет в `ledger` ссылку на уже существующие физические `parts` (и `replicas`, если они есть) с тем же `hash`. В разделе «Облако» всё ещё проще: если узел просто хранит `file_id`, можно сразу привязать новый узел к найденному `storage_file.id`, вообще не плодя вторую строку в `storage_file`.
   - **Если совпадения нет**: файл штатно заливается в выбранный сервер(ы), и `commit` сохраняет запись вместе с вычисленным `hash`.
2. **Чистый однопроходный `ReadableStream` с переданным `expectedHash`**:
   - Ещё до заливки вызывается `ledger.findByHash(expectedHash, size)`. Если такой файл уже есть и жив — входящий поток дочитывается только через локальный потоковый `SHA-256` (для честной проверки, что клиент действительно прислал байты с этим хешем, а не подделал чужой `expectedHash` ради чтения чужого файла!), без отправки байтов в облако. Хеш совпал — привязываем к существующим `parts`; не совпал — отклоняем с ошибкой целостности.
3. **Чистый однопроходный `ReadableStream` без `stageToDisk` и без `expectedHash`**:
   - Байты идут потоком на сервер хранения и одновременно считаются в потоковом `SHA-256`.
   - На финише перед `ledger.commit` вызывается `ledger.findByHash(hash, size)`. Если за время приёма или раньше в реестре уже есть живой файл с тем же `(hash, size)`, запись в `ledger` переключается на существующие физические `parts`, а только что залитый лишний объект тут же удаляется (`driver.del`), освобождая бронь — дубликат на облачном сервере места не занимает.

#### Г.3. Безопасное удаление (`del` / перезапись) и честный подсчёт квоты `usage()`
Чтобы удаление одного файла не стерло физические байты на S3/WebDAV, на которые ссылается другой дедуплицированный путь:
- `ledger.deleteFile(path)` и `ledger.commit(...)` (при замене старой записи по тому же `path`) внутри транзакции реестра проверяют каждую физическую пару `(part.server, part.path)` и возвращают список **`orphanedParts: readonly StoredPart[]`** — только те физические объекты, на которые в `storage_file` больше не ссылается **ни одна** оставшаяся запись.
- `storage.del` и уборка после перезаписи вызывают `driver.del(...)` **исключительно для `orphanedParts`**. Пока остаётся хотя бы одна живая ссылка — физический файл в облаке неприкосновенен; когда удаляется последняя ссылка — файл штатно удаляется с сервера.
- Подсчёт занятого места `ledger.usage(servers)` (и в `computeLedgerUsage`, и в SQL-запросе `pgStorageLedger`) агрегирует `storedBytes` по **уникальным физическим парам `(server, path)`** (`DISTINCT ON`), чтобы 10 дедуплицированных ссылок на один файл весом `50 МБ` учитывались в квоте сервера ровно как `50 МБ`, а не `500 МБ`.

### Д. Параллельная раздача клонированных файлов сразу с нескольких серверов

Цель: когда файл склонирован на несколько серверов (`clone`), запросы чтения и отдачи не должны все бить в один «первичный» сервер — соседние посты и скачивания должны одновременно раздаваться с разных серверов пула.

#### Д.1. Уход от `N+1` запросов к БД: реплики внутри `StoredFileRecord`
- Сейчас `resolveReadCandidates` на каждое чтение делает отдельный запрос `@replica:<server>:<path>` для каждого сервера пула.
- Переносим список реплик прямо внутрь основной записи `StoredFileRecord`:
  ```ts
  export interface StoredReplica {
    readonly server: string
    readonly path: string
    readonly storedBytes: number
    readonly encrypted: boolean
    readonly etag?: string
    readonly missingAt?: number
  }
  ```
  Поле `replicas?: readonly StoredReplica[]` хранится в том же JSON-документе `storage_file.parts` / `replicas` (сохраняя обратную совместимость чтения старых `@replica:…` записей при миграции).
- В результате **один** вызов `ledger.getFile(cleanPath)` за `1` запрос к БД сразу возвращает и основной сервер (`parts`), и все его клоны (`replicas`), и отметки здоровья каждой копии. `usage()` учитывает `storedBytes` и основных частей, и всех `replicas` на соответствующих серверах.

#### Д.2. Стратегии выбора сервера чтения (`readStrategy`)
В `StorageConfig` (дефолт пула) и в опции чтения/раздачи (`StorageReadOptions`, `StorageServeOptions`) добавляются:
- `readStrategy?: 'primary' | 'round-robin' | 'consistent-hash'` (по умолчанию в `appStorage` для раздачи с клонами включаем `'consistent-hash'` или `'round-robin'`);
- `affinityKey?: string` — необязательный ключ привязки (например `postId`, `fileId` или путь файла).

Как собирается упорядоченный список серверов-кандидатов `resolveReadCandidates` из всех здоровых локаций файла `[primary, ...replicas]` (отфильтровав отключённые серверы и копии с `missingAt != null`):
1. **`'primary'`**: основной сервер первый, реплики идут следом как горячий резерв.
2. **`'round-robin'`**: атомарный курсор сдвигает стартовый сервер по кругу (`[A, B, C]` → `[B, C, A]` → `[C, A, B]`). Первый кандидат обслуживает чтение; если он в последний момент ответил ошибкой или `404` — цикл без обрыва клиента тут же берёт следующего кандидата из хвоста списка.
3. **`'consistent-hash'` (оптимально для ленты постов и медиа с `Range`)**: стартовый индекс вычисляется детерминированным быстрым хешем `fnv1a32(affinityKey ?? cleanPath) % healthyCount`.
   - Почему это важно для постов и видео: Пост №1 (`posts/101/cover.webp`) стабильно летит с Сервера A, Пост №2 (`posts/102/cover.webp`) — одновременно с Сервера B, Пост №3 — с Сервера C (браузер грузит ленту параллельно с трёх разных облаков!). При этом `Range`-докачка кусков одного большого файла (`206 Partial Content`) попадает в тот же сервер и не конфликтует по HTTP-кешу.

#### Д.3. Единообразная работа и для стриминга через `serve()`, и для прямых `302`-редиректов (`cdn: true`)
- В `storage.serve()` сильный `ETag` строится детерминированно от метаданных записи реестра (`hash` или `path + size + lastModified`), поэтому `ETag` и `If-Range` остаются **идентичными** независимо от того, какой именно сервер-реплика отдал байты (даже если у двух S3/WebDAV серверов разные внутренние серверные `etag` или разное шифрование ключом слота).
- В ветке `cdn: true` (`publicBaseUrl` для незашифрованных публичных вложений постов) убираем жёсткую привязку к `primary`: `serve()` выбирает здорового кандидата с `publicBaseUrl` через ту же `readStrategy`, поэтому клиенты получают `302` сразу на разные внешние домены облаков, разгружая и сами облака, и исходящий канал веб-сервера.

### Е. Счётчик «пропавших» файлов, отключение/мягкое удаление серверов и крон-восстановление

Здесь чётко разводим две совершенно разные аварии:
- **Транспортный сбой** (таймаут сети, DNS, `500/502/503`) — сервер временно недоступен, файл с него не удаляли → работает существующий короткий карантин `cooldownMs`.
- **Пропажа файла («фантом»)** — сервер живо ответил без сетевой ошибки, в `storage_file` записано, что файл/реплика лежит на этом сервере, но драйвер вернул `null` (`404 Not Found`).

#### Е.1. Фиксация пропажи и счётчик до перевода сервера в «мёртвый» (`dead_missing`)
1. **Точка перехвата в `#lib/storage`**:
   - В `head()`, `lazy()`, `serve()`, `copy()`, `clone()` при чтении по записи `rec` из `ledger`: если вызов драйвера к серверу `S` завершился штатно (без исключения), но вернул `null`:
     - вызывается внутренний обработчик `reportMissingPart(rec, S, partPath)`:
       - в `ledger` у конкретной части/реплики на сервере `S` ставится отметка `missingAt = Date.now()` (чтобы повторные хиты к этому же битому файлу каждую секунду не накручивали счётчик повторно — **один пропавший физический объект даёт ровно `+1` страйк серверу**);
       - если у файла есть живая реплика на другом сервере — клиент прозрачно получает файл с неё без ошибки;
       - если живых копий не осталось (или пропал один из шардов нарезанного `split`-файла) — у самой записи файла выставляется `status = 'missing'` (при этом сама строка из `storage_file` **не удаляется**, чтобы крон знал, что и где проверять).
2. **Межинстансный счётчик потерь сервера и авто-блокировка**:
   - В `StorageServerPolicy` / конфиге пула задаётся порог `missingThreshold` (например, `3` уникальных пропавших файла; настраивается глобально или на сервер в `/storage-servers`).
   - Счётчик ведётся в общем `sharedStore` / таблице `storage_server` (`missing_count`), поэтому работает согласованно между всеми serverless-инстансами.
   - Как только `missing_count >= missingThreshold`:
     - в памяти пула и через хук `onServerDead(slotName, info)` в строке `storage_server` сервер переводится в статус **`dead_missing`** (`enabled = false`, в `meta` пишутся `deadReason: 'missing_files'`, `deadAt`, `missingCount`);
     - сервер **немедленно исключается** из выбора на запись (`writePool`) и обычное чтение, и в отличие от `cooldownMs` **не включается обратно сам по таймеру** — он остаётся заблокированным до проверки и повторной активации (админом в `/storage-servers` или после успешной крон-сверки).

#### Е.2. Выключение и мягкое удаление (`deleted_at`) серверов хранения
В модели `storageServer` (`src/hooks/storage-schema.ts` и `src/content/storage-servers/`):
1. **Три явных состояния активности сервера**:
   - активен (`enabled = true`, `deleted_at = null`);
   - выключен вручную админом (`enabled = false`, `deadReason = null`) — не принимает запись и не раздаёт, включается кнопкой в `/storage-servers` после предпроверки `probe`;
   - остановлен защитой по пропаже файлов (`enabled = false`, `deadReason = 'missing_files'`) — в списке `/storage-servers` подсвечен предупреждением с числом пропавших файлов и кнопками «Перепроверить файлы» и «Включить повторно».
2. **Мягкое удаление серверов (`softDelete` через `deleted_at`)**:
   - В `STORAGE_ACL` и схему `storage_server` включается `deletedAt: 'deleted_at'`.
   - При удалении сервера проверяется `ledger.countServerReferences(slot)`:
     - если за слотом числится **`0` файлов** — строку можно удалить физически;
     - если за сервером **числятся файлы** (живые или пропавшие) — выполняется **только мягкое удаление (`deleted_at = now()`)**: сервер пропадает из активного пула («выведен до востребованности»), но его `slot` и запечатанный DSN сохраняются в архиве удалённых серверов, не ломая ссылки в `storage_file` и позволяя в любой момент восстановить сервер (`restore`) вместе с его файлами.

#### Е.3. Мягкое удаление файлов и периодический крон-опросник восстановления
1. **Индексированный контур проблемных файлов в `storage_file`**:
   - В `storage_file` добавляются поля `status text NOT NULL DEFAULT 'ok'` (`'ok' | 'missing' | 'deleted'`), `deleted_at timestamptz` и `checked_at timestamptz` с частичным индексом `WHERE status <> 'ok' OR deleted_at IS NOT NULL`, чтобы крон выбирал кандидатов за миллисекунды без полного сканирования таблицы.
   - При мягком удалении файла в приложении запись не стирается физически с облака сразу (`status = 'deleted'`, `deleted_at = now()`), оставляя окно на восстановление.
2. **Сервис сверки `reconcileStorageFiles` (крон + ручной запуск из админки)**:
   - Берёт пачку записей с пропавшими частями (`missingAt != null` / `status = 'missing'`) в порядке давности `checked_at ASC NULLS FIRST` (например, по `50` объектов за проход, укладываясь в лимиты serverless-вызова).
   - Для каждого соответствующего сервера (включая находящиеся в `dead_missing`, а по флагу — и мягко удалённые при подготовке к возврату) открывает драйвер в режиме чтения и вызывает лёгкий `driver.head(part.path)`.
   - **Если файл снова отвечает на сервере** и его размер `meta.size === part.storedBytes`:
     - снимает `missingAt` с этой части/реплики;
     - если теперь у файла доступны все необходимые части — возвращает `storage_file.status = 'ok'` (файл снова качается, а связанные узлы в «Облаке» автоматически оживают или становятся доступны к восстановлению в один клик);
     - уменьшает `missing_count` этого сервера. Когда `missing_count` у сервера в `dead_missing` падает до `0`, сервер помечается готовым к возврату (либо автоматически реактивируется, если задана политика авто-возврата после 100% нахождения файлов, либо подтверждается одной кнопкой в `/storage-servers`).
   - **Точка вызова крона**: защищённый заголовком `Authorization: Bearer <CRON_SECRET>` маршрут `/api/internal/storage-reconcile` (совместим с расписанием Vercel Cron и любым внешним планировщиком) + кнопка с прогрессом в `/storage-servers` для немедленной ручной сверки админом.

## 3. Сводка модели раздела «Облако» и иерархии доступа (зафиксировано ранее)

### 3.1. Одна самореферентная модель «Облако»
Поля строки:
- `id` (`uuid`)
- `name` — отображаемое имя папки или файла
- `auth_id` (`user_id`) — владелец узла
- `cloud_id` (`uuid | null`) — родительская папка (`null` = корень)
- `file_id` (`uuid | null`) — ссылка на обезличенную строку `storage_file` (`null` = папка)
- `visibility` — `'all' | 'users' | 'nobody'` (или `null` на вложенном узле для наследования от родителя)
- `access_uids` (`uuid[]`) — персональный доступ конкретным пользователям через `user.picker` (механизм `schema` / `checkGrants` в `#lib/db` на `id` пользователей **не расширяем**)
- `password` (`text | null`) — хеш пароля для доступа, когда не пропустили уровни 1 и 2

Матрица `cloud_id` × `file_id`:
- `(null, null)` — папка в корне;
- `(null, uuid)` — файл в корне;
- `(uuid, null)` — вложенная папка (любая глубина);
- `(uuid, uuid)` — файл внутри папки.

### 3.2. Трёхуровневая иерархия доступа (строго сверху вниз)
1. **`visibility` + статическая схема ACL модели (`defineAcl`)**: `owner`, `admin` и обладатели служебного права чтения модели (`storage.read`) проходят **безусловно в любом случае** без пароля; для остальных вычисляется эффективный `visibility` узла (явный закрытый `visibility` на подпапке перебивает открытую родительскую папку и скрывает подпапку из списка родителя).
2. **Персональный список `access_uids` (`Uid`)**: если Уровень 1 не пустил, проверяется вхождение `actor.id` в `access_uids`; при совпадении доступ открыт без пароля.
3. **Пароль (`password`)**: запрашивается только если не пустили ни Уровень 1, ни Уровень 2; подтверждение хранится в запечатанной `HttpOnly`-куке (работает и с JS, и через нативный `POST` без JS).
