# Доверенный внешний прокси: IP в SvelteKit

`KIT_EDGE_PROXY_TOKEN` — приватная **runtime**-переменная приложения. Пусто: интеграция выключена, используем исходный адрес адаптера. Значение: 32 случайных байта в каноничном base64url без `=` (43 символа), например создаются командой `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`. Используйте разные секреты окружений, храните их в secret-хранилищах приложения и прокси, не в Git; при утечке меняйте одновременно на обеих сторонах. Статический bearer-токен можно переиспользовать до ротации.

## Контракт одного доверенного хопа

| Заголовок | Источник и назначение |
| --- | --- |
| `CDN-Proxy-Token` | Произвольный пользовательский заголовок с общим секретом; **на edge всегда перезаписывать**, не добавлять к клиентскому. |
| `CF-Connecting-IP` | Ровно один адрес клиента без порта, скобок и zone-id. Этот же заголовок выставляет Cloudflare; Caddy обязан перезаписывать клиентскую копию. |
| `User-Agent` | Обычный клиентский User-Agent; сам по себе не удостоверяет личность. |
| `CDN-Geo-Region` | Необязательный регион; edge обязан перезаписать его своим вычисленным значением либо полностью удалить. |

Ранний `Handle` сверяет токен через WebCrypto и валидирует поля. При правильном токене и допустимом IP следующие хуки, маршруты, формы, авторизация и WS получают адрес через **штатный `event.getClientAddress()`**. Хук передаёт `resolve` копию `RequestEvent` с заменённым методом: поле SvelteKit имеет тип `readonly`, поэтому оно не мутируется. Верифицированные необязательные метаданные доступны только на сервере в `event.locals.edge`. Для гео используем только `CDN-Geo-Region`, а не сырые `CF-IPCountry` или любые другие поля, которые могли сохраниться от клиента. Для Cloudflare явно настройте вычисление `CDN-Geo-Region` либо удаляйте его (ниже).

При отсутствии/неверном токене либо невалидном IP остаётся оригинальный адрес адаптера; это **не запрет запроса**. Если адаптер сам доверяет заголовкам, fallback зависит от его конфигурации и гарантий платформы. Источник проверяется только секретом, без списка IP VDS. Токен не заменяет Origin/CSRF, TLS и права доступа.

SvelteKit создаёт новый `RequestEvent` для внутреннего same-origin `event.fetch`. Хуки связывают запросы с проверенным контекстом по объекту `Request` в памяти процесса, **не добавляя токен или адрес в сетевые заголовки**. Когда функция выключена, эта связка не используется. Одновременное повторное использование одного и того же объекта `Request` для разных внутренних запросов при включённой функции намеренно отклоняется, чтобы не смешать идентичности; создавайте отдельный `Request` на каждый вызов. Для внешнего `fetch` идентичность не переносится.

## VDS Caddy → приложение

Входящий `CDN-Proxy-Token` остаётся в `event.request.headers` на сервере: хуки приложения, middleware и диагностические маршруты не должны логировать или отражать его клиенту. Сам по себе токен не переносится во внутренние запросы нашим хуком.

Caddy по умолчанию **пропускает** `CF-Connecting-IP`, `CF-IPCountry` и произвольные заголовки клиента. Не нужно ожидать, что он самостоятельно удалит поддельный Cloudflare-IP. Он обрабатывает `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host` особым образом, а также удаляет hop-by-hop заголовки. Наш контракт их не использует для доверенного IP.

Пример для топологии клиент → Caddy → HTTPS-приложение. Подставьте публичное имя и upstream; это схема, а не готовый конфиг VDS — отдельно проверяйте маршруты, Origin, TLS, наблюдаемость и очистку логов:

```caddyfile
harness.example.com {
  reverse_proxy https://{env.UPSTREAM_HOST} {
    header_up Host {env.UPSTREAM_HOST}
    header_up CF-Connecting-IP {http.request.remote.host}
    header_up CDN-Proxy-Token {env.KIT_EDGE_PROXY_TOKEN}
    header_up -CDN-Geo-Region
    header_up -CF-IPCountry
    header_up -CDN-CF-Token
  }
}
```

`header_up` без `+` заменяет клиентское значение. Секрет передавайте Caddy через защищённое окружение, не логируйте его и не возвращайте заголовки запроса в ответе. **Caddy не скрывает произвольные заголовки-токены автоматически**: его стандартная редактировка распространяется на Cookie, Set-Cookie, Authorization и Proxy-Authorization. Включите проверенные фильтры для всех access/error/debug логгеров, не включайте бесконтрольный debug и не оставляйте авто-сохранённую конфигурацию или открытый admin API с секретами. Проверка сертификата upstream должна оставаться включённой. Northflank может требовать свой upstream `Host` и точный публичный `Origin` в разрешённом списке.

## Cloudflare → приложение

Cloudflare в обычном проксировании присылает `CF-Connecting-IP`; его значение зависит от настроек Workers и Pseudo IPv4. Правило **Request Header Transform Rule** для всех запросов нужного hostname должно сделать `Set static` для `CDN-Proxy-Token`, чтобы перезаписать любую клиентскую копию. Для `CDN-Geo-Region` правило должно сделать `Remove` или `Set dynamic` из `ip.src.country`; если это не настроено, клиент сможет протащить поддельный произвольный регион вместе с корректно установленным Cloudflare токеном. Raw `CF-IPCountry` приложением не используется. Не включайте `Remove visitor IP headers`, если требуется `CF-Connecting-IP`.

Реальная доступность конкретного правила на тарифе и сохранность заголовков промежуточным ingress должны быть проверены на тестовом hostname. Статический секрет Transform Rule может быть виден пользователям с правами управления правилами и в инфраструктурном state; учитывайте это при хранении, ротации и аудите доступа. Не используйте исходящие Worker subrequests и cross-zone/Pseudo IPv4, не проверив их семантику клиентского IP по документации Cloudflare.

## Cloudflare → Caddy → приложение

Если Caddy видит TCP-соседом Cloudflare, `{http.request.remote.host}` даст адрес Cloudflare, а не посетителя. Принимать `CF-Connecting-IP` от любого посетителя нельзя. Для такого маршрута нужен **отдельный секрет Cloudflare → Caddy**: Cloudflare перезаписывает отдельный `CDN-CF-Token`; Caddy проверяет его и только при совпадении передаёт проверяемый Cloudflare-IP дальше, затем удаляет первый токен и выставляет независимый `CDN-Proxy-Token` для приложения. При отсутствии или ошибке токена Caddy использует TCP peer и перезаписывает CF-IP. Принимаемые геозаголовки также должны быть гарантированно перезаписаны на каждом хопе; иначе удаляются.

Caddy header matcher умеет сравнивать точное значение, однако в версии 2.11.7 это обычное строковое сравнение, не заявленное как constant-time; при дубликатах достаточно совпадения **любого** значения, а `*` в шаблоне имеет специальный смысл. Для безопасной эксплуатации дополнительно нужны проверка непустого, корректного случайного секрета без `*` при старте, защита всех логов/конфигурации, корректная перезапись Cloudflare, а также тесты дубликатов, настройки правил и реального маршрута. Локальный синтетический стенд в `trusted-proxy-ip-work/header-lab` показывает принцип, но **не является производственной конфигурацией**. Для первого опыта с прямым подключением к Caddy дополнительный входящий Cloudflare-токен не нужен.

Схема независима от необязательного Node-режима `KIT_TRUST_PROXY_HEADERS`/`KIT_TRUSTED_PROXY_IPS`: если оба активны, токенизированный адрес имеет приоритет после адаптера; fallback остаётся адресом, который вернул адаптер. Для token-only схемы прежний Node-режим оставляйте выключенным.
