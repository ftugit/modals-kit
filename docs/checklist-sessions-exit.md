## 1. Что подтверждено живьём (14.11)

Стенд: `npm run dev` (Node 22, `KIT_ADAPTER=node`), вход по seed администратора,
Playwright 1.65.1 (headless shell), страница `/?modal=user.logout`.

| Сценарий | Что реально произошло |
| --- | --- |
| Одиночный выход («Выйти», чекбокс снят) | POST `/user/logout?/exit` → **200**, `data: { step: "done", variant: "logout", revoked: 1, requested: 1 }`. Куки `auth_sid`/`auth_tmp` **сняты**. Адрес остался `?modal=user.logout`. Модалка тут же перерисовалась в экран «Сессию прочитать не удалось — доступен только выход на этом устройстве» (`session-delete-no-read`) с кнопкой «Выйти только здесь». |
| Массовый выход (чекбокс «Закрыть все сессии» отмечен) | POST `/user/logout?/exit` → **400**, `errors: [{ code: "request.unexpected-field", params: { name: "include_current" } }]`, `values: {}`. Куки на месте. Экран: «Исход неизвестен» + «Повторить» / «Выйти только здесь». |
| Повторное нажатие после успешного выхода | Актора уже нет: `load` отдаёт `canRevoke: false`, экран снова «выйти только здесь». Текст «Сессия не найдена — войдите заново» (`auth.session-unknown`) приходит из домена, когда строки уже нет. |

Вывод: одиночный выход **на сервере срабатывает** (сессия отозвана, куки сняты),
но экран об этом не знает и превращается в экран удаления кук. Массовый выход
**не доходит до сервера** — его режет проверка полей формы.

---

## 2. Причины (по одной, без обвинений)

**P1. У одной формы две разные ревизии.**
Экран выхода собирает форму закрытия устройств в варианте «выход»: в ней есть
поле `include_current` и скрытое `spread`. Сервер регистрирует ту же форму
**без варианта** — в ней этих полей нет. Клиентский POST несёт
`__form_id = user-session-delete`, поэтому его разбирает зарегистрированное
серверное описание, а не экшен маршрута. Лишнее поле → 400
`request.unexpected-field`. Это и есть «массовый выход вообще не работает».

**P2. Экшен маршрута выхода — мёртвая ветка для браузера.**
Он описан формой массового выхода (`spread`) и умеет `runBulkExit`, но
браузерный POST до него не доходит: его перехватывает регистрация компонентной
формы. Поэтому «закрыть все сессии» физически не может дойти до доменного
`runBulkExit` — обработчик закрывает только явный `ids` (текущую строку) и
игнорирует чекбокс.

**P3. Успех вытесняется перезагрузкой данных.**
После отзыва текущей сессии гейтвей снимает куки, компонент чистит память
браузера, хост перезапрашивает `load`. Новый `load` уже без актора →
`canRevoke: false` → модалка монтируется заново в ветке «нет чтения». Ветка
«Вы вышли» (`session-delete-done`) в разметке есть, но её никто не успевает
увидеть. Дополнительно `Logout.svelte` не передаёт `onDone`, поэтому и перехода
на `/user/auth` не случается.

**P4. Домен удаления снимает куки.**
`revokeSessionById`/`revokeBulkSessions` снимают куки, если в закрытых есть
текущая сессия. Для «удалить строку в списке» это неверно: удаление устройства
не должно разлогинивать того, кто нажимает. Отсюда же ощущение «нажал выход —
и меня выкинуло на экран кук».

**P5. «Исход неизвестен» подменяет любую ошибку.**
Компонент считает `unknown` любую неуспешную форму варианта «выход», включая
400 с точным кодом и текстом. Пользователь видит общую фразу вместо причины;
сервер, как и ожидалось, умеет вернуть нормальную ошибку — её просто не
показывают.

**P6. Права на массовое закрытие выданы всем.**
`load` ставит `canRevoke: true` любому, кто смог прочитать актора, без проверки
права читать сессии. Поэтому чекбокс массового выхода виден и тем, кому
массовое закрытие недоступно (план §7.4).

## 3. План правок (порядок и критерии приёмки)

Порядок выбран так, чтобы каждый шаг был проверяемым сам по себе и не требовал
переделывать предыдущий.

### Шаг 1. Один контракт формы выхода (P1, P2)

Свести описание формы на клиенте и сервере к одному: экран выхода объявляет те
же поля, что принимает сервер, и серверная регистрация знает вариант «выход».
Решение о том, «только текущая» или «все активные», принимает домен по
значению чекбокса, а не по тому, какое поле случайно отрендерилось.

Готово, когда: POST с отмеченным чекбоксом не даёт 400; в ответе виден
`revoked`/`requested`; тест на «лишнее поле» и на «поле принято» есть на уровне
формы.

### Шаг 2. Массовый выход — одним доменным вызовом (P2)

Экран выхода с отмеченным чекбоксом идёт тем же путём, что и массовое закрытие
в списке сессий (срез активных, один вызов домена), а не циклом по одной
строке. Явный набор `ids` остаётся для одиночных строк списка.

Готово, когда: с одним активным устройством массовый выход закрывает его и
уводит на `/user/auth`; с тремя устройствами закрыты все три; число в ответе
совпадает с фактически закрытым.

### Шаг 3. Экран успеха одиночного выхода (P3)

После успеха показывается «Вы вышли» (и/или переход на `/user/auth`), а не
экран «сессию прочитать не удалось». Успех нельзя перерисовывать в состояние
«сессии нет»: это разные факты, и экран обязан их различать.

Готово, когда: нажатие «Выйти» даёт видимый экран успеха; повторный заход в
модалку уже как гость даёт экран «выйти только здесь», и это не выглядит как
ошибка выхода.

### Шаг 4. Настоящая ошибка вместо «исхода неизвестен» (P5)

`unknown` остаётся только для случаев, когда исход действительно неизвестен
(обрыв, ответ без тела, таймаут). Ошибка формы с кодом показывается человеку
своим текстом; 400 «неожиданное поле» — это дефект контракта, а не неизвестный
исход.

Готово, когда: подмена ответа на 400/500 показывает конкретное сообщение;
«Исход неизвестен» встречается только в сценарии реального обрыва.

### Шаг 5. Куки снимает только выход (P4)

Закрытие строки в списке (своей или чужой) не трогает куки зрителя; куки
снимает исключительно сценарий выхода и только когда закрыта именно текущая
сессия. Контракт «при броске домена куки остаются» сохраняется.

Готово, когда: удаление текущей строки в списке оставляет зрителя в системе;
выход снимает куки; оба случая закреплены тестами.

### Шаг 6. Права на массовое закрытие (P6)

«Можно выйти» и «можно массово закрывать» — разные права. Чекбокс массового
закрытия показывается только тем, кому оно разрешено; выход на этом устройстве
доступен всем, у кого есть живая сессия.

Готово, когда: актор без права чтения сессий не видит чекбокс и не может
отправить массовый набор; выход на этом устройстве у него работает.

### Шаг 7. Браузерная проверка сценария

Обновить браузерные шаги выхода (сейчас часть из них ссылается на удалённые
элементы) и закрепить два сценария: одиночный выход и «закрыть все сессии».
Проверка идёт по видимому результату: экран успеха, адрес, наличие кук,
количество закрытых строк в списке.

Готово, когда: оба сценария проходят в браузере на локальном стенде.

## 4. Предусловие стенда: шрифты для браузера

Приложенный `setup-playwright.sh` ставит браузер и системные библиотеки, но не
ставит шрифты и конфиг fontconfig. Его собственный probe проходит, потому что
не рисует текст, а первая же настоящая страница роняет Chromium:
`FATAL ... SkFontMgr_FontConfigInterface.cpp:163] Not implemented`
(`Cannot load default config file`).

Обход, которым снято воспроизведение (сделан только в `.agent-tools`, в
репозиторий не попал): распаковать в sysroot `fonts-dejavu-core` и
`fontconfig-config`, положить минимальный `fonts.conf` с каталогом шрифтов и
экспортировать `FONTCONFIG_FILE`/`FONTCONFIG_PATH`. Это стоит внести в скрипт
отдельным мелким приказом, иначе браузерная проверка невоспроизводима с нуля.
