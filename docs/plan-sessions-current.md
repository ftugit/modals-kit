## 1. Выход из аккаунта

Существующий код: `Logout.svelte`, `SessionDelete.svelte`, `session-delete/*`,
`runBulkExit`, `logout/form.ts`. Выход уже строится как вариант удаления сессий.

1.1 Один контракт формы. Клиент и сервер описывают форму одинаково; вариант
«выход» известен серверу. POST с чекбоксом «включая текущую» не даёт 400.
**Статус:** реализовано в `sessionDeleteForm` (`include_current`).

1.2 Массовый выход — одним доменным вызовом, тем же путём, что массовое
закрытие в списке, а не циклом по строкам.
**Существующий код:** срез идёт через `runBulkExit`; явный набор `ids` пока
закрывается циклом в `session-delete.form.server.ts`.
**Новый этап:** перевести явный набор на тот же доменный вызов (комментарий
`этап S15` в коде).

1.3 Успех и отсутствие сессии — разные состояния. Экрана «Вы вышли» нет;
после успешного выхода показывается главная страница приложения. Экран формы,
где пользователь узнаёт, что не может выйти, остаётся. Пользователь в любом
случае выходит без ошибки, если ошибка относится к исключениям: сессии не
существует, нет прав и т. п.
**Существующий код:** `SessionDelete.svelte` рисует экран `Вы вышли` при `done`.
**Новый этап:** убрать этот экран для варианта `logout`, сразу показывать
главную (`doneHref` по умолчанию `/`, а не `/user/auth`).

1.4 Куки снимает только компонент выхода из аккаунта. Удаление строки сессии
не разлогинивает того, кто нажимает.
**Существующий код:** `vault.clear()` вызывается только в `SessionDelete.svelte`
при `variant === 'logout'`.
**Статус:** реализовано.

1.5 Настоящая ошибка сервера показывается вместо «исход неизвестен»;
«неизвестность» — только обрыв или ответ без тела.
**Существующий код:** `unknown` вычисляется из `outcome === 'unknown'` или
ошибки без `done`.
**Статус:** реализовано, но требует проверки по сценариям.

1.6 Права: «можно выйти» и «можно массово закрывать» — разные права.
**Существующий код:** `canRevoke` и `canReadOthers` разделены в списках.
**Статус:** реализовано.

1.7 Браузерные сценарии выхода и массового выхода проверяются по видимому
результату.
**Новый этап:** добавить/обновить браузерные проверки после 1.2 и 1.3.

## 2. Входы и блоки

Существующий код: `SiteListsEntry.svelte`, `site-entries.ts`,
`BlocksModal.svelte`, `BlocksList.svelte`, `Profile.svelte`.

`/blocks`. Адрес и права те же.
**Существующий код:** `BlocksModal.svelte` и `blocksListRoute` уже есть.
**Статус:** реализовано.

2.3 Входы в сессии: остаются ровно два пути — из профиля (сессии этого `uid`)

**Новый этап:** аудит точек входа и удаление лишних кнопок.

2.4 Демо-пользователи с блокировками разных состояний (бессрочная, со сроком,
истёкшая, снятая, мягко удалённая) — только в демо-модуле (dev), в прод не
попадают.
**Существующий код:** демо-модуль устанавливается отдельно (`MODULES=demo`).
**Статус:** правило соблюдается, отдельной реализации в ядре не требуется.

2.5 Лист профилей (новый этап): тот же носитель, что у seed-списка (страница +
модалка + общая разметка, один `load`, догрузка страницами). Строка — профиль
(никнейм, аватар, дата создания), без seed. Фильтров нет ни в форме, ни в
адресе. Поиск по никнейму — отдельное поле (ключ `q`, fuzzy), не фильтр.
Права: только для вошедших; seed-права не требуются; удалённые и чужие
seed-поля не показываются. Публичность: ACL уже готов (`profile.visibility`
`all`/`users`/`nobody`), поэтому отдельный этап публичности не нужен; профиль
виден гостю при уровне `all`.
**Существующий код:** отдельного листа профилей нет; шаблон —
`SeedUsersList.svelte` + `seed-users/*` + `Paginator` с поиском `q`.
**Новый этап:** создать `ProfilesList` по образцу seed-списка, убрать
seed-права и фильтры, добавить поиск `q` и права `profile.read`.

2.6 Канонический компонент — `SessionsList.svelte`. Текущий `SessionsDomain.svelte`
должен быть переименован в `SessionsList.svelte` (или стать его обёрткой), а
старый дубль `SessionsList.svelte` — удалён/слит. Один компонент: по умолчанию
показывает все сессии, при переданном `uid` — сессии пользователя. Фильтры
одинаковые. В фильтрах должна быть возможность выбрать пользователей и показать
их сессии (как в блокировках).
**Существующий код:** оба файла почти идентичны; `SessionsDomain.svelte`
содержит выбор строк (`useListSelection`) и больше возможностей, а
`SessionsList.svelte` — устаревший дубль.
**Новый этап:** переименовать `SessionsDomain.svelte` в `SessionsList.svelte`,
слить уникальные части, удалить старый дубль, обновить импорты.

## 3. Метки фильтров

Существующий код: `FilterLabels.svelte`, `FilterChips.svelte`,
`ActiveFilters`/`activeFilterItems`, `FilterBlockPopup`, `filter-registry`.

3.1 Один компонент меток вместо трёх: только активные поля, одна метка = одно
поле, значения склеены через запятую (например, «Жанры: экшен, драма»).
**Существующий код:** метки полей (`FilterLabels`) и чипы активных фильтров
(`FilterChips`) уже разделены; объединения значений в одну метку нет.
**Новый этап:** либо объединить в один компонент меток, либо явно зафиксировать
разделение и не создавать третий механизм.

3.2 Один реестр блоков: метка находит свой блок независимо от того, где
нарисована форма.
**Существующий код:** `filter-registry.svelte.ts` уже ведёт реестр блоков по
имени списка.
**Статус:** реализовано, требуется проверка на всех носителях.

3.3 Немедленная запись: изменение поля во всплывашке строит патч одного ключа

**Существующий код:** `setExtra` и `Floating` уже поддерживают немедленную
запись.
**Новый этап:** привести метки/всплывашки к одному поведению и покрыть тестами.

3.4 Меток у пустых полей нет.
**Существующий код:** `activeFilterItems` пропускает пустые значения.
**Статус:** реализовано для чипов; для меток полей требуется проверка.

3.5 Без JS строка меток не нужна.
**Существующий код:** метки рендерятся только при наличии хоста модалок.
**Статус:** реализовано.

3.6 Диапазон дат — одна метка, объединяющая параметры среза («Создан: 1–10»).
Поля с длинными списками (студии и т. п.) обрабатываются существующим

**Существующий код:** срезы объединяют параметры в фильтрах.
**Новый этап:** добавить объединение дат в метках.

4.8 Steps: на страницах — режим `url`/`hybrid`, в модалках — `local`;

**Новый этап:** вынести шаги в отдельные компоненты и скрывать запрещённые
