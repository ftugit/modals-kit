## 1. Выход из аккаунта

1.1 Один контракт формы. Клиент и сервер описывают форму одинаково; вариант
«выход» известен серверу. POST с чекбоксом «включая текущую» не даёт 400.

1.2 Массовый выход — одним доменным вызовом, тем же путём, что массовое
закрытие в списке, а не циклом по строкам.

1.3 Успех и отсутствие сессии — разные состояния. Экрана «Вы вышли» нет;
после успешного выхода сразу экран входа. Экран формы, где пользователь узнаёт,
что не может выйти, остаётся. Пользователь в любом случае выходит без ошибки,
если ошибка относится к исключениям: сессии не существует, нет прав и т. п.

1.4 Куки снимает только компонент выхода из аккаунта. Удаление строки сессии
не разлогинивает того, кто нажимает.

1.5 Настоящая ошибка сервера показывается вместо «исход неизвестен»;
«неизвестность» — только обрыв или ответ без тела.

1.6 Права: «можно выйти» и «можно массово закрывать» — разные права.

1.7 Браузерные сценарии выхода и массового выхода проверяются по видимому
результату.

## 2. Входы и блоки

2.1 На главной один блок, связанный с пользователем, с кнопками:
«Seed-юзеры», «Профили», «Журнал сессий», «Блокировки». «Серверы хранилища»
остаются отдельной карточкой.

2.2 «Блокировки» с главной: с JS — модалка поверх главной, без JS — страница
`/blocks`. Адрес и права те же.

2.3 Входы в сессии: остаются ровно два пути — из профиля (сессии этого `uid`)
и с главной (журнал всех сессий сайта). Убрать остальные: шапка, меню с
аватаром (оба пункта), профиль «Все сессии», настройки «Сессии», сам список
«Все сессии», seed-юзеры «Все сессии».

2.4 Демо-пользователи с блокировками разных состояний (бессрочная, со сроком,
истёкшая, снятая, мягко удалённая) — только в демо-модуле (dev), в прод не
попадают.

2.5 Лист профилей (новый этап): тот же носитель, что у seed-списка (страница +
модалка + общая разметка, один `load`, догрузка страницами). Строка — профиль
(никнейм, аватар, дата создания), без seed. Фильтров нет ни в форме, ни в
адресе. Поиск по никнейму — отдельное поле (ключ `q`, fuzzy), не фильтр.
Права: только для вошедших; seed-права не требуются; удалённые и чужие
seed-поля не показываются. Публичность — только если ACL готов (приватность
`all`), иначе отдельным этапом.

2.6 Канонический компонент — `SessionsList.svelte`. Текущий `SessionsDomain.svelte`
должен быть переименован в `SessionsList.svelte` (или стать его обёрткой), а
старый дубль `SessionsList.svelte` — удалён/слит. Один компонент: по умолчанию
показывает все сессии, при переданном `uid` — сессии пользователя. Фильтры
одинаковые. В фильтрах должна быть возможность выбрать пользователей и показать
их сессии (как в блокировках).

## 3. Метки фильтров

3.1 Один компонент меток вместо трёх: только активные поля, одна метка = одно
поле, значения склеены через запятую (например, «Жанры: экшен, драма»).

3.2 Один реестр блоков: метка находит свой блок независимо от того, где
нарисована форма.

3.3 Немедленная запись: изменение поля во всплывашке строит патч одного ключа
и уходит в `setExtra`. «Применить» остаётся только у полной формы и без JS.

3.4 Меток у пустых полей нет.

3.5 Без JS строка меток не нужна.

3.6 Диапазон дат — одна метка, объединяющая параметры среза («Создан: 1–10»).
Поля с длинными списками (студии и т. п.) обрабатываются существующим
механизмом срезов (поиск/прокрутка внутри всплывашки).

3.7 Тесты: объединение значений, немедленная запись, отсутствие метки у пустого
поля, снятие.

## 4. Настройки и сессии в одном listing

4.1 Убрать заголовок «Настройки» для своих настроек (дубль рядом со steps).
Чужие настройки (`foreignTitle`) оставить.

4.2 В группе «Безопасность» — кнопки «Настройки» и «Сессии» внутри группы
(не верхний переключатель экранов). Они переключают содержимое тела между
формой настроек и списком сессий. Реализация: либо второй хост `Steps`,
либо составной ключ. Решить до кода.

4.3 Встроить сессии в listing настроек без отдельного `Listing`: один `Surface`,
слева steps настроек, справа controls активного listing, тело переключается.

4.4 `Listing` получает встроенный/«без шапки» режим: отдаёт шапку (controls,
фильтры, счётчик) и тело (paginator) родителю. Канонический `SessionsList` строится на
`Listing` и в встроенном режиме отдаёт свои controls родителю.

4.5 `Surface` — общий хост: `start` = steps настроек, `end` = controls
активного listing, тело = форма настроек или paginator сессий. Единый владелец
скролла тела.

4.6 Фильтры сессий: sidebar на ПК, fallback на кнопку в модалке.

4.7 ACL: настройки и сессии имеют разные права; встроенный listing сессий
сохраняет свои проверки.

4.8 Steps: на страницах — режим `url`/`hybrid`, в модалках — `local`;
исключение — всплывашки и модалки без url. Адресуемые шаги работают без JS.

4.9 Разнести настройки на отдельные компоненты по шагам: каждый шаг рисует
свой компонент (форма/ACL), переключение показывает нужный. Запрещённые шаги
скрываются из навигации; прямая ссылка на запрещённый шаг срабатывает `Acl`
(экран отказа). Схема прав по разделам — по аналогии с фильтрацией полей по
правам (найти существующие упоминания схем в коде и следовать им).

## 5. Подтверждения — отдельный экран

5.1 «Заблокировать все» из списка сессий: кнопка-ссылка открывает отдельную
модалку подтверждения; на экране — число закрываемых сессий; выполнение —
отдельной отправкой, не GET. Имя кнопки — «Заблокировать все».

5.2 «Заблокировать» в экране сессии: отдельная модалка подтверждения;
карточка остаётся входом и не меняет разметку; отмена возвращает к карточке;
без JS — страница подтверждения по адресу.

5.3 Текущая сессия в списках с `uid`: выбор текущей сессии запрещается в UI;
на сервере, если такая сессия передана, она закрывается наравне с другими.
Куки при этом не снимаются — куки снимает только выход из аккаунта.

5.4 Серверы хранилища: добавить подтверждение удаления, но в отдельном этапе
(сейчас только демо-модуль, не тестировалось).

5.5 Аудит остальных экранов: все разрушительные действия — отдельные модалки
(выход, seed-юзеры, блокировки, профиль, настройки без разрушительных
подтверждений ок). Исключение — серверы хранилища (5.4).

## 10. Существующие возможности (проверено по демо-модулю)

Демо-модуль установлен (`MODULES=demo`) и проверен по коду, чтобы не
изобретать велосипед:

- Steps: режимы `url`, `local`, `hybrid`, `form`, `mixed`, `popup`; ключи брони
  (`ustep`, `hstep` и т. д.); `useSteps`, `stepLink`, `PopupSteps`.
- Пагинатор: поиск — отдельный ключ `q` (fuzzy, `normalizeSearchQuery`),
  отличный от фильтров; `usePaginatorSearch`.
- Фильтры: `FiltersPanel`, `FilterChips`, `ActiveFilters`, `FilterLabels`,
  всплывашка блоков через `Floating`; срезы объединяют параметры; запись
  применяется целиком (`live: false`) или сразу (как в метках).
- Профили как отдельного листа нет; поиск по никнейму — как `q` у пагинатора.

Использовать эти механизмы, а не создавать новые.
