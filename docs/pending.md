# Хвосты: что не сделано

Единственный сводный файл про незакрытое. Здесь отложенные задачи и памятки
по решениям владельца. Принятые решения живут в коде и в [`docs/design/`](./design).
Закрытые планы и аудиты в дереве не хранятся: контракт уже в README рядом с
кодом, полный текст — в git.

Обозначения: **P1** — блокирует обещанное поведение, **P2** — заметно
пользователю, **P3** — отложенный функционал без срочности, **P4** — гигиена.

---

## 1. В планах

- **Системный контекст — P3, раньше сессий** ([`docs/plan-system-context.md`](./plan-system-context.md)):
  известное сделано локально, не закоммичено: `get`/`markDeleted` и конфиг принимают `ctx`, слот и удаление сервера идут от актора. Сессии и три открытых вопроса в плане не начаты.
- **Сессии, выход и хост списков — P2, план в работе, реализация не начата** ([`docs/plan-sessions-components.md`](./plan-sessions-components.md)):
  каждая операция = компонент + роут + ключ модалки. План **самодостаточен** (ред. 5): стандарт
  пересказан внутри, карта кода — Приложение А, разбор рецензии и уточнений — Приложение Б.
  **Ред. 5 добавила:** хост списков как достройку существующей оболочки `Listing` (состояние
  выбора, контракт набора `id`/`ids`/срез, описание списка), три компонента действия
  (удалить / заблокировать / разблокировать), аудит остальных списков и доменных дверей,
  входы в сайтовые списки с главной. Этапы: 1–2 сессии (S0–S10), **3 хост и эталон (S11–S17)**,
  **4 остальные списки (S18–S23)**.
  **Аудит списков:** оболочка уже даёт порции/фильтры/поиск/строку сниппетом/признак выбора/слот
  кнопок; нет состояния выбора и контракта набора. Сессии — без поиска и без подключённого
  выбора; юзеры — выбор только своей реализацией в пикере; блокировки — без поиска и выбора;
  **серверы хранилища вообще не на оболочке**.
  **Доменные двери (входят в объём, решение владельца):** сессии — `ids` только как исключения,
  нужен набор; блокировка срезом — нет; удаление чужих аккаунтов — нет вовсе (только своё);
  снятие и удаление блокировок — только по одной записи. Без этих дверей кнопки не обещаем.
  **Разблокировка ≠ удаление:** снятие правит окончание (`until = момент снятия`), запись
  становится строкой истории; мягкое/жёсткое удаление — другие операции. Поэтому отдельный
  компонент действия. Подтверждено кодом (`blocks.ts:389–408`, `schema.ts:377–378`).
  **Выбор внутри фильтра:** список seed-юзеров в режиме выбора строит срез по целям — единственный
  такой сценарий; отдельная реализация выбора в пикере после этого удаляется (S21).
  Нарушения на `d015fa8`: массовый сброс — шаг внутри `SessionsList` (`?/others` на роутах списка),
  закрытие одной — инлайн в `SessionCard` (`?/revoke` на роутах списка, `intercept:false`), локальный
  выход инлайн в `Logout`; все exit-экшены всегда `redirect(303)` → `goto` уводит из модалки; пропы
  `backHref`/`actionHref`; страж `sessions-dead-actions` закрепляет старую карту. Двухрежимные шаги и
  `rename` из реестра уже исправлены планом 6 и повторно не чинятся.
  **P0 найден воспроизведением на деплое:** отзыв чужой сессии проходит, но всегда показывает
  `?notice=revoke-failed`. Причина — динамический `kitRoute.href()` зовёт `resolve()` внутри запроса и
  отдаёт относительный путь (`paths.relative` не выключен), `safeRedirect` такой адрес отбрасывает,
  проверка `startsWith('/')` в экшене падает в ветку отказа. Свои сессии и `/user/logout` не задеты
  (статический роут / литерал). Дифференциал на деплое: своя → `/user/sessions`, чужая →
  `?notice=revoke-failed` при фактически отозванной строке. Чинится `paths.relative: false` (этап S0),
  не ослаблением защиты. Прежняя гипотеза про in-memory PGlite **опровергнута**: на деплое 3020 сессий
  и 82 аккаунта, данные постоянны, `DATABASE_URL` задан.
  Отдельное требование владельца: **ошибка не закрепляется за URL** — `noticeOf` и `?notice=` удаляются,
  отказ рендерится inline результатом формы, при неизбежном редиректе — одноразовая flash-кука.
  **Состав (ред. 4, уточнение владельца): компонент удаления сессии — ОДИН**, умеет три формы
  набора: `id`, `ids`, срез. **Выход — отдельный компонент без своего UI:** рисует удаление
  через пропс `variant` (текст «удаление»/«выход») и добавляет только логику — разбирает сценарий
  ответа сервера и снимает куки/память браузера. Прежний счёт «3/3/5» отменён; вывод из решения —
  **2 компонента, 2 ключа, 3 адреса** (удаление: свой/чужой адрес; выход: один) — разбивка
  адресов помечена в плане как требующая подтверждения. Существующие единицы (список, журнал,
  фильтры, карточка, выход) сохраняются — таблица судеб в плане §6.2.
  **Журнал `/sessions` остаётся отдельной единицей** (ключ, адрес, страж не удаляются).
  Кнопка «Свои сессии» убрана, вход из профиля, компонент должен уметь быть шагом в настройках
  безопасности. Кнопка обычная, на удержание меняется при наборе > 1; примитив удержания уже
  есть, новый не заводится, без JS удержания нет. Набор едет параметрами адреса для любой формы
  (`id`/`ids`/условия среза) без привязки к хранилищу списка; ссылка только открывает подтверждение.
  **Чистый список:** тела списков не знают кнопок действий — **доменный компонент вызывает
  список сессий и рисует оболочку listing с кнопками**; список отдельно кнопок не имеет; механика
  строки и выбранность приходят пропами по образцу списка seed-юзеров.
  **Режим выбора ничего не переключает** — только даёт отмечать строки. Какая форма набора уйдёт
  в удаление (`id` со строки / срез с кнопки / `ids` отмеченных), решает **доменный компонент**.
  Формы не смешиваются, права перепроверяются на каждую строку. То же для списков юзеров
  и блокировок — этап S15.
  **Права разделены:** запрет читать устройства не должен мешать выйти и закрыть свою
  авторизацию (сейчас мешает: закрытие сначала читает строку); массовый чекбокс без права читать
  не показывается. **Модель устройства:** каждая авторизация — новое устройство, метка клиента
  не вводится, механика входа не меняется (решение владельца).
  **Правило цели (этап S1, второй после S0):** цель берётся из авторизации, если `uid` не передан;
  в UI допустимо только сравнение `uid` цели с `uid` авторизации для отдельных кнопок. Нарушение:
  карточка устройства выбирает адрес закрытия и шага по клиентскому зеркалу. Блокировки молча
  вычитают себя из целей/фильтра — решено владельцем: **своя цель видна, неактивна, с пометкой**,
  серверный запрет остаётся границей. Серверные цели уже корректны. Оболочка списка сбрасывает
  порции при смене актора → нужен тест на пустое зеркало.
  **Механика успеха (возвращена в план после рецензии):** все exit-экшены сейчас отдают `303`,
  поэтому требование «адрес не меняется» без правки контракта не выполняется — действия
  переводятся на компонентную регистрацию с результатом для JS и серверным решением о переходе
  для no-JS, отказ отдаётся вместе со страницей; критерий «успех в модалке не меняет адрес носителя».
  **Числа модели подтверждены в коде:** предел 50 активных авторизаций и обрезка истории подсетей
  до 8 живут в доменном слое авторизации (`auth.ts:79, 292–300, 467`), а не в модуле сессий;
  нужны только тесты. **Этапы (ред. 5):** 1–2 сессии — S0 базовая линия + абсолютные адреса,
  S1 правило цели, S2 каркас, S3 удаление сессии (срез и `id`), S4 чистый список и доменный
  компонент, S5 выход, S6 права, S7 ошибки, S8 список шагом, S9 стражи, S10 финал сессий.
  **Этап 3 (хост и эталон):** S11 состояние выбора, S12 контракт набора, S13 описание списка +
  сессии на хосте и режим выбора, S14 три компонента действия, S15 домен сессий `ids` набором,
  S16 долги реестра (схема, параметр целей фильтров, адрес пикера), S17 стражи.
  **Этап 4 (остальные списки):** S18 юзеры/профили + домен (блокировка срезом, удаление
  аккаунтов набором), S19 блокировки + домен (снятие и удаление набором), S20 серверы хранилища
  на оболочку, S21 пикер = список в режиме выбора внутри фильтра, S22 входы с главной в
  сайтовые списки, S23 финал.
  **Открыто:** разбивка сессионных адресов/ключей (2/2/3) — вывод, ждёт подтверждения; считаются
  ли кнопка фильтров и поиск «кнопками действий» (предложение — оставить оболочке); массовое
  удаление аккаунтов — предложение мягкое с грейсом, ждёт подтверждения; сброс базы при сборке
  preview.
- **Сессии — P3** ([`docs/plan-sessions.md`](./plan-sessions.md)):
  Этапы 1–3 реализованы: экран своих устройств на `Listing`, форма фильтров (sidebar, модалка, страница `filters?from=`), карточка устройства с переименованием.   Устройства чужого аккаунта открываются путём `/user/<uuid>/sessions` (цель — параметр пути и проп `uid`, как `/user/[id]/blocks`), общий журнал без аккаунта — страницей `/sessions` (этап 4 закрыт; входы — «Сессии» в чужом профиле и «Все сессии» в своих устройствах и в списке аккаунтов). `server` остаётся фаерволу куки, не всему порту.

## 3. Исключительно по обращению

- **Расширения `#lib/db` (generic REST, таблица ручных SQL-миграций `kit_migration`, вычисляемые поля)**:
  не считаются очередным планом. Архитектура — один проект, без внешнего generic REST.
- **Время жизни WebSocket-загрузки**: исследование 2026-11-03 закрыто, реализация не заказана. HTTP-предвалидация не усиливает проверки: права, лимиты и бюджет и так идут после `init`. Дешёвый предел, если работу закажут, — дедлайн от `accept`, а не от `init`; `pong` не должен продлевать простой, пока нет данных. Внешний таймаут прокси Northflank первоисточником не подтверждён. Без отдельной команды код не менять.
- **Не переносить без отдельного решения владельца** (снято из закрытого плана аудита):
  принудительный `KIT_ADAPTER=node` для `prepare`/`check`/`test`, сужение `engines` до Node 22 и dependency
  overrides агента — только после анализа совместимости; изменённая агентская политика регистрации фильтров,
  пагинация, скрывающая навигацию при пустом списке, и упрощённая fix-логика `busy`, оставляющая `aria-disabled`
  в состоянии ошибки.
- **HSTS `includeSubDomains`**: заголовок в `src/hooks.server.ts` живёт один–два года. Если прокси пропускает его на домен VDS, политика ляжет и на поддомены этого домена. Не менять молча.

## 4. Заметки среды

- **Версия Node.js**: `>=22.17 <25` (`package.json#engines`).
- **Полный прогон vitest** идёт около двух минут на 2 vCPU / 1,9 ГБ RAM. В ходе работы гоняется затронутая область, полный набор — перед финальным коммитом пачки.
- **Браузерные сьюты демо** (`db-demo`, `paginate`, `shikimori` и остальные из `package.json`) появляются вместе с модулем `demo`. Чистое ядро их не содержит; `test/browser/run-all.mjs` берёт только существующие файлы.
