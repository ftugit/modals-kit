# No-JS путь для фильтров списка seed-юзеров — СДЕЛАНО

Решение владельца: вариант 1 — страница-fallback `/users/filters`.
Условия: переход тянет текущие фильтры с собой; возврат — к адресу
носителя списка, не на фиксированный роут.

## Как устроено

- Модалка `user.list.filters` получила `route: userListFiltersRoute`
  (`/users/filters`, канон `user.menu`). Без JS кнопка ведёт на страницу
  этого роута; с JS открывается модалкой.
- Данные берутся из `load` страницы фильтров (`useLoader`), а не из
  params: у модалки с route произвольные params кнопки ломают SSR
  («ключ не забронирован»).
- Кнопка несёт `href=/users/filters?from=<текущий адрес носителя>`
  (страница, модалка поверх любой страницы — любое место сайта).
- Общая форма `SeedUsersFiltersForm.svelte`: модальный режим патчит
  `extra` пагинатора; нативный — GET `method=get` на путь носителя.
  Поля названы адресными ключами среза (`users.ord` и т.д.). Чужие
  ключи `from` (поиск, `modal=…`, размер) едут скрытыми полями;
  указатель порции сбрасывается; `from` валидируется `localPath`,
  самого себя страницей фильтров не подменяет.
- Страница фильтров сама проверяет доступ (`canSeeDeleted`, `fact`
  через `listSeedUsers` page 1): доступна только тем, кто и так видит
  список; форма открывается из-под списка и с роутных адресов любых
  страниц, где стоит модалка списка.

## Проверка (2026-10-26)

- Проба без JS (`java_script_enabled=False`): кнопка имеет `href`
  с `from`; страница фильтров открывается; префилл из текущего среза
  (`state=deleted`); нативный GET возвращается на `/users` с применённым
  срезом (SSR «всего: 20», пометки «на удалении»). 6/6.
- Регрессия с JS (`/tmp/pw_stage1.py`): поиск, фильтры-модалка, сброс —
  9/9.
- Известный пробел (не масштабировать без задачи): возвращение из
  no-JS страницы в АДРЕС носителя-модалки (`/?modal=user.list…`)
  формально поддержано скрытыми полями, живой пробой носителя-модалки
  без JS не проверялось (невозможно без JS открыть список-модалку).
