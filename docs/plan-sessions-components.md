> Статус: **план, реализация не начата.** Основание — `uploads/components-standard.md`
> (черновик по коммиту `1a43a376`) и поручение владельца: привести сессии и выход к
> стандарту, включив **все** места, где нет нормального компонента, в том числе
> закрытие одной сессии (инлайн-шаг в карточке) и массовый сброс (шаг внутри списка);
> назвать причину, по которой нынешний подход не работает на Vercel.

> Формат — проза и таблицы статуса по конвенции репозитория (`AGENTS.md` §5.1);

## 1. Цель и критерий готовности

Единица — **три имени одного**: ключ модалки, роут (no-JS/SSR/POST-фолбэк) и компонент
(стандарт §1). Один компонент на двух носителях, режим — явным флагом
(`useSteps` `mode: 'local' | 'url'`, пагинатор `url: false`), а не «повезло ли с адресом» (§3).

Готово, когда:

1. У каждой операции сессий/выхода есть своя пара «модалка + роут» и свой компонент;
   список и карточка рисуют только **вход** в пару (`asModalLink`), а не шаг внутри себя.
2. POST-экшен живёт на роуте **своей** единицы, `action` абсолютен и не зависит от
   страницы-носителя (§6); набор считает сервер по срезу, клиент шлёт намерение и фильтр.
3. В модалке успех не уводит со страницы-носителя: JSON-ответ несёт результат,
   no-JS — 303; адрес носителя не читается и не пишется (§3, §7).
4. Названа и устранена причина неработоспособности на Vercel (§5 плана); архитектурная
   правка и деплой-конфиг разведены — рефакторинг сам по себе Vercel не чинит.
5. Каждый инвариант §7 стандарта выражен тестом/стражем; у каждого нового теста есть
   негативный контроль (мутация прогнана, вывод приложен).
6. README рядом с кодом правится в том же коммите, что и поведение; гейты зелёные,
   лимиты веса не поднимаются.

## 4. Целевая архитектура

### 4.1. Единицы

| Ключ модалки | Компонент | Роут(ы) — no-JS/POST | Экшен | Параметры пары |
|---|---|---|---|---|
| `user.sessions.exit` | `SessionsExit.svelte` + `SessionsExitModal.svelte` | `/user/sessions/exit` (свои), `/user/[id=uuid]/sessions/exit` (чужие) | `?/exit` | `uid?`, фильтр `state/net/country/cfrom/cto/sfrom/sto` |
| `user.session.exit` | `SessionExit.svelte` + `SessionExitModal.svelte` | `/user/sessions/[id=uuid]/exit`, `/user/[id=uuid]/sessions/[sessionId=uuid]/exit` | `?/exit` | `id`, `uid?` |
| `user.logout` | `Logout.svelte` + `LogoutModal.svelte` (выход из аккаунта, `spread`) | `/user/logout` | `?/exit` | — |
| `user.logout.local` | `LogoutLocal.svelte` + `LogoutLocalModal.svelte` | `/user/logout/local` | `?/local` | — |

Статические сегменты `exit`/`local` не конфликтуют с матчерами `[id=uuid]`/`[sessionId=uuid]`
(как уже сосуществует `/user/sessions/filters`). Журнал массового сброса не имеет
(`!journal` в списке) — так и остаётся; расширение на журнал — отдельное решение владельца.

### 4.2. Состав и реестр

- `ui/sessions-exit/` — `SessionsExit.svelte` (единица массового сброса), `ExitCore.svelte`
  (внутреннее ядро форма+удержание+`spread`, бывший `ExitSteps`; **не** единица и не
  публичный полукомпонент), `load.server.ts` (сводка: счёт набора по фильтру).
- `ui/session-exit/` — `SessionExit.svelte` (единица закрытия одной), `load.server.ts` (деталь).
- `ui/logout/` — `Logout.svelte` (выход из аккаунта на `ExitCore`), `LogoutLocal.svelte`
  (локальный выход), `form.ts` (`logoutLocalForm` остаётся).
- `routes.ts` — `userSessionsExitRoute`, `userAccountSessionsExitRoute`, `userSessionExitRoute`,
  `userAccountSessionExitRoute`, `userLogoutLocalRoute`; `modals.ts` — три новые регистрации.
- Формы `sessionBulkExitForm` / `sessionRevokeForm` остаются в `sessions.form.ts`
  (контракты rev.3, `SESSIONS_BULK_IDS_LIMIT=500`, `except` порциями по 100 — без изменений).

### 4.3. Контракты

- **Режим.** Компонент единицы владеет шагом через `useSteps({owner, key, mode})`;
  носитель передаёт только `mode` (`'modal'` → `local`, страница → `url`) и данные/`id`.
  Пагинатор в единицах выхода не участвует (сводка — счёт, не строки).
- **Привязка.** Цель и фильтр едут параметрами пары и сегментами пути, не адресом
  носителя и не `visibleAddress()`. `load` роута единицы заново разбирает фильтр тем же
  whitelist/клампом (`sessions-list/source.ts`), считает набор сервером.
- **Экшен.** `action` абсолютен из реестра (`route.href() + '?/exit'`). Серверные экшены
  переводятся на `registerComponentForm` с `redirectOnSuccess` (образец — `block-delete`):
  JSON-запрос получает `data:{step:'done', current, requested, revoked, notice?}` (без `goto`),
  нативный no-JS — 303 на `selfHref`/`doneHref` (`/user/auth`, если закрыта и своя сессия).
  `runBulkExit`/`runLocalExit` в `sessions-exit.server.ts` остаются общей серверной логикой,
  но возвращают разделённые «данные для JS / редирект для no-JS».
- **Набор.** Клиент шлёт фильтр + `include_current`/`spread` + `except` (≤500, в теле, не в
  URL); сервер применяет срез в момент POST. Клиентские `ids`/`pick`/`scope` не посылаются.
- **Объявления.** `bulk-exit-partial`/`revoke-failed` рисует единица, выполнившая операцию
  (из `data.notice` для JS); для no-JS редирект несёт query, и список по-прежнему показывает
  баннер. Отказ и «исход неизвестен» различаются и видны (§6).
- **Закрытие слоя.** Успех в модалке: `onDone` → `invalidateLoader('user.sessions')` /
  `invalidatePaginator(SESSIONS_NAME)`, при закрытой своей сессии — `vault.clear()`, снятие
  слоя; адрес носителя не тронут. Образец — `BlockDeleteModal.handleDone`.
- **Правило текущей сессии.** Карточка по-прежнему не закрывает свою текущую сессию
  (`closable = canRevoke && !deleted && !current`) — для неё есть выход в меню.

### 4.4. Что умирает

- `actions.revoke` и `actions.others` у обоих роутов списков; `actions.local` у `/user/logout`.
- Инлайн-шаги `useSteps owner:'user-sessions-exit'` / `'user-session-exit'` в списке/карточке;
  `ExitSteps` как публичный полукомпонент (растворяется в `ExitCore` внутри единиц).
- Пропы `backHref`/`actionHref` у `SessionCard`, `backHref` у `Logout`; кнопка «К списку»
  внутри карточки (вход/возврат рисует носитель из реестра).
- Старый контракт `tooling/sessions-dead-actions.test.mjs` (переписывается под новую карту).

## 5. Vercel: причина и устранение

Рефакторинг §4 чинит архитектуру на любом хосте, но **не** заменяет деплой-конфиг.
Причины названы по коду; какая именно сработала на конкретном деплое, подтверждается
симптомом/логами (шаг S7). Три независимых причины:

| Симптом на деплое | Причина (код) | Устранение |
|---|---|---|
| Сборка падает: `platform.adapter` / «задайте KIT_ADAPTER» | `vercel.json` задаёт только `framework`+`buildCommand`; `detectPlatform` требует `KIT_ADAPTER` (`tooling/platform.mjs`), `VERCEL` не читается | `KIT_ADAPTER=vercel` в Build-окружении Vercel (README это уже предписывает) |
| Каждая форма (вход/выход/отзыв) → `403 origin.rejected` | `originGuard` сравнивает `Origin`/`Referer` с `new URL(request.url).origin`; за краем Vercel они разные; `csrf.trustedOrigins` зашивается при сборке и сравнивается точно, wildcard отбрасывается (`vite.config.ts`, `.env.example`) | `KIT_TRUSTED_ORIGINS=https://<точный-домен>` и в Build, и в Runtime; пересобрать после смены |
| Вход прошёл, но список пуст / `session.unknown` / отзыв «не найдено» между запросами; троттл/брони «сбрасываются» | без `DATABASE_URL`/`HYPERDRIVE` `openDriver` открывает **PGlite in-memory на инстанс** (`db.server.ts:262-266`, `memory: !DATABASE_DIR`); serverless-инстансы не делят память; `sharedStore=pgStore(db)` и `createIpThrottle` тоже per-instance | внешний Postgres `DATABASE_URL` (pooler Neon/Supabase), Preview и Production — раздельные базы; `DATABASE_DIR` на Vercel не задавать |
| Редирект/экшен уводит на неверный host | `paths.origin` зашивается из `ORIGIN` при сборке (`vite.config.ts:49`, `bakeOrigin:true` для vercel) | `ORIGIN=https://<домен>` в Build-окружении |

Основной кандидат на «сессии не работают» — **in-memory PGlite** (если `DATABASE_URL` не
задан) и/или **CSRF 403** на каждом POST. Обе причины видны в коде и обе задокументированы
в `.env.example`; диагностика на живом деплое — шаг S7 (нужен доступ владельца к окружению
и логам). In-memory `localStore`/троттл отдельной правки не требуют: при внешнем Postgres
`sharedStore` общий.

## 7. Тесты и стражи

- **Новые SSR-тесты** единиц: своя/чужая цель, page/modal, no-JS `href` из реестра,
  абсолютный `action` поверх чужого носителя, правило текущей сессии, удержание только
  при `N>1`, семантика `spread`/`include_current`, отказ и partial видны.
- **Переписываются**: `SessionCard.ssr.test.ts` (вместо инлайн-отзыва — кнопка входа),
  `Logout.ssr.test.ts` (локальный выход — ссылка на пару), тесты списка (вход в массовый сброс).
- **Браузер**: `sessions-local-steps`, `sessions-target`, `sessions-live`, `sessions-journal`,
  `stage2-session` — под новые пары; новый сценарий «успех в модалке закрывает слой и не
  меняет адрес носителя».
- **Стражи**: `sessions-dead-actions` — новая карта (списки без `revoke`/`others`, экшены на
  роутах единиц, `?/revoke`/`?/others` не в UI); `journal-path-guard` — литералы новых роутов
  только из реестра; новый статический страж «нет инлайн-шагов выхода вне единиц».
- **Негативный контроль** обязателен для каждого нового теста: мутация прогоняется, вывод
  прикладывается к отчёту этапа.

## 8. Риски и открытые вопросы

- Перенос фильтра в URL пары — 7 ключей, длина допустима; `except` (≤500) — в теле POST, не в URL.
- Миграция на `registerComponentForm` меняет no-JS редиректы — сохранить `selfHref`/`doneHref`/
  notice и закрепить no-JS тестом; JS-ветка не должна делать `goto`.
- Вес клиента: новые роуты добавят манифест; замерить, лимиты **не поднимать**; при превышении —
  назвать вслух и искать оптимизацию, а не повышать бюджет.
- Журнал без массового сброса — сохраняется; расширение только по решению владельца.
- Vercel: какая из причин §5 сработала, подтверждается на живом деплое (нужен доступ владельца);
  план называет причины по коду, но не выдаёт догадку за факт.
- Вопросы владельцу до реализации: имена ключей (`user.sessions.exit` / `user.session.exit` /
  `user.logout.local`) и выделение локального выхода в отдельную пару — подтвердить; есть ли
  `DATABASE_URL` на деплое — для диагностики §5.
