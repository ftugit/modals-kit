## Объяснение «URL меняется / не меняется» (дано владельцу, ход 261)

Механизм один, транспорта два. Без JS шаг писать некому, кроме сервера: экшен после успеха
делает `redirect(303, '/user/auth?step=profile')` — адрес меняет браузер. С JS экшен отвечает
данными (accept: application/json), шаг присваивается состоянию виджета
(`step = next.step` в AuthWidget) — URL никто не трогает. Отсюда разница, которую видел владелец.

## Гипотезы тихого отказа (по чтению кода; проверить воспроизведением)

1. **Ошибки поля аватара не показываются.** Шаг профиля рисует ошибки никнейма
   (`nickF.errors`) и клиентскую `avatarError`; серверные отказы садятся в поле `avatar`
   (скрытое) — их ошибок в разметке нет. Отказ есть — владелец его не видит.
2. **Сжатие впритык.** Клиент ищет качество, пока блоб ≤ 20 480 Б; сервер считает байты ВСЕЙ
   `data:image/jpeg;base64,`-строки (префикс ~30 Б) и отбраковывает «впритык» сжатое
   (`profile.ts: checkAvatar`) → `profile.avatar-size` → по гипотезе 1 отказ невидим.
3. Прочее — исключается по результату воспроизведения (не гадать до пробы).

## Стадии

1. Воспроизведение: браузерная проверка (в `auth.mjs`): аватар размера у границы лимита →
   «Сохранить» → зафиксировать тихий отказ (ошибок в DOM нет, шаг не ушёл). Проверка «красная до».
2. Фикс показа: ошибки поля `avatar` рисовать в шаге профиля (как у никнейма — `errorProps`).
3. Клинот веса: сверка сервера — байты от запятой `data:` и/или резерв (переезд на `lib/image`
   закрывает клиентскую сторону: `fit` меряет всю строку).
4. Повтор пробы п.1 — зелёная; сохранение профиля с первой отправки в тесте.

## Критерий готовности

закреплено тестом; объяснение шагов владелец подтвердил.
