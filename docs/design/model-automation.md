# Автоматика модели `lib/db`: что модель делает сама и как это разово отключить

**Статус: СОГЛАСОВАНО (ход 209), ждёт команды начать.** Код не менялся. Порядок работ — §11.

Общее состояние работы — [`docs/plan.md`](../plan.md).

## 1. Что уже решил владелец

- **Пустые значения в `timestamps`.** `null`, `''`, `undefined` и отсутствие ключа значат одно:
  поле выключено. Сейчас `null` и `''` дают ошибку объявления — это меняется (§5).
- **Форма отключения — колбэк с временным экземпляром.** Вызов получает список ключей
  автоматики и колбэк. Колбэк получает временный экземпляр модели, у которого эти ключи
  выключены. Остальной код (параллельные запросы, другие вызовы) их не теряет, общего
  состояния нет.
- **Отключить можно всё, что модель делает сама или по сценарию**, вплоть до прав доступа.
- **Внутри колбэка временный экземпляр сообщает, что реально выключено.** Снаружи поведение
  модели узнаётся там же, где модель вызывается. Через `ctx` — нет: поведение принадлежит
  модели, а не запросу.
- **Права — два ключа:** `policy` (строки) и `grants` (поля).
- **Механика — клон схемы.** Временный экземпляр — та же модель, заново собранная в памяти из
  схемы, где отключаемые опции заменены на `null`. Операции (`select`, `insert`, …) не знают
  об отключении: они работают как обычно, просто у модели другая схема. См. §8.
- **Ответы на §8 (ход 202):** ключи — пути в схеме; `null` в правах ведёт себя одинаково в клоне
  и в обычной схеме («модель без прав — выбор разработчика»); `deletedAt: null` — удаление навсегда
  и чтение удалённых, это верно; клон не участвует в синхронизации базы — `without` управляет
  только настройками модели; подпись курсора не привязывается к выключенному — `without` и так
  виден в коде каждый раз.
- **`without` только сужает.** Писать больше полей, чем разрешает исходная схема, `without` не
  даёт; ключа `protect` в нём нет. Запись системных полей — отдельная функция (§9).
- **Будущие функции, меняющие опции схемы, работают так же** — новая схема, клон — и
  вызываются цепочкой из `without`: сначала отключили, потом поправили.

## 2. Что модель делает сама — полный список

Сверено с кодом на `66fa84a`. «Когда»: Ч — чтение (`select`, `get`, `count`, `cursor`,
`estimate`), З — запись (`insert`, `insertMany`, `update`, `delete`, `restore`), П — проверка
без записи (`validator`).

## 3. Что предлагаю НЕ давать отключать — и почему

| # | Почему |
|---|---|
| 10 Проверка схемой поля | Значение уходит в SQL с типом из схемы (`fieldParam`). Непроверенное значение ломает запрос или пишет мусор в обход CHECK, которых у `store`-полей нет. |
| 21 Ошибки БД → поля | Это перевод ошибки, а не правило. Без него вместо «Это значение уже занято» — общая ошибка. Отключать нечего. |
| 22 Неизвестные ключи | Ваше правило: «БД не должна молча игнорировать неизвестные поля». |
| 23 Лимиты | Защита от тяжёлых запросов. Временный экземпляр может поднять лимиты явно (`limits`), но не снять их. |
| 24 Параметры SQL | Без них — SQL-инъекция. |
| 25 Транзакция | Хуки и каскад без неё оставляют полузаписанные данные. Если отключены `hooks`/`checks`/`cascade`, транзакция и так не нужна. |
| 26 Порядок | Не автоматика: порядок уже задаётся во вводе (`order`), а `primaryKey` в конце нужен курсору. |
| 27 Подпись курсора | Без неё клиент подделает позицию и область. |
| 28 Отмена и вид ошибок | Не правило модели. |
| 29 Метка проверки | Отключение значило бы «проверять дважды» — результат тот же. |

## 4. Что значит «выключено» для каждого ключа

| Ключ | Чтение | Запись |
|---|---|---|
| `policy` | все строки, без правил `policy.select` | без `policy.insert/update/delete/restore` |
| `grants` | все поля читаемы, фильтр и сортировка по любому полю с любым оператором | запись в любое поле, кроме защищённых (`protect`) |
| `protect` | — | разрешена запись в `generated`, `immutable`, `primaryKey`, `ownerField`, поля с `createValue` (перенос данных со своими id и датами) |
| `createValue` | — | значение не подставляется; не передано — DEFAULT колонки или ошибка БД |
| `normalize` | значения фильтра не приводятся | значение пишется как пришло |
| `required` | — | отсутствие поля проверяет только NOT NULL в базе |
| `fill` | — | не дозаполняется |
| `store` | — | пишется как есть (уже готовый хэш) |
| `hooks` | без `afterRead` | без `beforeWrite`, `afterWrite`, `afterCommit` |
| `checks` | — | без правил данных (`validator` — тоже) |
| `validateFinal` | — | итоговая строка не проверяется |
| `timestamps` | — | `updatedAt` не двигается; `createdAt`/`updatedAt` можно передать, если выключен и `protect` |
| `softDelete` | удалённые видны (как `includeDeleted`, но без `readDeleted`) | `delete` удаляет навсегда; `restore` — `unsupported` |
| `cascade` | — | дети не помечаются, `restrict` не проверяется |

**Зависимости.** Внешние ключи и NOT NULL работают в самой базе — их не отключает ни один ключ.
Если выключить `softDelete`, но не `cascade`, при удалении навсегда каскад делает база
(`references.onDelete`), а не `softDelete.children`.

## 5. Как это выглядит в коде (предложение)

```ts
const api = db.resource(posts)

// Снаружи: поведение модели. Где доступна модель, там и это.
api.behavior()
// → { timestamps: { createdAt: 'created_at', updatedAt: 'updated_at', deletedAt: 'deleted_at' },
//     live: { inserted: true, updated: true, deleted: true },
//     off: [] }

// Разово: временный экземпляр без указанной автоматики.
await api.without(['timestamps'], (api) => api.update(ctx, id, { views: 5 }))

// Удалить навсегда (очистка по запросу пользователя):
await api.without(['softDelete'], (api) => api.delete(ctx, id))

// Перенос из старой базы: свои id, даты и готовые хэши паролей.
await users.without(['protect', 'createValue', 'timestamps', 'store'], async (users) => {
  users.behavior().off // → ['protect', 'createValue', 'timestamps', 'store'] — выключение подтверждено
  await users.insertMany(ctx, rows)
})
```

- **Ключ, не подходящий модели, — ошибка.** Например, `softDelete` у модели без мягкого
  удаления. Иначе `behavior().off` обещал бы то, чего нет. Неизвестный ключ и пустой список —
  тоже ошибки.
- **Вложенный `without` складывает списки.** Временный экземпляр может выключить ещё что-то,
  но не включить выключенное.
- **Внутри транзакции:** `tx.resource(posts).without([...], …)` — временный экземпляр пишет
  в ту же транзакцию.
- **Ключи берутся только из кода.** API модели серверный, из запроса клиента в `without` ничего
  не попадает.
- **`liveCapabilities(resource)`** становится частью `behavior().live`; отдельная функция
  остаётся для описания модели без базы.
- **`null` и `''` в `timestamps`** = поле выключено, как отсутствие ключа. В типе:
  `createdAt?: string | null`. У объектной формы `deletedAt: { field: '' }` — тоже выключено.

## 6. Вопросы (первый круг)

Ответ на п.1 — два ключа. Пп.2–4 пересобраны в §8 под механику «клон со схемой».

1. **Ключи прав.** Два ключа (`policy` — строки, `grants` — поля) или один `acl` на всё?
   Рекомендую два: «показать админу все поля своих строк» и «показать все строки» — разные
   случаи.
2. **Список «не отключается»** (§3) — согласны? Спорный пункт один: проверка схемой поля (№10).
3. **Имена.** `without` и `behavior()` — или свои? Остальные ключи — как в таблицах §2.
4. **Разовое отключение без `protect`.** Выключенный `timestamps` с включённым `protect` — только
   «не двигать `updatedAt`»; писать даты нельзя. Так и оставить (рекомендую: опасное — отдельным
   ключом)?

## 7. Как это сделано в других ORM

| ORM | Выключить поле дат в схеме | Разовое отключение | Как устроено разовое |
|---|---|---|---|
| Laravel Eloquent | `const UPDATED_AT = null` | `withoutTimestamps(fn)`, `withoutEvents(fn)`, `unguarded(fn)`, `withoutGlobalScope(...)`, `saveQuietly()` | колбэк меняет статическое состояние класса на время вызова |
| Rails ActiveRecord | `record_timestamps = false` | `no_touching { }`, `unscoped { }`, `update_columns` (без проверок, хуков и `updated_at`) | блок меняет состояние класса; или отдельный метод записи |
| Sequelize | `createdAt: false` (строка — имя, `false` — выключено), `paranoid` | `Model.unscoped()`, `Model.scope(...)`; опции вызова `hooks: false`, `silent: true`, `paranoid: false`, `validate: false` | `scope`/`unscoped` возвращают **копию класса модели** |
| Mongoose | `timestamps: { createdAt: false }` | опция вызова `timestamps: false`; писать `createdAt` — ещё и `overwriteImmutable: true` | опция одного вызова |
| TypeORM | декораторы `@CreateDateColumn` и др. | опции `listeners: false`, `withDeleted: true` | опция одного вызова |
| MikroORM | фильтр `softDelete` с `default: true` | `filters: { softDelete: false }`, `filters: false`; `em.fork()` | опция вызова или копия менеджера |
| Prisma | — | `$extends(...)` | **новый клиент**, исходный не меняется |
| Doctrine / Hibernate | фильтры `softdeleteable` | `getFilters()->disable(...)`, `session.disableFilter(...)` | переключатель на всю сессию |

Выводы:

- **`null` как «выключено» уже есть:** Laravel (`UPDATED_AT = null`). Sequelize и Mongoose
  используют `false`.
- **Приставка `without…` общепринята** (Laravel); Rails и Sequelize — `unscoped`, `no_touching`.
- **Разовое отключение в Laravel и Rails** — это изменение общего состояния класса на время
  колбэка. В Node с параллельными запросами так нельзя: соседний запрос увидит выключенное.
  Клон, как в Sequelize `scope()` и Prisma `$extends`, этой проблемы не имеет.
- **Mongoose разделяет «не ставить даты» и «разрешить писать даты»** (`timestamps: false`
  против `overwriteImmutable`). Это подтверждает §6 п.4: даты при переносе — отдельный ключ.
- Узнать поведение: в Laravel — `isIgnoringTimestamps()`, `isUnguarded()`.

## 8. Что меняет «клон со схемой» — и вопросы

Схема модели уже описывает, что модель делает. Клон — `defineResource` от той же схемы с
`null` в выбранных опциях. Отсюда:

1. **Ключи = пути в схеме, а не придуманные имена.** `'hooks'`, `'checks'`, `'validateFinal'`,
   `'policy'`, `'timestamps.updatedAt'`, `'timestamps.deletedAt'`, `'timestamps.deletedAt.children'`,
   а для опций полей — `'fields.*.store'` или `'fields.password.store'`. Словарь из §2 не нужен;
   `behavior().off` — список обнулённых путей.
2. **`policy: null` и `grants: null`.** Сейчас `policy` обязателен (ошибка объявления без него).
   Предложение: в клоне `null` = «без ограничения»; в обычной схеме отсутствие `policy` —
   по-прежнему ошибка, чтобы таблица не открылась случайно.
3. **Обнулённое поле дат клон «не знает».** База всё равно заполнит `created_at` своим DEFAULT
   при вставке, а передать свою дату нельзя — поле для клона неизвестное. Значит:
   `timestamps.updatedAt: null` — «не двигать `updatedAt`» (главный случай); для переноса
   своих дат нужен `protect` — снять у полей `generated`/`immutable`, поле остаётся известным.
4. **`timestamps.deletedAt: null`** — клон удаляет навсегда **и видит удалённые строки при
   чтении** (фильтр пропадает вместе с полем). Это прямое следствие механики.
5. **Клон не участвует в синхронизации структуры базы.** Колонки и индексы строятся только
   по исходной модели; иначе обнулённое поле выглядело бы как «удалить колонку».
6. **Указатель курсора клона** подписывается с учётом списка выключенного — указатель,
   выданный клоном без прав, исходная модель не примет.

Вопросы:

1. Ключи — пути в схеме (п.1)?
2. `null` в `policy`/`grants` — «без ограничения» только в клоне (п.2)?
3. Даты при переносе — через `protect` (п.3)?
4. Имя функции — `without` (как в Laravel) или ваше?

## 9. Системные поля, права полей и `writable` (план, ход 204)

**Решения владельца (ход 204):**

- Мы защищаемся от того, кто работает с моделью через запросы, а не от разработчика. Что
  разработчик делает в обход — его ответственность; ломать «рельсы» ради обходных путей не нужно.
- `insert`/`update` **никогда** не создают и не меняют системные поля. «Удалить» через `update`
  нельзя: `deletedAt` — системное поле.
- **`writable` — сырая запись.** Ничего не фильтруем, не проверяем, не дополняем: что передали,
  то и записано. Кто вызвал — осознаёт последствия.
- **Права полей:** нет маски — нет защиты («всем»). Для служебных моделей защита — лишние
  расходы.
- Каскад при **полном** удалении должен работать, чтобы база не отказывала из-за ссылок;
  при мягком удалении каскад — опция (`softDelete.children`, уже есть).

**Системные поля** — их заполняет модель или база, клиент их не передаёт:

| Поле | Кто заполняет |
|---|---|
| `primaryKey` | `createValue` или DEFAULT базы. Тип выбирает разработчик (uuid, число, текст); в демо uuid |
| `ownerField` | `createValue` / `fill` из `ctx` |
| `timestamps.createdAt` / `updatedAt` / `deletedAt`, ручной `softDelete.field` | база (`clock_timestamp()`), `delete`/`restore` |
| поле с `generated` | DEFAULT базы |
| поле с `createValue` | `createValue` |

Не системные: `immutable` (клиент пишет один раз при вставке) и поле только с `fill` (переданное
значение побеждает, если маска разрешает). Чтобы `slug` в `posts.ts` остался закрытым при новом
правиле масок, ему нужно явное `create: []` — пустой список ролей = «никому».

**Права полей после изменения.** `read`, `create`, `update`: нет ключа или `null` — «всем»;
`[]` — «никому»; список ролей или функция — как сейчас. `read` становится необязательным.
`policy`: нет ключа или `null` — без ограничения.

**`writable((p) => …)` — клон с сырой записью.**

```ts
await posts.writable(async (p) => {
  await p.insert(ctx, { id, title, slug, created_at, deleted_at })   // как есть, со своим id
  await p.update(ctx, id, { created_at })                            // по id, без прав и сдвига updated_at
  await p.delete(ctx, id)                                            // настоящий DELETE
})
```

- Нет: прав строк и полей, защиты системных полей, `normalize`/`fill`/`createValue`/`store`,
  проверки схемой, хуков, `checks`, `validateFinal`, сдвига `updatedAt`, мягкого удаления,
  каскада из `softDelete.children`. Значения по умолчанию ставит сама база — если поле не передали.
- Остаётся только то, без чего запроса нет: имена полей переводятся в колонки (неизвестное
  поле — ошибка, колонку не угадать), значения уходят параметрами SQL (без этого — инъекция),
  транзакция `tx.resource(...)`, отмена по `signal`. Остальное проверяет Postgres.
- Чтение в клоне — обычное чтение модели.
- Числовой счётчик после вставки своих id не поднимается — это дело того, кто вставлял.

**Каскад при полном удалении.** Сейчас внешний ключ по умолчанию `on delete no action`: база
откажет удалять запись, на которую ссылаются (в том числе мягко удалённые дочерние строки —
физически они есть). Предложение: по умолчанию `onDelete: 'cascade'`; запретить —
явным `'restrict'`/`'no action'`. Синхронизация пересоздаёт такие ключи сама.

**Системные поля с работающей автоматикой (ход 205, предложение).** `writable` — сырая
запись. Чтобы поменять `created_at` или `id`, а остальная автоматика работала, защита системных
полей становится отключаемым правилом — ключ `protect` в `without`:

```ts
await posts.without(['protect'], (p) => p.update(ctx, id, { created_at: '2020-01-01T00:00:00Z' }))
```

- Переданное системное поле берётся как есть; не переданное — автоматика как обычно
  (`createValue`, DEFAULT, сдвиг `updatedAt`). Передали `updated_at` — сдвига в этой операции нет.
- Всё остальное работает: проверка схемой поля, `normalize`, хуки, `checks`, `validateFinal`,
  `policy` и маски (если их не выключили тем же `without`).
- Новых полей не появляется — снимается ограничение, как и при выключении прав.
- Отдельный ключ, а не часть `policy`/`grants`: «админ видит все строки» не должно само по себе
  разрешать переписать `id`.

**Ответы (ход 206):** `protect` — отдельный ключ, `writable` — сырая. Сырой клон выключает всё,
и чтение тоже (права строк и полей, скрытие удалённых, хуки, белые списки фильтров и сортировки,
лимиты). Это «без всего», а не «для записи» — предлагаю имя `raw((m) => …)`. Внешний ключ по
умолчанию остаётся `no action`: каскад — функция модели (§10).

## 10. Цепочка удаления (план, ходы 206–207)

**Решения владельца:**

- Сырой клон — `raw((m) => …)`: выключено всё, и чтение тоже.
- Из ссылок `references` убираются `onDelete: 'cascade' | 'set null'`; остаются `no action` /
  `restrict`. Удалить связанные записи — только отдельно запрошенной цепочкой.
- Без цепочки `delete` удаляет одну запись по правилам модели; есть ссылки — ошибку даёт база.
- **Цепочка** — отдельная функция: собирает модели, id записей и сведения о праве удаления. Для
  проверки она спрашивает каждую модель «можно ли удалить и как она удаляет по умолчанию» —
  без удаления.
- **`delete` принимает способ:** мягко (по умолчанию у модели с `deletedAt`) или полностью
  (`force: true`). С цепочкой `delete` проверяет собранное и удаляет с конца, корень — последним,
  в одной транзакции.
- Полное удаление корня — вся цепочка удаляется полностью; мягкость моделей цепочки не важна,
  важны права.
- Мягкое удаление корня — все модели цепочки обязаны уметь мягко; хоть одна не умеет — не
  удаляется ни корень, ни цепочка, ошибка называет модель.

**Предложение по устройству:**

```ts
const plan = await posts.chain(ctx, id)          // ничего не удаляет
// plan.links: [{ model: 'demo.comment.v1', ids: [...], allowed: 3, total: 3, soft: true }, ...]
await plan.delete({ force: true })               // полностью: корень + цепочка, с конца

await posts.delete(ctx, id)                      // одна запись, как умеет модель (мягко)
await posts.delete(ctx, id, { force: true })     // одна запись полностью; ссылки → ошибка базы

await comments.canDelete(ctx, ids)               // { allowed: [...], soft: true } — без удаления
```

1. **Откуда связи.** Таблицы создаёт синхронизация схемы при запуске (`schema.gate`) из списка
   моделей; описание модели само таблицу не пишет. Связи можно читать из Postgres
   (`pg_constraint`), но ответ — таблицы и колонки, а для прав нужна модель (её `policy` — код,
   из базы её не получить). Значит в любом случае нужен список моделей у `db`. Предложение:
   `createDb({ resources: [...] })` — тот же список, что у синхронизации; связи — из `references`
   в моделях (это ровно те внешние ключи, что создаёт синхронизация). Ссылка из таблицы без
   модели (ручной SQL) — база откажет при удалении, транзакция откатится.
2. **`chain` не бросает ошибку из-за прав, а собирает всё** — права и способ удаления по каждому
   звену. Способ удаления известен только в `delete` (`force`), поэтому проверка — в одном месте,
   в `delete`. Заодно `plan.links` годится для интерфейса: «будут удалены 3 комментария».
3. **`plan.delete` перепроверяет внутри транзакции:** собирает цепочку заново с блокировкой
   строк. Набор изменился (кто-то добавил комментарий) — `conflict`, ничего не удалено.
4. **Полное удаление** берёт и уже мягко удалённые дочерние строки — физически они есть, без них
   база не даст удалить родителя. **Мягкое** — только живые.
5. **Дочерние строки удаляются через свою модель** (её права, время удаления, хуки) — пачкой
   на уровень, а не запросом на строку.
6. Право на полное удаление — тот же `policy.delete`.
7. Число строк цепочки — лимит в `limits`. Круги — см. «Роль ссылки» ниже.
8. Ошибка: `forbidden` или `unsupported` с `{ model, path, count }`; текст выбирает интерфейс.

**Клон и дочерние модели (уточнение вопроса 3).** `posts.without(['policy'])` выключает права
только у `posts`. Цепочка спрашивает права у `comments` через модель `comments` — и там права
работают. Чтобы «удалить не глядя», выключенное в клоне корня должно переходить на модели
цепочки (неподходящие ключи пропускаются).

**Роль ссылки (ход 208).** Владелец: не каждая ссылка значит «удалить вместе». Ссылка бывает
двух видов:

- **принадлежность** — строка живёт только вместе с целью: комментарий → запись, запись →
  категория. Входит в цепочку;
- **указатель** — для показа (`join`): пользователь → «закреплённая запись», запись → автор.
  В цепочку не входит; удаление цели при живой ссылке — ошибка базы (при мягком удалении
  `join` просто перестаёт показывать удалённую цель).

Объявление — флаг у ссылки: `references: { resource: () => posts, chain: true }`; без флага —
указатель. Круги тогда:

- по моделям из одних принадлежностей (A ⊂ B ⊂ A) — ошибка объявления при `createDb`;
- ссылка модели на саму себя (ответы на комментарии, дерево категорий) — допустима: строки
  собираются рекурсивно, повторы отбрасываются, работает лимит строк.

**Ответы (ход 209): все «да».** Флаг `chain: true`; связи из `references` + список моделей у
`createDb`; `chain` собирает, решает `delete`; выключенное у корня переходит на цепочку; имена
`chain`, `canDelete`, `force`.

**Как `plan.delete` удаляет (владелец, ход 209):**

- Проверка — моделями цепочки (с выключенным у корня, если корень — клон).
- Удаление — с конца, клонами `without` моделей цепочки: при полном удалении корня в клоне
  выключено мягкое удаление (`timestamps.deletedAt` / `softDelete`), плюс выключенное у корня.
  Последним удаляется корень.
- Ошибка SQL посреди цепочки значит, что в цепочке что-то не учтено: транзакция откатывается,
  пользователю уходит ошибка базы.
- Сбор цепочки повторяется внутри транзакции с блокировкой строк (п.3 выше): иначе при мягком
  удалении новый комментарий, добавленный между `chain` и `delete`, остался бы живым под
  удалённой записью — база тут не возразит.

## 11. Порядок работ

Каждый шаг — отдельный коммит с зелёными проверками; тесты на PGlite в `db-rules`, README и
PORTING — в том же шаге.

1. `timestamps`: `null`, `''`, `undefined`, нет ключа — поле выключено.
2. Права: маска поля без ключа или `null` — «всем», `[]` — «никому»; `read` необязателен;
   `policy` без ключа или `null` — без ограничения. В `posts.ts` — явное `create: []` у `slug`.
3. `without(paths, fn)` и `behavior()`: клон из схемы с `null` по путям; вложенный `without`
   складывает; работает в `tx.resource`; клон не участвует в синхронизации.
4. Ключ `protect`: системные поля можно передать, остальная автоматика работает.
5. `raw(fn)`: клон без всего, и при чтении.
6. `delete(ctx, id, { force })` и `canDelete(ctx, ids)`.
7. Цепочка: `createDb({ resources })`, `references.chain`, проверка кругов принадлежности,
   `chain(ctx, id)` → `plan.delete({ force })`. Из ссылок уходят `onDelete: 'cascade' | 'set null'`;
   `softDelete.children` и `deletedAt.children` заменяются цепочкой (несовместимое изменение
   API, в демо их нет).

Размер: `posts.ts` попадает в браузер, рост `lib/db` бьёт по бюджетам — превышение сообщаю.
