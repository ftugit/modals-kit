# Проектирование: специальное поле для создаваемых полей

**Статус: НА УДЕРЖАНИИ** (решение владельца, ход 10). Не реализовывать, пока владелец
не вернётся к задаче: зачем это нужно и как должно работать, ещё не обсуждалось.

Связанные находки: **F24** (пробел в дизайне), **C12** (обходной путь в демо),
**F16** (исправлено в библиотеке — см. «Что уже изменено»).

## Проблема

Владелец ожидал, что возможность создавать поля заложена в библиотеку через
специальный field. Проверка (ход 10) показала, что её нет:

- **Специального типа поля нет.** Встроенных типов 10 (`builtins.ts`), среди них
  нет «слота» или «расширяемого» поля.
- **Протокола «клиент создал поле, сервер знает спецификацию» нет.**
  `compileFieldSpec()` компилирует спецификацию на клиенте, в памяти.
  `createAppSource` + `UserFieldStore` только ЧИТАЮТ готовые спецификации из
  хранилища приложения; записать туда поле с клиента нечем.
- **`sideEffect: 'mutate-schema'` объявлен, но не исполняется.** Тип —
  `describe.ts:57`; демо объявляет действия `add-row`, `remove-row`, `add-field`
  (`routes/(site)/(app)/form/signup.ts`). Поиск по `src`: признак нигде не читается,
  `server.ts` не применяет `SchemaOp` для служебных intent'ов.
- **README не соответствует коду:** раздел «Повторяемые группы» утверждает, что
  «тот же SchemaOp применяется в памяти при перехвате и на сервере при нативной
  отправке. Второго код-пути не существует». На сервере этого кода нет.

### Следствия, видимые в демо `/form`

- `routes/(site)/(app)/form/handle.ts` `expandFor` угадывает по именам в теле запроса,
  какие строки групп (`items.rN.*`) и `u_`-поля добавил клиент.
- `u_`-поля сервер принимает как text **без валидаторов**, хотя клиент объявил
  `required` + шаблон `e164`. Любой POST с `u_любое=…` проходит слой имён.
- `handleSignup` читает тело через `request.clone().formData()` ДО слоя лимитов
  (без предела), чтобы выбрать описание.
- `__form_spec` в демо занят переключателем режима ошибок
  (`SPEC_FIRST`/`SPEC_ALL`), а не версией набора полей.
- Без JavaScript «+ позиция», «удалить», «+ поле», судя по коду, отправляют
  форму, но набор полей не меняется (демо подтверждает служебное действие пустым
  `commit()`). **В браузере не проверено**, браузерных тестов на это нет.

## Варианты, обсуждавшиеся до удержания (не утверждены)

Для демо без изменений библиотеки:

1. Каталог спецификаций в изоморфном модуле демо + `UserFieldStore`, отдающий
   первые N из каталога; версия кодирует N и режим ошибок (`N*10 + режим`).
2. То же, но разворот строк групп по серверному шаблону переезжает в `lib/form`
   (новая публичная обёртка источника).
3. Режим ошибок — отдельный `formId`; `__form_spec` означает только число полей.

Направление для библиотеки (набросок, не решение):

- Поле-«слот» в описании, например `field.extensible({ catalog, max })`: сервер
  знает каталог разрешённых спецификаций, клиент выбирает из него, сервер
  проверяет добавленные поля своими правилами.
- Сервер исполняет действия с `sideEffect: 'mutate-schema'` (строки групп,
  добавление полей) — тогда это работает и без JS, а `expandFor` исчезает.
