## 1. Модель входа — seed как у криптокошелька

Пользователь генерирует пару ключей **локально** (seed → приватный ключ); приватный ключ
никогда не покидает устройство. Сайт хранит только публичный ключ. Вход — «вызов-ответ»:

1. Сайт выдаёт одноразовый `nonce` (в `#lib/cache`, TTL ≈ 2 минуты, одноразовый).
2. Пользователь подписывает `nonce` приватным ключом (браузер/WebCrypto или расширение).
3. Сайт проверяет подпись публичным ключом, находит строку identity и открывает сессию.

Пароля нет; восстановление = восстановление seed самим пользователем (сайт помочь не может —
это честно пишем в интерфейсе: «ключ утерян — доступ утерян»).

## 2. Правила безопасности из статьи (все)

Проблема: JWT самодостаточен и живёт до `exp`; централизованного «удалить сессию» у него нет.
Компрометированный токен валиден до конца срока, а в распределённой системе каждый сервис
должен одинаково признавать отзыв. Семь способов отзыва:

| # | Способ | Как работает | Плюсы | Минусы |
|---|---|---|---|---|
| 1 | **Чёрный список токенов** | на сервере список отозванных идентификаторов (`jti` или userId); проверка перед каждым запросом; хранение в БД или in-memory (Redis), запись с TTL = остаток `exp` | гранулярно: гасится конкретный токен; совместим с любыми бэкендами и провайдерами | состояние на сервере (против идеи stateless); рост списка деградирует поиск, особенно в БД |
| 2 | **Короткий срок жизни** (`exp` ≈ 15 мин) | окно применения украденного токена минимально; новый токен — через re-auth или refresh | снижает риск; сохраняет stateless | нет мгновенного отзыва; пользователю чаще пере-логиниваться |
| 3 | **Ротация секрета подписи** | периодическая смена ключа: все токены старого ключа недействительны разом | массовый отзыв (инцидент, смена стратегии); дополнительный слой | сложное управление ключами; после ротации клиенты обязаны получить новые токены; «самостоятельный менеджмент секретов — источник уязвимостей» |
| 4 | **Версионирование токенов** | в записи пользователя счётчик `tokenVersion` входит в токен; отзыв = инкремент в БД; проверка версии на каждом запросе | селективно гасит ВСЕ токены пользователя; гибко | лишняя логика и поход в БД на каждый запрос |
| 5 | **Выход + принудительная инвалидация** | при logout сессия помечается/удаляется на сервере (в OAuth/OIDC — отзыв у провайдера) | мгновенный эффект; пользователь управляет своей безопасностью | stateful; в распределённой среде сложнее согласовать |
| 6 | **Список отзыва (TRL)** | централизованный/распределённый сервис «отозван ли токен», опрашиваемый всеми конечными точками | масштабируется; единая точка политики отзыва | латентность (лечится in-memory); свой сервис проектировать и поддерживать |
| 7 | **Refresh-токены для длинных сессий** | access короткий; refresh хранится на сервере и выдаёт новые access; компрометация → отозвать refresh | длинная сессия без длинного access; отзыв сессии без чужих | сложность на клиенте и сервере; отзыв refresh НЕ убивает уже выданный access — остаётся короткое окно |

Лучшие практики статьи: refresh-токены хранить безопасно и **часто ротировать**; минимизировать
срок жизни access (`exp` по вкусу, баланс с UX); хранить токены в **cookie с `HttpOnly` и
`Secure`** (не в открытом клиентском хранилище); **мониторить аномалии** (токен ходит из многих
мест); **автоматизировать** управление токенами готовыми средствами.

Риски плохого управления: несанкционированный доступ, кража токена при небезопасном хранении,
replay-атаки украденным токеном, плохой UX (лишние логауты), юридические последствия в
регулируемых отраслях.

## 3. Что берём в проект

| Правило статьи | Решение у нас |
|---|---|
| чёрный список `jti` (1) + выход (5) | сессия = **серверная бронь** (`#lib/cache`, контракт → Postgres-хранилище — та же задача «бронь отправки в транзакции», README `lib/cache` §6). Обычный выход — удалить бронь; проверка сессии на каждом запросе и так есть (серверный `handle`) |
| короткий `exp` (2) + refresh (7) | access-токен в cookie: жизнь 15 минут; продление — ротацией брони (новый `jti`, старый гасится) — «refresh» без второго токена |
| версионирование (4) | `tokenVersion` в строке identity: «выйти со всех устройств» и «ключ скомпрометирован» → инкремент — все брони пользователя мертвы |
| ротация секрета (3) | ключ подписи с `kid` в токене; ротация по схеме курсорных ключей (уже реализовано: `DB_CURSOR_KID`/`DB_CURSOR_OLD_KEYS` — старый ключ принимает, новый пишет) |
| TRL (6) | НЕ выделяем сервис: приложение одно, проверка брони локальна в том же процессе/БД. ТRL появится, только если пойдут микросервисы |
| хранение (практики) | cookie `HttpOnly; Secure; SameSite=Lax`; в `localStorage` токен не пишем |
| мониторинг (практики) | счётчик «брони одного identity из многих подсетей» — краткоживущий (TTL минуты) хеш подсети в памяти, IP целиком не храним (§4) |

## 4. Приватность: что сознательно НЕ храним и почему

**РФ.** 152-ФЗ: оператор до начала обработки ПДн уведомляет Роскомнадзор (ст. 22; с
30.05.2025 неуведомление — ч. 10 ст. 13.11 КоАП, до 300 000 ₽; исключения ч. 2 узкие:
госсистемы, бумага, транспортная безопасность). Куки, идентифицирующие пользователя, — ПДн
(практика РКН); законы 420-ФЗ и 156-ФЗ (2025): активное согласие на не-технические куки,
баннер с двумя равнозначными кнопками, отказ = счётчики не загружаются, согласия логируются;
технические куки (сессия, CSRF) согласия не требуют, но описываются в политике. Ст. 18(5):
первичный сбор ПДн граждан РФ — на серверах в РФ.

**ЕС/мир.** GDPR ст. 4(1); EDPB Guidelines 02/2025: адрес кошелька/публичный ключ — **персональные
данные, если связываемы с человеком** (KYC, аналитика, внешние данные); CNIL: карту «личность ↔
ключ» держать off-chain, и без неё ключ фактически анонимен. ePrivacy: согласие на
не-необходимые хранилища на стороне клиента.

**Следствие — не храним (и это осознанная архитектура, не лень):**

| Не храним | Почему это безопасно юридически |
|---|---|
| email, телефон, имя, пароли (их нет вообще) | нет прямой идентификации → нет оператора ПДн → нет уведомления РКН и реестра |
| IP в долговременных логах | IP — ПДн (GDPR, практика РКН); в памяти держим только краткоживущий хеш подсети для счётчика аномалий (§3) |
| аналитические/рекламные счётчики и их куки (Метрика, GA, пиксели) | они требуют баннера, согласия, лога согласий и (для чужих счётчиков) трансграничной политики; без них баннер не нужен вообще — на сайте только технические куки |
| fingerprint, соцграф, cross-device связки | профилирование = ПДн + отдельные согласия |
| карту «публичный ключ → человек» | без неё публичный ключ — псевдоним без разумных средств связи с личностью: не ПДн по 152-ФЗ и вне личных данных по EDPB-тесту |

Публичный ключ храним как **псевдоним**: строка (seed, createdAt, tokenVersion). Право на
удаление исполняется удалением этой строки — больше за пользователем ничего не стоит.
«Продолжая использовать сайт, вы соглашаетесь» — не согласие; мы обходим вопрос: соглашаться
нечего.

Если когда-нибудь понадобится email (уведомления, восстановление) — включается пакет:
уведомление РКН, баннер, политика, лог согласий, локализация серверов, отдельное согласие.
Это осознанное решение владельца, не дефолт.

## 5. Шаги внедрения

Оболочка API написана каркасом (`src/content/user`, ход 251): `user.ts` — голые функции
(тела пустые, правила статьи помечены «статья: N»), `ports.ts` — что даёт приложение,
`sveltekit.ts` — связка с хвостами и фасад `auth(event)` для REST и POST одновременно,
`README.md` — цепочка вызова и таблица покрытия. Внедрение = наполнить тела по шагам ниже.

1. **identity** — ресурс `lib/db` (`demo.auth + demo.profile`: seed, createdAt, tokenVersion; ключ
   доступа — см. §7 README `lib/db`; у гостя прав нет).
2. **challenge** — `POST /api/auth/challenge`: nonce в `#lib/cache` (TTL 2 мин, одноразовый).
3. **вход** — `POST /api/auth/login`: проверка подписи, создание брони сессии, cookie
   (`HttpOnly; Secure; SameSite=Lax`) с `sid` + подписанным токеном (`jti`, `exp` 15 мин, `kid`).
4. **проверка** — в `handle`: подпись, `exp`, бронь жива, `jti` не в чёрном списке,
   `tokenVersion` совпадает; `principal` берётся из брони (`DEMO_PRINCIPAL` уходит).
5. **выход** — удалить бронь + занести `jti` в чёрный список (TTL = остаток `exp`); «выйти
   со всех устройств» — `tokenVersion += 1`.
6. **ротация `kid`** — по схеме курсорных ключей (старый принимает, новый пишет).
7. **мониторинг** — счётчик аномалий в памяти (без хранения IP).
8. **условия по другим моделям** (§1 п. 5 плана) — ключ доступа у записи против условия
   «через связь» — решать при подключении прав, как договорились.

Открытые вопросы владельцу: срок жизни брони сессии (день? неделя?); нужен ли пользователю
список активных сессий (тогда храним по строке на устройство — больше состояния, но всё ещё
без ПДн); подтверждать ли вход подписью на каждое критическое действие.

## 7. Эмуляция подходов (ход 251, код модуля не тронут)

Стенды: `/home/user/emul/sql-approaches.mjs` (pglite 0.5.8, WASM Postgres в процессе,
200 000 строк в demo_sessions) и `/home/user/emul/token-seal.mjs` (iron-webcrypto 2.0.0,
Node 24). Запуск: `node /home/user/emul/…`. Абсолютные числа включают накладные WASM;
беруться относительный порядок и число round trip (RT).

### SQL: как проверять бан/блокировки и выполнять действие

| Вариант | Медиана | p95 | RT |
|---|---|---|---|
| два запроса: guard, потом действие | 0.96 мс | 1.63 | 2 |
| единый CTE: guard (blocked — jsonb-сферы с until) + действие | 0.87 мс | 1.12 | **1** |
| единый CTE, guard дешёвый (`blocked <> '[]'`) | 0.70 мс | 0.98 | **1** |

- Бан через CTE: `ok=false`, `rights=null` — данных НЕТ (протечки нет).
- Отзыв девайс-токена (`revoked=true`): все временные токены сессии мертвы
  (sealed-строка несёт dt, guard по нему режет любое действие).
- 200 000 строк в сессиях: план не меняется (Index Scan по PK) — lookup константен.
- JSONb-сферы с `until` дороже дешёвой проверки на ~0.17 мс (WASM); на реальном PG
  разница меньше, но сферы нужны владельцу — берём их, форма запроса та же.
- Итог: **CTE «if(нет блокировок) select одним sql» — самый дешёвый** (−1 RT всегда,
  −строки кэша, −инвалидация). Серверные права на действие берутся живьём из БД —
  п. 2 владельца (UI пустил, сервер проверил актуальные права) выполняется по построению.

### Токен без серверного хранилища: sealed-строка (iron-webcrypto)

Библиотека (та, что владелец помнил): **iron-webcrypto** — наследник @hapi/iron,
движок iron-session; WebCrypto (изоморфно), 0 зависимостей, **2.4 КиБ gzip**.

| Замер | Значение |
|---|---|
| seal (aes-256-cbc + hmac-sha256) | 0.32–0.40 мс |
| unseal | 0.70–0.78 мс |
| строка для payload {sub, ver, dt, prof, iat, exp} | **497 Б** (кук-лимит 4096 Б) |
| подмена строки (любой байт) | **отвергнута** — изменить содержимое нельзя |
| чужой ключ | отвергнут |
| replay просроченной строки | отвергнут (exp внутри); живой replay ≤ exp ловит guard по dt/ver |
| ротация ключа | id ключа в строке + карта ключей при unseal ✓ (как курсорные) |

- Опубликованная 2.0.0 НЕ содержит подмодуль `/gcm` (AEAD заявлен в README репозитория,
  в npm его нет): работает стандартный формат iron — AES-256-CBC + HMAC-SHA256
  (encrypt-then-MAC), подмена ловится HMAC. AEAD-усиление — при появлении в релизе
  или PASETO v4.local (не мерялся).
- Что внутри временного токена: sub, ver (token_version), dt (девайс-токен), снапшот
  profile (никнейм/аватар), iat/exp. Сервер НИЧЕГО не хранит о временном токене.
- Ключ запечатывания — `AUTH_SEAL` из env; ротация картой ключей (прецедент курсорных).

### Самый дешёвый на каждое действие (итог эмуляции)

1 request: unseal строки (~0.7 мс CPU, 0 RT) → guard-CTE с действием (1 RT к БД).
Против серверного кэша: −1 RT к Redis, −строки, −инвалидация. Секрет — ключ в env.
Цена безопасности (принята владельцем, п. 2): забаненный пользуется сайтом, пока
приложение не обратится к api auth; сам access отозвать мгновенно нельзя.

### Решения хода 251 (дополнение): шаблон гварда, iron-webcrypto, no-JS

- [ ] **SQL-шаблон гварда**: функция, принимающая конечный select действия + список
  сфер блокировки; строит `WITH guard AS (...) SELECT … LEFT JOIN LATERAL ON g.ok`,
  чтобы гигант не повторялся в каждой функции. НЕ каждая блокировка выкидывает
  из аккаунта: сфера 'auth' — кик (падают все действия), остальные сферы
  (пример владельца: смена настроек безопасности) — блок только своих действий;

  (решить вместе с вопросом о месте API).
- [ ] **iron-webcrypto — библиотека временного токена у юзера** (выбор владельца

- [ ] **no-JS**: работает — sealed-строка это HttpOnly-кука (браузер без JS просто

### Решение владельца (ход 251): состав sealed-куки и когда зовётся api auth

- [ ] **UI рендерит из токена, api auth до отправки формы НЕ зовётся** (уточнение
  модели: рендер НЕ проходит через guard — вариант «права из CTE при каждом
  рендере» отозван владельцем). Токен — несущий источник витрины.
- [ ] **Состав строки (замер: кука 836 Б при лимите 4096; token-budget.mjs)**:
  обязательные sub, ver, dt, iat, exp + НИКНЕЙМ + ПРАВА ДОСТУПА + ЗАБЛОКИРОВАННЫЕ
  ДЕЙСТВИЯ (ключи сфер). Аватар-url — опционально, влезает.
- [ ] **Когда api auth зовётся**: (1) отправка формы/действие — guard-CTE проверяет
  блокировки и АКТУАЛЬНЫЕ права из БД (UI мог врать); (2) продление — ТОЛЬКО при
  истечении access (не на каждый запрос, иначе цель «без api auth» ломается);
  (3) мутации auth (вход/выход/удаление).
- [ ] Следствия приняты владельцем: витрина устаревает до продления (≤ срока
  access); забаненный/отозванный видит «можно» и ловит отказ на действии;
  украденная кука = кража сессии (bearer; HttpOnly/Secure/SameSite — защита,
  guard не страхует от кражи самой куки).
- [ ] Побочка-опция: отдельная страница может СОЗНАТЕЛЬНО позвать guard на GET
  (пример: страница настроек безопасности) — выбор места, не правило рендера.

### Хранение у юзера — гибрид (уточнение владельца, ход 251)

- [ ] **Временный токен (витрина)**: у юзера с JS — в RAM (замыкание, не window),
  приложение читает ТОЛЬКО память; без JS — носит в куках. Сервер ничего не хранит.
- [ ] **Девайс-токен (продление)**: HttpOnly-кука; JS его не читает и в память не
  переносит — он нужен только серверу при продлении. Где ещё хранить (localStorage
  у REST-клиента и т.п.) — решает то приложение, которое юзает модуль; в нашем
  приложении — куки.
- [ ] **Выход — порядок строго**: (1) POST → сервер гасит девайс-токен И снимает
  куки (HttpOnly снимает только сервер), (2) JS чистит память → UI мгновенно гость.
  Перезапуск сайта: кук нет → в память нечего переносить → гость. Удалять куки по
  сигналу «из памяти» НЕЛЬЗЯ (сервер не отличит намерение от очистки/CSRF — риск
  принудительного логаута); удаление кук — только ответ на явный POST.
- [ ] Скрытие токена в замыкании: не спасает от живого XSS (обёртка fetch/XHR читает
  в момент отправки; session riding без чтения) — это осознанная цена RAM-носителя;
  HttpOnly девайс-куки страхуют от ВЫНОСА продления с сайта.
- [ ] Выход без JS: та же форма, сервер снимает куки + redirect на гостя.

### Исправление владельца (ход 251): софт-удаление вместо «банов»

- [ ] ОТДЕЛЬНОЙ структуры банов НЕТ (ни таблицы, ни ячейки): «заблокировать
  девайс-токен» = **софт-удалить строку сессии** в таблице session (`deleted_at`).
  Guard читает ту же строку: условие вместо `revoked = false` —
  `s.deleted_at IS NULL` (форма CTE и план не меняются: PK-lookup + проверка NULL).
- [ ] Все операции ревокации — софт-удаления строк сессий: выход (своя строка),
  отзыв устройства из списка (его строка), «выйти со всех» (все строки identity).
- [ ] auth.blocked (сферы блокировок) остаётся ЕДИНСТВЕННЫМ механизмом блокировок
  аккаунта/действий — для сессий он не используется.
- [x] token_version — РЕШЕНИЕ владельца (ход 251): **убрать**. Все отмены покрывает
  софт-удаление строк сессий (sealed-строка несёт dt, guard по нему видит удаление).
  При переделке каркаса снять: колонку auth.token_version, ver из клеймов/sealed-
  строки, инкремент-логику. «Выйти со всех» = софт-удалить все строки сессий юзера.
- [x] Guard возвращает СТАТУС сессии (вопрос владельца «отозвана vs не существовала»
  — да, различает; эмуляция session-status.mjs): ключи **ok / revoked / expired /
  unknown** одним PK-lookup (те же чтения, что у EXISTS; EXPLAIN — два Index Scan):

      WITH st AS (
        SELECT CASE
          WHEN s.jti IS NULL            THEN 'unknown'  -- строки нет
          WHEN s.deleted_at IS NOT NULL THEN 'revoked'  -- софт-удаление = отозвана
          WHEN s.expires_at <= $2       THEN 'expired'
          ELSE 'ok'
        END AS status
        FROM (SELECT $3::text AS jti) x
        LEFT JOIN demo_sessions s ON s.jti = x.jti
      )
      SELECT st.status, r.rights FROM st
      LEFT JOIN LATERAL ( /* действие */ ) r ON st.status = 'ok'

  Отличать revoked от unknown безопасно: jti — случайный uuid, ездит только в
  HttpOnly-куке (зондажу нечем перебирать). Софт-удалённые строки ХРАНЯТСЯ
  (история устройств — модель владельца), отличимость не деградирует; expired-
  строки может убирать чистильщик по расписанию. UX: revoked → «сеанс завершён
  на этом устройстве», unknown/expired → «войдите заново».

### Конфликты с гайдом (все осознаны, места в §2)
- способ 1 (блэклист на каждом запросе) — отклонён: фаервол = guard на действиях;
- способ 2 Cons «No Immediate Revocation» — принят: витрина живёт до exp/продления;
- способ 7 «frequently rotated» — усилен: одноразовость; детекция повтора — ВНЕ
  статьи (OAuth BCP), источник помечен;
- best practice «Monitor for Suspicious Activity» — ВЫПАЛО при чистке (noteActivity
  удалён; кандидат на возврат — сверка масок при renew).

### Дыры (кроме «юзер сам себе злоумышленник»)
- [ ] Кража куки девайса вредоносом (не юзер): malware читает cookie-БД браузера,
  HttpOnly не спасает — сессия на весь TTL (30 дней?). Мит.: сверка масок при renew,
  список устройств + отзыв, короткий TTL, (опц.) переподпись при смене маски.
- [ ] Живой XSS (наш баг или supply-chain): session riding без чтения токенов +
  перехват в момент отправки (замыкание не спасает). Мит.: строгий CSP (nonce +
  strict-dynamic + object-src 'none', web.dev), Trusted Types (MDN), HttpOnly
  девайс-куки (продление не выносится), короткий access, захваченный fetch (ниже).
- [ ] Безлимитная регистрация — рост demo_auth/сессий: rate limits (выше).

### Защита вызова: fetch не через глобал (исследование)
- Сервер: УЖЕ изолирован — SvelteKit даёт event.fetch, Node может импортировать
  fetch (undici); глобал браузера к серверным вызовам отношения не имеет.
- Браузер, уровень 1 — ЗАХВАТ ссылки: модуль при первом исполнении берёт
  const native = globalThis.fetch; ВСЕ вызовы приложения — через него; подмена
  глобала после старта не затрагивает захваченное; целостность проверяется
  fn.toString().includes('[native code]') (mmazzarolo). Точка в проекте УЖЕ ЕСТЬ:
  #lib/fetch — единственный approved вход сетевых вызовов; capture+freeze ложится
  туда без новых мест.
- Браузер, уровень 2 — Service Worker владеет сетью: страница шлёт postMessage,
  SW зовёт СВОИМ захваченным fetch; патч страницы физически не участвует.
  Ограничения честно: SW-скрипт same-origin и secure context (Chromium FAQ);
  XSS + возможность положить JS на origin = SW сам «постоянный monkey-patch»
  (rmrf.tips) — мит.: CSP на ответ SW (Chromium FAQ), Trusted Types на register()
  (MDN: scriptURL = injection sink), сбой/потеря SW = приложение отказывает
  (fail-closed: «подмена ломает вызов»).
- Браузер, уровень 3 — не дать патчеру запуститься: CSP script-src 'nonce-…'
  'strict-dynamic'; object-src 'none'; base-uri 'none' (web.dev strict CSP);
  Trusted Types роняет innerHTML-синки TypeError (MDN). ГЛАВНАЯ защита: нечего
  перехватывать, если чужой скрипт не исполняется.
- Вердикт: фреймворк позволяет все три (SvelteKit не ограничивает captured refs,
  SW в static/, CSP-заголовки из hooks). Полного локдауна клиента нет (память
  читается в момент использования; подмена видимого юзером исключена владельцем).
  Цель «замена fetch просто ломает вызов» достижима: captured+freeze — наш вызов
  игнорирует глобал; SW — вызов вне страницы; CSP/TT — патчеру негде жить.
  ПРЕДЛОЖЕНИЕ: протокол в #lib/fetch (capture + freeze + целостность + опц.
  SW-канал) — внедрять по «го».

### Решения владельца по §8 (вечер хода 251) + исследование IP

- [x] **no-JS вход — оставляем, как всегда**: lib/form после оживления не выполняет
  экшен, а прописывает свой маршрут; без JS проверку за юзера выполняет сервер.
  Юзеру показываем предупреждение: это потенциальный риск, не входите из
  небезопасных точек доступа (текст формулирует владелец).
- [x] **IP — исследовано (152-ФЗ, РКН, суды)**. Полный IP: Роскомнадзор относит к ПДн
  (в совокупности с cookie/агентом/временем — письма и разъяснения с 2017; письмо
  07.02.2020), КС РФ 17-П (16.07.2018) — «может квалифицироваться при
  использовании для идентификации»; ВС РФ 14.01.2020 № 225-АПУ19-4 — IP сайта =
  ПДн оператора; был и противоположный суд (13АП-5614/2017 — не ПДн, страдает
  точность) — практика расходилась, но позиция регулятора однозначна. Частичный IP
  (маска) — всё ещё косвенный идентификатор. Практика минимизации в логах —
  маскирование/хэширование. ВЫВОД ДЛЯ SESSIONS: хранить не IP и не маску, а
  **хэш подсети** (подсеть вместо адреса; соль на аккаунт — чтобы нельзя было
  заранее посчитать хэш всех подсетей и сравнить); сравнение «сменилась ли
  подсеть» работает по детерминированному хэшу. Соль на аккаунт: между юзерами
  связать нельзя, внутри истории одного юзера — можно. Перед внедрением: текст в
  политике ПДн, срок хранения истории (юрист — не наше решение).
- [x] **Опция сессии (владелец)**: поведение при пересоздании сессии —
  (а) строгий режим: запрет менять подсеть (хэш не совпал — сессия не
  пересоздаётся), (б) обычный: обновить актуальную информацию, старую складировать
  в историю. Опция меняется на лету для отдельного устройства; управление
  значениями — ролью (обычному юзеру — реже, админу — чаще).
- [x] **TTL — не зашивать в код**: это опции, меняемые на лету, вплоть до
  отдельного устройства; управление — ролью юзера. По умолчанию: временный токен —
  1 час, девайс-токен — 1 год. Константы каркаса (15 мин / 30 дней) при переделке
  снять, заменить механизмом опций.
- [x] **Никнейм и профиль**: при первом создании seed показывается компонент
  указания никнейма; пропуск = аноним (никнейма нет вовсе). Профиль создаётся при
  ПЕРВОМ заполнении личных данных (не при входе). Таблица profile обязана работать
  в анонимном режиме: без связи с auth возвращать значения по умолчанию. Запас
  прочности: профиль может оказаться на серверах других стран — недоступный сервер
  не ждём, показываем значения по умолчанию.
- [x] **Аудит** («следить за каждым шагом юзера, как в Дискорде») — отдельная
  будущая система; детекция смены подсети при продлении — тоже из режима аудита.
  В текущую модель входит только опция сессии из пункта выше.
- [x] **Ритм работ**: переделка каркаса будет поручена отдельной ночной задачей —
  поэтому все решения здесь дотошно записаны; код ждёт этого поручения.
- [ ] **Отмена удаления в грейсе** — осталось открытым (не отвечено).
- [x] **Защита вызова от подмены** — отложена в отдельный план
  `docs/design/client-integrity.md` (уровни, что уже делает SvelteKit: настройка
  kit.csp сама проставляет ключи/хэши своим встроенным скриптам; исследование
  готовых модулей и рисков — там же). Вердикт владельца: сейчас делать сложнее,
  чем надо, — стрельба в ноги.

- [ ] **Отмена удаления — открыт, варианты показаны владельцу** (примеры в отчёте):

### Настройки: предложение по итогам исследования (ждёт решения)

Слои (практика: overrides-only + реестр ключей + смешивание при чтении):
1. **Значения по умолчанию — в коде**, вместе с РЕЕСТРОМ ключей: имя, тип,
   значение по умолчанию, кому менять можно (роль). Реестр в коде, потому что
   он меняется вместе с релизами; это продолжение правила lib/db «неизвестное
   отвергается»: ключа нет в реестре — запись не проходит.
2. **Общие настройки — одна маленькая таблица** (jsonb на ключ или одна строка):
   меняет админ. Таблица крошечная — Postgres сам держит её страницы в памяти
   (буферный кэш PG), чтение микросекунды; ОТДЕЛЬНЫЙ кэш не нужен — интуиция
   владельца про «pg кэш» подтверждена.
3. **Личные отличия юзера — только то, что он поменял** (jsonb на юзера), не
   полный слепок всех настроек.

Смешивание — силами PG, одним запросом: оператор `||` для jsonb, правый перекрывает
левый: `итог = по_умолчанию || общие || личные`. Можно приклеить к guard-CTE —
действие и настройки одним обращением к БД. Мелочь при записи: одновременные
изменения не затирают друг друга, если писать `SET значение = значение || новый_кусок`
(само по себе атомарно); форма «прочитал-изменил-записал целиком» требует блокировки
строки на чтение (FOR UPDATE).

Роль: реестр решает, кому ключ виден и меняем; при записи сервер сверяет роль.
Открытый подвопрос (решить при внедрении): ключ стал запрещён после понижения
роли — при чтении его применять (PG смешал всё) и фильтровать на странице
настроек, или чистить при понижении.

Отдельный план на систему настроек — по «го» (система общая для приложения, не
только user-модуль).

- [x] **Отмена удаления — решение владельца (как в ВК; редакция третья, верная)**:
  попытка входа в аккаунт с незавершённым удалением СЕССИЮ НЕ СОЗДАЁТ — авторизации
  нет. Вместо приложения юзер видит СТРАНИЦУ-ШАГ (наш компонент steps, ход 250):
  «аккаунт удаляется, время удаления — …» и возможность ОТМЕНИТЬ удаление.
  Юзер отменил → снимается метка удаления (soft) И происходит авторизация
  (обычный вход, сессия живёт). Не отменил — никакого входа: метка остаётся,
  аккаунт умирает по истечении времени из настроек сервера. Детали для внедрения:
  (1) login по pending-аккаунту возвращает «направление на шаг восстановления»

  вайпа вход отвечает «не существует», даже если строка-надгробие жива;
  (3) экран восстановления — шаг steps, поддержка no-JS как у всех форм проекта.

### Профиль как «просто значения» (решение владельца, ход 251)

- [x] Целый стек приложения в каждой стране — ЖИРНО. Профиль — тупое хранилище
  значений: только отображение и редактирование, никакой «работы» с данными;
  экосистему под каждый регион не поднимаем. Кандидат: бесплатный уровень
  серверов РФ-хостера (Яндекс) — файл значений или небольшая база. Нюанс: SQLite
  живёт на файловой системе — для него нужен маленький виртуальный сервер;
  для «просто значений» удобнее файл JSON в объектном хранилище или серверлесс-
  база значений. Яндекс = серверы в РФ = первичная запись в РФ — идея закону
  о размещении дружит.
- [x] **Метка хранения в auth**: строка auth несёт признак, где лежит профиль
  (адрес хранилища или короткое имя места). Носитель метки — auth; фактическая
  выдача и запись — через ПОРТ профиля модуля (адаптер читает метку, ходит в
  хранилище, при недоступности отдаёт значения по умолчанию — ранее принятое).
- [x] **«Клей» — модуль, не страница**: UI никогда не ходит в хранилище профиля
  сам. Показ: никнейм/аватар уже в запечатанном токене (витрина) либо значения
  по умолчанию; редактирование: форма → функция модуля → порт → хранилище →
  токен пере-запечатывается с новыми значениями. Хранилище принимает операции
  только от нашего модуля (проверка подписи/секрета) — иначе «редактирование»
  означало бы «редактирование кем угодно, кто узнал адрес».
- [x] **Кэш и закон (152-ФЗ)**: (1) запечатанный токен у юзера — вообще не база
  оператора, данные лежат у самого юзера (как любая кука) — не нарушение;
  (2) кратковременный серверный кэш-копия при актуальной базе в РФ — практика
  разрешает копии за границей при русской основной базе, но с 2023 любое
  перемещение за границу — уведомление РКН; кратковременность/без
  систематизации — снижает риски; (3) ПОСТОЯННАЯ копия на чужой стране —
  по букве правки 01.07.2025 риск «хранения в иностранной базе» — не делать.
  Правило: первичная запись и актуальная база — в РФ; кэши — недолговечные;
  уведомление РКН — при появлении трансгранички (решение с юристом).
- [ ] Открытое (решить при появлении требования): конкретное хранилище значений,
  способ проверки операций (секрет/подпись), миграция метки при переезде юзера
  между странами.
