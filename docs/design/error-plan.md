# Ошибки: код и текст

Решение владельца (2026-10-25): ошибка, которая доходит до человека или до обработчика,
состоит из **кода** и **текста**. Текст показывается **как есть**, код — для идентификации
ошибки и для будущего перевода. Человекопонятные строки внутри `src/lib` — работа
будущего: она вынесена сюда и формы не блокирует.

---

## 1. Контракт

| Часть | Кому | Правило |
|---|---|---|
| `code` | машине | стабильная строка (`required`, `maxSize`, `profile.avatar-format`); по ней тесты, обработчики и перевод |
| `message` | человеку | готовая строка: UI печатает её **как есть** — не склеивает, не склоняет, не досочиняет |
| `params` | шаблону | подстановки (`name`, `bytes`, `max`); текст в правиле не пишется |

Следствие: пять плохих файлов дают **пять строк** («Файл a.pdf больше 512 КБ»,
«Файл b.zip не подходит по типу», …). Повтор шаблона — не дефект: строки различаются
параметрами, и человек видит, о каком именно файле речь.

## 2. Что уже так (проверено по коду)

| Место | Факт |
|---|---|
| `Issue` валидатора (`src/lib/form/validators.ts:18`) | `{ code, params?, path?, message? }` — правило отдаёт код, не текст |
| `FormError` (`src/lib/form/result.ts:9-19`) | `{ id, code, message?, template?, params? }`; `id` стабилен (`path:code:hash(params)`) |
| словарь (`src/lib/form/messages.ts`) | `MessageDictionary` + `ru`: шаблон строкой или функцией от `params` |
| подстановка | `policy.interpolate(template, params)` — одна точка на всё ядро |
| тест | `src/lib/form/messages.test.ts` требует запись в `ru` для каждого документированного кода |

Вывод: контракт «код + текст» в ядре **уже выполнен**. Открыт не контракт, а полнота
словаря и происхождение текстов.

## 3. Что ещё не сделано

1. **Полнота словаря.** Коды рождают не только валидаторы: `instruction({ code })` из
   серверных проверок, ошибки `#lib/db` (`unique`, `check`, `invalid`), отказы
   `#lib/image`. Если кода нет в `ru`, `message` остаётся пустым — ошибка есть,
   показать нечего.
2. **Шаблон в правиле.** `v.…().message('…')` (аварийный выход, F56) оставлен; каждый
   такой случай — кандидат в словарь, а не норма.
3. **Человекопонятные строки вне словарей.** 466 кириллических литералов в 57 файлах
   `src/lib/**`: ~78 — сам `messages.ts`, остальное диагностика для разработчика
   (`throw new Error`) и русские буквы **в данных** (транслитерация в
   `paginate/search/fuzzy.ts`). Ничего не ломает; переносится только вместе со второй
   локалью.
4. **Локаль.** Словарь один (`ru`). Вторая локаль — тот момент, когда `code` становится
   обязательным для каждой строки; до неё перечисленное выше терпит.

## 4. Порядок работ

- [ ] **Шаг 1 — инвентаризация.** Собрать все `issue('…')`, `f.error = { code }`,
      `instruction({ code })` и литералы `code:` из `src/**`, сверить с `ru`; результат —
      список кодов без текста.
- [ ] **Шаг 2 — закрыть дыры словаря** текстами в `ru`, не трогая правила.
- [ ] **Шаг 3 — вторая локаль** (по потребности): пользовательские тексты из `src/lib`
      в словарь пакета; диагностику оставить как есть.
- [ ] **Шаг 4 — страж** (решает владелец): правило `tooling/` «кириллица в
      `src/lib/**/*.ts` только в `messages.ts` и в известных данных».

## 5. Чего не делаем

- i18n-фреймворк, цепочки fallback, ICU-плюрализация — до второй локали.
- Переписывание текста на клиенте «под контекст»: текст отдаётся как есть.
- Перевод диагностических `throw new Error('…')` — они для разработчика, не для человека.
- Сравнение ошибок по тексту: только по `code`.
