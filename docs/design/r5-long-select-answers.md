| С JS и без JS | один и тот же модуль сопоставления и одни пороги на сервере и в клиенте; одинаковый порядок при равных оценках | — |

## Что не стыкуется с принятым

- **Б: панель через серверный эндпоинт.** Сейчас Select фильтрует локально (ход 34: «фильтр, не
  сортировка; без запроса — N вариантов»). Довод Б по существу: у клиента топ-1000, у источника
  1933 — один и тот же текст с JS и без JS может дать разный ответ. Это вопрос к владельцу, не
  баг.
- **Оба: повтор параметра вместо `1,858`.** Наш адрес — `filters.studios.and=1,858`. В id запятых
  нет, поэтому проблема «запятая в названии» к адресу не относится — она про текстовое поле, и её
  снимает схема «выбранные + поле добавить». Менять формат адреса из-за этого не нужно.

## Что решать владельцу (когда дойдёт до UI)

1. Неуверенное сопоставление: короткий список кандидатов вместо ошибки «опция не выбрана»?
2. Мультивыбор без JS: выбранные — чекбоксами, плюс одно поле «добавить». «И»/«не» — два поля
   (А) или одно поле с двумя кнопками (Б)?
3. ~~JS-панель: локальный фильтр или кандидаты с сервера?~~ **Решено (ход 56): в браузере.**
   С JS select оживает и фильтрует сам через `paginate/search`; сервер сопоставляет текст только
   у клиента без JS, при отправке формы. Отдельного адреса для вариантов нет.
4. Кто решает, что поле «длинное»: число вариантов от источника (А) или явная настройка поля в
   схеме (Б)?

## Предложено (ход 55, ждёт подтверждения)

Всё поведение длинного поля — в одном примитиве `Select` и одном типе поля `lib/form`.
У конкретного select только имя и варианты: `<Select name="studios" options={…} multiple />`.
Режимы «и»/«не» — один раз в компоненте фильтров.
