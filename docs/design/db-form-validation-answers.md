# Формы и БД: правила один раз — разбор ответов других ИИ

Вопрос: `~/prompts/db-form-validation.md`. Ответы: краткий вывод в переписке (далее **А**),
`uploads/ANSWER2.md` (далее **Б**). Статус: **решения выбраны (ход 64, владелец поручил выбор), код не менялся.**

## В чём сходятся (и совпадает с нашим планом)

| Тема | Вывод |
|---|---|
| Механизм | Вариант 3: метка «это значение проверено этой схемой». Метка — только способ не повторять проверку. Без неё или при несовпадении БД проверяет всё сама. |
| Кто за что отвечает | Правила полей модели — модель (пропуск по метке). Свои правила формы (`sameAs`, файлы) — только форма. Правила данных (`checks`) — только БД, всегда, в транзакции записи. PG (CHECK, индексы) — последняя защита. |
| Уникальность | `checks` не заменяет индекс: гонку закрывает только индекс. Его ошибку (23505) переводим в ошибку поля по имени ограничения, как `unique_constraint(name:)` в Ecto. |
| Формы без записи (вход) | `resource.validator(db, op)` → Standard Schema → существующий `createFormHandler({ schema })`. |
| Формы с записью | Заранее не проверять: `create()` сам возвращает ошибки по всем полям, форма их показывает. `checks` выполняются один раз. |
| NOT NULL | Новый признак в формат не нужен: остаётся `nullable` у поля БД. |
| Варианты 1 и 2 | Отклонены. 1 — «забыл `check()`, и защиты нет» (так устроен `save()` в Django, Б ссылается на ticket 13100). 2 — флаг не говорит, какой схемой и какое значение проверено. |

## Что Б добавил (полезное)

1. **`beforeWrite` меняет черновик** — поле нужно перепроверить. Метка была верна до хука.
   У нас то же касается `field.normalize` в `lib/db` (`validation.ts`, `validateField`):
   значение после нормализации другое, метка не совпадёт, будет перепроверка. Это безопасно.
2. **Копия объекта (`{...values}`, JSON, очередь) теряет метку** — перепроверка. Это безопасно.
   Через HTTP или очередь метку не передавать никогда.
3. **Две формы с разными правилами на одно поле** — у них разные схемы, ложного пропуска нет.
4. **Модель угроз:** метку может поставить только наш код, а такой код и так может записать что
   угодно. Подделка обходит только правила значения в коде. CHECK, индексы и `checks` обойти
   нельзя.
5. **Версия в имени символа:** `Symbol.for('…validated-proof.v1')`.

## Где не согласен с Б (сверено с нашим кодом)

| Б предлагает | Почему иначе |
|---|---|
| Протокол метки — «маленький третий пакет» | Это третья зависимость. Делаем как в Standard Schema: ~10 строк типа копируются в обе библиотеки, плюс тест договорённости с каждой стороны. |
| Строковый `schemaId` у каждого поля | В пределах процесса достаточно ссылки на сам объект схемы (`proof.schema === field.schema`). Не нужно придумывать уникальные id; HMR даёт новый объект → перепроверка. |
| Заморозить значения при ставке метки | Замораживать контейнер нельзя: приложение добавляет поля (`ownerId`). Строки и числа сравниваются `Object.is` без заморозки. Массивы (multiselect) и объекты — либо заморозить только их, либо сравнивать по содержимому. Открытый вопрос. |
| Новый `createFormHandler(form, extra)` и `create()` → `WriteResult` | Ломает наш API без нужды. У нас есть `execute` + `ctx.fail(errors)` (`src/lib/form/server.ts:346`), а `lib/db` бросает `DbError`. Достаточно, чтобы `DbError` нёс ошибки по всем полям. |
| Читаемые имена ограничений (`posts_slug_key`) | У нас имена с хэшем (`…_ux_<hash>`) нужны синхронизации схемы. Поле находим по описанию объектов из `defineSchema` — там известны колонки. |
| «В демо ревалидация видна в трассе» | Не проверить: демо нам недоступно. |

## Что нужно в коде при любом исходе

- `lib/db`: собирать ошибки по **всем** полям, а не останавливаться на первом (`validateField`).
- `lib/db`: 23505 и 23514 → ошибка конкретного поля (сейчас `errors.ts:62` даёт общую ошибку).
- Пользовательский текст для «уже занято» — согласовать.

## Решения (выбраны по поручению владельца)

1. **Вариант 3 + `checks` в модели.** Это единственный вариант, где БД защищена всегда, а
   правило проверяется один раз.
2. **Метка ссылается на объект схемы** (`proof.schema === field.schema`), строковых id нет.
3. **Массивы в метке сравниваются по содержимому:** поэлементно, если элементы — строки, числа или
   булевы. Для любых других объектов пропуска нет, БД проверяет поле заново. Ничего не
   замораживаем, чтобы не ломать код приложения.
4. **Ошибка уникальности:** код `unique`, текст по умолчанию «Это значение уже занято».
   Поле или форма может задать свой текст через существующий механизм `messages`.
   Для форм входа и сброса пароля общий текст выбирает приложение (совет OWASP).

## Порядок работ

1. ✅ (ход 65) `lib/db`: ошибки по всем полям с кодом и параметрами; 23505/23514/23502 → поле;
   свои тексты `messages` у поля; `failureIssues` → `ctx.fail(issues)` в `lib/form`.
2. `lib/db`: `checks` в модели (при записи, в транзакции) и `validator(db, op)` для форм без записи.
3. Метка проверки в обеих библиотеках (копия типа + тест договорённости с каждой стороны).
4. Поля `lib/form` отдают ограничения через Standard JSON Schema → `lib/db` строит из них тип и CHECK.
5. Демо: форма постов и модель из одного описания поля (убирает расхождение `max 120`).
