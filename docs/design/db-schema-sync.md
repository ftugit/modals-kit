# План: схема БД разворачивается сама (Vercel), конфликт решает человек через UI

**Статус: ПРЕДЛОЖЕНИЕ** (ход 50). Код не писался. Реализация — после ответов на «Решения».

## Что хочет владелец (ход 50)

- На Vercel достаточно указать в env адрес БД (`DATABASE_URL`). Всё остальное — само, в фоне.
- Схема таблиц описана в коде (модели), а не отдельной ручной установкой.
- Если изменение нельзя применить безопасно (конфликт), приложение само показывает
  UI-компонент: «нужен перенос данных» и кнопку/выбор.

## Как это решают другие

| Система | Как | Что берём |
|---|---|---|
| WordPress | В коде зашит номер версии схемы (`$wp_db_version`), в БД — применённый (`wp_options.db_version`). Не совпали — экран «Database Update Required» с кнопкой ([SO](https://stackoverflow.com/questions/17308436/wordpress-error-database-update-required)). Автоматическое обновление выполняет то же само, без кнопки ([r/Wordpress](https://www.reddit.com/r/Wordpress/comments/1hkzx8d/why_is_database_update_required_exposed_to_the/)) | версия в коде против версии в БД; экран с кнопкой — только когда само нельзя |
| Drizzle `push` | Читает схему из кода, читает схему БД, строит разницу, применяет ([docs](https://orm.drizzle.team/docs/drizzle-kit-push)) | сравнение «модель ↔ БД» |
| Payload (поверх Drizzle) | `push` — только в разработке; в production — файлы миграций, есть режим `prodMigrations` — запуск миграций при старте сервера, а не при сборке ([гайд](https://www.buildwithmatija.com/blog/payload-postgres-drizzle-adapter-config-queries-migrations)). Известный провал: `push` на боевой базе попытался `ALTER` типа колонки text→jsonb и упал ([разбор](https://hackernoon.com/fixing-payload-cms-jsonb-errors-in-production-postgres)) | автоматически — только безопасное; опасное — явно |

Вывод: «всё само» безопасно только для **добавляющих** изменений. Удаление, переименование,
смена типа, `NOT NULL` на существующих данных — это и есть «конфликт» владельца: их делает
человек одним нажатием, понимая, что произойдёт.

## Как будет работать

### 1. Модель = ресурс + SQL-подробности

`defineResource` уже знает таблицу, поля, вид поля (`uuid`, `text`, `timestamp`, …), первичный
ключ и сортировку (→ индекс keyset). Добавляется необязательное описание того, чего не хватает
для DDL: `NOT NULL`/значение по умолчанию, `CHECK`, ссылки (`references`), уникальность,
дополнительные индексы. Соответствие видов типам PostgreSQL одно на библиотеку
(`timestamp` → `timestamptz`, `json` → `jsonb`, `decimal` → `numeric`, …).

Демо-строка `MIGRATION` в `src/lib/server/db.ts` исчезает: таблица `demo_post` описана ресурсом.

### 2. Сверка при открытии БД (уже ленивом)

`lazyDriver` открывает БД при первом запросе. В этот момент, один раз на экземпляр:

1. Взять блокировку `pg_advisory_xact_lock(<ключ приложения>)` — на Vercel экземпляров много,
   применять изменения должен один, остальные ждут и видят результат.
2. Прочитать фактическую схему (`pg_catalog`) и служебную таблицу `kit_schema` (что и когда
   применено, отпечаток моделей).
3. Отпечаток моделей не изменился — ничего не делать (обычный случай, один запрос).
4. Иначе построить разницу и разделить её:
   - **само** (в одной транзакции, DDL в PostgreSQL транзакционный): новая таблица, новая
     колонка с `NULL` или значением по умолчанию, новый индекс, новый `CHECK` без проверки
     старых строк (`NOT VALID`);
   - **конфликт** (не применять): удалить или переименовать колонку/таблицу, сменить тип,
     `NOT NULL` без значения по умолчанию, уникальность на данных, где есть дубли.
5. Записать в `kit_schema` применённое и найденные конфликты.

### 3. Пока есть конфликт

- Ресурсы, которых конфликт касается, отвечают отказом `schema_pending` (HTTP 503) с понятным
  текстом. Остальные работают.
- UI-компонент «Нужен перенос данных» (в `components/`, не в lib): что изменилось в моделях,
  что будет сделано с данными, кнопка «Выполнить». Для неоднозначного — выбор, как в Drizzle:
  «колонка `name` пропала, `title` появилась: это переименование или удаление + новая?».
- Кнопка → серверное действие → тот же код сверки, но с разрешением применить конфликтные
  шаги; под той же блокировкой, в транзакции. Перенос большого объёма — порциями с
  продолжением (см. ограничения Vercel ниже).
- Для того, что разницей не выразить (разделить поле на два, пересчитать данные), — шаг
  переноса данных в коде с номером версии; он показывается в том же компоненте.

## Ограничения Vercel, которые это учитывает

- **Время функции.** С Fluid compute: Hobby — до 300 с, Pro/Enterprise — до 800 с, 30 минут в
  бете ([Vercel KB](https://vercel.com/kb/guide/what-can-i-do-about-vercel-serverless-functions-timing-out)).
  Сверка — миллисекунды; долгий перенос данных — порциями, каждая в своём запросе.
- **Много экземпляров одновременно** — блокировка (п. 2.1); второй экземпляр после ожидания
  видит новый отпечаток и ничего не делает.
- **Preview-деплои.** Если у preview тот же `DATABASE_URL`, что у production, ветка с новой
  моделью изменила бы боевую базу. Решение 3.
- **Права роли БД.** Для `CREATE`/`ALTER` у роли из `DATABASE_URL` должны быть права на схему.
  Нет прав — отказ с понятным текстом в том же компоненте, а не 500.

## Решения (нужны до начала)

1. **Кто может нажать «Выполнить»** до появления авторизации: (а) секрет из env
   (`DB_ADMIN_TOKEN`), после авторизации — роль администратора; (б) любой (как WordPress —
   шаги заданы кодом, ввода нет); (в) другое.
2. **Что видит обычный посетитель** во время конфликта: (а) затронутые страницы — сообщение
   «идёт обслуживание», остальное работает (предлагаю); (б) весь сайт — экран обслуживания.
3. **Preview-деплои:** (а) применять изменения схемы только при `VERCEL_ENV=production`,
   preview с той же базой — только чтение; (б) у preview своя база (env со scope Preview);
   (в) не различать.
4. **Отказ от `applyMigrationText`-строк в приложении:** демо-таблица описывается ресурсом
   (предлагаю) или ручные SQL-миграции остаются рядом как второй путь.
