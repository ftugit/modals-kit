## B. Перехват полей (lib/form) — дизайн закрыт

- Объявление: функция у конкретного поля при привязке (клиент):
  `bind(forms, desc, { takeovers: { avatar: (f) => … } })`. Сервер
  импортирует только описание формы; поля и перехваты рождаются у
  клиента. Умолчание проекта при повторе — `forms.config`.
- Ручка — сам `FieldView`: значение и ошибки уже есть
  (`f.value`/`f.onInput`/`f.errors`). lib/form добавляет ровно два
  писателя: `setError` (ошибка операции поля: `origin: 'external'`,
  живёт по pins — видна до смены значения, собственная проверка
  сильнее, блокирует клиентскую отправку; сервер не воспроизводит)
  и удержание отправки, пока перехватчик готовит значение.
- Замена видимого компонента — возвратом фабрики
  `{ view, base, dispose? }`: база сверяется с примитивом, который
  resolve дал этому полю (обобщение существующего `Field instead`:
  там база захардкожена на Input, реестр — руками в Field.svelte;
  здесь база приходит в возврате явно). Несовпадение — прежний
  компонент + dev-предупреждение. Ошибки при замене остаются на
  месте: их рисует `FieldShell` вокруг любого компонента поля.
- Правда отправки — DOM (bind строит FormData из элемента формы при
  отправке, оценке, проверках и pins). Запись значения
  перехватчиком — пара: значение в именованный носитель из
  `f.attrs` (для файла — DataTransfer в carrier) + `f.onInput(...)`.
  Внутренние инпуты перехватчика имени не имеют и существуют только
  после оживления; до оживления — штатный компонент поля (noJS
  честный). Blob от lib: `new File([blob], 'avatar.jpg', {type})`.
- Гард: `setError` вне кита полей и перехватчиков запрещён.
- Потребитель №1 — фото (бывший R2): staging без имени → lib/image
  готовит JPEG → File в carrier + onInput; ошибка подготовки —
  setError; валидация содержимого — check из R1.

## A. Шаги — целевая картина (замысел владельца)

Один хост `useSteps` на экран; ВСЕ шаги экрана объявлены заранее
одним списком. Поверх хоста — аддон `formSteps` для шагов, являющихся
срезами ОДНОЙ формы: сначала проверяются видимые поля (subset
экшена шага), когда все поля проверены — форма уходит на сервер;
сервер вернул ошибки — нарезка отключается и работают все поля
(чистые шаги в свёрнутом виде — ради длинных форм). Остальные шаги
того же хоста — обычные: отдельный компонент со своей формой или
чистый UI без формы. Переключение — ссылкой, кнопкой (submit шага)
и событием (результат экшена, функция).

Авторизация по этой картине — один хост; шаги объявлены одним
списком, срезы формы — тем же списком через точку (схема имён
владельца): `auth.entry`, `auth.register`, `auth.deleted`
(восстановление; имён может быть больше — это куст формы
авторизации), дальше обычным списком: блокировка аккаунта,
блокировка действий, редактирование профиля. Адрес несёт полный
ключ: `?stage=auth.deleted`. Переключает и отображает всё
оригинальный хост по полному ключу; аддон внутри экрана `auth`
читает свой срез из суффикса ключа. Так будущие аддоны получают
готовую схему имён, а не пишутся заново. Профиль — отдельный
компонент со своей формой (nickname + photo, свой обработчик —
серверная часть R3); блокировки — UI-шаги без формы («Принято» —
программная отправка конверта auth, механизм `authEnvelope*` есть).
«Пропустить профиль» перестаёт быть отправкой — смена шага/закрытие.
Без JS шаг после POST определяет сервер (load по сессии); deep-link
на шаг профиля без сессии сворачивается на авторизацию.

Как восстановление работает сейчас (сверено, для раскладки срезов):
логин по seed+подписи проходит даже при заявке на удаление,
сервер выдаёт сессию и отвечает шагом `restore`; на этом шаге seed
не рисуется и в отправку не едет — отмена удаления идёт по сессии
(кука), не по seed. Порядок шагов после логина захардкожен в роуте:
blocked → restore → restrictions → profile → done.

**Пункт 3 (владелец): срез `auth.deleted` — обход политики по
доказательству владения; нынешний серверный сценарий политике
противоречит и переписывается.** Сейчас `findBySeed` ходит с
`includeDeleted: true`: обычный логин находит удалённый аккаунт,
выдаёт ему сессию (права заморожены guard-ом, кроме `cancelDelete`
с `allowPending`) — то есть удалённый аккаунт технически
авторизован. Должно быть наоборот: обычный поиск идёт по политике
(`deleted_at IS NULL`) и удалённого не видит; попытка создать
аккаунт с тем же seed упирается в уникальность — по этому
конфликту приложение понимает, что аккаунт удалён, и показывает
`auth.deleted` БЕЗ сессии: авторизации ещё нет и быть не должно.
Срок удаления приложение НЕ проверяет и не может: без прав
удалённую запись читать нельзя. Принимается на веру: seed ещё на
месте — значит, время на восстановление есть; по истечении срока
seed и прочие данные аккаунта стираются окончательно, и тот же
seed снова становится обычной регистрацией. Механизма стирания в
коде пока нет (`deleteGraceDays` используется только для срока в
ответе при заявке) — предположение: будущий крон или аналог, вне
этого чеклиста; восстановимость ≡ seed ещё существует. Поэтому seed и
является полем среза: срез держит его в DOM на фоне (для этого
аддон и не вырезает поля срезов), и подтверждение восстановления —
отправка среза, где сервер проверяет владение (подпись свежего
nonce по seed) специальным select без учёта `deleted_at`, снимает
метку — и только после этого выдаёт сессию и ведёт дальше обычным
порядком. Следствия: `login()` токены при удалённом аккаунте не
выдаёт; путь «cancelDelete по сессии» умирает (операция остаётся,
вызывается после доказательства); у среза `auth.deleted` поля есть
(seed фоновно + nonce/signature) и свой subset.

Чего не хватает до этой картины — простыми словами:

1. Сервер не умеет переключать шаг. После отправки сервер говорит
   «покажи этот шаг», а услышать некому: виджет и демо руками
   достают шаг из ответа и тычут в хост. Нужен канал: ответ формы
   пришёл — хост сам переключил шаг (место — аддон для своих
   срезов и set() хоста для остальных).
2. Аддон жадный: считает все шаги хоста своими и рисует каждый
   внутри своей формы — чужие шаги рядом жить не могут. Схема с
   точкой это чинит: аддон ведает только своим кустом (`auth.*`),
   остальное не трогает.
3. Объявленный служебный шаг получает адрес (?stage=blocked), а
   ссылка на блокировку не нужна. С точками адрес срезов осмыслен
   (`?stage=auth.deleted`); для блокировок — решить флагом
   «без адреса» в объявлении шага, если адрес будет мешать.
Плюс мелочь: `filled` (шаг-ссылка или текст) потребитель считает
руками; для срезов аддона заполненность выводима из формы.

Модели скрытых значений при этом две и обе законны, каждая в своём
месте: срезы одной формы (аддон) держат поля в DOM — значения едут
в каждый POST, ради этого и существует отключение нарезки при
ошибках; обычные шаги-экраны живут своей разметкой и своими
формами. Смешивать модели внутри одной формы нельзя.

1. lib/form: перехват в bind (setError, hold, возврат view+base) —
   контракт-тесты жизненного цикла ошибки (установка → показ →

2. Шаги: канал события → шаг; демо /steps переведено на хост +
   нарезку + subset; паразит удалён; README шагов переписан под
   одну систему.
3. Декомпозиция AuthWidget; форма профиля с фото-перехватом;
   эмуляции авторизации (54 теста) переживают декомпозицию.

Документация: README lib/form (перехват), README шагов, ревизия
объёма R2/R3 в `image-transfer.md`. Вес: перехватчики — ленивые
чанки владельцев полей (как `photo.ts` в R1), ядро bind не раздувать.
