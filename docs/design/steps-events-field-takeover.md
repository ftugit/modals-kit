## B. Перехват поля (lib/form + кит полей) — контракт утверждён владельцем, реализация предстоит

- Объявление — callback `takeover` у UI-компонента `Field`, у
  конкретного поля: поле уже выбрано в разметке
  (`of={bound.f.avatar}`), callback ставится там же и получает это
  поле как `f`. НЕ карта функций в bind, НЕ реестр, НЕ функция в
  описании формы (описание импортирует сервер — оно остаётся
  данными). Callback зовётся один раз при оживлении на клиенте; до
  оживления и без JS поле штатное (для фото — нативный carrier),
  сервер перехвата не видит.
- Ручка — само поле `f`, живое. Существующее: `f.value`,
  `f.onInput`, `f.errors` (ошибки поля сейчас), `f.attrs`
  (именованный носитель). Новых функций НЕТ (ни
  getValue/setValue/getError, ни setError). Добавляются ровно два
  записываемых свойства:
  - `f.error = { code, params? }` — ошибка операции поля
    (`origin: 'external'`, pins: видна до смены значения,
    собственная проверка поля сильнее, блокирует клиентскую
    отправку; сервер не воспроизводит и не обязан);
    `f.error = undefined` — снять.
  - `f.pending = promise` — пока задан, отправка ждёт его
    завершения и перечитывает DOM (правда отправки — FormData из
    элемента формы).
- Замена видимого компонента — возвратом callback-а
  `{ view, base, dispose? }` (или ничего). Base сверяется с
  примитивом, который resolve дал этому полю; несовпадение —
  прежний компонент + dev-предупреждение. `instead` в разметке
  сильнее. Ошибки рисует FieldShell вокруг любого компонента — при
  замене остаются на месте. Тот же живой `f` получает заменяющий
  компонент пропом. dispose — при размонтировании.
- Запись значения — пара: значение в носитель из `f.attrs` (файл —
  `new File(...)` через DataTransfer в carrier) + `f.onInput(...)`.
  Внутренние инпуты перехвата имени не имеют (staging) и существуют
  только после оживления; на сервер уезжает только значение
  оригинала.
- Гард: присваивания `f.error`/`f.pending` разрешены только в
  takeover и в ките полей; виджетам запрещены.
- Потребитель №1 — фото (B+R2), подключается с формой профиля:
  staging без имени → lib/image готовит JPEG → File в carrier +
  onInput; ошибка подготовки — `f.error`; проверка содержимого —
  check из R1.
- Первая попытка (объявление в bind: `903c40b` + `438681c` +
  `7577ba5`) владельцем отклонена по форме и откачена до конца
  пункта 3 (`e9ce427`). Механика сохранена за пределами отката:
  ветка `archive/bind-takeovers`, патч `~/takeover-archive/`.
  Оттуда брать ядро pins-ошибки и сверку базы; bind-форму
  объявления не воскрешать.

## A. Шаги — целевая картина (замысел владельца)

Один хост `useSteps` на экран — корень; его шаги объявлены
заранее одним списком, у шага свой ключ. Steps в steps напрямую
не вкладывается: продолжить цепочку ключей внутри шага может
только АДДОН на этом шаге — он держит свои ключи следующего
уровня и читает свой сегмент из полного ключа (`auth.restore`:
`auth` — шаг, `restore` — ключ аддона; переключает по полному
ключу по-прежнему хост). Аддонов два рода:

- **formSteps** — срезы ОДНОЙ формы (лист цепочки: внутри среза
  поля, не шаги). Сначала проверяются видимые поля (subset
  экшена шага), когда все поля проверены — форма уходит на
  сервер. При реворке сохранить текущий «разбор»
  (`isReview`/`viewOf`): сервер вернул ошибки — нарезка
  отключается (все поля и полные валидаторы), шаги с ошибками
  открыты, чистые свёрнуты и места не занимают, пока юзер сам не
  раскроет. formSteps работает и БЕЗ хоста шагов — страница, где
  кроме формы делить нечего: тогда ключи — просто ключи срезов,
  без чужого префикса.
- **Аддон вложенных шагов** (новый; имя — при реализации) — даёт
  шагу свои подшаги («вариант 1», «вариант 2», …). На подшаге
  может сидеть следующий аддон любого рода — глубина цепочки
  схемой не ограничена.

Остальные шаги того же хоста — обычные: отдельный компонент со
своей формой или чистый UI без формы. Переключение — ссылкой,
кнопкой (submit шага) и событием (результат экшена, функция).

Авторизация по этой картине — один хост; у шага хоста свой ключ
(`auth`; дальше обычным списком: блокировка аккаунта, блокировка
действий, редактирование профиля). formSteps на шаге `auth`
держит свои ключи срезов формы (`entry`, `register`, `restore` —
восстановление удалённого аккаунта; имён может быть больше — это
куст формы авторизации); адрес экрана восстановления — цепочка
`?stage=auth.restore`. Профиль — отдельный
компонент со своей формой (nickname + photo, свой обработчик —
серверная часть R3); блокировки — UI-шаги без формы («Принято» —
программная отправка конверта auth, механизм `authEnvelope*` есть).
«Пропустить профиль» перестаёт быть отправкой — смена шага/закрытие.
Без JS шаг после POST определяет сервер (load по сессии); deep-link
на шаг профиля без сессии сворачивается на авторизацию.

Как восстановление работает (после пункта 3): логин удалённого
аккаунта не находит (политика), создание упирается в unique —
сервер отвечает фактом `auth.deleted` и шагом `restore` БЕЗ
сессии; seed живёт скрытым полем шага (значение с шага входа),
подтверждение проверяет подпись до привилегированного поиска
удалённой строки, снимает метку (`restore` модели) и только
тогда выдаёт сессию. Порядок шагов после входа в роуте:
blocked → restrictions → profile → done.

**Пункт 3 (владелец): срез `restore` — обход политики по
доказательству владения. СДЕЛАНО (`933f02f`).** Было наоборот:
`findBySeed` ходил с `includeDeleted: true`, обычный логин
находил удалённый аккаунт и
выдавал ему сессию (права заморожены guard-ом, кроме `cancelDelete`
с `allowPending`) — то есть удалённый аккаунт был технически
авторизован. Теперь: обычный поиск идёт по политике
(`deleted_at IS NULL`) и удалённого не видит; попытка создать
аккаунт с тем же seed упирается в уникальность — по этому
конфликту приложение понимает, что аккаунт удалён, и показывает
шаг восстановления (`restore`) БЕЗ сессии: авторизации ещё нет и
быть не должно.
Срок удаления приложение НЕ проверяет и не может: без прав
удалённую запись читать нельзя. Принимается на веру: seed ещё на
месте — значит, время на восстановление есть; по истечении срока
seed и прочие данные аккаунта стираются окончательно, и тот же
seed снова становится обычной регистрацией. Исполнитель стирания
в домене есть (`sweepDeletions`, seed зануляется по
`deleteGraceDays`) — нет только вызывающего планировщика в
приложении (будущий крон, вне этого чеклиста); восстановимость ≡
seed ещё существует. Поэтому seed и является полем среза: шаг
держит его в DOM на фоне, и подтверждение восстановления —
отправка шага, где сервер проверяет владение (подпись свежего
nonce по seed) специальным select без учёта `deleted_at`, снимает
метку — и только после этого выдаёт сессию и ведёт дальше обычным
порядком. Сделано: `login()` токены при удалённом аккаунте не
выдаёт (факт `auth.deleted`); путь «cancelDelete по сессии»
удалён вместе с исключением guard `allowPending`; восстановление
— `restoreDeleted` (доказательство → привилегированный поиск →
`restore` модели). У среза поля есть (seed фоновно +
nonce/signature); subset экшена среза — со схемой шагов.

**Где проверка (безопасность пункта 3).** ACL анонима к удалённой
записи не пропускает и не должен: у запроса нет принципала на эту
строку, через data API она ему невидима. Дверей две и они разные:
по роли (админ и сервер видят удалённое — `readDeleted:
['server','admin']`) и по доказательству владения (восстановление).
Вторая — не дыра в ACL, а доменная операция сервера; этапы строго
по порядку:

1. Обнаружение — конфликт уникальности seed: факт БД, а не чтение.
   Наружу не отдаётся ничего из удалённой строки (ни ника, ни дат) —
   только предложение восстановить.
2. Доказательство — ДО первого касания удалённой строки:
   одноразовый nonce потреблён, подпись проверена по
   предъявленному seed; чистая криптография, как в `login`
   (подпись и сегодня проверяется до `findBySeed`). Не сошлась —
   обычная ошибка входа, без оракулов; строка даже не читалась.
   noJS: доказательство — знание самого seed, как у noJS-логина
   сегодня (слабее, но та же действующая политика).
3. Только после доказательства серверный принципал (роли
   `server`,`admin` — те, кому `readDeleted` разрешён политикой)
   одной именованной доменной операцией читает удалённую строку
   по доказанному seed и снимает метку. `includeDeleted` живёт
   только внутри этой операции, не в обычном поиске.
4. Дальше — обычный логин обычной политикой: строка снова видима,
   блокировки, сессия, порядок шагов.

Почему не восстанавливать сразу при обнаружении (подпись
попытки входа уже проверена): восстановление — действие с
последствиями; нужно явное согласие отдельным подтверждением и
свежий nonce против повторов. Сюда же: троттлинг попыток по seed
(как у логина) и запись восстановления в аудит/историю сессий.
Схема к стиранию уже готова: seed обновляют только роли
server/admin («стирает исполнитель удаления»), unique допускает
много NULL — будущий исполнитель зануляет seed, и тот же seed
снова обычная регистрация; самого исполнителя пока нет.

**Специальной функции в модель писать не надо, прямой вызов не
страшен.** lib/db уже умеет всё общими средствами и сама стережёт
границу: обычный select добавляет `deleted_at IS NULL` сам;
`includeDeleted` модель разрешает только принципалу с грантом
`readDeleted` (`resource.ts:232` — иначе `forbidden`, проверяет
модель, а не вызывающий); есть готовая операция `restore(ctx,id)`
со своей политикой (по умолчанию — как у delete). Пишется обычная
доменная функция в `content/user` рядом с `login()` — компонует
примитивы: доказательство → привилегированный поиск → `restore`.
Злоумышленник может дёрнуть маршрут подтверждения напрямую,
минуя экран, — и это ничего не даёт: проверка подписи живёт
ВНУТРИ доменной функции (как в `login`, где подпись проверяется
до поиска аккаунта), этапы экрана — UX, а не граница. Прямой
POST без подписи на свежем одноразовом nonce получает тот же
отказ, что прямой POST на логин. Принципал из запроса не
подделать: `DataContext` чеканит только серверный код — guard
из проверенного токена или константа SYSTEM в gateway; роли из
тела/строки запроса не берутся, а `includeDeleted` из query
модель всё равно сверяет с грантом принципала. Привилегия здесь
не «знать маршрут», а владеть ключом seed — как пароль у логина.

**Маршрут удалённой учётки.** От select никто не отказывается —
отказ только от `includeDeleted` в обычном пути. Логин и сегодня
не data-API select принципалом пользователя (принципала до
логина нет), а доменная функция `login()`, внутри которой те же
select/insert модели под SYSTEM. Раскладка по шагам:

1. POST входа: форма валидирует только форматы полей (про
   удалённость не знает) → `login()`: подпись сошлась, обычный
   `findBySeed` удалённую строку НЕ видит, `create` упирается в
   уникальность (`DbFailure`, kind `conflict`) → факт `auth.deleted`,
   сессии нет → роут отвечает шагом `restore`.
2. Срез `restore` — именно для этого: поле seed с
   шага входа остаётся в DOM на фоне и без повторного ввода едет
   в следующую отправку; nonce форма обновляет после каждой
   отправки (механизм есть), подпись ставит transport.
3. POST подтверждения (экшен среза, subset: seed+nonce+signature)
   → `restoreDeleted()`: подпись → привилегированный поиск
   удалённой → `restore(ctx,id)` → обычный хвост логина (сессия,
   порядок шагов). Гонка со стиранием: удалённой строки уже нет,
   но доказательство валидно — обычный путь «найти или создать»,
   seed снова свободен.

Чего не хватает до этой картины — простыми словами:

1. Сервер не умеет переключать шаг. После отправки сервер говорит
   «покажи этот шаг», а услышать некому: виджет и демо руками
   достают шаг из ответа и тычут в хост. Нужен канал: ответ формы
   пришёл — хост сам переключил шаг (место — аддон для своих
   срезов и set() хоста для остальных).
2. Аддон жадный: считает все шаги хоста своими и рисует каждый
   внутри своей формы — чужие шаги рядом жить не могут. Схема с
   точкой это чинит: аддон ведает только своим кустом (`auth.*`),
   остальное не трогает.
3. Объявленный служебный шаг получает адрес (?stage=blocked), а
   ссылка на блокировку не нужна. С точками адрес срезов осмыслен
   (`?stage=auth.restore`); для блокировок — решить флагом
   «без адреса» в объявлении шага, если адрес будет мешать.
Плюс мелочь: `filled` (шаг-ссылка или текст) потребитель считает
руками; для срезов аддона заполненность выводима из формы.

Модели скрытых значений при этом две и обе законны, каждая в своём
месте: срезы одной формы (аддон) держат поля в DOM — значения едут
в каждый POST, ради этого и существует отключение нарезки при
ошибках; обычные шаги-экраны живут своей разметкой и своими
формами. Смешивать модели внутри одной формы нельзя.

  общей опцией хоста для шагов вне форм?
