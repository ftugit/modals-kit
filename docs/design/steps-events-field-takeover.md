# Шаги по событиям и перехват полей — чеклист модернизации

Записано 2026-10-21 по поручению владельца (после R1 и чистки AuthWidget,
коммиты `b49fa0a`/`4f99518`/`5632c01`). Документ — план и раскачка двух
идей владельца; код — после ответов на открытые вопросы в конце.
Пересечение с `image-transfer.md`: пункты A5/B4 переписывают объём R2
(фото-полем владеет перехватчик; профиль — отдельная форма), R3/R4
привязываются к обработчику формы профиля. R1 (spec/checks) не меняется.

## Исходные идеи владельца (дословно по смыслу)

A. **Step по событиям.** Шаг не обязан быть продолжением формы: шаг —
отдельный view, который показывается при событии (выбор пункта, нажатие
кнопки, после валидации, функция внутри формы). Шаги объявляются
заранее — в т. ч. служебные (блокировка и т. п.), которые выполнит не
пользователь, а события/функции. Обычный step (хост) и step формы
работают вместе: шаг может быть отдельным компонентом со СВОЕЙ формой
(показ компонента вместо переадресации). Целевая декомпозиция
авторизации: регистрация/вход/восстановление — одна форма; ник+аватар —
другой компонент со своей формой (после успешной авторизации при
условиях показываем шаг профиля); блокировка — просто UI, заменяющий
содержимое (без формы).

B. **Перехват полей.** К lib/form добавить функции перехвата при
объявлении формы: после оживления они забирают отдельные поля себе —
могут менять UI-компонент, читать/писать ошибки, записывать значения в
оригинальное поле. Callback получает ручки полей (`{nickname, avatar}`),
каждая — объект вида setError/getError/setValue/getValue/setUi/getUi.
Наш случай: забрать поле, создать внутри скрытое поле, обработать
фото, записать в обычное поле; в UI вместо поля видно созданное
перехватчиком; на сервер уходит только оригинальное поле, внутренности
callback на клиенте и остаются. Ошибка lib/image отображается полем
перехватчика. Видимые замены полей — только от field (кит полей), чтобы
ошибки отображались одинаково.

## Факты, сверенные с кодом

- Хост шагов форм не знает (контракт `components/steps`); шаг —
  `{key, label, filled}`, `filled` = ссылка. Необъявленный ключ через
  `set()` — служебное состояние без адреса (документировано, пример в
  README — как раз `blocked`).
- Канала «Result → шаг» нет ни в хосте, ни в `formSteps`: склейку пишут
  руками AuthWidget (`stepOf` + эффект) и демо `/steps` (`stepOfResult`).
- `FieldView`: писатели — только `onInput` и `setTouched`; поставить
  ошибку или удержать отправку извне нельзя. `FormError.origin` уже
  имеет `'external'`, и `pins.ts` живёт с такими как с серверными
  (видна, пока значение не сменилось; своя проверка сильнее).
- `bind` уже имеет опцию `intercept` — но это перехват ОТПРАВКИ. Имя
  для перехвата полей нужно другое.
- Подмена компонента поля уже есть: `resolve` по виду ввода +
  `Field instead=` (CopyField, только Input-база). Запись значения
  снаружи — `mirrorToField` (костыль виджета, не механизм lib).

## Раскачка: где идеи надо уточнить, чтобы не сломать систему

### A. Шаги по событиям

- A1. Модернизировать не хост, а склейку `formSteps`: научить следовать
  за результатом привязки (`settled + data.step → host.set`). Хост при
  этом остаётся агностиком форм. Это закрывает «сервер меняет шаг»
  без навигации и убивает ручную склейку в виджете и демо.
- A2. «Объявить заранее все шаги» vs служебные вне списка: объявленный
  шаг получает item и (в hybrid) адрес. Блокировке адрес `?stage=blocked`
  не нужен и вреден (deep-link без сессии). Варианты: оставить
  служебные вне списка (как сейчас) или добавить в `StepDef` флаги
  «не ссылка / без адреса» и объявлять всё. **Открытый вопрос Q3.**
- A3. Кто объявляет событийный переход: сервер кладёт `step` в
  `Result.data` (как сейчас — сервер знает состояние аккаунта), или
  виджет объявляет карту «событие → шаг» и сервер шлёт только факты
  (флаги вида `needsProfile`)? От этого зависит, где живёт машина
  состояний авторизации. **Открытый вопрос Q4.**
- A4. Шаг-компонент со своей формой: две привязки на экране законны
  (конверты и instance независимы), но договориться: форма шага
  монтируется при показе (состояние рождается заново) или живёт всегда
  (значения переживают уход с шага)? Для профиля после логина —
  монтирование при показе; зафиксировать как канон таких шагов.
- A5. Декомпозиция авторизации (целевая): хост + экраны; форма входа
  (entry/register/restore — один `authForm` без полей профиля); форма
  профиля (свой `defineForm`: nickname + photo; свой обработчик);
  blocked/restrictions — UI-шаги. Следствия: интенты profile/skip-
  profile уходят из auth-обработчика (это и есть серверная часть R3,
  но на отдельном обработчике); «пропустить профиль» перестаёт быть
  отправкой — просто смена шага/закрытие; restrictions «Принято» —
  программная отправка конверта auth (механизм `authEnvelope*` уже
  есть) или мини-действие без формы на экране.
- A6. Без JS: шаг после POST по-прежнему определяет сервер (load по
  сессии + результат); каждая форма-шаг — свой нативный POST; deep-link
  на шаг профиля без сессии load обязан сворачивать на entry.

### B. Перехват полей

- B0. Имя не `intercept` (занято отправкой). Рабочие варианты:
  `takeover`, `controllers`, `hosts`. Выбрать при реализации, в доке —
  «перехватчик».
- B1. Гранулярность РЕШЕНА владельцем: перехват объявляется у
  КОНКРЕТНОГО ПОЛЯ, не у формы в целом (групповой колбэк отклонён,
  см. B5). Открыто лишь, в какой форме живёт объявление у поля:
  `defineForm` изоморфен (его импортирует сервер), UI-компонентов и
  клиентских импортов там быть не может. Кандидаты:
  (а) ИМЯ в описании поля (`field.photo({ takeover: 'photo' })`),
  фабрику по имени разрешает клиентский реестр (forms.config) — ровно
  идиома проверок (`check('photo:avatar')` + CheckRegistry): сервер
  имя игнорирует, описание остаётся данными (живы saved-спецификации
  полей); (б) ФУНКЦИЯ прямо в опциях поля — поверхность проще, но
  описание перестаёт быть серверно-чистым, как только колбэк тянет
  клиентский код, и ломается сериализация полей в спецификации.
  Рекомендация — (а). **Открытый вопрос Q1 (уточнённый).**
- B2. Не плодить второй API поверх `FieldView`: getValue/setValue —
  это `f.value`/`f.onInput` (уже есть); setUi — это `resolve`/`instead`
  (уже есть). Реально нового нужно два механизма: **setError**
  (ошибка операции поля) и **удержание отправки**, пока перехватчик
  готовит значение (фото). Всё остальное перехватчик получает как
  обычный `FieldView`.
- B3. Семантика setError: ошибка `origin: 'external'` (тип и pins уже
  готовы): видна до смены значения, собственная проверка поля сильнее,
  блокирует клиентскую отправку, сервер её не воспроизводит и не
  обязан (сервер готовит сам — R3). Право на setError — у компонента
  поля/перехватчика; виджетам гардом запретить (как ручные `name=`).
- B4. «Создать внутри скрытое поле» уточняется вчерашним правилом:
  носитель в FormData — ОРИГИНАЛЬНОЕ поле из описания (carrier);
  внутренние инпуты перехватчика имени не имеют (staging) и
  существуют только после оживления. Это ровно дизайн PhotoField из
  R2; перехват — его обобщение: вид `photo` получает перехватчика
  вместо особого компонента.
- B5. Групповой колбэк `{nickname, avatar}` ОТКЛОНЁН решением по B1:
  перехват — по одному полю. Совместная логика полей, если появится, —
  дело компонента-шага над формой, а не перехвата. Ручка перехватчика —
  не новый объект с дублями имён, а расширенный `FieldView`:
  getValue/setValue = `f.value`/`f.onInput` и getError = `f.errors`
  уже есть; добавляются setError (`f.report`) и удержание отправки.
  setUi = возврат компонента кита полей из фабрики (getUi — текущий
  по resolve, чтобы оборачивать, а не заменять вслепую). Жизненный
  цикл: фабрика зовётся при привязке на клиенте по одному разу на
  поле, `dispose` — при смерти привязки; на сервере фабрика не зовётся.
- B6. До оживления поле рисуется штатно по описанию (для photo —
  нативный carrier), перехват включается после гидратации; сервер
  перехват не видит: проверки и значения те же на обеих сторонах.

## Дополнено мной (по канонам проекта и владельца)

- Порядок работ: A1 (formSteps следует за Result — маленькая, чистит
  демо и виджет сразу) → B-ядро (setError + точка перехвата в bind) →
  A5 (декомпозиция авторизации; форма профиля) → фото перехватчиком
  (= R2 в новой форме) → сервер профиля (= R3 на отдельном
  обработчике) → R4 очередь на execute формы профиля.
- Гард: setError/report вне кита полей и зарегистрированных
  перехватчиков запретить (source-правило, как `name=`); перехватчик
  не имеет права на сырые теги и именованные инпуты — носитель один.
- Тесты-гейты: formSteps follow-result (unit); жизненный цикл setError
  (установка → показ → блокировка отправки → смена значения → снятие;
  серверный паритет не затронут); эмуляции авторизации (54 теста
  content/user) переживают декомпозицию; паритет шагов JS/noJS по
  сценариям входа (blocked/restrictions/profile после логина).
- Документация: README шагов (§ «шаги по событиям», шаг-форма, шаг-UI),
  README lib/form (перехватчики и setError), правки объёма R2/R3 в
  `image-transfer.md` одной ревизией с этим документом.
- Вес: перехватчики и PhotoField-логика — ленивые чанки по владельцам
  полей (как `photo.ts` в R1), ядро bind не раздувать: setError —
  маленькая ветка состояния ошибок.
- Термины не плодить: «шаг-событие» не вводить; есть шаг (view),
  событие (источник перехода) и служебное состояние (шаг без ссылки).
