## Задача (слова владельца, свёрнуто)

- Моя lib интегрируется в папку к остальным lib проекта; всё работает
  через механизмы проекта (lib/form), без отдельных костылей.
- Поле формы работает с `input type="file"`; именно валидатор формы
  определяет тип файла по содержимому, веры в расширение нет; рамки
  проверяет через lib. Никнейм проверяет тоже валидатор формы.
- Тот же валидатор выполняется на сервере. Только после него серверный
  POST либо пропускает файл (уже подготовлен клиентом), либо пытается
  конвертировать лёгкими алгоритмами до рамок. Очередь в уточнённом
  сценарии владельца — не фоновый job и не БД: это ожидание свободного
  слота конвертации внутри того же POST («дождись или потеряй»,
  ориентир — 5 одновременных конвертаций); ошибка конвертации и
  исчерпание бюджета ожидания — код ошибки поля. Это fallback для
  no-JS: скорость и минимум ресурсов; выход — JPEG, качество можно
  убивать до пола ради веса.
- Сервер принимает именно File (в том числе уже конвертированный
  клиентом) и сохраняет результат строкой в БД; base64 — внутренняя
  сериализация серверного адаптера, а не транспорт и не код по местам.
  Предел сырого файла именно для серверного fallback — 8 MiB (решение
  владельца 2026-10-21); клиентский вес как продуктовая рамка не
  задаётся, у клиента остаются ресурсные пределы декода/времени.
- Локальное превью выбранного файла у JS-клиента может делать
  UI-примитив без lib — как Attachment у shadcn: object URL и показ
  через `<img>`. Это только отображение локально выбранного файла, не
  валидация, не преобразование и не обещание, что файл принят. Сейчас
  в работе изображения; та же граница затем расширяется на все файлы,
  поступающие через формы. Будущий `lib/storage` только забирает уже
  проверенный и подготовленный файл и хранит его — валидация и
  преобразование не его зона.
- Число клиентов неизвестно (десятки–сотни): одновременных
  конвертаций — ограниченное число слотов, остальные ждут внутри
  своего POST до общего дедлайна. Уход клиента до записи — потеря
  попытки, а не фоновая заявка. Сервер — Vercel/Cloudflare/любой.
- Клиентский бюджет 3–5 с, серверный — ≤0,5 с худший случай на старом
  Xeon (замеры — PROFILES.md в репозитории lib).

## Что уже есть в проекте (discovery, факты по коду)

**lib/form.** Ядро без фреймворка; один `evaluate()` для JS- и
no-JS-путей; описание формы изоморфно (`defineForm`, сахар `field.*`).
- Тип значения — `FieldType` (`field-types.ts`): `kind`, `inputs`,
  sync `decode(entries)→значение`, `encode`, проекции видов ограничений
  в атрибуты, `degradation`. Встроенные `file`/`files` есть
  (`builtins.ts`): decode гасит File-заглушку (`name: ''`) в `null`;
  виды: `required`, `accept` (проецируется в атрибут), `maxSize`, `opaque`.
- Синхронные валидаторы `v.*`: для файла — `v.accept(types)` (честно
  документировано: сверяется ЗАЯВЛЕННЫЙ тип, содержимое НЕ проверяется —
  это и есть дыра, которую закрываем) и `v.maxSize(bytes)`. Своё правило:
  функция + `describe(...)` с видом ограничения, либо `opaque`.
- Асинхронные проверки: `check('имя')` в описании + `CheckRegistry`
  приложения (`src/lib/components/form/extend.ts`, прецедент
  `email-taken`); на сервере выполняются всегда, в браузере — с
  дебаунсом/отменой (`ctx.signal`), кэш по значению настраивается.
- Свой тип значения — устоявшийся прецедент `rating`/`phone` в
  `extend.ts`: `declare module` (`FieldValues`, `InputModes`) →
  `registerType` → работает сахар `field.phone()`; компонент поля —
  в `components/form` (PhoneField), выбор — `resolve.ts` по `f.input`
  (+`variant`). Ядро lib/form при этом не трогается (решение хода 261).
- Серверный приём `createFormHandler` (`#lib/form/server.js`): слои
  method → origin → body → names; `bodyLayer` считает поток
  (`limits.maxBytes`, умолчание 2 MiB на ВСЁ тело; `maxFileSize` 8 MiB —
  для сырого фото поднимать per-handler через `limits`); `prepare` —
  синхронная очистка ДО правил (для конвертации НЕ годится: «внешняя
  модерация — в checks или execute»); бизнес-действие —
  `execute({values, pick, intent, request, commit, fail, after})`,
  исходы `committed|unknown|queued`, идемпотентность по `submissionId`
  (повтор не переделывает работу — ответ на «клиент не дождался»).
- `Result.values` никогда не несёт File (сериализация): после отказа
  файл выбирают заново — клиентская подготовка обязана быть дешёвой
  для повтора или жить в состоянии компонента до успеха.
- Показ: `FileField` → `FileInput` (вариант `preview`, миниатюры
  compressorjs ленивым чанком; значение поля — сам File через
  `f.onInput`). Подмена компонента страницей — `instead` (ход 261).

### Граница «файлы формы» (решение владельца 2026-10-20)

- **Локальное превью — UI-примитив, не preview-API lib.** Для файла,
  только что выбранного пользователем, допустим примитив в духе
  shadcn Attachment: `URL.createObjectURL(file)` → адрес только в
  `<img src>` → `revokeObjectURL` при замене, ошибке и разборке. В
  image-контексте SVG не выполняет скрипты и не грузит внешние
  ресурсы, а файл не покидает браузер. Жёсткие условия: blob URL не
  давать ссылкой и не вставлять в iframe/object/embed; не делать
  dataURL, canvas или перекодирование ради показа; показ не считать
  валидацией и не скрывать ошибку поля, если браузер картинку смог
  отобразить, а spec её отверг. Ресурсная оговорка: браузер вправе
  декодировать оригинал в полном размере, поэтому примитив не даёт
  пиксельного бюджета. У photo-поля после клиентской подготовки тот
  же примитив показывает подготовленный File (он уже ограничен spec и
  показывает реальный crop); отдельная миниатюра как файл или
  авторитетное превью уже сохранённого актива — задача lib/image и
  будущего контура, не UI-примитива. Без JS превью до отправки нет —
  только нативный file input.
- **Единая внешняя граница.** Снаружи для форм будет один контур
  приёма файлов: определение вида по содержимому, spec-валидаторы,
  клиентская и серверная подготовка, сигналы бюджета/очереди и
  нормализованные коды ошибок. Внутри обработчики
  разделяются по видам файлов; изображения делегируются `lib/image`.
  Имя/место общего фасада (`lib/file` или расширение текущего слоя) —
  решение перед первым не-картиночным видом; R1–R3 оно не блокирует.
- **Роли.** `lib/form` владеет транспортом, описанием, выполнением
  валидаторов и исходами handler-а; файловый контур — содержимым и
  подготовкой; UI — только показом; маршрут/домен — выбором spec и
  места сохранения; будущий `lib/storage` принимает подготовленный
  файл/Blob с метаданными и только сохраняет/отдаёт его.
- **Защита после миграции.** По образцу стражей адреса/GET:
  `layer-guard` должен ронять dev/build на обход контура в маршрутах,
  контенте и компонентах — ручные чтение байтов/sniff/base64 для
  входящих файлов формы, прямые canvas/`createImageBitmap`/кодеки/
  compressorjs и самодельная preview-механика вне UI-примитива.
  Разрешённые зоны: транспорт `lib/form`, файловый контур, `lib/image`,
  ввод/вывод `lib/storage`, object URL только в FileInput/Attachment-
  примитиве для `<img>`, тесты и фикстуры. Запрет касается файлов, поступающих
  через формы, а не любых Blob приложения (например, скачивание или
  сгенерированный экспорт). Одних regex мало: граница усиливается
  типизированным `PreparedFile`, который вправе выпускать только
  файловый контур, а storage принимает именно его.

## Выбранный подход

**Вендоринг в `src/lib/image/`** исходниками (как остальные lib:
`index.ts` точка входа, colocated `*.test.ts`, относительные импорты
с `.js` — стиль совпадает). Переносится ядро: types/errors/registry/
decode/frame/pipeline/fit/*/codecs/*/quantize/probe (+presets).
Фактически перенесён весь `src/` кроме `testing.ts` (решение владельца
по составу — целиком; суммарные size-лимиты подняты его же решением).
Серверный адаптер слушает сырые `state`-события конвейера —
`state-collector` для решения об очереди не нужен.
Фасад под дизайн-док (`open(blob).frame().quantize().encode()/fit()`) в
этапы R1–R7 не входит: интеграция форм использует внутренний
`image()`; chain-обёртка — только по отдельному запросу владельца.
Серверная часть (инициализация wasm Node/Workers, EXIF-поворот кадра,
приём-конвертация) — в серверной зоне: `src/lib/image/server.ts`
нельзя (импортнётся клиентом случайно) → `src/lib/server/image.ts`
по образцу остальных серверных модулей, либо подпапка с серверным
индексом; точку выберем по стражу на этапе 2.

**Фронтенд (через lib/form, ядро не трогаем).**
- Тип `photo` в `extend.ts` по образцу phone: `FieldType<File | null>`,
  `inputs: ['photo']`, decode как у file (заглушка → null), constraints:
  required/accept/maxSize как у file + opaque; `declare module` →
  сахар `field.photo({...})`.
- Валидаторы поля — ОБЫЧНЫЕ серверные рамки, одинаковые везде:
  `[v.accept(серверные форматы), v.maxSize(8 MiB), photoImage(specId)]`
  (+ `v.required()` только там, где файл обязателен; у аватара пусто =
  без изменения), где `photoImage(specId) = check('photo:<specId>', {cacheByValue: false})`, а проверка
  в реестре читает голову файла (256 KiB) и зовёт `probe`
  из `#lib/image`: не картинка → код `image.format`;
  пиксели сверх предела → `image.dimensions`. Тексты — в `messages`
  поля/приложения (словарь пакета на первом этапе не трогаем).
  Валидатор всегда видит только файл, который реально уйдёт на сервер:
  no-JS сырьё или уже подготовленный JS-клиентом JPEG.
- Компонент `PhotoField.svelte` (образец PhoneField/FileField) держит
  ДВА input: оригинальный named carrier поля (SSR/no-JS путь, enabled)
  и staging-input без `name`, который появляется только после
  оживления. Staging не является полем формы: `bind` его не читает,
  валидатор молчит, `FormData(form)` его не несёт. На выборе сырого
  файла (любые форматы lib, без продуктового предела веса) PhotoField
  лениво зовёт `#lib/image`, готовит JPEG под выходной spec (бюджет
  3–5 с), кладёт готовый File в carrier через `DataTransfer` и только
  тогда зовёт `f.onInput(prepared)` — recheck и submit читают
  `new FormData(formEl)`, поэтому порядок «сначала DOM, потом onInput»
  обязателен. Лимиты и широкий список staging-`accept` компонент
  получает снимком при оживлении (контекст хоста от load), не из
  валидаторов. Ошибка подготовки показывается у поля как локальная
  ошибка компонента; `DataTransfer` недоступен или lib не ожила —
  staging не показывается, работает исходный carrier с серверными
  рамками. Пока идёт подготовка, отправка формы удерживается
  компонентом (иначе уйдёт пустой carrier). Локальное превью — общий
  UI-примитив на object URL, после подготовки — по готовому File.
- Никнейм профиля: длина — из схемы (`formParams(profile)`),
  запрещённые имена — правило/check формы с тем же кодом
  `profile.nickname-forbidden`; обе стороны получают один снимок
  конфига (страница — из load, сервер — из UserConfig).
- `resolve.ts`: `case 'photo': return PhotoField`.

**Бэкенд (через lib/form server).**
- Тот же `check('photo:<specId>')` с той же реализацией сервер
  выполняет всегда до execute: серверные форматы, 8 MiB и содержимое.
  Никаких capability-профилей у валидатора нет — асимметрию закрывает
  staging-input на клиенте (см. исследование ниже).
- Хендлер фото-формы: `limits: {maxFileSize: 8 MiB, maxBytes: 8 MiB +
  служебный запас}` под сырьё, throttle/idempotency — как принято в
  проекте.
- Конвертация — серверный помощник из lib/image-зоны. Два пути в
  `execute`: уже готовый клиентский JPEG внутри рамок принимается
  байт-в-байт и пишется сразу (синхронный `committed`); сырью нужна
  серверная конвертация — токен и claim `user:<id>` в общем
  хранилище lib/cache (pg), конвертация стартует сразу под
  семафором (5 одновременных), POST ждёт короткую льготу и только
  не уложившись уходит в `queued` с токеном (фон — `afterResponse`).
  Финиш сверяет токен claim и пишет профиль одной записью
  (ник + фото); статус живёт в хранилище, не в профиле. Точная схема — в
  исследовании токен-режима ниже; реализация — R4.
- «Подпись клиента» не делаем: секрет в браузере публичен
  (ср. вердикт владельца в `client-integrity.md`); пропуск даёт
  дешёвая проверка рамок по заголовкам. COM-маркер квитанции — только
  телеметрия.
- Инициализация wasm: Node — байты с диска (createRequire по
  node_modules приложения); Workers — `instantiateWasm` из
  импортированных модулей; вызов — лениво первым запросом (memoized)
  из серверного помощника. На Workers `maxInputPixels` держать ≤12 MP
  (память изолята 128 MB), на Node/Vercel — конфигом выше.

### Асимметрия и очередь: уточнение владельца (2026-10-21)

Capability-профили валидатора из предыдущей ревизии НЕ нужны —
владелец указал более простой механизм, и исследование по коду его
подтверждает.

**Staging-input вместо разных валидаторов.** Валидатор поля один и
буквально тот же на обеих сторонах: серверные форматы + 8 MiB +
содержимое через probe. JS-клиент не спорит с ним, а просто не даёт
ему сырьё: после оживления PhotoField показывает второй file input
без `name` (staging). Он не поле формы: `evaluate`/`recheck`/submit
собирают значения из `new FormData(formEl)`, где записи без имени нет,
а `scheduleCheck` запускается только от `f.onInput`. Сырой файл
обрабатывает lib/image; готовый JPEG кладётся в оригинальный named
carrier через `DataTransfer`, затем `f.onInput(prepared)` — и только
тут валидатор видит файл, уже внутри серверных рамок. Подстановка в
DOM обязательна: перехваченная отправка читает именно
`new FormData(form)`, одного `f.onInput` мало (прецедент — `removeAt`
в FileInput: `input.files = dt.files` + событие `change`). Без JS
staging не существует: работает carrier с теми же серверными
рамками. Лимиты подготовки и широкий `accept` staging — не правила
формы, а снимок spec, который хост отдаёт компоненту при оживлении
(load уже отдаёт limits виджету; канал — контекст приложения).
Остающиеся частности компонента, а не архитектуры: удержать submit,
пока lib готовит файл (иначе уйдёт пустой carrier); ошибку подготовки
показать у поля локально; при недоступном `DataTransfer` не показывать
staging вовсе. «Все форматы lib» = те, что различает probe и реально
декодирует среда (JPEG/PNG/WebP/AVIF); GIF/HEIC конкретного браузера
— отдельное расширение probe, не обещание этого плана.

**Что нативно делает lib/form с `queued` у no-JS (проверено по
коду).** `createFormHandler` при `out.queued` собирает `Result`
`ok: true, status: 202, outcome: 'queued'`, адреса — в `Result.data`;
без пары `pollUrl`+`statusUrl` — `QueuedWithoutProtocolError`. Дальше
решает маршрут: демо `/form` в action просто возвращает `{ result }`,
SvelteKit перерисовывает страницу тем же POST-ответом, `bind`
поднимает продолжение синхронно при связывании — и серверная разметка
уже содержит баннер «принято» со ссылкой `statusUrl`. Никакого
автообновления без JS нет: итог человек узнаёт, только открыв
`statusUrl` (страницу статуса, чей load в демо читает `jobStatus(id)`)
и перезагружая её вручную. С JS та же страница сама зовёт
`pollUntilDone(pollUrl)` и `form.lift(итог)`; сама связка не опрашивает.
Нынешняя обёртка `/user/auth` к этому не готова: при `result.ok` без
JS она делает redirect по `step`/`next` и `queued`-данные потеряла бы.

**Семантика очереди — заменена токен-режимом ниже.** Первая ревизия
этого раздела описывала живое ожидание слота внутри того же POST
(семафор + per-user мьютекс, ответ сразу финальный). Владелец уточнил
режим: фоновый процесс за токеном в lib/cache (см. следующий абзац).
От живой схемы остаются семафор конвертаций (5 одновременных — теперь
внутри фоновых задач) и принцип «запись профиля одна и атомарная»;
per-user мьютекс в POST заменён живой заявкой юзера в кэше (п. 4
схемы ниже). Очереди в БД по-прежнему нет.

**Второй режим очереди — токен в lib/cache: исследование
(2026-10-21, вопрос владельца).** Идея владельца: POST пишет токен в
lib/cache и возвращает его со статусом «ожидание»; оживлённая форма
периодически отправляет себя сама, без JS — повторная отправка или
обновление страницы; POST по токену восстанавливает состояние вместо
новой обработки. Проверено по коду:

- Токен уже существует, дважды. (1) `submissionId` конверта формы:
  генерируется на логическую отправку, связка меняет его только
  после settled-исходов (`committed|unknown|queued`), после
  `not-applied` тот же id остаётся в скрытых полях. Сервер формат
  только сверяет (UUID), одноразовость даёт не конверт, а бронь.
  (2) Идемпотентность handler-а: `storeIdempotency(localStore.scope
  (...))` — бронь по `submissionId` на 5 мин и готовый `Result` на
  сутки в lib/cache; параллельный дубль получает 409
  `submission.in-flight` (`retryable`, тот же id), повтор после
  финиша — сохранённый результат без повторного execute. В демо
  `/form` так же живёт и токен заявки: UUID в
  `localStore.scope('demo-form:jobs')`. У auth-handler идемпотентность
  сейчас не подключена — это дешёвое добавление этапа R3, закрывающее
  дубль на время долгой живой конвертации.
- Повторная отправка формы как транспорт опроса механически возможна
  только с отдельным скрытым полем-токеном (токен = `submissionId`
  при включённой брони до execute не дойдёт: handler вернёт
  сохранённый `queued`-результат). Но она строго хуже нативного
  GET-опроса: каждый опрос заново шлёт тело (с JS — файл до 8 MiB),
  проходит разбор, sync-оценку и async checks целиком — проверка
  токена в execute стоит в самом конце конвейера, а слои умеют
  только отказывать, не возвращать ранний результат. Без JS файл
  после навигации в поле не восстанавливается, а F5 после POST —
  подтверждение переотправки браузером; схема выживает, только если
  сервер игнорирует поля в пользу снимка по токену. Опросы-POST
  также едят throttle формы. Единственный плюс варианта — запись в
  БД естественно происходит в POST, а не лениво на GET-опросе.
- Синхронизация lib/image ↔ токен: lib без состояния и о токенах не
  знает (по построению); синхронизирует серверный preparer-адаптер.
  Токен → запись в scope кэша `{userId, state, spec, result|error}`;
  фоновая конвертация — `afterResponse` (Vercel/Cloudflare
  `waitUntil`), под тем же семафором и атомарным claim (`cache.add`).
  Сырые байты в кэш не кладём: контракт lib/cache — JSON-значения и
  потолок по числу записей, не по байтам; сырьё держит замыкание
  фоновой задачи в процессе, в кэш ложится только готовый выход
  (~20 KiB base64 у аватара). Финализация — два подварианта: фон сам
  пишет профиль (присутствие юзера не нужно, «потеряй» теряется,
  per-user мьютекс обязателен) или фон только конвертирует, а
  применяет следующий опрос/POST юзера один раз («потеряй»
  сохраняется). Пределы те же, что у демо-заявок: память одного
  процесса/изолята — токен на чужом инстансе = «истекло, отправьте
  заново»; вытеснение по потолку scope может уронить заявку раньше
  срока.
- Уточнение владельца (2026-10-21): токен-режим принят как режим
  этапа R4 — фоновый процесс lib/image закрепляется за токеном, по
  готовности фото ник и фото пишутся в БД вместе одной записью.
  Точная схема:

  1. POST: валидаторы формы (ник + файл) уже прошли. execute создаёт
     токен и атомарно занимает ключ юзера в общем хранилище lib/cache
     (scope заявок): `add('user:<id>', token, TTL)`. Не занялось —
     задача у профиля уже висит: берём её токен тем же хранилищем и
     отвечаем статусом той заявки, вторую не создаём. Занялось —
     `set('job:<token>', {state: 'processing', nickname})` (ник — уже
     проверенное значение из этой отправки), конвертация стартует
     сразу (промис, зарегистрированный в `afterResponse`, под
     семафором 5), и POST **ждёт её короткую льготу** (конфиг,
     секунды): уложилась — обычный синхронный `committed`; не
     уложилась — ответ `queued`, токен в `pollUrl`/`statusUrl`
     (`?job=<токен>`), конвертация продолжается фоном. Очередь
     создаётся только для не уложившихся. Идемпотентность не мешает:
     дубль той же отправки вернёт сохранённый результат с тем же
     токеном.
  2. Финиш конвертации один на оба пути: фон сверяется, что
     `user:<id>` в хранилище всё ещё его токен (claim не истёк и не
     заменён; дедлайн конвертации строго меньше TTL claim, поэтому
     подмена mid-flight исключена бюджетом), пишет профиль одной
     записью (ник из заявки + фото), ставит `job:<token>` →
     `{state: 'done'}` и снимает `user:<id>`. При сбое конвертации —
     `{state: 'failed', error}`, в БД профиля не пишется ничего.
     lib/image о токене не знает: один промис = один токен, переходы
     state пишет адаптер.
  3. Проверка токена — GET, одной функцией поверх lib/cache: с JS
     страница опрашивает `pollUrl` через `pollUntilDone` и поднимает
     итог `lift`; без JS — `load` страницы формы по `?job=`
     (`statusUrl`) при открытии/перезагрузке. Токен после обновления
     не теряется: F5 переотправляет POST — бронь вернёт тот же
     результат с тем же токеном; чистый заход на форму спрашивает
     хранилище по `user:<id>` из сессии — висит задача, значит есть
     токен и статус без токена в адресе. Чужой сессии статус не
     отдаётся (токен сверяется с `user:<id>` сессии).
  4. Хранилище заявок — общее, не память процесса: pg-реализация
     контракта lib/cache (`sharedStore`) — СДЕЛАНА до R4 отдельным
     заходом (`docs/design/cache-pg-store.md`, `db01cfb`): драйвер
     `#hooks/cache-db.js`, KV-таблица моделью lib/db (`cacheKv`,
     пара (scope, key) составной уникальностью, `f.json`-значение,
     срок), зарегистрирована в `db.ts`, таблицу при открытии БД
     создаёт sync на любом движке. Все операции драйвера — одним
     SQL-оператором через `db.query` по таблице модели (upsert и
     атомарных `add`/`incr` в `ResourceApi` нет); будущие места берут
     контракт `AtomicStore`, свой SQL не пишут.
     Дескриптор модели живёт в самом драйвере (`src/hooks/cache-db.ts` —
     папка, где приложение соединяет lib), `db.ts` его только
     регистрирует — цикла импортов нет, ядра cache и db друг друга
     не импортируют. Локально/
     одноинстансно тот же код работает на `memoryStore` — выбор в
     единственной точке `src/lib/server/cache.ts`. Почему не
     pg-блокировка (`FOR UPDATE`/advisory): она живёт только внутри
     одной открытой транзакции/соединения, а заявка обязана пережить
     ответ POST, фон и опросы с чужих инстансов; держать транзакцию
     на время wasm-конвертации нельзя (и негде: транспорты проекта —
     transaction-pooling и Hyperdrive, где advisory locks не
     поддерживаются, а proxy-адаптер вообще без транзакций; правило
     пакета в `src/lib/db/docs/TRANSPORTS.md` — session-состояния
     нет, локадч только `FOR UPDATE` внутри короткой транзакции).
     Атомарность операций при этом как раз pg: каждый `add`/`set` —
     один оператор. Это закрывает многоинстансный сценарий
     владельца: второй инстанс видит живой `user:<id>` и статус той
     же заявки. В памяти процесса остаются только сырые байты
     задачи и семафор (5 × инстансы — ресурсный предел, не
     корректность). Процесс умер до финиша — ключи истекут по TTL,
     статус честно «истекло, отправьте заново», в БД ничего нет.
  5. Быстрый путь без хранилища: уже готовый клиентский JPEG
     конвертации не требует — execute пишет профиль сразу. Статус в
     профиле не хранится (решение владельца 2026-10-21): строка
     профиля служебных полей не получает; таблица одна —
     KV-модель lib/cache, создаётся sync-ом lib/db при подключении,
     общая и для брони форм.

## Отклонённые альтернативы

- Разные capability-профили одного валидатора, две проверки или два
  описания формы ради асимметрии форматов — лишнее: staging-input
  оставляет валидатор буквально одним (см. исследование выше).
- Очередь в БД (таблица задач) и платформенная очередь — владелец
  прямо не хочет; статус в строке профиля — тоже (2026-10-21).
  Принят токен-режим: заявка ключами в общем pg-хранилище lib/cache
  (своя KV-таблица) + фон `afterResponse` + нативный `queued`
  (см. схему выше). Опрос повторной отправкой формы отклонён —
  строго хуже GET-опроса; живое ожидание слота внутри POST
  superseded токен-режимом.
- Внешний npm-пакет browser-image-pipeline — отвергнут владельцем:
  lib живёт в `src/lib` исходниками, как остальные.
- Конвертация в `decode` типа или в `prepare` — обе границы синхронны
  по построению ядра; async место ровно два: checks и execute.
- Доверие клиентскому маркеру/токену — см. выше.
- sharp/нативные зависимости — платформы Vercel/Workers и политика
  зависимостей проекта; wasm @jsquash уже принят дизайн-доком.

## Этапы (каждый: изменения → гейты → локальный коммит)

Сделано: вендоринг (`04f23d6`) и промежуточный аватар на движке lib

   execute: авторизация → preparer → сохранение строки одной записью
   профиля (никнейм + аватар атомарно, после успешной конвертации). Удалить `avatar.ts` и `checkAvatar`; контракт

   схема БД остаётся последним рубежом вида строки); тесты
   emulate/handler переписать на File-путь. Гейты: сырой JPEG →
   строка 200×200 ≤ maxBytes; готовый клиентский — без
   перекодирования; EXIF-6; плохой никнейм — preparer не вызван;
   битый декод — field error, не 500; параллельный дубль той же
   отправки — 409 `submission.in-flight`, повтор после финиша —
   сохранённый результат без второй конвертации и записи.
R4. **Токен-режим очереди.** Предпосылка закрыта: pg-хранилище
   lib/cache (`sharedStore`) сделано отдельным заходом —
   `docs/design/cache-pg-store.md`, `db01cfb`. По схеме
   исследования выше: `add('user:<id>', token)` + `job:<token>` в
   общем хранилище, конвертация стартует в POST под семафором (5) и
   ждёт короткую льготу; не уложилась — `queued` с токеном, фон
   через `afterResponse` доводит, сверяет токен claim и пишет
   ник + фото одной записью. Проверка токена — GET поверх хранилища:
   poll-endpoint для JS (`pollUntilDone` + `lift`) и `load` страницы
   формы для no-JS; статус находится и без токена — по сессии
   (`user:<id>` → токен). Обёртку `/user/auth` починить: no-JS
   redirect не должен терять `queued`. Гейты: pg-store проходит тот
   же контрактный набор, что memory (`add` атомарен на параллельных
   вызовах, TTL, scope); быстрая конвертация — синхронный `committed`
   без токена наружу; медленная (принудительно крошечная льгота) →
   202/queued → опрос `processing` → `done`, в БД ник + фото одной
   записью; вторая отправка при живом `user:<id>` — статус той же
   заявки без второй конвертации; финиш с истёкшим claim профиль не
   пишет; битая конвертация → `failed`, записи нет; чужая сессия
   статус не читает; 7 параллельных — не больше 5 конвертаций
   одновременно; prepared JPEG идёт быстрым путём без хранилища.
R5. **Второй потребитель — доказательство переиспользования.**
   `/fields` record переводится на photo-валидатор и preparer:
   ручные `sniff`/base64 из route удаляются, остаётся выбор хранения
   (строка в демо-кэше). Критерий: новая загрузка = поле в описании
   + один вызов preparer в execute + выбор сохранения.
R6. **Превью и чистка (после загрузки).** Миниатюры общего FileInput
   переводятся на примитив object URL + `<img>` без перекодирования,
   compressorjs удаляется, plan.md/README обновляются; Workers-прогон
   под wrangler при подтверждении цели.
R7. **Защита границы и расширение на файлы формы.** После миграции
   потребителей — правила `layer-guard` против обхода файлового
   контура (см. границу выше) с тестами стража и явными разрешёнными
   зонами. Следующие виды файлов подключаются обработчиками за тем же
   фасадом; `lib/storage` остаётся отдельной последующей задачей и
   получает только `PreparedFile`.

## Команды

- Node ≥22.17 обязателен (engines). В песочнице: системный 20.20.2 +
  `/tmp/node22` (22.20.0, tmpfs — при потере переустановить тарболом).
- `npm install --ignore-scripts` (node_modules не переживают сессии),
  затем `npx svelte-kit sync`.
- Внутренний цикл: `npx vitest run <файлы этапа>`; полный набор перед
  коммитом этапа: `npm run check`, `npm run test:unit`,
  `npm run test:guard`, по этапу — `npm run build && npm run test:size`,
  браузерные — точечно (`test:browser:forms` и т.п.), не browser-all.

## Риски и честные оговорки

- Workers-инициализация wasm написана по правилам платформы, но под
  wrangler ещё не запускалась (этап 8); free-тариф Workers по CPU
  декод не потянет — нужен платный или Vercel Node runtime.
- Клиентский вес: ядро конвейера в пакетной сборке — 10.8 KiB gzip
  (pipeline-core), кодеки/квантование — ленивые чанки; в вендоре
  пересчитать по факту, бюджетный гейт может потребовать решений.
- EXIF-поворот на серверном декоде — ручная таблица отображений;
  покрыть фикстурами реальных телефонов на этапе 5.
- Playwright в песочнице не установлен (скачивание Chromium трижды
  зависало по ~470 с): браузерные гейты этапов 4/6 до установки —
  непроверены здесь. Сильнейшая альтернатива до установки — unit +
  svelte-check.

## Вопросы владельцу (решения до кода)

Отвечено по ходу: состав lib — целиком (size-лимиты подняты решением
владельца), первый потребитель — аватар, ветка — `upgrade/kit3`
локальными коммитами без push. Фасад `open()` для форм-интеграции не
нужен (внутри — `image()`), вопрос снят до отдельного запроса.

Решено владельцем 2026-10-21: «го» на план дано; валидатор обычный,
серверный (форматы + 8 MiB), асимметрия — staging-input на JS-клиенте
(все форматы lib в подготовку, в форму только готовый JPEG); очередь —
ожидание слота внутри POST, без БД и без нативного `queued`,
ориентир — 5 одновременных конвертаций. Осталось до/во время R3–R4:

1. Подтвердить серверное «простое сырьё» = JPEG/PNG/WebP (нынешнее
   обещание UI и рекомендация плана).
2. Числа spec кроме веса: абсолютный предел пикселей/стороны для
   серверной попытки, потолок ждущих и суммарный дедлайн ожидания —
   по замерам R3 на целевом железе, доложить владельцу числами.

## Процедура (регламент агента, приложенный владельцем)

Пять жёстких правил: (1) нет правок до VCS-снимка; (2) коммит положен,
когда файлы изменены и хотя бы один гейт зелёный; (3) «готово» — только
с блоком доказательств; (4) невыполнимое требование называется вслух;
(5) после поправки владельца — стоп, ответ, ожидание решения.

- VCS: репозиторий modals-kit, ветка `upgrade/kit3`; checkpoints:
  план `d7545e3`, вендоринг `04f23d6`, промежуточный аватар
  `7149ce8`; push не делается без явной просьбы.
- Среда: Linux x86_64, 2 CPU, ~2 GB RAM; `/tmp` — tmpfs 992 MB
  (эфемерен); `/home/user` персистентен, но `node_modules`, `.cache`,
  `dist` в снапшоты сессий не попадают.
- Пропущено: Playwright-проверка фазы ноль (см. риски); целевой
  сценарий владельца (валидатор формы, File, no-JS, очередь ожидания)
  не реализован — этапы R1–R7. «Го» получено 2026-10-21; механизм
  staging-input и семантика очереди уточнены владельцем этой
  ревизией — точный следующий шаг: R1.
