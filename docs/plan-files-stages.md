# Этап 1. Возможности окружений, готовый модуль стриминга и каркас `#lib/storage`

## 1.1. Решения и замечания владельца (хронология)

### Итерация 1 (2026-10-28)
- Убрать забегающие вперёд этапы — разбираем только один текущий этап: что умеет
  окружение (`Cloudflare`, `Vercel`, `Node`, `Bun`) и через какой готовый модуль
  одинаково стримить файлы туда и обратно без изучения всех платформенных багов
  вручную.
- Чанкование мессенджеров — рано.
- Вместо бессмысленного хранения юзерских файлов в RAM (`memory`) локальное
  файловое хранилище называть понятно (`local`), а облачным бакетом на перспективу
  считать R2 с отдельной схемой под хост (+ `aws4fetch`).

### Итерация 2 (2026-10-28)
1. **Фундамент стриминга — УТВЕРЖДЁН:** берём пакеты **`@remix-run/lazy-file` +
   `@remix-run/response` + `@remix-run/fs` + `@remix-run/form-data-parser`**
   (попутно апстрим сам будет чинить новые баги стримов в рантаймах).
2. **Состав полного набора адаптеров (`local`, `r2` и др.) — ОТЛОЖЕН («пока отложим»):**
   не распыляемся на пачку адаптеров заранее.
3. **Тестовый стенд — Облако Mail.ru по WebDAV:** у владельца есть рабочее
   личное Облако Mail.ru с уже лежащими там тяжёлыми файлами — подходит для
   реальной проверки стриминга без поднятия локального WebDAV-сервера.
4. **Независимость от SvelteKit (переносимость на React):** `sveltekit` — это
   фреймворк; в ките его можно подключать только как изолированный фреймворк-адаптер
   (как в существующих пакетах `src/lib/*`), а при переносе `lib/storage` в
   React-проект тащить за собой `@sveltejs/kit` недопустимо.

## 1.2. Что даёт окружение и утверждённый стек `@remix-run/*`

### Подводные камни рантаймов (`Node`, `Bun`, `Vercel`, `Cloudflare`)
1. **Ловушка `await res.blob()` во всех 4 средах:** выкачивает весь файл в RAM
   сервера до отдачи первого байта клиенту → используем только `LazyFile` поверх
   `res.body` (`ReadableStream`).
2. **Дефолт `BODY_SIZE_LIMIT = '512K'`** в `@sveltejs/adapter-node` и
   `svelte-adapter-bun` (+ `IDLE_TIMEOUT = 10` с в Bun) → для загрузки файлов
   `> 512 КБ` через сервер лимит поднимается в env.
3. **Исходящий потоковый `PUT` в `fetch`:** в Node/Vercel (`undici`) обязателен
   `duplex: 'half'`; в Cloudflare Workers и большинстве WebDAV-серверов нужен
   известный `Content-Length`. Утечка `Blob#stream()` в Node `< 24.20`
   (`nodejs/node#63574`) уже обойдена внутри `@remix-run/form-data-parser`.
4. **Лимит 4.5 МБ на входящее тело функции в Vercel:** выходящий стрим ответа
   не режется, а входящие загрузки `> 4.5 МБ` в будущем обходятся прямой
   загрузкой в облако (`presignPut`).

### Утверждённые готовые модули (MIT, 0 привязки к фреймворкам)
- **`@remix-run/lazy-file@5.0.8`** — `LazyFile` / `LazyBlob` (стандартный Web
  `File` без буферизации байтов в RAM: `{ byteLength, stream(start, end) }`).
- **`@remix-run/response@1.0.1`** — `createFileResponse(file, request, options)`
  (`200`, `206 Partial Content` по `Range`, `416`, `ETag` weak без чтения в память,
  `304`, `If-Range`, `HEAD` без открытия потока, `X-Content-Type-Options: nosniff`).
- **`@remix-run/fs@1.0.0`** — `openLazyFile` / `writeFile` для локальной ФС
  Node и Bun (когда дойдём до локального адаптера).
- **`@remix-run/form-data-parser@1.1.0`** — потоковый приём `multipart/form-data`
  от клиента без буферизации тела в памяти.

## 1.3. Как устроена независимость от SvelteKit (перенос в React 1-в-1)

Проверены существующие прецеденты в репозитории (`src/lib/modals/entrypoints.json`,
`src/lib/paginate/entrypoints.json`, `src/lib/db/entrypoints.json`,
`src/lib/address/entrypoints.json`) и страж `tooling/core-purity.mjs`:

1. **Ядро и все сторадж-адаптеры `src/lib/storage` вообще не знают про SvelteKit:**
   - Всё построено исключительно на веб-стандартах **`Request`, `Response`,
     `File` (`LazyFile`), `ReadableStream`**.
   - В React-мире (Next.js App Router `app/api/.../route.ts`, React Router v7,
     TanStack Start, Hono) роуты принимают **ровно тот же стандартный Web
     `Request` и возвращают `Response`** — значит `lib/storage` работает в
     React-проекте **напрямую без единой обёртки и без `@sveltejs/kit` в
     `package.json`**.
2. **Даже для чтения статических файлов самого приложения SvelteKit в ядре не нужен:**
   - В ядре адаптер чтения ассетов приложения принимает простую функцию
     `read: (asset: string) => Response | ReadableStream | Promise<Response | ReadableStream>`
     (чистый TypeScript без импортов).
   - Если нужен готовый ярлык под SvelteKit (который передаёт `read` из
     `$app/server`), он кладётся в отдельный необязательный вход
     `src/lib/storage/sveltekit/` (по канону `modals/cores/sveltekit.ts` и
     `paginate/sveltekit/router.ts`, проверяемому `core-purity.mjs` и
     `public-api.mjs`). При копировании `src/lib/storage` в React папку
     `sveltekit/` просто не берут (или удаляют) — ни один файл ядра и адаптеров
     от неё не зависит.

## 1.4. Особенности стенда Облака Mail.ru по WebDAV (и защита личных файлов)

Проверены документация Облака Mail.ru и рабочие клиенты (`mailRuCloudFetch`):
1. **Протокол и адрес:** `https://webdav.cloud.mail.ru/`, стандартные RFC 4918
   (`PROPFIND` с `Depth: 0` / `Depth: 1` → `207 Multi-Status`, отдаёт
   `getcontentlength`, `getcontenttype`, `getlastmodified`, `getetag`) и
   RFC 9110 (`GET` с `Range: bytes=start-end` → `206 Partial Content` +
   `Content-Range`).
2. **Авторизация:** HTTP `Basic` — полный email (`...@mail.ru` и др. домены Mail) +
   **пароль для внешнего приложения** (создаётся в Mail ID → «Безопасность» →
   «Пароли для внешних приложений» с полным доступом к облаку/WebDAV; обычный
   пароль от почты по WebDAV закрыт). Примечание: в бесплатных тарифах Mail.ru
   может ограничивать доступ к WebDAV или размер загружаемого файла (до 1 ГБ), на
   платных Mail Space доступ полный.
3. **Редиректы и заголовки:** `redirect: 'manual'` на `PROPFIND`/`PUT` (чтобы
   при ошибке авторизации или слэша креды `Authorization` не утекли на чужой
   редирект и не превратили `PROPFIND` в `GET`), корректное `encodeURIComponent`
   для русских имён папок и пробелов в путях.
4. **Защита твоих личных файлов при тестах (обязательно!):**
   - так как облако **личное и живое**, в адаптер WebDAV сразу закладываются два
     жёстких ограничителя:
     - **`readOnly?: boolean`** — при `readOnly: true` любые методы записи/удаления
       (`put`, `remove`, `mkdir`) заблокированы на уровне самого источника и
       `capabilities` (для теста стриминга твоих существующих тяжёлых файлов
       включаем `readOnly: true` — 0 шансов что-то перезаписать или удалить);
     - **`basePath?: string`** (песочница подпапки, например `'/modals-kit-test'`) —
       если проверяем запись/удаление, адаптер физически не может обратиться ни к
       одному пути выше этой подпапки (любой `..` режется).
   - логин и пароль приложения читаются только из локального некоммичиваемого
     `.env` (или переданного тобой файла в `/home/user/uploads/`), никогда не
     выводятся в консоль/логи.
