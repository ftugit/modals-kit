# Этап 1. Отдача файлов клиенту стримом (`#lib/storage` + `webdav`)

## 1.1. Решения и замечания владельца (хронология)

1. **Фокус Этапа 1 — сначала научиться отдавать файл клиенту стримом:**
   - приём файлов от клиента (`form-data-parser`) **пока не трогаем**;
   - пачку остальных адаптеров (`local`, `r2` и др.) **пока откладываем**;
   - проверяем на живом личном **Облаке Mail.ru по WebDAV**, где уже лежат
     тяжёлые файлы (обязательны предохранители `readOnly` и `basePath`).
2. **Фундамент стриминга для Этапа 1:** `@remix-run/lazy-file` +
   `@remix-run/response` (для Этапа 1 достаточно этих двух пакетов, без единой
   зависимости от SvelteKit — переносится в React 1-в-1).
3. **Решения по API (после ревью примера):**
   - обычный `cloud.get(key)` сам забирает вес, тип, дату и `ETag` у WebDAV;
   - метод `cloud.lazy(key, meta)` **оставляем** в API — не мешает и пригодится
     позже, когда метаданные уже известны из БД.

## 1.2. Справка: возможно ли шифрование и дешифровка прямо во время стрима?

**Короткий ответ: да, полностью на лету — скачивать файл целиком на сервер (ни в
RAM, ни во временный файл на диске) НЕ нужно, и даже перемотка видео (`HTTP Range` /
`206 Partial Content`) продолжает работать.**

### Почему монолитное шифрование не годится, а блочное (STREAM AEAD) работает идеально
1. **Как делать НЕЛЬЗЯ (монолитный `AES-GCM` на весь файл одним куском):**
   - `crypto.subtle.decrypt('AES-GCM', ...)` в Web Crypto API принимает только
     буфер целиком, а проверочный тег подлинности (`16 байт`) лежит в самом конце
     файла. Такой файл действительно пришлось бы выкачивать в память целиком, и в
     середину видео перемотать нельзя.
2. **Как делают промышленно (`age` STREAM — `FiloSottile/typage`, `rclone crypt`, Google Tink `StreamingAEAD`):**
   - Поток режется в `TransformStream<Uint8Array, Uint8Array>` на небольшие
     фреймы фиксированного размера — например **64 КБ** открытого текста.
   - В начале зашифрованного файла пишется короткий заголовок (например 32 байта:
     версия + соль файла для вывода ключа через HKDF + базовый префикс `nonce`).
   - Каждый 64-КБ чанк № `i` (`0, 1, 2, …`) шифруется и заверяется отдельно через
     штатный аппаратно-ускоренный **`crypto.subtle.encrypt('AES-GCM', ...)`**
     (работает нативно в **Cloudflare Workers, Vercel, Node и Bun** с 0 внешних
     зависимостей; `nonce` содержит номер чанка `i` и флаг последнего блока, что
     защищает от перестановки и обрезки кусков).
   - На каждые `65 536` байт данных добавляется ровно `16` байт тега (`65 552`
     байт в облаке — наценка всего **0,024%**).
   - **Память сервера при стриме файла любого размера (хоть 20 ГБ):** всего
     **один буфер ~64 КБ** внутри `TransformStream`!
   - **Как при этом работает `LazyFile` и `Range` (`206` перемотка видео):**
     - истинный размер расшифрованного файла вычисляется из размера в WebDAV за
       $O(1)$ одной формулой деления без скачивания данных;
     - когда браузер просит `Range: bytes=10_000_000-10_500_000`, обёртка делит
       смещение на `65 536`, вычисляет номера нужных зашифрованных блоков
       (`152..160`), запрашивает у WebDAV по `Range` **только эти 9 блоков**,
       расшифровывает их на лету в потоке и отрезает точные края под `206`!
3. **Что это значит для архитектуры `#lib/storage` прямо сейчас:**
   - Ничего в предложенном контракте `StorageAdapter` менять не требуется:
     потоковое шифрование идеально ложится как будущая обёртка-декоратор поверх
     **любого** адаптера (`withEncryption(webdav(...), { key })`), которая сама
     пересчитывает `stat().size` и `openStream(key, range)`.

## 1.3. Утверждаемый API Этапа 1 (`#lib/storage`)

### Входы (`src/lib/storage/entrypoints.json`)
```json
{
  "//": "`index.js` — фасад `createStorage`, HTTP-отдача `serveFile`, типы и ошибки (0 провайдеров, 0 node:fs, 0 фреймворков); `webdav.js` — адаптер WebDAV на чистом fetch; `state.js` — необязательный коллектор телеметрии.",
  "entrypoints": ["index.js", "webdav.js", "state.js"]
}
```

### Контракт (`src/lib/storage/index.ts`)
- `createStorage(adapter, { state? }) -> Storage`:
  - `capabilities: { range, write, list, presignGet, presignPut }`
  - `get(key, { signal? }) -> Promise<LazyFile | null>` — запрашивает метаданные
    у адаптера и возвращает потоковый `LazyFile` без загрузки тела в память
  - `lazy(key, meta) -> LazyFile` — собирает `LazyFile` без сетевого `stat`,
    когда `size`/`type`/`lastModified` уже известны вызывающему
  - `has(key, { signal? }) -> Promise<boolean>`
  - `stat(key, { signal? }) -> Promise<StorageStat | null>`
  - `put(key, body, { size?, type?, lastModified?, overwrite?, signal? }) -> Promise<StorageStat>`
  - `remove(key, { signal? }) -> Promise<void>`
  - `list({ prefix?, limit?, cursor?, signal? }) -> Promise<StorageListResult>`
- `serveFile(file, request, { disposition?, filename?, cacheControl?, etag?, acceptRanges? }) -> Promise<Response>`:
  - опирается на `@remix-run/response` (`createFileResponse`: `200`, `206 Partial Content`,
    `304 Not Modified`, `416`, `HEAD`, `X-Content-Type-Options: nosniff`) +
    кодирует UTF-8 имена файлов по RFC 5987 в `Content-Disposition`.
- `webdav({ url, username?, password?, headers?, basePath?, readOnly?, fetch? }) -> StorageAdapter`
  (`src/lib/storage/webdav.ts`):
  - `PROPFIND` (`Depth: 0` / `Depth: 1`) + `HEAD`, потоковый `GET` с `Range`,
    потоковый `PUT` (`duplex: 'half'`, `Content-Length`, авто-`MKCOL`), `DELETE`;
  - жёсткая нормализация ключей (запрет `..`, `\0`, обратных слэшей), песочница
    `basePath` и блокировка записи при `readOnly: true`.
