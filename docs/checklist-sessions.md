# Часть A. Выход из аккаунта

## A1. Что подтверждено живьём (14.11)

Стенд: `npm run dev` (Node 22, `KIT_ADAPTER=node`), вход по seed администратора,
Playwright (headless shell), страница `/?modal=user.logout`.

| Сценарий | Что реально произошло |
| --- | --- |
| Одиночный выход («Выйти», чекбокс снят) | POST `/user/logout?/exit` → **200**, `data: { step: "done", variant: "logout", revoked: 1, requested: 1 }`. Куки `auth_sid`/`auth_tmp` **сняты**. Адрес остался `?modal=user.logout`. Модалка тут же перерисовалась в экран «Сессию прочитать не удалось — доступен только выход на этом устройстве» с кнопкой «Выйти только здесь». |
| Массовый выход (чекбокс отмечен) | POST `/user/logout?/exit` → **400**, `errors: [{ code: "request.unexpected-field", params: { name: "include_current" } }]`. Куки на месте. Экран: «Исход неизвестен» + «Повторить». |
| Повторное нажатие после успешного выхода | Актора уже нет: `load` отдаёт `canRevoke: false`, экран снова «выйти только здесь». «Сессия не найдена — войдите заново» — доменный ответ, когда строки уже нет. |

Вывод: одиночный выход **на сервере срабатывает** (сессия отозвана, куки сняты),
но экран об этом не знает. Массовый выход **не доходит до сервера**.

## A2. Причины

**P1. У одной формы две разные ревизии.** Экран выхода собирает форму закрытия
устройств в варианте «выход»: в ней есть поле «включая текущую» и скрытый
признак «весь срез». Сервер регистрирует ту же форму **без варианта** — этих
полей в ней нет. Браузерный POST несёт идентификатор формы, поэтому его
разбирает серверное описание, а не экшен маршрута. Лишнее поле → 400.

**P2. Экшен маршрута выхода — мёртвая ветка для браузера.** Он умеет массовый
выход, но браузерный POST до него не доходит: его перехватывает регистрация
компонентной формы. Поэтому «закрыть все сессии» физически не может дойти до
домена.

**P3. Успех вытесняется перезагрузкой данных.** После отзыва текущей сессии
гейтвей снимает куки, компонент чистит память браузера, хост перезапрашивает
данные. Новый ответ уже без актора → экран «нет чтения». Ветка «Вы вышли» в
разметке есть, но её никто не успевает увидеть; перехода на вход тоже нет.

**P4. Домен удаления снимает куки.** Отзыв строки, если в ней есть текущая
сессия, снимает куки. Для «удалить устройство в списке» это неверно: удаление
не должно разлогинивать того, кто нажимает.

**P5. «Исход неизвестен» подменяет любую ошибку.** Компонент считает
неизвестным исходом любую неуспешную отправку, включая 400 с точным кодом и
текстом. Настоящая ошибка сервера приходит, но её не показывают.

**P6. Права на массовое закрытие выданы всем.** Признак «можно закрывать»
ставится любому, кто прочитал актора, без проверки права читать сессии.

## A3. План правок выхода

1. **Один контракт формы** (P1, P2). Клиент и сервер описывают форму одинаково;
   вариант «выход» известен серверу. Готово, когда POST с чекбоксом не даёт 400.
2. **Массовый выход одним доменным вызовом** (P2). Тот же путь, что массовое
   закрытие в списке, а не цикл по одной строке.
3. **Экран успеха** (P3). «Вы вышли» и переход (или явная кнопка), а не «сессии
   нет». Успех и отсутствие сессии — разные состояния.
4. **Настоящая ошибка вместо «неизвестно»** (P5). Неизвестность — только обрыв
   или ответ без тела.
5. **Куки снимает только выход** (P4). Удаление строки не разлогинивает.
6. **Права** (P6). «Можно выйти» и «можно массово закрывать» — разные права.
7. **Браузерные сценарии** выхода и массового выхода, по видимому результату.

## B5. Лист профилей — новый этап **[Н]**

**Листа профилей нет.** Проверено по маршрутам: `/user/[id]` — один профиль,
`/users` — список seed-аккаунтов (право `account.read`, колонка seed, фильтры
по состоянию и удалённым). Списка профилей как такового в проекте не было, и в
плане его нет.

Нужен новый лист на подобии seed-списка, с двумя отличиями: seed-права не
нужны и фильтры не нужны вовсе — даже в фильтрах. По сути это может быть
публичный список пользователей сайта, но **не на текущем этапе**.

Как проектируется:

- тот же носитель, что у seed-списка: страница плюс модалка плюс одна общая
  разметка, один `load` на все носители, догрузка страницами;
- строка — профиль, а не аккаунт: никнейм, аватар, дата создания; seed не
  показывается и не спрашивается;
- кнопки фильтров нет, строки активных фильтров нет, параметров фильтров в
  адресе нет; размер порции — как у остальных списков;
- права: сейчас только для вошедших; seed-права (`account.read`) не требуются;
  удалённые аккаунты и чужие seed-поля не показываются;
- на будущее: у профиля уже есть приватность `all` / `users` / `nobody`
  (этап 8 плана профиля). Публичный список — это `all`, и он остаётся на
  потом: сейчас лист не публичный;
- вход — кнопкой из общего блока на главной (B1).

Открытые вопросы: имя листа и адрес («Профили» / «Люди» / `/profiles`),
нужен ли поиск по никнейму (фильтры не нужны, а поиск — отдельное решение),
порядок по умолчанию и что показывать у профиля без никнейма.

Готово, когда: есть страница и модалка одного листа; seed-прав не требуется;
фильтров нет ни в форме, ни в адресе; строка показывает профиль; пустой и
отказной экраны есть; ссылка стоит в общем блоке на главной.

# Часть C. Метки фильтров **[Н]**

## C0. Что есть в коде: три разных места одной идеи

| Где | Что показывает | Всплывашка | Пишет в хранилище |
| --- | --- | --- | --- |
| `FilterChips` над списком (seed, блокировки, сессии) | только активные фильтры, по одной метке на ключ | да, но только если форма фильтров смонтирована (sidebar/модалка); открытая метка переносит сам узел поля из формы | изменение во всплывашке остаётся черновиком формы, нужен «Применить»; снятие крестиком — сразу |
| `FilterLabels` в панели каталога | **все** поля схемы сразу, независимо от активности | да, тем же переносом узла | нет: форма панели применяется целиком («Применить») |
| `ActiveFilters` в панели каталога | по одной метке на каждое значение (каждый жанр отдельно), только снятие | нет | снятие — сразу |

Панель каталога (`FiltersPanel`), в которой живут вторые два, не подключена ни
одним маршрутом этого репозитория: каталог Шикимори — отдельный демо-модуль вне
`img`. Но именно её поведение владелец и увидел.

## C1. Чего хочет владелец (поведение Шикимори)

1. Метки появляются **только у активных** фильтров: нет значений — нет метки.
2. Одна метка на поле, значения **через запятую** («Жанры: экшен, драма»), а не
   отдельная метка на каждый жанр.
3. Клик по метке открывает всплывашку с быстрым изменением именно этого поля.
4. Изменение во всплывашке **сразу** попадает в хранилище и в список; шаг
   «Применить» для этого не нужен — иначе быстрое изменение теряет смысл.

## C2. Что было в плане

План этой работы из дерева удалён (коммит «убрать закрытые планы»), но остался
в git: `git show ab9faa2:docs/tmp-listing-sidebar.md`, этап 2. Действующий
контракт — `src/lib/paginate/filters/README.md` (раздел «Нарезка») и
`src/components/listing/README.md`.

- Всплывашки у меток — **были** в плане: метка забирает уже собранный кусок
  формы в `Floating`, второй копии полей нет.
- «Только активные», «объединение значений через запятую», «запись сразу» —
  **не были**. План говорил обратное: метка — подпись поля схемы (все поля
  видны), блок — ровно один ключ, форма применяется целиком (`live: false`).

То есть из четырёх требований планом покрыт только сам факт всплывашки; три
остальных — новое решение, и оно меняет контракт меток.

## C3. План правок

1. **Один компонент меток вместо трёх.** Только активные поля; одна метка =
   одно поле; значения склеены через запятую. `FilterLabels` и `ActiveFilters`
   из панели и `FilterChips` из списка сводятся к нему одному.
2. **Один реестр блоков.** Сейчас их два: контекст панели и реестр по имени
   списка. Метка должна находить свой блок независимо от того, где нарисована
   форма.
3. **Немедленная запись.** Изменение поля во всплывашке строит патч одного
   ключа и уходит в `setExtra`; «Применить» остаётся только у полной формы и
   без JS. Снятие крестиком — как сейчас, сразу.
4. **Метки без значений нет.** Поля, которых нет среди активных, живут в форме,
   а не в строке меток.
5. **Без JS** строка меток не нужна: форма работает как сейчас, обычным GET.
6. **Тесты:** объединение значений, немедленная запись после изменения,
   отсутствие метки у пустого поля, снятие.

Открытые вопросы: диапазон дат — одна метка «Создан: 1–10» или две;
несколько значений «кроме» — красным, как сейчас, или иначе; где заканчивается
«быстрое изменение» для полей с длинными списками (студии и т. п.).

# Часть D. Настройки и сессии в одном listing **[Н]**

## D0. Что есть сейчас

- `UserConfig` рисует `Surface` с заголовком «Настройки» (свои) / «Настройки
  пользователя» (чужие) и `controls`: слева `Steps` конфиг-групп («Профиль»,
  «Безопасность»), справа кнопка «Сессии», открывающая модалку `user.sessions`.
- `UserConfigFields` рисует те же шаги внутри формы, если `embedSteps`.
- `SessionsDomain` — отдельный `Listing` со своим `Surface`, фильтрами,
  счётчиком и кнопками «Все сессии» / «Заблокировать остальные».
- Итог: настройки и сессии — два независимых экрана; сессии открываются
  отдельной кнопкой, а не живут в listing настроек.

## D1. Убрать «Настройки» рядом со steps

Заголовок `ownTitle: 'Настройки'` стоит в центре шапки рядом со steps слева, от
чего создаётся дубль. Убрать текст для своих настроек (заголовок не рендерить
или оставить пустым), когда показана навигация steps; чужие настройки
(`foreignTitle`) оставить — там steps нет или они другие.

## D2. Внутри «Безопасности» — шаги «Настройки» и «Сессии»

В группе «Безопасность» (сейчас один ключ `session.ipLock`) нужно добавить
шаги-кнопки «Настройки» и «Сессии». Открытый вопрос: это два отдельных шага
верхнего уровня (переключение между экраном настроек и экраном сессий) или
кнопки внутри группы. `Steps` плоский и не умеет вложенность, поэтому либо
нужен второй хост steps, либо составной ключ. Решить до реализации.

## D3. Кого модернизировать, чтобы сессии вписались в listing настроек

Цель: не рисовать отдельный `Listing` сессий внутри страницы настроек, а
встроить его в тот же listing настроек: слева остаются steps настроек, справа
появляются кнопки listing сессий, тело переключается между формой настроек и
списком сессий.

Кто требует изменений:

1. **`Listing`** — нужен встроенный/«без шапки» режим: не рисовать свой
   `Surface`/заголовок, а отдать шапку (controls, фильтры, счётчик) и тело
   (пагинатор) родителю. Сейчас `Listing` всегда оборачивает всё в `Surface`.
2. **`SessionsDomain`** — строится на `Listing` и добавляет свои controls
   (фильтры, «Все сессии», «Заблокировать остальные»). В встроенном режиме он
   должен отдавать эти controls родителю, а не рисовать собственный `Surface`.
3. **`UserConfig`** — `Surface` должен стать общим хостом: `start` = steps
   настроек (и, возможно, «Сессии»), `end` = controls активного listing
   (настроек — пусто или «Сохранить»; сессий — фильтры и revoke all), тело —
   либо форма настроек, либо paginator сессий.
4. **`Surface`** — уже умеет `start`/`end` группы, менять не нужно; но нужен
   единый владелец скролла тела при переключении.
5. **`Steps`** — либо второй хост для верхнего переключения, либо расширение
   шагов составными ключами; плюс сохранение текущего шага в адресе.
6. **Фильтры сессий** — их sidebar-слот регистрируется через контекст страницы;
   во встроенном listing внутри модалки настроек контекста страницы может не
   быть, нужен fallback на кнопку (как сейчас в модалке).
7. **ACL** — настройки и сессии имеют разные права; встроенный listing сессий
   должен сохранить свои проверки, а не унаследовать права настроек.

Готово, когда: на странице/в модалке настроек один `Surface`; при выборе
«Сессии» в теле показывается список сессий без собственной шапки; слева — steps
настроек, справа — кнопки listing сессий; фильтры, пагинация и revoke all
работают как в отдельном списке; без JS доступна страница сессий по ссылке.

# Часть E. Подтверждение — отдельный экран

## E1. «Заблокировать все» из списка сессий **[П]**

Сейчас: кнопка «Заблокировать остальные» в шапке списка разворачивает блок
подтверждения **над списком** (не отдельное окно). При этом у блока есть шаг
«сводка» со строкой «Будет завершено сессий: N», но список его пропускает и
сразу открывает подтверждение. Название «остальные» планом не задавалось.

Нужно: кнопка-ссылка «Заблокировать все», открывающая отдельный экран
(модалку) подтверждения; на экране сказано, сколько сессий будет закрыто;
выполнение — отдельной отправкой, не GET.

План требовал именно этого: §6.3 — «ссылка только открывает подтверждение;
набор показан словами и числом», §9 — «подтверждение внутри списка» исчезает.
**Не сделано.**

Готово, когда: подтверждение живёт отдельным слоем, а не блоком над списком;
на экране число; кнопка называется «Заблокировать все»; без JS работает та же
страница; тест проверяет число.

## E2. «Заблокировать» в экране сессии **[П]**

Сейчас: в карточке устройства (и на её странице) подтверждение разворачивается
**внутри** карточки — нижний блок заменяется формой «Завершение сессии» с
кнопками. Отдельного окна нет.

Нужно: карточка — только вход; подтверждение — отдельное окно (слой), как у
удаления сессии из списка. План: §8.2 — «карточка остаётся; подтверждение
закрытия выносится, карточка — вход», §9 — «подтверждение внутри карточки»
исчезает. **Не сделано.**

Готово, когда: нажатие «Заблокировать» открывает отдельный слой с
подтверждением; карточка не меняет свою разметку; отмена возвращает к карточке;
без JS — страница подтверждения по адресу.

# Часть G. Предусловие стенда: шрифты для браузера

Приложенный `setup-playwright.sh` ставит браузер и библиотеки, но не ставит
шрифты и конфиг fontconfig. Его probe проходит, потому что не рисует текст, а
первая настоящая страница роняет Chromium:
`FATAL ... SkFontMgr_FontConfigInterface.cpp:163] Not implemented`
(`Cannot load default config file`).

Обход, которым снято воспроизведение (только в `.agent-tools`, в репозиторий не
попал): распаковать в sysroot `fonts-dejavu-core` и `fontconfig-config`, положить
минимальный `fonts.conf` с каталогом шрифтов и экспортировать
`FONTCONFIG_FILE`/`FONTCONFIG_PATH`. Внести в скрипт отдельным мелким приказом —
иначе браузерная проверка невоспроизводима с нуля.
