## 1. Карточки

### `OI-01` — `TB-01` / этап `R6`: байты аватара в куке `auth_tmp` (**P0**)

**Что в коде.** `issueTokens()` (`src/content/user/auth.ts:209-221`) кладёт витрину профиля в запечатанный `access`:

```ts
prof: { nickname: profile?.nickname ?? null, avatarUrl: profile?.avatarUrl ?? null }
```

`avatarUrl` — это `data:image/jpeg;base64,…` (`src/content/user/profile.ts:90`), длиной до `avatarMaxBytes = 20 480` байт исходника (`src/content/user/config.ts:47`). Печать — `Iron.seal` (`gateway.server.ts:293-297`), кука — `ACCESS_COOKIE` (`gateway.server.ts:389`).

**Замер (этот день, `iron-webcrypto` с теми же параметрами, что в `gateway.server.ts`).**

| Исходник фото | `dataURL` | Кука `auth_tmp` | Отношение к лимиту `4096 B` |
|---|---|---|---|
| — (только nickname) | 0 | **371 B** | 0,09× |
| 1 КБ | 1 047 B | **1 757 B** | 0,43× |
| 2 КБ | 2 071 B | **3 123 B** | 0,76× |
| 8 КБ | 8 215 B | **11 315 B** | **2,8×** |
| 20 КБ (потолок конфига) | 20 503 B | **27 699 B** | **6,8×** |

Порог `4096 B` достигается уже на **~2,8 КБ** `dataURL`, то есть на JPEG **~2 КБ**. Дефолтный потолок конфига — 20 КБ, то есть **любой настоящий аватар ломает куку с запасом**.

**Что происходит при превышении.** Браузер молча отбрасывает `Set-Cookie` (RFC 6265 §6.1: лимит на пару имя/значение — 4096 байт) — сервер об этом не узнаёт, ошибок в логах нет. Последствия:

1. витрина `prof` не доезжает до клиента: после сохранения профиля и перезагрузки аватар не появляется (nickname появляется, если кука без фото);
2. `+layout.server.ts` при каждом SSR вызывает `resolveVault(event)`, а тот «бесшовно выпускает новую пару» при отсутствии живого `access` → **каждый документный ответ несёт `Set-Cookie` на 27 КБ, который браузер тут же выбрасывает** (лишние ~27 КБ на запрос, включая префетчи и навигации);
3. при выключенном JS пользователь видит старое состояние профиля после «успешного» сохранения — форма отчиталась, а данных нет.

`renewal` (долгоживущая кука) маленькая и продолжает работать, поэтому «вход вообще не работает» — не про этот сценарий; ломается именно витрина профиля и вес ответов.

> **Решение (2026-10-24, владелец):** аватар из куки **вырезается**. Пока нет
> `lib/storage`, витрина профиля собирается в RAM при обновлении временного
> токена (`issueTokens`/`freshAccess` читают `profiles.get`), а `avatarUrl` в
> `prof` не возвращается. Памятка продублирована в коде —
> `src/content/user/auth.ts`, шапка модуля («ПАМЯТКА ДЛЯ `lib/storage`»).
> Осталось выбрать, куда картинка уезжает из RAM: см. вопрос Q1 ниже.

**Как проверить самому.** Открыть DevTools → Application → Cookies, сохранить профиль с фото 10–20 КБ: `auth_tmp` в списке не появится (или останется прежним), в консоли — предупреждение браузера вида «Cookie 'auth_tmp' has been rejected because it is too large». Серверная проверка — скрипт замера из таблицы выше.

**Варианты.**

| # | Решение | Плюсы | Минусы |
|---|---|---|---|
| A | В `prof` остаётся только `nickname` + компактный `avatarId` (короткий id/ревизия); изображение отдаёт кэшируемый `GET /api/user/avatar/<id>` | кука ~371 Б, аватар кэшируется браузером и CDN, вес ответов падает | нужен маршрут, ETag/`Cache-Control`, инвалидация при смене фото, `vault` учится собирать URL |
| B | Подписанный короткий токен вместо id (`HMAC(id, rev)`), отдавать тем же роутом | не нужен доступ к БД на чтение аватара | тот же объём работы, что A, плюс крипто-клеймо |
| C | Из куки убрать `avatarUrl` совсем; профиль всегда читать из БД в `load` | минимум кода | лишний запрос к БД на каждый SSR-документ (сейчас витрина бесплатна) |
| D | Оставить как есть, урезать `avatarMaxBytes` до ~1,5 КБ | одна строка конфига | фото 200×200 в 1,5 КБ — мыло; проблема не решена, а замаскирована |

**Рекомендация:** A (+ `Cache-Control: private, max-age`, ETag по ревизии, `404` → заглушка). Пункт `R6` из `image-transfer.md` описывает ровно это; `C` — если хочется «сначала просто починить».

### `OI-02` — `TB-04`: неатомарный `challenge.consume()` (**P1**)

**Что в коде.** `src/content/user/gateway.server.ts:277-282`:

```ts
async consume(nonce) {
  const k = `nonce:${nonce}`
  const had = await store.get<boolean>(k)
  await store.delete(k)
  return had === true
}
```

**Почему плохо.** Два параллельных запроса с одним `nonce` (двойная отправка формы, ретрай браузера, два инстанса) оба увидят `had === true` → одноразовый `challenge` принимается дважды. `localStore` — ещё и на процесс: при двух инстансах второй вообще не знает про nonce первого (тогда второй получит отказ — это безопасно, но ломает UX: «ссылка истекла» через балансировщик).

**Варианты.** A — расширить `ChallengePort` методом `take(nonce): Promise<boolean>` и реализовать в `sharedStore` (`cache_kv`) атомарным удалением с возвратом значения; B — оставить `consume`, но требовать от адаптера атомарности в документации; C — не чинить (single-instance), записать ограничение.

**Рекомендация:** A. Интерфейс порта уже минимальный, меняется одна строка реализации; для `localStore` — синхронная реализация (в JS однопоточно, атомарно по факту).

### `OI-03` — `TB-05` (часть 2): `secure: false` у всех кук (**P1**)

**Что в коде.** `src/content/user/gateway.server.ts:52`:

```ts
const COOKIE_BASE = { path: '/', httpOnly: true, sameSite: 'lax', secure: false } as const
```

**Почему плохо.** `Secure` не выставляется никогда: за HTTPS-прокси кука всё равно уходит и по `http://` (даунгрейд, случайный `http`-редирект, подмена ссылки) — сессия утекает открытым текстом. Сейчас это «работает» только потому, что весь деплой — localhost без TLS.

**Варианты.** A — `secure: event.url.protocol === 'https:'` (учитывает `ORIGIN`/`PROTOCOL_HEADER` от адаптера); B — env-флаг `COOKIE_SECURE=auto|true|false` (управляемо, но добавляет конфиг); C — `secure: true` всегда (ломает `http://localhost` и превью).

**Рекомендация:** A как поведение по умолчанию + B как явный override. В `vite.config.ts` уже есть доверенные источники (`src/server/trusted-origins.ts`), `X-Forwarded-Proto` брать только оттуда.

### `OI-04` — `TB-06` (часть 2): тело POST буферизуется по максимуму реестра (**P1**)

**Что в коде.** `src/hooks/component-form/server.server.ts:47-55` считает **максимум по всем зарегистрированным формам**, `:162-166` — читает им всё тело:

```ts
function maxRegisteredBytes(): number {
  let max = DEFAULT_LIMITS.maxBytes           // 2 МиБ
  for (const reg of componentFormRegistry().values()) {
    const candidate = reg.limits?.maxBytes
    if (typeof candidate === 'number' && candidate > max) max = candidate
  }
  return max
}
```

**Замер.** Самая тяжёлая регистрация — профиль: `PHOTO_RAW_MAX_BYTES (8 МиБ) + 256 КиБ` (`profile.form.server.ts:32`), значит `maxRegisteredBytes() = 8 650 752 Б`. `peekFormDataBounded()` дополнительно делает `request.clone()` — поток tee-ится, и дочитанное до конца висит в буфере второй ветви, пока его не вычитают или не соберёт GC.

**Почему плохо.** Область шире, чем кажется: хук проверяет только метод и content-type (`server.server.ts:155`, `isFormBody`), а не маршрут и не регистрацию. Значит тело читается целиком до маршрутизации для **любого POST с `application/x-www-form-urlencoded` или `multipart/form-data`** — включая запросы к маршрутам, где встраиваемых форм нет вовсе. JSON-POST и прочие типы не задеваются. Цена: память до 8,25 МиБ на запрос (плюс столько же в tee-ветви `clone()`), латентность «дочитать, потом отдать». 50 одновременных загрузок — сотни мегабайт в 2 ГиБ контейнере без swap.

**Варианты.**

| # | Решение | Плюсы | Минусы |
|---|---|---|---|
| A | Читать только префикс (например 64 КиБ) и искать `__form_id` в нём; не нашли — пропускаем запрос дальше, не буферизуя | независимость от размера, работает без JS | ломается, если конверт окажется позже 64 КиБ (наш рендерер ставит скрытые поля первыми — но это надо закрепить тестом) |
| B | `__form_id` в query (`action="/path?__form_id=…"`), тело не трогаем | работает и без JS, нулевая буферизация | id в URL (логи, история), конфликт с `?step=`/поиском маршрута |
| C | Регистрация объявляет префикс пути; хук сравнивает `event.url.pathname` и берёт лимит конкретной формы | просто и предсказуемо | дублирование знания о маршрутах в регистрации |
| D | Оставить как есть, записать ограничение | ноль работы | 8,25 МиБ на любой POST остаются |

| **SvelteKit form actions** | дискриминатор действия — в адресе (`?/actionName`), тело читается `request.formData()` без своего предела | — | прецедент варианта B: id в адресе снимает необходимость читать тело заранее |

**Решение (2026-10-24, владелец): вариант A** — читать префикс, а не тело.

**План реализации A (что обязательно учесть).**

1. Предел префикса — `64 KiB`; читать только его и **отменять** ветвь `clone()` сразу после решения (иначе tee продолжит копить остаток).
2. Конверт искать **сканером байтов**, а не `formData()`: обрезанный multipart не парсится. Два вида: `__form_id=<value>&` в urlencoded и `name="__form_id"` + `\r\n\r\n<value>\r\n` в multipart.
3. `Content-Length` — только для раннего отказа; байты всё равно считать самому (урок CVE Hono).
4. Конверт не найден в префиксе, но content-type — форма: отвечать `400` с кодом `form.envelope-missing`, а не отдавать запрос маршруту (иначе получим невнятный `405`). Закрепить тестом «рендерер ставит скрытые поля первыми».
5. После распознавания формы тело дальше читает `bodyLayer` с пределом **конкретной** формы — это уже работает.
6. Не испортить `too-large`: если `Content-Length` больше предела **всех** форм, ранний `413` остаётся.

**Рекомендация:** A (с тестом «конверт в первых 64 КиБ»), B — если готовы поменять провод (это разово и на обе ветки: JS-транспорт и нативный POST). C годится как временная мера.

### `OI-05` — `TB-08`: удаление аватара без подтверждения и без отмены (**P2**)

**Что в коде.** `ProfileForm.svelte:145-153`: при гидрации чекбокс `remove_avatar` прячется в `<div hidden>`, решение принимает `AvatarTakeover`. Плашки «текущее фото будет удалено — Отменить» нет; отменить можно только выбрав новый файл или закрыв страницу без сохранения (до отправки ничего не удаляется).

**Почему плохо.** Удаление необратимо и происходит «молча» в момент сохранения: пользователь нажал крестик, пролистал вниз, сохранил форму из-за правки nickname — фото ушло. Восстановить можно только повторной загрузкой (прежних байт нет).

**Варианты.** A — плашка с `Отменить` (клиентское состояние: снятие крестика возвращает прежний URL), без изменения сервера; B — мягкое удаление с корзиной на N дней (нужно где-то хранить байты — конфликтует с `OI-01`); C — подтверждение в момент submit (`confirm()`/второй шаг).

**Рекомендация:** A. Это ровно то, что просит `TB-08`, и это не требует серверных изменений.

> **Решение (2026-10-24, владелец):**
> - **без JS** — уже работает и менять нечего: `remove_avatar` рендерится обычным чекбоксом, снятие галочки и есть отмена.
> - **с JS** — карточка не должна исчезать. Правка в композициях, а не в `Attachment` (он только рисует сниппет `actions`): в `AvatarTakeover.svelte:138-145` кнопка «Удалить текущее фото» переключается на «Восстановить» (`aria-label`, `title`, иконка × → ↺), сама карточка остаётся с меткой «будет удалено» (приглушение + подпись), `remove_avatar` держится `true` до отправки; повторное нажатие снимает метку. То же для новых файлов в `FileAttachment.svelte:180-195`: `removeAt` → `markRemoved` + `restoreAt`.
> - сервер не меняется: удаление по-прежнему применяется только при `remove_avatar` в теле.

### `OI-27` — пределы приёма: raw принадлежит серверу, проверки — валидаторам (**P1, решение 2026-10-24**)

**Решение владельца, дословно по смыслу.** `raw` — это опция **сервера**, а не приложения: если сервер разрешает тело до 8 МБ, приложение не диктует ему свои условия. Пока raw не загружен, понять, что внутри, невозможно — разве что файл всегда идёт последним, а поля впереди. Вес и тип файла — дело валидаторов.

**Что сегодня не так (проверено).**

| Факт | Где | Вывод |
|---|---|---|
| приложение **само** задаёт пределы приёма на форму | `profile.form.server.ts:32` → `limits: { maxBytes: PHOTO_RAW_MAX_BYTES + 256 КиБ }`; `fields.form.server.ts:62` → `limits: { maxFileSize: IMAGE_MAX_BYTES }` | ровно то, чего быть не должно: настройка инфраструктуры задаётся приложением |
| `Limits` применяются пер-регистрация | `server.server.ts:206` → `createFormHandler({ limits })` (`server.ts:527,582`) | механизм есть, но используется не по назначению |
| умолчания противоречивы | `DEFAULT_LIMITS` (`server.ts:36-39`): `maxBytes: 2 МиБ`, `maxFileSize: 8 МиБ` | предел на файл **выше** предела тела → при дефолтах `file.too-large` недостижим, его всегда опережает `body.too-large` (мёртвая ветка) |
| `maxFileSize` / `maxValuesPerKey` дублируют валидаторы | `server.ts:118-124` против `v.maxSize` / `v.maxCount` | после перевода на валидаторы удаляются |

**Целевое устройство.**

| Что | Владелец | Как задаётся |
|---|---|---|
| предел raw (тело запроса) | **сервер** (деплой/адаптер) | одно место конфигурации, приложение не переопределяет |
| вес одного файла | валидатор `v.maxSize(N)`, **ограниченный серверным raw** | данные в описании, потолок — из `Limits` |
| число файлов | валидатор `v.maxCount(N)` | данные в описании |
| тип файла | валидатор `v.accept([...])` | данные в описании |
| содержимое | асинхронная проверка сигнатур в реестре проверок | валидатор, не серверный слой |
| запас raw на «накладные» (multipart-границы, имена, текст других полей) | **UI-опция** (см. `OI-28`) | только в браузере, потому что только там видно остальные значения |

**Валидатор веса читает лимит сервера (уточнение владельца).** `v.maxSize` не может разрешить больше, чем принимает сервер: действующий предел = `min(N, raw − reserve)`. Если разработчик попросит гигабайты, валидатор всё равно срежется серверным raw; для запаса из максимума можно вычесть резерв (например 1 МБ) на накладные и текст остальных полей. `v.maxSize()` без аргумента означает «сколько позволяет сервер».

**Что для этого нужно в коде (сегодня нет):**

1. `FieldContext` (`validators.ts:23-30`) содержит только `path`, `values`, `constraints` — **лимитов там нет**; добавить `limits` (или `rawLimit`).
2. Клиент должен получить серверный raw: значение из `Limits` попадает в описание формы или в передаваемые данные, иначе браузер не сможет ни проверить, ни посчитать бюджет (`OI-28`).
3. `v.maxSize(N)` остаётся данными (`{ kind: 'maxSize', bytes }`), ограждение делает рантайм валидации: `effective = min(bytes, raw − reserve)`. В описании видно намерение, потолок диктует сервер.

**Тип проверяется по медиатипу, содержимое не сниффится (решение владельца).** `v.accept` сравнивает `File.type` — заявленный клиентом MIME — по правилам атрибута: `type/*` — префикс подтипа, иначе точное совпадение; расширение — только для токенов вида `.ext` (`validators.ts:212-218`). Отдельной проверки магических байтов не будет. Следствие записано осознанно: файл с подставленным MIME пройдёт; защита строится на том, что сервер не исполняет содержимое, а не на разборе заголовков.

**Удаляется:** `Limits.maxFileSize`, `Limits.maxValuesPerKey`. **Остаётся:** `Limits.maxBytes` (теперь как серверная настройка), `maxKeys`, `timeoutMs`.

**Связь с порядком полей.** Если файл объявлен **последним**, сервер может разобрать префикс (остальные поля) и узнать описание — это уже используется в `OI-04` (префикс 64 КиБ + сканер конверта). Наш кодировщик пишет поля в порядке описания (`decode.ts:44-53`), значит порядок «файл последним» достижим; при нативной отправке без JS порядок задаёт разметка.

### `OI-28` — динамический бюджет загрузки в UI (**P2, новое, 2026-10-24**)

**Идея (владелец).** Зная серверный лимит raw и вес остальной нагрузки (текстовые поля, служебные ключи, накладные multipart), можно **вычислить**, сколько остаётся на файл: `fileMax = raw − overhead − payload`. Считать это может только браузер (у него есть все значения и размеры), поэтому это **не валидатор, а UI-опция**, работающая **дополнительно** к валидатору веса.

**Почему нельзя валидатором:** сервер видит только уже принятые байты; «сколько было в остальных полях» он узнаёт лишь по факту разбора, то есть после того, как предел raw пришлось применить. Плюс `FormData` не отдаёт размер «остального» без обхода значений.

**Что нужно от реализации:**

1. опция поля `budget` (в UI-слое, рядом с опцией сжатия `OI-06`), принимает серверный `raw` и запас `overhead`;
2. в браузере на `change`/`input`: `payload = СУММА(Blob.size) + ТЕКСТ(длина текстовых значений) + overhead`; при `payload > raw` — файл не принимается, сообщение под полем;
3. вычисленный `fileMax` показывается пользователю как предел («до N МБ»), а не как ошибка после отправки;
4. при `multiple` бюджет общий на все файлы (`OI-25` — ошибки скопом);
5. без JS опции нет: там работает только `v.maxSize`, а излишек ловит серверный `body.too-large` (`413`).

### `OI-29` — no-JS: обрезка raw, порядок частей и «файл в конце» (**P2, новое, 2026-10-24**)

**Требование владельца.** Без JS заранее отклонить тяжёлый файл нельзя. Значит: текст доезжает, файл обрезается — и **у файла должна быть ошибка «тяжёлый»**, а не отказ всей формы.

**Что сегодня (проверено).**

| Шаг | Код | Факт |
|---|---|---|
| объявленная длина | `server.ts:107-108` | `content-length > maxBytes` → `413 body.too-large` до чтения |
| поток | `metered()` (`server.ts:129-143`) | счётчик; при превышении `controller.error` → поток рвётся |
| разбор | `server.ts:110-112` | `formData()` на оборванном теле бросает → `catch → reject(413, 'body.too-large')` |
| итог | — | **вся форма отказом, ни одного поля не доезжает, ошибки по файлу нет** — ровно противоположное требованию |

**Можно ли достоверно сказать, что raw обрезан?** Да, тремя независимыми признаками:

1. счётчик `metered` пересёк предел — это уже есть;
2. объявленный `content-length` больше фактически принятого;
3. **закрывающая граница multipart `--boundary--` не встречена до конца потока** — это доказательство неполноты тела, а не догадка.

#### Зачем нужен сканер границ (уточнение 2026-10-24)

Не для того, чтобы «получить обрезанный raw» — raw и так обрезан, и его байты бесполезны. Причина в другом: **`request.formData()` атомарен** — он либо разбирает тело целиком, либо бросает исключение, и тогда теряется всё: и уже пришедший текст, и имена файлов, и сведения о том, на чём оборвалось. Именно поэтому сегодня обрезка превращается в `413` на всю форму.

Сканер даёт три вещи:

| Что | Зачем |
|---|---|
| части, пришедшие **до** обрыва, остаются пригодными | текстовые поля декодируются и валидируются как обычно — «текст доехал» |
| известно, **какая часть была открыта** в момент обрыва | виновник назван по имени: ошибка вешается на конкретный файл, а не на форму |
| отсутствие закрывающей границы `--boundary--` | положительное доказательство обрезки, а не догадка по размеру |

Чего сканер **не** делает: не хранит байты обрезанного файла (они не нужны), не копит тело целиком (предел тот же `raw`), не проверяет содержимое и не заменяет валидаторы.

**Альтернатива без сканера** — оставить `formData()` и честно отвечать `413` на всю форму. Это ровно текущее поведение; сканер покупает только «текст доехал + виновник назван».

#### Готовый парсер вместо своего сканера (решение 2026-10-25)

Свой сканер границ **отклонён**: разбор multipart — задача с готовыми решениями, а самописный код пришлось бы отдельно испытывать на граничных случаях (граница внутри данных части, `\r\n` на стыке чанков, недописанный заголовок, `filename*`). Берём зависимость.

**Сравнение кандидатов** (данные реестра npm на 2026-10-25):

| Пакет | Версия | Лицензия | Зависимости | Объём | Публикация | Вердикт |
|---|---|---|---|---|---|---|
| `@remix-run/multipart-parser` | 1.1.0 | MIT | `@remix-run/headers` | 159.2 KiB, 43 файла | 2026-10-23 | **выбран** |
| `@mjackson/multipart-parser` | 0.10.1 | MIT | `@mjackson/headers` | 779.6 KiB, 32 файла | 2025-06-13 | репозиторий архивирован; нет `maxTotalSize` |
| `@mjackson/form-data-parser` | 0.9.1 | MIT | `@mjackson/multipart-parser` | 387.8 KiB, 13 файлов | 2025-06-13 | обёртка над архивированным пакетом |
| `busboy` | — | — | — | — | — | только Node-стримы, не Web Streams — не портируем |

**Почему `@remix-run/multipart-parser`:**

- активен (публикация за два дня до решения), MIT, ровно одна зависимость;
- Web Streams (`Request`, `ReadableStream`) — Node, Deno, Bun, Cloudflare Workers; `node:*` только в необязательном подпути `./node`, основной вход чистый;
- лимиты ложатся на наши `Limits`: `maxFileSize`, `maxParts`, `maxTotalSize`, `maxHeaderSize`;
- ошибки различимы через `instanceof`: `MultipartParseError`, `MaxFileSizeExceededError`, `MaxPartsExceededError`, `MaxTotalSizeExceededError`, `MaxHeaderSizeExceededError` — сводятся к нашим кодам, а не к отказу всей формы;
- у части есть `name`, `filename`, `mediaType`, `isFile`, `bytes`/`text` — виновник определяется по имени части.

**Проверено запуском, не по документации.** Тело: текстовая часть `title`, затем файл 50 000 Б.

| Сценарий | Результат |
|---|---|
| полное тело | обе части: `title` = 12 Б, файл = 50 000 Б |
| тело обрезано на 40 % | `MultipartParseError` «Multipart stream not finished»; **`title` получен целиком**, обрыв — на файле |
| `maxTotalSize = 10 000` | `MaxTotalSizeExceededError`; `title` получен, обрыв на файле |
| `maxFileSize = 5 000` | `MaxFileSizeExceededError` (`instanceof` срабатывает), `title` получен |

Это ровно то, чего не умеет `formData()`: **части до обрыва остаются пригодными**, виновная часть известна по имени. Известный баг `multipasta` (часть не закрывается при агрегатном лимите, поток висит) здесь не воспроизводится — при `maxTotalSize` поток завершается ошибкой.

**Стриминговый вход `@remix-run/multipart-parser/future`.** Часть отдаёт `body` как `ReadableStream` и `bodyUsed`, а имя части известно **до** чтения содержимого — файл не приходится держать в памяти дважды. Требует `Promise.withResolvers` (Node ≥ 22), но проект и так требует `node >= 22.17` (`package.json:13-14`) — ограничение не новое. Основной вход работает и на Node 20, буферизуя часть целиком, — при `raw` в единицы МиБ этого достаточно; выбор входа не блокирует реализацию.

**Выбор владельца (2026-10-25):** пакет — `@remix-run/multipart-parser`, вход — **основной**, не `/future`. Установка **отложена** («первый вариант, но не сейчас»): до отдельной команды пакет не ставится, `server.ts:110-112` остаётся на `formData()`, поведение не меняется. Пакетный менеджер и место в `package.json` — по той же команде.

**Границы встраивания:**

| Правило | Причина |
|---|---|
| только `*.server.ts` внутри `src/lib/form` | `LIB-PORTABILITY`: серверная зависимость не попадает в клиентский граф `src/lib/*` |
| клиентский бандл не меняется | импорт живёт в `src/lib/form/server.ts`, бюджеты (raw 354 200 / gzip 102 200) остаются прежними |
| заменяет `formData()` в `server.ts:110-112` | `metered()` (`server.ts:129-143`) остаётся: он стережёт `raw` и не даёт прочитать лишнее |
| `Limits` → опции парсера | `maxFileSize` ← `raw`, `maxParts` ← `maxKeys` + запас на файлы, `maxTotalSize` ← `raw`, `maxHeaderSize` ← 8 KiB по умолчанию |
| ошибки → наши коды | `MaxFileSizeExceededError` → `file.too-large` **на часть**; `MultipartParseError` «not finished» → `body.truncated`; `MaxPartsExceededError` → `body.too-many-parts` |

**Следствие для `OI-27`.** `maxFileSize` возвращается — но не как настройка приложения, а как **серверный предохранитель** внутри `raw`: один файл не может занять больше, чем `raw` минус запас на текст. Приложение по-прежнему не задаёт `limits`; то, что видит пользователь, — валидаторы веса (`v.maxSize`).

#### Примитив `file`: label и input раздельно (решение владельца, 2026-10-25)

`FileAttachment` **наследует примитив `file`**, а примитив состоит из двух отдельных элементов: `Label` (`src/components/ui/label/Label.svelte`, принимает `for`) и нативного `<input type="file">` (`src/components/ui/file-input/FileInput.svelte`), связанных `for`/`id`.

- `FileAttachment` рисует **label** (видимая область выбора) и список; сам `<input>` может стоять в другом месте DOM — например, в конце формы.
- Список, удаление и действия берут input **по id из label** (`label.htmlFor` → узел по id), а не по `ref`.
- id приходит от поля: `FieldView.attrs.id` (`bind.svelte.ts:673`) — тот же id, на который уже указывает подпись поля (`labelProps() → { for: id }`, `bind.svelte.ts:695`).

Что это меняет в нынешнем коде:

| Сейчас | Станет |
|---|---|
| `FileAttachment` держит `inputEl` и пишет в него: `inputEl.files = dt.files`, `inputEl.value = ''`, затем `dispatchEvent('change')` (`:141-151`) | те же операции над узлом, найденным по `htmlFor`; `ref` остаётся необязательным быстрым путём |
| `<FileInput>` рендерится **внутри** `FileAttachment` (`:174-190`) | input рендерит тот, кто знает его место; `FileAttachment` получает id и рендерит label |
| `bind:files` связывает input и список в дереве компонентов | `bind:files` не пересекает DOM: состояние идёт через `FieldView.onInput`/`files` |
| `change` слушается на собственном `<FileInput>` | `change` слушается на найденном узле |

**Открытый вопрос (нужно решение владельца).** `FieldShell` уже рисует подпись поля с `for={id}`. Второй `label` на тот же input легален, но доступное имя склеится («Выберите файл, Аватар»). Значит либо область выбора рисуется **без имени** (и имя даёт только подпись поля), либо подпись поля убирается и имя даёт label области.

#### Порядок частей — вот где ловушка

| Путь | Порядок | Кто задаёт |
|---|---|---|
| нативная отправка (без JS) | **порядок элементов в DOM** (спецификация форм: entry list строится обходом дерева) | разметка |
| наш `encode()` (`decode.ts:44-53`) | порядок полей **в описании** | `d.fields` |

Значит **без JS** файл, объявленный в разметке первым, уносит с собой всё, что после: `title`, тексты, служебные ключи — при обрезке они не доедут. С JS этого не случится: `encode` пишет поля в порядке описания, и файлы можно отсортировать в конец **уже сейчас** (правка на несколько строк).

**Предложение владельца — «невидимый файловый input в конце, пользователь видит label» — рабочее.** Что для этого есть и чего не хватает:

| Часть | Состояние |
|---|---|
| `label` указывает на input по id | **есть**: `FieldShell` рендерит `Label {...f.labelProps()}`, а `labelProps()` возвращает `{ for: id }` (`bind.svelte.ts:115,695`) |
| визуально скрыть input, оставив его доступным | **есть** утилита `sr-only`, уже используется (`Fieldset.svelte:31`, `SelectList.svelte:408`, `Spinner.svelte:46`) |
| держать `Attachment`-список на месте поля | **есть**: список читает состояние поля, а не соседство с input |
| вынести input в конец формы | **нет**: `FileField` рендерит input внутри `FieldShell` (`FileField.svelte:24-30`); нужен слот «хвостовых полей» на уровне формы |
| `aria-describedby` | не ломается: id подсказки/ошибки глобальны |

**Обязательные оговорки при реализации:**

- скрывать только `sr-only`, **не** `display:none`/`hidden`: иначе input недоступен с клавиатуры и не читается экранным диктором;
- порядок табуляции меняется — input уедет в конец формы; это осознанный компромисс, но его надо проверить клавиатурой;
- кликабельной остаётся область label; перетаскивание файла на список тоже должно открывать выбор.

**Что это даёт:** при обрезке все текстовые поля доезжают, обрезанной оказывается последняя часть — файл; сервер помечает **именно её** ошибкой (`file.too-large` / `body.truncated`), форма возвращается с ошибкой у поля и `outcome: 'not-applied'`. Ровно то поведение, что заявлено.

### `OI-08` — `TB-12`: пустой `nickname` нельзя очистить (**P2**)

**Что в коде.** `profile.form.server.ts:46` — `String(values.nickname ?? '').trim()`, `:71` — `...(nickname ? { nickname } : {})`. Пустая строка не попадает в патч, то есть означает «не менять»; стереть nickname (сделать `null`) через форму невозможно.

**Почему это спорно, а не просто баг.** В форме нет способа отличить «поле не трогали» от «поле очистили»: браузер всегда отправляет `nickname=""`. Варианты семантики:

| # | Решение | Что видит пользователь | Последствия |
|---|---|---|---|
| A | `''` = очистка (`null`), «не менять» = отсутствие ключа (в HTML это `disabled`/чекбокс «не менять») | очистил — стёрлось | нужен явный механизм «не менять», иначе любая форма без поля сотрёт nickname |
| B | Отдельный чекбокс/кнопка «Убрать имя» (`clear_nickname`) | явное действие | +1 поле в описании формы, зато семантика однозначна |
| C | Пустой запрещён валидатором (`v.required`) | нельзя сохранить без имени | противоречит «можно заполнить потом» (`ProfileForm.svelte:140`) |

**Рекомендация:** B — единственный вариант, где «не менять» и «очистить» различимы без догадок, и он же понадобится для будущей очистки любого необязательного поля.

> **Решение (2026-10-24, владелец): вариант A — `''` = очистка.** Форма редактирования всегда отображает и отправляет текущие значения, поэтому «пустая строка = не менять» — неверная семантика: чтобы стереть имя, его надо специально удалить в поле, а «не менять» в такой форме недостижимо по определению. Правка серверная и одна: в `profile.form.server.ts:71` вместо `...(nickname ? { nickname } : {})` — `{ nickname: nickname === '' ? null : nickname }`. Чекбокс (вариант B) не нужен.

### `OI-09` — `TB-13`: «spread теряет геттеры `RequestEvent`» (**P2**, предпосылка опровергнута)

**Что в коде.** `src/hooks/component-form/server.server.ts:111-115`:

```ts
const rendered = await resolve({
  ...event,
  request: new Request(event.url, { method: 'GET', headers: getHeaders }),
})
```

**Что проверил.** SvelteKit **3.0.1**, `node_modules/@sveltejs/kit/src/runtime/server/respond.js`:

- `:194-241` — `const event = { cookies, fetch: null, getClientAddress, locals, params, platform, request, route, setHeaders, url, isDataRequest, isSubRequest }` — **литерал, все поля собственные и перечисляемые**, геттеров в прототипе нет;
- `:246` — `event.fetch = create_fetch({...})` — присваивание, тоже собственное поле;
- `:378,380` — `event.route = { id }` и `event.params = result.params` — присваивания **на том объекте, который передан в `resolve`**, то есть на нашей копии.

Значит: spread копирует все поля по ссылке (`locals`, `cookies` — те же объекты, `setHeaders` пишет в тот же `headers`), а маршрутизация внутри `resolve` проставляет `params`/`route` уже копии. **Потери полей и «мёртвых» геттеров на текущей версии нет.**

**Что остаётся риском.** Это следствие реализации, а не контракта: если SvelteKit переедет на класс с геттерами, spread начнёт терять поля молча. Поэтому предлагаю не «чинить» код, а **закрыть `TB-13` на основании замера и закрепить поведение регресс-тестом**: собрать фейковый `RequestEvent` с `params`/`route`, прогнать через `renderInlineWithResult` и проверить, что отрендеренный маршрут видит свои `params` и `url`.

**Варианты.** A — закрыть `TB-13` + регресс-тест (рекомендую); B — на всякий случай переписать на `Object.assign(Object.create(Object.getPrototypeOf(event)), event, { request })` (нулевая польза сейчас, +код); C — оставить открытым до мажора SvelteKit.

> **Решение (2026-10-24, владелец):** бага нет — фиксируем вариант A. `TB-13` закрывается по замеру, к нему добавляется регресс-тест: фейковый `RequestEvent` с `params`/`route` → `renderInlineWithResult` → страница видит свои `params` и `url`, а выставленные внутри рендера куки доезжают до ответа. Тест ловит будущий переход SvelteKit на геттеры.
