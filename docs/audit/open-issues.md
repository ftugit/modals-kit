### `OI-22` — гибридное поле файлов: превью, компактный ряд, прогресс (**P2**)

**Ожидание:** для `field.files` работает гибридное поле, где видны все выбранные файлы; среди них фото получают браузерное превью, остальные — иконки; компактный режим — один ряд со скроллом; прогресс бара нет, потому что метод фреймворка не даёт.

**Сейчас:**

| Часть | Факт |
|---|---|
| показ выбранных | есть — `FileAttachment` (`src/components/ui/file-attachment/FileAttachment.svelte`) рисует `<ul data-file-list>` из `pickedFiles` |
| превью фото у файлов | есть — `Attachment` в режиме `media: 'auto'` создаёт `URL.createObjectURL(File)` (`Attachment.svelte:158-172`), вид определяется по MIME (`model.ts:215`: `mime.startsWith('image/') → 'image'`), остальные → иконка `ATTACHMENT_KIND_LABELS` |
| компактный ряд со скроллом | **нет** — раскладок всего две: `'row'` → `flex flex-col gap-2`, `'tile'` → `flex flex-wrap gap-2.5` (`FileAttachment.svelte:155-157`, тип `model.ts:11`). Горизонтального ряда с `overflow-x` нет: и список, и плитка переносятся/складываются |
| прогресс в UI | **готов, но не подключён** — `Attachment` принимает `progress` и `progressVariant` и рисует `role="progressbar"` (`Attachment.svelte:57,102,458-465`), `FileField` эти пропсы не передаёт и `itemProps` не использует |
| прогресс загрузки | **физически недоступен на текущем транспорте**: отправка идёт `fetch` (`src/hooks/component-form/transport.ts`), а у `fetch` нет событий прогресса **отправки** (`upload.onprogress` есть только у `XMLHttpRequest`). Тот `report`, что есть (`bind.svelte.ts:788-790`, `transport.ts:41,136`), — это строки стрима **ответа** сервера (`fetchWithTask`/`readTaskStream`, `src/lib/fetch/stream.ts`), то есть прогресс серверной задачи, а не загрузки тела |

**Уточнение по формулировке:** «метод фреймворка не даёт» — верно по факту, но причина не в SvelteKit: тело уходит через `fetch`, у которого нет прогресса отправки. Варианты, если прогресс нужен: (а) `XMLHttpRequest` в транспорте — только для загрузок, с сохранением текущего контракта `Transport`; (б) условная загрузка кусками (`Content-Range`/chunked) с прогрессом по частям; (в) оставить без прогресса, но задействовать индетерминантное состояние `state: 'uploading'` (`Spinner` уже есть, `Attachment.svelte:341`).

### `OI-25` — ошибки по файлам скопом, а не по одной (**P2**)

**Решение владельца (2026-10-25):** ошибка поля идёт **строкой на файл** — «Файл a.pdf больше 512 КБ», «Файл b.zip не подходит по типу». Сколько проблемных файлов, столько строк; строки различаются `params.name`. В JS их показывает клиент, без JS те же строки возвращает сервер.

**Сейчас:** правила возвращают **первую** ошибку: `v.accept` — `filesOf(value).find(f => !types.some(...))` (`validators.ts:352-362`), `v.maxSize` — так же (`:364-372`); проверка содержимого `checkPhotoFile` возвращает один `Issue` (`photo.ts:93-115`). `FieldShell` показывает первую ошибку и список остальных **ошибок правил** (`FieldShell.svelte:55-60`), но не «по файлу».

**Расхождение:** нужно по `Issue` на файл, а правила отдают первую. При пяти плохих файлах пользователь видит одну строку про первый — вместо пяти про каждый. Повтор шаблона в списке ожидаем: это разные файлы, а не дубли.

**Что править:** правила для множественных значений должны отдавать по `Issue` на каждый проблемный файл (с `params.name`), а `FieldShell`/`FileAttachment` — раскладывать их рядом с карточкой файла (`itemProps.error` у `FileAttachment` для этого уже есть, `FileAttachment.svelte:29-45`).

**Ожидание:** можно выбрать файлы из разных папок (несколько заходов в диалог), а убрать файл можно только через `Attachment`.

### `OI-30` — аватар описан в двух местах: UI и сервер (**P2**)

**Что в коде.** Рамки аватара заданы дважды. Сервер: `readUserChecksSnapshot()` читает из конфига `avatarEdge`/`avatarMaxBytes` (`profile.form.server.ts:20-27`), входные форматы — `SHORT_PHOTO_FORMATS` из `SERVER_PHOTO_FORMATS` (`:18`), описание поля — `form.ts:29-37` (`field.photo`, `v.accept`, `v.maxSize`, `photoImage`). Экран: `ProfileForm.svelte:7-8` берёт `defaults.avatarEdge`/`defaults.avatarMaxBytes`, `AvatarTakeover.svelte:126` подставляет `accept={SERVER_PHOTO_FORMATS.join(',')}`, а конвейер `prepareAvatar` (`avatar.ts`) держит вторую копию правил `edge`/`maxBytes`.

**Почему это работа, а не вопрос.** Владелец (2026-10-25): аватар — **не сущность**. Файл грузится по общим валидаторам, в JS приводится к нужному весу конвертером, на сервере — тоже. Описание должно быть одно и читаться обеими сторонами.

**Что править.** `SpecAvatar` в `src/content/user/spec-avatar.ts` — обычный `.ts` (его импортируют и серверный обработчик, и экран). Это **набор параметров, а не функция и не описание поля**:

| Параметр | Значение | Смысл |
|---|---|---|
| `width`, `height` | 200 × 200 | размеры готового аватара, px |
| `maxBytes` | 20 480 | вес готового файла, байт |
| `format` | `jpeg` | конечное расширение |

В спеке нет `raw`, резервов, входных форматов и валидаторов: `raw` — работа транспорта, форматы входа — работа валидаторов страницы (`v.accept([...])`). Значения дают конфиг-ключи `avatarEdge`/`avatarMaxBytes` (`config.ts:45,47`); спека — единственный источник: сервер отдаёт её загруженной странице, страница — файловому полю (`<Field of={f.avatar} preview photoConvert={SpecAvatar} />`), обработчик читает те же параметры.

**Как выглядит редактирование профиля.** Поле ника и его валидаторы; поле файла (одно) и его валидаторы — фото-типы, `v.maxSize(30 МиБ)`; фактический предел всё равно 7 МиБ из встроенной защиты файлового поля (`OI-31`). UI-поле получает из спеки размеры, желаемый вес и формат. Сервер: повторная проверка формы теми же валидаторами; поиск среди загруженных именно фото (по медиатипу); файл, не подходящий под спеку по размерам/весу/формату, конвертируется; результат в base64 пишется в БД.

**Что снимается.** `avatarPhotoSpec` (`checks.ts:32-46`), `SHORT_PHOTO_FORMATS` (`profile.form.server.ts:18`), `AvatarLimits` и правила `prepareAvatar` (`avatar.ts`), `field.photo(...)` (`form.ts:29-37`), `defaults` в `ProfileForm.svelte:7-8`; `AvatarTakeover` не нужен — его место занимает опция `Field` ([`../plan.md`](../plan.md) §3, `OI-06`).

**Не трогать.** `avatarFormats` остаётся: это формат **base64-хранения**, а не входа; уйдёт вместе с base64-контуром, когда `lib/storage` начнёт отдавать URL.

### `OI-31` — бюджет тела, формы и файлов (**P1**)

**Что в коде.** `v.maxSize` проверяет **каждый файл отдельно**: `filesOf(value).find((f) => f.size > max)` (`validators.ts:364-372`), соседей не суммирует; суммарного правила нет. Пять файлов по 5 МиБ проходят `v.maxSize(30 МиБ)`, а тело режет транспорт: `Limits.maxBytes` → `413 body.too-large` (`server.ts:108,135`).

**Решение владельца (2026-10-25).**
- Бюджет тела объявлен в **env** — это потолок развёртывания (Vercel 4.5 МБ, Cloudflare 100 МБ; 413 приходит от платформы до кода, `adapter-auto` + `vercel.json` + `wrangler.jsonc`).
- При создании формы бюджет можно **уменьшить** — `defineForm({ limits: { budget } })`. Значение больше env **игнорируется**: `budget = min(объявленный, env)`.
- Бюджет файлов = бюджет формы − 1 МиБ (резерв на текст; константа ядра).
- `v.maxSize(n)` — **возможность**, а не бюджет: личный предел одного файла = `min(n, бюджет файлов)`. Он вправе быть больше бюджета формы — тогда режет бюджет.

| env | `v.maxSize(n)` | бюджет файлов | один файл | все файлы вместе |
|---|---|---|---|---|
| 8 МБ | 10 МБ | 7 МиБ | 7 МиБ | 7 МиБ |
| 100 МБ | 10 МБ | 99 МиБ | 10 МБ | 99 МиБ |
| 8 МБ | 2 МБ | 7 МиБ | 2 МБ | 7 МиБ |

**Как число доезжает.** env → `limits.maxBytes` обработчика → SSR `data-budget` на `<form>` → `bind` читает атрибут (`formEl` уже есть, `bind.svelte.ts:242`) → `ctx.limits.filesBudget`. Импортом ядро env взять не может: `#lib` лежит ниже `#hooks`/`#server` и сети не делает (`core-purity`). Ручных чисел в описании формы нет — страница может только уменьшить.

**Проверки.**
1. При старте: бюджет формы ≤ env, иначе платформа отдаст 413 раньше наших сообщений.
2. `v.maxSize(n)`: `f.size > min(n, filesBudget)` по каждому файлу, затем сумма по всем файлам формы; ошибку даёт файл, первым вышедший за бюджет, и только его поле — сообщение одно, а не по числу файлов.
3. Транспорт: `limits.maxBytes = budget` (тело целиком), `limits.maxFileSize = filesBudget` (один файл всё равно не больше бюджета файлов); счётчик потока — вторая линия до разбора.
4. `defineForm` бросает `FormDefinitionError`, если у поля `file`/`files` нет `maxSize` (механизм дефектов есть — `describe.ts:143,478`).

**Сумма пересчитывается** на каждом прогоне из `values` в порядке полей описания и файлов в значении — добавление и удаление файлов меняют свободный вес сами. Для плашки «осталось 3,2 МиБ» тот же расчёт выносится в геттер `bind`.

**Почему не общий счётчик.** Правила зовутся многократно: на каждый ввод, на отправку, на сервере и в тестах. `static` в php живёт в пределах запроса, модуль в Node — процесса, в браузере — вкладки: счётчик «устанет» на втором прогоне, а валидатор обязан быть идемпотентным.
