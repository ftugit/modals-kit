# Drive: поведение операций, возврата, переноса и доступа

Статус: **активный план; список находок открыт и будет дополняться**.

Этот план не переписывает домен, ACL, WebDAV и структуру источников, уже
сделанные по [`plan-drive-repair.md`](./plan-drive-repair.md). Он меняет
**поведение носителей и операций**, потому что несколько решений старого плана
оказались неверными для пользователя:

- разный результат JS и no-JS submit;
- отдельные компоненты операций вместо одной универсальной формы;
- возврат/закрытие после успеха вместо стационарной квитанции;
- «Назад» как реальный шаг истории, а не ссылка на корень модуля;
- понятная деградация upload без подключённого storage;
- полный список папок для переноса и переход в целевую папку;
- выбор получателя доступа списком пользователей, а не вводом UUID.

## 2. Новые инварианты

### 2.1. Один результат для JS и no-JS

Успешная мутация всегда означает **возврат к прежнему экрану**:

- в модалке — закрыть текущую модалку, инвалидировать список/loader, остаться на
  странице под модалкой;
- на странице операции — перейти на `next` (обычно `return_to`), без экрана
  «Готово»;
- без JS — `303` на тот же `next`;
- для `move` `next` — маршрут **целевой папки**, а не источника;
- для `copy` `next` остаётся адресом источника, пока отдельно не решено иначе;
- для `dav-issue` секрет — единственное исключение: его нельзя отправить в PRG
  или потерять. JS показывает секрет в модалке/на странице и закрывает только по
  явной кнопке; no-JS показывает ту же квитанцию inline. Это исключение
  фиксируется в коде и тесте, а не маскируется общим `step: 'done'`.

Общий `step: 'done'` для обычных операций удаляется. Сервер возвращает `next`
(и, где нужно, данные для исключения), клиентский носитель сам решает
`close`/`goto`.

### 2.2. Операция — отдельный компонент, а не одна универсальная форма

`operations.ts` остаётся реестром имён, route/modal и form ID, но перестаёт
быть описанием полей и разметки. Для каждой операции:

- свой `form.ts` с полями и валидацией;
- свой `<Operation>.svelte` с разметкой и success-поведением;
- свой `<operation>.form.server.ts` (или общий dispatch только для вызова
  домена, но не для UI);
- тонкие route/modal-носители, как сейчас.

Общими остаются только примитивы: `Form`, `Field`, `Surface`, `Acl`,
`DriveOperationShell` (заголовок/назад/ошибки), invalidation-хелперы. Общая
матрица полей удаляется: именно она заставляла mkdir/rename/move/share вести
себя одинаково.

### 2.3. «Назад» — история, а не корень

Ввести `DriveBackLink` (или эквивалентный хук) с контрактом:

- `href` — validated `return_to` для no-JS и как fallback;
- JS `onclick`: `preventDefault()` и `history.back()`, если в истории есть
  предыдущая запись; если истории нет — `goto(href)`;
- в модалке «Назад» делает то же, что системная кнопка: закрывает слой истории,
  а не уводит на `/drive`;
- `return_to` по-прежнему проверяется `localPath`; внешний адрес не проходит.

`backHref` в `Acl` для операций не должен подменяться корнем модуля, если
известен `return_to`.

### 2.4. Upload без storage — доменный отказ

- `resolveAppStorage()` вызывается через безопасную обёртку, которая ловит
  исключения и возвращает `{ storage: null, reason }`;
- при `storage === null` или `writable === false` операция возвращает
  `drive.storage-unavailable` / `drive.storage-readonly`, а не 500;
- load операции отдаёт `storageReady`/`storageReason`, чтобы форма показала
  сообщение «Хранилище файлов не подключено» и не предлагала выбрать файл;
- POST повторяет проверку; узел в БД не создаётся, байты не читаются;
- 500 остаётся только для настоящего неизвестного исключения, но не для
  штатного «нет storage».

### 2.5. Move: полный список целей и переход в target

- заменить `targetFolders()` на обход доступных живых папок владельца/актора:
  корень, все папки, куда есть `canWrite`, с путными подписями;
- исключить сам узел и всё его поддерево (цикл), корзину и чужие недоступные
  папки;
- при большом дереве — тот же список с поиском/лимитом, но не «только корень»;
- после успеха `next = driveFolderRoute.href({ folderId: targetId })` (корень —
  `driveRootRoute`);
- модалка закрывается и переходит в target; no-JS получает `303` туда же.

### 2.6. Доступ: получатели списком, ids как у блокировок

- в форме `share` вместо текстового `uid` — `subjects` (CSV/UUID-list), как
  `subjects` у блокировок; выбранные ids приходят из списка, а не набираются
  руками;
- форма получает `subjectsSource`:
  - `seed` — если у актора есть право перечислять seed-пользователей
    (`auth.select` + право share): показываем `SeedUsersList`/`user.picker`
    (`multiple`), при наличии права на никнейм запрашиваем `users.nick=1` и
    показываем имя из профиля, иначе seed/id;
  - `profile` — если seed-список недоступен: показываем `ProfilesList`;
- оба списка используют ids-набор и тот же контракт `picked`/`onPicked`, что
  блокировки; для профильного списка ids-срез хранится в выбранном наборе
  (публичный `listProfiles` пока не имеет `ids`-фильтра — это фиксируется в
  плане, а не имитируется);
- `DriveAccess` показывает имя получателя (seed → профиль → uid), а не только
  UUID; uid остаётся техническим fallback;
- сервер принимает набор subjects и выдаёт доступ по каждому; частичный отказ
  возвращается по конкретному uid, успешные строки не откатываются молча;
- `unshare` остаётся по одному uid, но в списке доступа показывает имя.

### 2.7. Корзина: тот же возврат, без «Готово»

- `restore`, `purge` и `trash-action` подчиняются §2.1: JS закрывает модалку и
  инвалидирует live/trash-списки, страница операции возвращает на `return_to`;
- no-JS делает `303` на тот же адрес и перезапрашивает список; «ничего не
  произошло» — это баг, а не режим;
- для restore/purge в корзине `return_to` — `/drive/trash` с текущими фильтрами;
  после успеха строка исчезает из корзины, live-список обновлён;
- отдельного `DriveTrash.svelte` нет: корзина — тот же `DriveBrowse` с
  `initial.trashed`; менять нужно успех операций, а не вводить второй список.

### 2.8. Toast вместо квитанции

- в проекте сейчас нет toast: `grep` находит только комментарий в
  `core/lib/paginate/events.ts`, поэтому generic `step: 'done'` и `payload.count`
  больше не используются как UI;
- добавить минимальный transient-toast host (очередь, `aria-live`, автоскрытие)
  в общий слой `core/ui`/`AppShell`, без привязки к Drive;
- JS: после закрытия модалки/возврата носитель вызывает `notify('Готово')` или
  короткий текст операции; никаких «Затронуто узлов» и отдельных экранов;
- no-JS: PRG на `next` с `?notice=done`; после гидратации тот же toast
  показывается один раз, без JS остаётся компактная строка-подтверждение, а не
  полноценная квитанция;
- до появления toast операции завершаются молча: успех не рисует `done`-блок,
  счётчики не считаются и не передаются только ради текста.

### 2.9. «Важное»: list, а не только отметка

Сейчас `starred` — это boolean в `drive_node` плюс фильтр `drive.starred=1`.
Отдельного экрана нет, поэтому «Важное» выглядит как немая галочка.

Выбранный вариант — **список**:

- маршрут `/drive/starred` (identity `starred`) поверх того же `Listing`,
  `loadDrivePage({ starred: true, folderId: null })` уже поддерживает выборку по
  всему своему диску;
- вход — пункт «Важное» в шапке/навигации Drive и счётчик в фильтрах;
- строки ведут в обычные node/folder маршруты, действия — те же операции;
- звёздочка остаётся отметкой, но перестаёт быть скрытой: её видно в списке и
  можно снять/поставить на месте;
- ярлыки на главной (`DriveEntry`) — не в этом этапе: сначала list, затем решить,
  нужен ли отдельный блок «Важное» на главной. Не делать два входа одновременно.

### 2.10. Опция области: текущая папка или весь диск

Есть два режима выдачи:

- **текущая папка** — обычный list: файлы и подпапки, навигация по `folderId`;
- **весь доступный диск** — плоский список результатов: выборка без `parent_id`
  текущей папки, подпапки не являются элементами навигации.

Правило: режим меняет **явная опция**, а не любой фильтр. В форме фильтров
появляется `scope`:

- `folder` (по умолчанию) — текущая папка, подпапки остаются;
- `global` — глобальная выборка, `parent_id` не добавляется.

`ord` и `size` сами по себе режим не меняют. Опция живёт в `extra` и адресе как
`drive.scope=global` (значение по умолчанию в адрес не пишется), поэтому
работает и в JS, и в no-JS, и переживает перезагрузку.

Границы:

- свой диск в `global` — весь доступный актору набор, а не только открытая
  папка; в `folder` — текущая папка;
- чужая папка по ссылке в `global` не выходит за пределы доступного поддерева;
- корзина в `global` остаётся в пределах корзины;
- в `global` `type=folder` показывает найденные папки как результаты, а не как
  «подпапки текущей папки»; клик не должен незаметно возвращать в навигацию;
- снятие `global` возвращает обычный list текущей папки.

Требует решения: сейчас `q` и `starred` уже глобальны. Либо они тоже подчиняются
`scope` (единая модель, но поиск по умолчанию станет локальным), либо остаются
семантическими исключениями (текущее поведение сохраняется). Это фиксируется
отдельным пунктом, а не угадывается в реализации.

## 3. Этапы

### Этап 0. Зафиксировать текущие дефекты тестами

До разделения операций добавить регрессии, которые сейчас падают или отсутствуют:

- JS mkdir/rename: успех закрывает модалку/возвращает страницу, экрана «Готово»
  нет;
- no-JS mkdir/rename: `303` на `return_to`, без «Готово»;
- `DriveBackLink`: JS вызывает историю, no-JS ведёт по `href`;
- upload без storage: форма показывает сообщение, ответ не 500, узла в БД нет;
- move: в target options есть корень, вложенная папка и папка-внук; цель не
  содержит сам узел/потомков; успех ведёт в target;
- share: поле `subjects`, seed-режим с ником из профиля, profile-режим без
  seed-прав, ids-набор, отображение имён в `/drive/access`;
- trash: restore/purge обновляют корзину и live-список, без «Готово»;
- toast: успех после возврата показывает transient toast, счётчик узлов не
  выводится;
- starred: `/drive/starred` показывает важное по всему своему диску.

### Этап 1. Разделить операции и унифицировать успех

- удалить `DriveOperationForm` и матрицу `fields`/`description` из
  `operations.ts`/`form.ts` как общий renderer;
- перенести поля в `<op>/form.ts`; разметку — в `<op>/<Op>.svelte`;
- регистрации — по файлу на операцию или общий dispatch, но с `next`/`close`
  контрактом;
- `onSuccess` носителя: modal → invalidate + close; page → `goto(next)`;
- no-JS — `redirectOnSuccess` на тот же `next`;
- DAV secret — отдельный inline-режим, не общий stationary receipt.

### Этап 2. Возврат, «Назад», корзина и toast

- `DriveBackLink` + замены во всех операциях, `Acl` и модалках;
- `return_to` всегда несёт реальный list pathname+search;
- тесты на историю и fallback;
- убрать `driveRootRoute` как backHref там, где известен `return_to`;
- restore/purge/trash-action получают тот же close/return, что mkdir/rename;
- toast host + `notify`; успешные операции не рисуют `done` и не считают узлы
  только ради текста.

### Этап 2b. «Важное» списком

- identity `starred` и маршрут `/drive/starred`;
- вход в шапке Drive, счётчик и снятие отметки на месте;
- SSR/no-JS и пагинация — тем же `Listing`; отдельного источника не заводить;
- главная не меняется, пока list не готов.

### Этап 2c. WebDAV как опция диска

Бэкенд уже есть: `/api/dav`, `drive.dav-issue`/`drive.dav-revoke`, HMAC-токены,

### 5.1. Фильтр и поиск Drive (пункт 12)

Проверено статически:

- `applyDriveFilters` формирует `ord`/`type`/`starred`/`from`/`to`, а
  `DRIVE_EXTRAS.reloadKeys` содержит `q` и эти ключи; `parseDriveFilters` читает
  те же `drive.*`-ключи. Рассинхрона «форма — адрес — load» не видно.
- `filtersForm` в `DriveBrowse` — snippet, переданный внутри `<Listing>`; это не
  забытый проп. Sidebar-форма регистрируется через `Listing`.
- `DriveBrowse` повторяет схему `SeedUsersList`: отдельный `filterStore`,
  `setExtra`, `appliedValues`/`appliedKey`. На странице без модалки оба стора
  должны сходиться в `getClientStore`, то есть это не очевидный «второй стор».

Гипотезы, которые нужно проверить тестом, а не правкой:

- `DriveBrowse` передаёт в `Listing` новый литерал
  `initial={{ snapshot, fact: null }}` при каждом обновлении родителя.
  `Listing` в `$effect` по `initial` делает `data = initial` и `asked = null`;
  это может возвращать старый снимок и мешать живому состоянию после
  `setExtra`. Сравнить с `SeedUsersList`, где передаётся стабильный `initial`.
- При непустом `initial` `Listing` вообще не делает собственный `preloadData` по
  адресу; перезапрос полностью зависит от `Paginator`/источника. Нужно
  проверить, что `setExtra` действительно доходит до `driveSource.data` и что
  `rehydratePaginator` не отбрасывает новый extra.
- `filters` и `returnTo` в `DriveBrowse` выводятся из `initial.snapshot`, а не из
  живого стора. После применения фильтра они остаются старыми: это точно влияет
  на ссылки/возврат и может маскировать обновление списка.
- `SearchBar` берёт стор из `useScopeStore`; проверить, что внутри
  `PaginatorScope`/snippet это тот же store, куда пишет sidebar-форма.
