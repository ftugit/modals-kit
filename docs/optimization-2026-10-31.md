# Сборка и тесты: что осталось ускорять (2026-10-31)

Изучение после обновления `img` до `8f798a4` (ядро + модуль `demo`). Все цифры — замеры на стенде
2 vCPU / 1.9 ГиБ RAM, Node 22.23.4, Playwright 1.63, `demo@1.0.0` установлен (`npm run mod -- add demo`).

## Короткий вывод

- **Сборка у флора.** 13.3–13.8 s (медиана 13.3 s), из них 8–9 s — работа самой vite. Проверены
  `sourcemap:false`, `reportCompressedSize:false`, `minify:false`, `--no-liftoff`, фильтрация UnoCSS
  по окружению — **ни один вариант не выходит за шум (±0.7 s)**. Осталось только структурное:
  `vite-plugin-svelte:compile` (1.8 s × 2 окружения) и `unocss` (1.1 s), и оба нужны.
- **Тесты — да, там ещё есть запас.** Виноват не код тестов, а режим запуска:
  vitest упирается в один воркер (207.8 s), браузерный набор — в последовательный запуск.
  Реализовано: **vitest 207.8 → 121.0 s** (сплит «чистые / PGlite», стабильно),
  **браузерные сьюты 552 → 272.5 s** (один preview + `KT_PARALLEL=2`); при 3 — 213.8 s,
  но с флейком `db-demo`, поэтому это опция, а не умолчание.
- Главный оставшийся резерв — не «ещё параллелизма», а **паузы внутри сьютов** и
  **гейт задержки демо-источника**: это отдельная работа (T1'–T3' плана из
  `docs/plan-test-speedup-2026-10-30.md`), оценка ниже.

## Сборка

Фазовая разметка (временный плагин, откачен) для `npx vite build`:

```
   464 ms  options (оба окружения стартуют здесь)
   481 ms  buildStart ssr
  4103 ms  buildEnd ssr          → трансформация 3.6 s (944 модуля)
  5577 ms  writeBundle ssr       → рендер + запись 1.5 s
  5612 ms  closeBundle ssr
  7145 ms  options client        → 1.5 s между окружениями (SvelteKit готовит клиентский граф)
  7157 ms  buildStart client
 10836 ms  buildEnd client       → трансформация 3.7 s (1037 модулей)
 11384 ms  writeBundle client    → 0.55 s
 11518 ms  closeBundle client
14 063 ms  стена  → хвост 2.5 s (размеры/gzip, анализ маршрутов, adapter-auto)
```

Внутри трансформации (PLUGIN_TIMINGS, `checks.bundlerTimings`):

| плагин | ssr | client |
| --- | --- | --- |
| `vite-plugin-svelte:compile` | 1.8 s (272 вызова) | 1.7 s (272) |
| `unocss:global:build:generate` | 1.1 s | — |
| `layer-guard` | < 1 s (было 81.6 s до правки regex) | < 1 s |

Проверенные и отвергнутые варианты (по 2 прогона, холодный `.svelte-kit`):

| вариант | стена |
| --- | --- |
| база | 13.7 / 13.8 s |
| `build.sourcemap: false` | 13.4 / 14.0 s (выход 27 → 20 МБ, 258 карт исчезают) |
| `build.reportCompressedSize: false` | 14.0 / 14.0 s |
| `sourcemap:false + reportCompressedSize:false` | 14.8 / 15.1 s |
| то же + `minify: false` | 14.4 / 14.1 s |
| `node --no-liftoff vite build` | 14.1 / 14.1 s |
| UnoCSS только в client-окружении (`applyToEnvironment`) | сборка падает; и неверно — SSR-сборка законно выпускает CSS (`output/server/_app/immutable/assets/*.css`) для `<link>` в SSR-разметке |

Вывод: единственная полезная «микро-настройка» — `sourcemap:false` для CI-артефактов (−7 МБ, время
в пределах шума). Сборку дальше не трогать; выигрыш надо искать в тестах.

## Тесты: vitest

Базовая линия `npx vitest run` (167 файлов) на этом стенде — **207.8 s** (`maxWorkers: 1`
принудительно: конфиг ограничивает прогон, если `totalmem ≤ 4 ГБ` или `availableParallelism ≤ 2`).

| режим | стена | файлы |
| --- | --- | --- |
| как есть, 1 воркер | **207.8 s** | 167 ok |
| `--maxWorkers=2` | 106.0 s | 164 ok, **3 падения** (`Worker exited unexpectedly`) |
| `--maxWorkers=2 --no-isolate` | 88.9 s | 160 ok, **5 падений** |
| 152 файла без PGlite, 2 воркера | 45.2 s | 150 ok |
| 15–17 файлов с PGlite, 1 воркер | 133.0 s | ok |
| PGlite, 1 воркер, `--no-isolate` | **73.3 s** | ok; с `--sequence.shuffle` — 73.5 s, ok |
| PGlite, 2 воркера, `--no-isolate` | 44.1 s | **краш** (3 файла) |
| «чистые» с `--no-isolate` | 28.2 s | **5 падений** (изоляция им нужна) |
| **сплит (реализован)**: чистые 2 воркера + PGlite 1 воркер `--no-isolate` | **121.0 s** | **167 ok** |

Что из этого сделано: `tooling/vitest-split.mjs` и `npm run test:fast` — два захода подряд.
Списки файлов вычисляются по содержимому (маркеры `@electric-sql/pglite`, `withTestDb`, `new PGlite`),
новые тесты попадают в нужный заход сами. Ускорение **1.72×** без изменения проверок.

Почему PGlite-блок не параллелится: два воркера = два WASM-инстанса `pglite.wasm` → процесс падает
(`Worker exited unexpectedly`). Предел памяти, а не CPU. `--no-isolate` работает, потому что
переиспользует граф модулей (и компиляцию WASM) между файлами; для «чистых» тестов это недопустимо
(5 падений) — им нужна свежая модульная среда.

## Тесты: браузерные сьюты

17 сьютов (ядро + `demo`), один `vite preview` на прогон:

| параллелизм | стена | результат |
| --- | --- | --- |
| 1 (как было до `run-all`) | 552.3 s | 15 ok, 2 fail |
| **2 (оставлено умолчанием)** | **272.5 s** | 15 ok, 2 fail |
| 3 (`KT_PARALLEL=3`, `test:browser:fast`) | 213.8 / 216.9 / 195.6 s | в одном из трёх прогонов **упал `db-demo`** |
| 4 | 604.8 s | **10 падений** |

Третий поток даёт −21 % времени, но **нестабилен**: `db-demo` упал в 1 полном прогоне из 3
(на 2 — 0 из 2, в одиночку — 3 из 3 зелёные). Сьюты пишут в общую демо-базу превью, и лишний
параллельный писатель ловит гонку по содержимому окна. Поэтому умолчание оставлено на 2,
а 3 — осознанный выбор в `npm run test:browser:fast`.

Сумма времён сьютов ≈ 521 s, значит при 3 сьютах одновременно теоретический минимум 174 s:
накладные расходы ~23 %. При 4 сьютах начинается деградация: `forms` 47 → 413 s, `db-demo` 33 → 367 s —
конкуренция за 2 ядра и память ломает таймауты самих проверок.

Изменено: `KT_PARALLEL` по умолчанию 2 → 3 (с обоснованием в комментарии), `test:browser:fast`
приведён к 3 (`KT_PARALLEL=4` на таком стенде не работает — оставлено в документе как отрицательный
результат, а не как «быстрый режим»).

### Что внутри сьютов осталось дорогим

Профиль по местам вызова (прошлый заход, `docs/review-test-speedup-2026-10-31.md`, цифры сохранились):

| сьют | стена (при 3) | главное внутри |
| --- | --- | --- |
| `regressions` | 71.9 s | 64 `waitForTimeout` (17.8 s) + 53 `waitForSelector` (33.4 s) + **30 s выжигание** на предсуществующем падении R-18 |
| `paginate` | 76.3 s | 46 пауз `sleep(300..1500)` из тела сьюта, 24 `goto networkidle` (22.2 s), `DEMO_TRANSPORT_MS = 500` |
| `forms-a11y` | 64.4 s | в основном полезная работа `axe-core`: 18.4 s видит инструментарий, остальное — `axe.run()` в `page.evaluate` |
| `forms` | 50.6 s | 43 `waitForTimeout` (26.5 s при одиночном прогоне) |
| `db-demo` | 35.0 s | после правки от 2026-10-30 — 13 `waitForTimeout` (12.5 s) и 11 `goto networkidle` |
| `fields` | 33.6 s | **30 s выжигание** на предсуществующем падении (нет `[data-testid="add-field"]`) |

Два предсуществующих падения (`regressions`, `fields`) стоят **60 s стены на каждом прогоне** —
это больше, чем даст любая микрогонка параллелизма. Их надо или починить, или честно снять.

## Что предлагаю делать дальше (по отношению «секунды / риск»)

1. **Починить два красных сьюта** (`regressions` R-18, `fields`): −60 s на прогон и зелёный набор.
   Риск нулевой для кода приложения, работа только в тестах.
2. **Гейт `DEMO_TRANSPORT_MS`** (тестовый сигнал: 0 мс для всех секций, кроме скелетонов): при 0
   `paginate.mjs` падает на первой же проверке скелетонов, значит гейт обязателен, но верхняя оценка
   видна — с 0 мс сьют идёт 12.6 s вместо 63. `paginate` + `db-demo`: ожидаемо −35…−45 s суммарно.
3. **`waitForTimeout` → ожидание факта** в `forms` (43), `regressions` (64), `db-demo` (13):
   это 55–60 s суммарного сна. Делать по местам с профилем, не общим патчем
   (общий патч `networkidle` уже проверен и откачен — давал флейки).
4. **`axe-core`: одна инъекция на страницу** вместо повторных в `forms-a11y` — оценка −15…−20 s,
   требует аккуратной проверки, что правила и набор прогонов не изменились.
5. Сборка: ничего не делать, кроме `sourcemap:false` для CI-артефактов (экономия диска, не времени).

## Режим «чистое ядро» (без модуля `demo`)

Все замеры выше сделаны с установленным `demo` (`npm run mod -- add demo`). Для контроля — те же
команды на том же коммите без модуля:

| проверка | ядро (без `demo`) | с `demo` |
| --- | --- | --- |
| `npm run build` | 12.8 s | 13.3–13.8 s |
| `npm run test:fast` (сплит vitest) | **106.4 s**, 151 файл | **121.0–125.8 s**, 167 файлов |

существующим файлам, а сплит vitest считает файлы по содержимому.

## Ограничения стенда (проверено на себе)

- `KT_PARALLEL=4` — не работает: 604 s и 10 падений. Не поднимать выше 3 на 2 vCPU.
- `--maxWorkers=2` для всего vitest — падения WASM. Только через сплит.
- Превью требует собранного `.svelte-kit/output`: после неудачной сборки `run-all` не поднимет
  сервер и упадёт с `preview не поднялся за 90 с` (проверено, сообщение честное).
- `npm run check` на 1.9 ГБ падает по OOM при дефолтном heap; с `NODE_OPTIONS=--max-old-space-size=1400`
  — `0 errors, 0 warnings`.
- Память: при 3 параллельных сьютах после прогона занято ~550 МБ из 1.98 ГБ — запас есть, но
  `db-demo` (PGlite в памяти) + `forms` одновременно ближе всех к пределу.
- **`npm run mod -- add demo` кладёт 148 файлов как untracked**, а `.modules/` — в `.gitignore`.
  Значит `git add -A` (или `git commit -a` после `add -A`) затянет ВЕСЬ модуль в коммит чистой
  ветки: файлы станут отслеживаемыми, а манифест установки — нет, и `mod remove` перестанет их
  видеть. Коммитить только свои файлы поимённо; в этом репозитории `git add -A` опасен.
