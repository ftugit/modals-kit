# Аудит: массивы, память, фильтрация, данные (2026-10-29)

Проход по ключевым местам `src/lib` (db, paginate, cache, image, storage,
form), `src/hooks`, `src/server`, `src/content`. Каждый кандидат сверен
с практикой зрелых человеческих репозиториев через GitHub Code Search
(postgres/postgres, supabase/supabase, isaacs/node-lru-cache,
nextapps-de/flexsearch, sveltejs/kit, vercel/next.js). Это аудит, не
план: правок по нему без указания владельца не делается.

## Находки

### F1. `contains`/`icontains` → `ILIKE '%…%'` без триграммного индекса — СРЕДНЯЯ (латентная)

`src/lib/db/query/sql.ts:252-263`: операторы `contains`/`icontains`
строят `LIKE/ILIKE '%значение%'` (экранирование `%_\\` сделано верно).
Ведущий `%` делает невозможным btree-индекс: на Postgres это seq scan
по таблице на каждый запрос. Поля с `icontains` уже есть в боевых
моделях: `src/content/user/schema.ts:62` и `:119` (поиск по seed/нику
в списке юзеров), `contains` — `src/content/demo-catalog/posts/posts.ts:37`.
`pg_trgm`/GIN в проекте не встречается ни разу (grep по `src/lib/db`,
`src/server` — 0).

Внешний ориентир: Supabase в миграции поиска по документации ставит
именно `create extension pg_trgm` + `gin (col gin_trgm_ops)`
(supabase/supabase, `supabase/migrations/20261026163622_improve_docs_search_v2.sql:4-9`);
классы операторов для LIKE/ILIKE — contrib/pg_trgm в postgres/postgres.

Пока таблицы аккаунтов малы — не болит. Болит при росте: любой потребитель,
который пустит `contains` в DB-фильтр большой модели, получит seq scan
на каждый запрос. Лечение на выбор:
(a) GIN trgm-индекс SqlStep-ом на поля с `icontains`; (b) задокументировать
потолок и запретить `contains` на больших моделях стражем в `defineResource`.

**Уточнение по факту (проверка 2026-10-29):** текущий поиск списка юзеров
`icontains` НЕ использует. `src/content/user/accounts.ts:149-154` прямо
комментирует: подстрока в DB-фильтр не кладётся (схема поля `seed` —
43–44 знака, слой валидирует значение полем), вместо этого адаптер
`src/content/user/gateway.server.ts:305-330` при `searchSeed`/`ids`
выгружает ВЕСЬ срез постранично по 100 и режет в памяти («таблица
аккаунтов мала» — осознанный приём, задокументирован в
`src/content/user/ports.ts:96-106`). То есть реальная цена поиска сегодня —
не seq scan SQL, а полная выгрузка среза в память на каждый поисковый
запрос; при росте таблицы аккаунтов это станет главным местом, а не F1.

### F2. Накопитель поиска пересортировывает весь ранк после КАЖДОГО батча — СРЕДНЯЯ

`src/lib/paginate/search/accumulator.ts:204`: `applyBatch` заканчивается
полным `acc.ranked.sort(...)`. Сканирование идёт постранично до бюджета,
итоговая сложность — O(батчей × N log N) вместо одного O(N log N) в конце.
Разрешение сканирования (`scan`) источник даёт осознанно, но цена растёт
квадратично от числа просмотренных страниц на длинных запросах.

Внешний ориентир: flexsearch не сортирует глобально — `intersect`
(nextapps-de/flexsearch, `src/intersect.js`) раскладывает результат по
корзинам разрешения скора и режет `limit` до материализации. Нам
достаточно дешевле: сортировать лениво при выдаче страницы (флаг
«грязно»), а не на каждый батч; либо держать top-k под текущий `target`.

### F3. `ORDER BY payload->>` по полю связи — НИЗКАЯ/СРЕДНЯЯ

`src/lib/db/resource.ts:341-349` (и дубль `src/lib/db/raw.ts:87`):
сортировка по `relation.field` идёт по текстовому извлечению из JSONB
payload включённой связи. Функционального индекса под это нет и быть
не может без знания поля заранее — сортировка в памяти по всему
отфильтрованному набору. Включается только явным `order` по связи,
поэтому риск ограничен, но на больших выборках это самый дорогой
путь чтения. Стоит хотя бы комментарий-потолок в README слоя db.

### F4. `structuredClone` черновика на КАЖДОЕ поле с `fill` — НИЗКАЯ

`src/lib/db/validation.ts:283`: внутри цикла по полям каждый `fill`
получает `freeze(structuredClone(draft))` — O(полей × размер строки).
Семантика сейчас: поздний `fill` видит значения ранних. Клон один раз
на операцию изменил бы семантику; безопасный вариант — клонировать
только при ≥2 `fill`-полей или явно задокументировать цену. Соседний
`snapshot` (`src/lib/db/resource.ts:116,826`) — один клон на проверки,
это нормально.

### F5. Median-cut: полная сортировка + два `slice` на каждый разрез — НИЗКАЯ

`src/lib/image/quantize.ts:206-231`: на каждый из ≤256 разрезов —
`[...box.points].sort(...)` и два `slice`. Авторы уже убрали худшее
(пересчёт разбросов, см. комментарий `:66-76`). Классические MMCQ
(color-thief/Leptonica) делают так же, поэтому это не дефект, а запас:
для разреза нужен только медианный порядок — `partition`/quickselect
по каналу снимает log-множитель. Ограничено сэмплированием по stride,
потолок понятен.

### F6. `Math.random` в идентификаторах — ИНФО

- `src/lib/db/adapters/proxy.ts:319`: `requestId` — `crypto.randomUUID`
  основной путь, `Math.random().toString(36).slice(2)` — фолбэк для
  среды без WebCrypto (короткий, предсказуемый; это корреляционный id
  кадра, не секрет — но коллизии в логах возможны).
- `src/lib/storage/index.ts:346-349`: id резервации —
  время + процессный счётчик + 6 символов base36 от `Math.random`.
  Внутри одного процесса уникальность держит счётчик; между инстансами
  окно коллизии — одинаковые мс+счётчик+суффикс. Если id резервации
  когда-нибудь станет capability-токеном — заменить суффикс на
  `crypto.randomUUID`. Сейчас — не секрет, приемлемо.
- Джиттер повторов (`src/lib/fetch/create.ts:106`,
  `src/lib/db/ops.ts:67`) — по назначению, вопросов нет.

### F7. `pgStore` игнорирует `max` области — ИНФО

`src/hooks/cache-db.ts` (pgStore, комментарий у объявления): потолок
областей сетевым хранилищем не применяется, вытеснение — только срок.
Для ключей с `ttlMs: Infinity` (кэш умолчаний конфига `defaults.v1`)
рост ограничен числом ключей. Общий случай «Infinity + безграничные
ключи» раздует таблицу `cache_kv`; контракт это разрешает явно —
зафиксировано как известное ограничение, а не дефект.

## Проверено — слабости НЕТ (важно не «чинить»)

- **Пагинация**: keyset-курсоры (`src/lib/db/query/sql.ts` `keyset`),
  потолки `pageSize/maxPage/filterDepth: 8/filterNodes`
  (`src/lib/db/types.ts:103-113`) — OFFSET-сканирования страниц нет.
- **Кэши**: области памяти с обязательным `max`
  (`src/lib/cache/memory.ts:73,129`), live-cache — 64 записи + TTL 5с
  + generation (`src/server/live-cache.server.ts:32-40`). Эталон
  isaacs/node-lru-cache требует «at least one of max/ttl/maxSize» —
  у нас максимум есть всегда.
- **LIKE-экранирование** (`%`, `_`, `\\` + `ESCAPE`) — верно.
- **Фильтры**: лимиты узлов/глубины в `filterSQL`, `Promise.all` по
  детям дерева ограничен этими же лимитами.
- **Левенштейн**: три скользящих ряда `Float64Array` — O(m) памяти
  (`src/lib/paginate/search/fuzzy.ts:100-120`), без полной матрицы.
- **Квантование**: гистограмма по stride-сэмплам, abort-проверки.
- **Массовая запись**: чанки (`src/lib/db/resource.ts:742-749`).
- **Прототипное загрязнение**: стражи `__proto__/constructor/prototype`
  на всех разборах (`paginate/adapter-url.ts:302`, `paginate/storage.ts:19`,
  `form/policy.ts:71`, `db/validation.ts:64`).
- **Регулярки из путей**: сегменты роутов экранируются
  (`src/lib/modals/cores/routes.ts:32`), `[param]` — `[^/]+`.
- **Устаревший стандарт**: `eval`/`new Function`/`substr`/`new Buffer`/
  прямой `hasOwnProperty`/`forEach(async` — 0 вхождений. Стиль —
  современный (`structuredClone`, `crypto.randomUUID`, собственный
  `own()` вместо `Object.hasOwn` — осознанно, `db/validation.ts:49`).
  `[...x].sort()` вместо `toSorted()` — не отставание, а та же
  семантика копирования; менять ради моды не нужно.

Итоговая очередь после проверки: (1) выгрузка среза поиском списка

будущих DB-фильтров по большим моделям; (3) F2. Остальное — запасы
и зафиксированные ограничения.

## План исправлений (принят к исполнению 2026-10-29)

- [x] FIX-1 (слой БД, корень F1 и выгрузки списка): значения операторов
  `contains/startsWith/icontains/istartsWith` валидируются как ФРАГМЕНТ
  (normalize поля, строка, потолок длины), а не полной схемой хранимого
  значения; колонка в LIKE приводится к `::text`, чтобы подстрока
  работала и по uuid. Критерий: фильтр `{seed, icontains, 'abc'}` на
  поле со схемой 43–44 знака проходит; не-строка и сверхдлинный
  фрагмент — `validation`.
- [x] FIX-2 (список юзеров): поиск — DB-фильтр домена
  `or[seed icontains, id icontains, exists(profile: nickname icontains)]`
  (никнейм — только при включённом параметре, как сейчас), срез по id —
  `{id, in}`; ветка полной выгрузки среза в адаптере порта и поля
  `searchSeed`/`ids` порта удаляются. Критерий: `listPage` получает
  только page/pageSize/filter/order/includeDeleted/withNickname;
  поведение выдачи (состав, total, порядок) не меняется.
- [x] FIX-3 (F1-индекс): trgm-Индексы НЕ ставим: `pg_trgm` недоступен
  в PGlite (`extension "pg_trgm" is not available`, проба 2026-10-29),
  безусловный SqlStep сломал бы превью и тесты. Вместо индекса —
  запись в README слоя db: на чистом Postgres при росте таблицы
  ставится `gin (seed gin_trgm_ops)` / `gin ((id::text) gin_trgm_ops)`
  миграцией окружения. Критерий: README обновлён, гейты зелёны без
  расширения.
- [x] FIX-4 (F2): накопитель поиска сортирует `ranked` лениво — флаг
  «грязно», сортировка перед выдачей страницы, а не на каждый батч.
  Критерий: тесты paginate зелёны, порядок выдачи не меняется.
- [x] FIX-5 (F4): снимок черновика для `fill` кэшируется и пересоздаётся
  только после записи поля в черновик. Критерий: тесты db зелёны,
  семантика «поздний fill видит ранние значения» сохранена.
- [x] FIX-6 (F6): суффиксы id резервации и фолбэк `requestId` — на
  `crypto.getRandomValues`, не `Math.random`. Критерий: grep
  `Math.random` в этих местах пуст, тесты зелёны.
- [ ] F3/F5/F7 правок не требуют: F3 — потолок дописан в README слоя db
  вместе с FIX-3; F5 ограничен константами (131072 сэмпла, 256 цветов)
  и совпадает с классикой MMCQ; F7 — контрактное ограничение pgStore,
  уже задокументировано у объявления.

## Итог

Критичных находок нет. Очередь по ценности: F1 (индекс под `icontains`
до роста таблиц) → F2 (ленивая сортировка накопителя) → F3/F4/F5
(точечные оптимизации с понятным потолком). F6/F7 — зафиксированные
ограничения, не дефекты.
