# План 2: Автономное внешнее крон-приложение (Hono + универсальный движок под Cloudflare, Docker и Google Apps Script)

Статус: **технический план до начала написания кода** (отдельный легковесный пакет/репозиторий без зависимости от кода `modals-kit`).

---

## 1. Главная идея: полностью автономный интерпретатор схемы

Внешний сервис **ничего не знает заранее** ни про хранилища, ни про картинки, ни про внутреннее устройство нашего приложения. Ему задаются только две переменные окружения:
- `CRON_TARGETS` — список адресов наших приложений (например `https://app.example.com/api/internal/cron`);
- `CRON_SECRET` — общий секрет авторизации.

При старте или очередном тике внешний сервис **сам запрашивает Схему (`CronManifest`)** у нашего приложения и дальше работает строго по ней как универсальный конечный автомат:
- видит все зарегистрированные ключи задач (`task`), интервалы их опроса и стартовые параметры (`defaults`);
- опрашивает `discover`, запускает `dispatch { task, itemKey, payload }` и собирает отчёт (`cloned`, `remaining` и т.д.);
- ведёт учёт неудачных попыток по каждому `task + itemKey` и при ошибках сам вычисляет следующую команду по правилам `onError` из схемы (увеличивает число нарезок `parts: 2 -> 4 -> 8 -> 16 -> 32` для зависающего файла при клонировании, ослабляет `maxBytes` или шлёт `action: 'cancel'` для несжимаемой картинки);
- ждёт подтверждения, что заданий больше нет (`remaining === 0` / `idle`), и завершает проход до следующего расписания.

Благодаря этому при добавлении любых новых задач в `modals-kit` **внешний сервис вообще не нужно обновлять и передеплоивать** — он подхватит новую схему на следующем тике автоматически.

## 2. Выбор движка и как один код работает на всех трёх бесплатных платформах

В основе — **чистое ядро оркестратора на Web Standards (`0` зависимостей)** + ультралёгкий HTTP-каркас **Hono** (`~12 КБ`, работает одинаково на Cloudflare Workers, Bun, Deno и Node.js):

```
cron-worker/
├── src/
│   ├── core/
│   │   ├── protocol.ts        # Типы CronManifest и кадров протокола
│   │   ├── escalator.ts       # Вычисление следующего payload по правилам scale / steps / cancel
│   │   ├── state-store.ts     # Интерфейс памяти попыток (Memory / KV / File / GAS Properties)
│   │   ├── transport-ws.ts    # Драйвер сессии по wss:// (с поддержкой ping/pong и пересменки rotate)
│   │   ├── transport-http.ts  # Драйвер пошагового HTTP POST (для Google Apps Script и фолбэка)
│   │   └── orchestrator.ts    # Автономный цикл: схема -> discover -> dispatch -> эскалация -> отчёт -> idle
│   ├── app.ts                 # Hono-приложение: GET /health, GET /status (последние отчёты), POST /trigger
│   └── adapters/
│       ├── cloudflare.ts      # export default { fetch: app.fetch, scheduled } (Cloudflare Workers)
│       ├── server.ts          # Hono на Node / Bun + встроенный минутный цикл + Dockerfile
│       └── gas.ts             # Точка входа runCronTick() для сборки в один файл под Google Apps Script
```

### Как это работает на каждой из трёх целевых площадок

1. **Cloudflare Workers (бесплатный тариф)**
   - **Транспорт к нашему сайту**: полноценный **`wss://`** через `fetch(targetUrl, { headers: { Upgrade: 'websocket', Authorization: 'Bearer ...' } })`.
   - **Запуск**: родной `[triggers] crons = ["* * * * *"]` в `wrangler.toml` (до 5 триггеров бесплатно, шаг 1 минута, до **15 минут** реального времени ожидания на один тик; ожидание по `wss://` не тратит 10-мс лимит CPU).
   - **Память попыток между тиками**: в памяти изолята + опционально бесплатный Cloudflare KV / D1 (чтобы счётчик попыток проблемного файла не сбрасывался даже между разными датацентрами).
   - **Бонус от Hono**: по HTTP-адресу воркера открывается лёгкий JSON-статус `/status` с последними отчётами и ручной вебхук `POST /trigger`.

2. **Бесплатный Docker-сервис (Koyeb Free / Render Free / Hugging Face Spaces / Fly / любой мини-VPS)**
   - **Транспорт к нашему сайту**: постоянный или минутный **`wss://`** (пакет `ws` в Node или встроенный `WebSocket` в Bun; образ на базе `oven/bun:alpine` или `node:22-alpine` весит `~35 МБ` и потребляет `< 30 МБ` ОЗУ).
   - **Запуск**: внутренний планировщик без дрейфа в `adapters/server.ts`, который сам держит расписание из `CronManifest.tasks[].intervalSec` для каждого ключа задачи.
   - **Защита от засыпания бесплатных Docker-контейнеров**: Hono отдаёт мгновенный `GET /health` (`200 OK`), который при необходимости пингуется внешним монитором (или будится тем же Google Apps Script), плюс `POST /trigger` для принудительного прогона.
   - **Память попыток**: в оперативной памяти процесса + сброс компактного JSON-снимка в `/tmp/cron-state.json`.

3. **Google Apps Script (`script.google.com` — полностью бесплатно на обычном Google-аккаунте)**
   - **Почему нужен отдельный адаптер транспорта**: в среде Google Apps Script **нет класса `WebSocket`** — есть только синхронный `UrlFetchApp.fetch(url, params)` (лимит одного HTTP-запроса ~60 с, лимит одного запуска триггера — **6 минут**, суточная квота — `90 минут` времени и `20 000` вызовов `UrlFetchApp`).
   - **Как работает**: команда `npm run build:gas` собирает `core/* + adapters/gas.ts` через `esbuild` в один чистый файл `dist/Code.gs` без единой внешней зависимости:
     - адаптер транспорта реализует тот же самый интерфейс, что `transport-ws`, но отправляет кадры через `UrlFetchApp.fetch(targetUrl, { method: 'post', headers: { Authorization: ... }, payload: JSON.stringify(cmd), muteHttpExceptions: true })`;
     - память попыток и кеш `CronManifest` сохраняются в штатном бесплатном хранилище скрипта `PropertiesService.getScriptProperties()` + `CacheService.getScriptCache()`;
     - триггер времени в GAS ставится на каждые `5 минут`: функция `runCronTick()` крутит пошаговый цикл `discover -> dispatch` в течение максимум `4.5 минут` (с запасом до 6-минутной отсечки Google), а как только получает `idle` («заданий нет») — завершается за `0.3 секунды`, расходуя меньше 3 минут из 90-минутного суточного лимита!

## 3. Алгоритм работы автономного мозга (`orchestrator.ts` + `escalator.ts`)

### Шаг 1 — Синхронизация схемы
- В начале сеанса оркестратор отправляет `{ type: 'schema', knownHash }`.
- Если сервер ответил `{ unchanged: true }` — используется закешированный `CronManifest`; иначе сохраняется новая схема.
- Оркестратор отбирает задачи, у которых подошёл интервал `now - lastIdleAt[task.key] >= task.intervalSec * 1000` (либо задачу, запрошенную явно при вызове `POST /trigger?task=...`).

### Шаг 2 — Поиск работы (`discover`) и проверка «заданий нет»
- Для каждой созревшей задачи `pipeline`-типа отправляется `{ type: 'discover', task: task.key }`.
- Если пришёл пустой список (`items.length === 0 && remaining === 0`), задача отмечается `lastIdleAt = now` — впустую сервер больше не дёргается до истечения её `intervalSec`.
- Если по всем задачам пусто — сеанс мгновенно закрывается со статусом `idle`.

### Шаг 3 — Выполнение и адаптивная эскалация ошибок по схеме
Для каждого найденного `itemKey` оркестратор смотрит в `stateStore.get(task.key, itemKey)`:

1. **Первая попытка (`attempts === 0`)**:
   - отправляет `{ type: 'dispatch', task: task.key, itemKey, payload: task.defaults }`.
2. **Успех (`ok: true`)**:
   - очищает счётчик ошибок `stateStore.clear(task.key, itemKey)` и записывает элемент в сводный отчёт успешных (`cloned` / `processed`).
3. **Ошибка (`ok: false, errorCode`)**:
   - увеличивает `attempts += 1` для этой пары `(task.key, itemKey)` и ищет подходящее правило в `task.onError` по `errorCode`:
   - **Сценарий А — Медленное клонирование файла (`action.kind === 'scale'`)**:
     - Попытка 1 упала по `slow_target` / `timeout` при `parts = 1` → формула `min(max, base * factor^attempts)` даёт **`parts = 2`**.
     - Оркестратор запускает цикл догрузки нарезок `partIndex = 0`, затем `partIndex = 1` отдельными командами `dispatch { task: 'storage.clone', itemKey, payload: { parts: 2, partIndex } }`.
     - Если целевой сервер настолько медленный, что даже `1/2` файла не уложилась в шаг — `attempts` становится `2`, и оркестратор автоматически командует нарезать файл уже на **`parts = 4`** (`8` → `16` → `32`), пока размер одного куска не станет достаточно маленьким, чтобы пролетать без таймаута!
     - Если уже залита часть кусков (например `3` из `8`), а на `partIndex = 3` сервер сообщил `shouldRotate: true` (кончается 5-минутное окно функции) — оркестратор запоминает `cursorPartIndex = 3`, переоткрывает новый `wss://`-сокет и продолжает ровно с `partIndex = 3`!
   - **Сценарий Б — Не сжимается картинка (`action.kind === 'steps'` → `cancel`)**:
     - Попытка 1 не уложилась в вес (`fit_exceeded`) → оркестратор берёт `patches[0]` из схемы (`{ maxBytes: 32768, qualityFloor: 45 }`) и повторяет `dispatch`.
     - Снова `fit_exceeded` → берёт `patches[1]` (`{ maxBytes: 51200, qualityFloor: 38 }`).
     - Если исчерпаны все ступени (`attempts > maxAttempts`) и в схеме указано `onExhausted: 'cancel'` — оркестратор отправляет завершающую команду `{ type: 'dispatch', task: 'image.convert', itemKey, payload: { action: 'cancel' } }`, приложение чисто закрывает зависшую задачу, а оркестратор стирает её из памяти попыток и переходит к следующей!

### Шаг 4 — Пересменка сокета (`rotate`) и итоговый отчёт
- Если в любом ответе пришёл флаг `shouldRotate: true` или кадр `{ type: 'rotate' }`, `transport-ws` штатно закрывает текущий сокет (`1000`), тут же открывает новое соединение к тому же `targetUrl` и продолжает цикл без потери состояния.
- По завершении прохода формируется структурированный отчёт по каждой задаче:
  - кто успешно обработан/склонирован (`completed`),
  - кто остался в очереди на следующий проход (`remaining`),
  - к кому была применена нарезка или смягчение рамок (`escalated`),
  - кто был отменён после исчерпания попыток (`cancelled`).

## 4. Этапы реализации Плана 2 (внешний универсальный сервис)

1. **Этап 1 — Чистое ядро `core/`**: типы `CronManifest`, интерпретатор правил эскалации `escalator.ts` (`scale` с курсором нарезок `partIndex`, `steps`, `cancel`), абстракция `state-store.ts` и сам автомат `orchestrator.ts` + полные юнит-тесты на мок-сервере (включая сценарий прогрессивной нарезки `1 -> 2 -> 4 -> 8` и сценарий смены рамок / отмены картинки).
2. **Этап 2 — Транспорты `wss://` и `HTTP POST` + Hono-приложение**: реализация `transport-ws.ts` (с `ping/pong` и авто-пересменкой `rotate`), `transport-http.ts`, маршрутов Hono (`/health`, `/status`, `/trigger` с защитой по токену).
3. **Этап 3 — Три готовые точки развёртывания**:
   - `adapters/cloudflare.ts` + `wrangler.toml` (под бесплатный Cloudflare Workers Cron Trigger);
   - `adapters/server.ts` + минимальный `Dockerfile` (под бесплатные Docker-площадки и любой VPS);
   - `adapters/gas.ts` + скрипт сборки в единый `dist/Code.gs` (под бесплатный триггер Google Apps Script с `UrlFetchApp` и `PropertiesService`).
