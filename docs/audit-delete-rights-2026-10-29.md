# Аудит: мягкое удаление, права на удаление и схемы (2026-10-29)

Проверка четырёх утверждений владельца по всем моделям приложения
(`user.profile.v1`, `user.auth.v1`, `user.session.v1`, `user.config`,
`user.block`, `demo.post.v1`, `cache.kv.v1`) и инвентаризация того,
что из механизмов удаления реально доступно из UI.

Слой, на который всё опирается (`src/lib/db/resource.ts`):

- мягкое удаление есть только у ресурса с `timestamps.deletedAt`;
  `delete` ставит метку, `delete(..., { hard: true })` — физический
  `DELETE` (`resource.ts:586`);
- `includeDeleted` слой отклоняет без гранта `readDeleted`
  (`resource.ts:233`);
- связка окончательного удаления в слое: политика `delete` плюс грант
  `readDeleted` — но грант расширяет только доступ к **уже удалённым**
  строкам (`idWhere`, `resource.ts:250`: без гранта предикат целит
  только живые строки). Следствие — находка A4.

## Проверка утверждений

### 1. Для окончательного удаления нужны права редактирования

| Модель | Политика `delete` | Вердикт |
|---|---|---|
| `user.profile.v1` | владелец, `server`, `admin`, `profile.edit` | ✔ право записи в политике |
| `user.block` | `server`, `moderator`, `block.edit`, `admin` | ✔ круг записи (модератор — ролью) |
| `user.auth.v1` | владелец, `server`, `admin` | ✘ `account.edit` в модели нет вообще: ни в `update`, ни в `delete` |
| `user.session.v1` | `server`, `admin` | ✘ `session.edit` в модели нет |
| `user.config` | `server`, `admin` | — права записи в каталоге нет, схемы ключей вместо неё (см. п. 4) |
| `demo.post.v1` | `author` | ✘ `editor` есть в `update`, в `delete` не дублируется |
| `cache.kv.v1` | `server` | — служебная, прав человека нет |

### 2. Права редактирования дублируются у чтения

| Модель | Право записи в `select` | Вердикт |
|---|---|---|
| `user.profile.v1` | `profile.edit` | ✔ |
| `user.block` | `block.edit` в круге чтения | ✔ |
| `user.auth.v1` | — | ✘ заодно и само `account.edit` моделью не используется |
| `user.session.v1` | — | ✘ `session.read`/`session.edit` в политиках отсутствуют |
| `user.config` | — | — только `config.read` |

У `auth` и `session` расхождение давнее и в шапке каталога отмечено:
правила этих моделей «примут права отдельным шагом» (`permissions.ts`).
Но описания каталога уже обещают то, чего модель не держит:
`account.edit` — «удалять и восстанавливать», `session.read` — «включая
завершённые» (завершённые = мягко удалённые, а `readDeleted` сессий —
только `server`/`admin`).

### 3. Чтение удалённых не даёт права читать в целом

| Модель | `readDeleted` | Даёт ли заодно живые | Вердикт |
|---|---|---|---|
| `user.auth.v1` | `server`, `admin`, `account.read` | да: `account.read` же стоит и в `select` | ✘ слито в одно право (и так прямо написано в его описании) |
| `user.block` | `server`, `block.readDeleted`, `admin` | да: `block.readDeleted` включён в круг чтения `select` | ✘ (внесено коммитом `cffa687`, см. A3) |
| `user.session.v1` | `server`, `admin` | тех же акторов пускает и `select` | — отдельного права человека нет |
| `demo.post.v1` | не задан (никому) | — | удалённые не читает никто |

Причина у `auth` и `block` одна: у слоя **одна** политика `select`,
и она — функция только от `ctx`, флага `includeDeleted` не видит.
Поэтому «видит только удалённые, живых — нет» одной политикой не
выражается: либо право вписано в `select` (и тогда оно видит и живые),
либо не вписано (и тогда удалённые не достать даже с грантом).

### 4. Схема даёт исключительное право на конкретный ключ

- **Конфиг — да.** `config-api.ts` проверяет схему ключа из данных:
  `editDefault`/`assign`/`editUser`/`deleteUser` глобальной строки и
  упрощённую схему строки юзера; роли — каталог плюс `owner`. Это и
  есть исключительное право на конкретный ключ, которого политикой
  слоя не выразить. Оговорки: `admin` проходит всегда
  (`ruleAllows` проверяет его первым), а прямой доступ к модели
  (`server`/`admin` в политиках) схему обходит — это объявленный
  запасной уровень.
- **Блокировка — нет.** В строках `user.block` схемы нет и по решению
  этапа 9 не будет: сферы — каталог в коде (`spec-block.ts`), права —
  статичные круги модели. Исключительного права «на конкретную сферу»
  или «на конкретную запись» не даётся; понадобилось бы — это уже
  функция по образцу конфиг-API.

| Модель | `deletedAt` | Кто видит удалённые |
|---|---|---|
| `user.auth.v1` | есть (заявка на удаление) | `server`, `admin`, `account.read` |
| `user.session.v1` | есть (отзыв = выход) | `server`, `admin` |

## Кто механизм использует из UI

Подтверждается догадка владельца: кроме seed/profile удалять из UI
нечего.

| Что | Из UI | Механизм под капотом |
|---|---|---|
| Профиль | `ui/profile-delete/` + модалка + роут `/user/[id]/delete` | физическое удаление строки профиля (`profiles.remove`, акторский контекст) — мягкой стадии у профиля нет |
| Seed-аккаунт | чекбокс «также удалить seed» в том же удалении профиля | мягкое удаление `auth` (`markDeleted` = `delete` системным контекстом) + отзыв всех сессий; восстановление — шаг `restore` формы входа; окончательная зачистка — исполнитель `sweepDeletions` по грейсу (стирает креды, строку-надгробие не удаляет) |
| Блокировки | только снятие (`BlockLift`, `until = now`) | записи не удаляются из UI никак — ни мягко, ни окончательно, хотя модель права на это уже даёт |
| Сессии | отдельного UI нет | отзыв — внутренний (выход, «выйти везде») серверным кодом |
| Конфиг | косвенно: приватность при значении = умолчание | `config-api` удаляет строку юзера (`settings.remove` → физический `DELETE`; `hard: true` без мягкой стадии — просто `DELETE`) |
| Демо-записи | форма в `/db-demo` | мягкое удаление автором (`demo.post`) |

## Находки

- **A1. `account.edit` моделью auth не используется.** Ни `select`,
  ни `update`, ни `delete` аккаунтов права не содержат (только
  владелец/`server`/`admin`, чтение списка — `account.read`).
  Каталог при этом обещает «удалять и восстанавливать». Домен список
  и операции ведёт системным портом с собственными проверками,
  поэтому пользовательски всё работает — но нативно моделью право
  не исполняется.
- **A2. `session.read`/`session.edit` — аналогично**: политики сессий
  знают только владельца, `server` и `admin`.
- **A3. `block.readDeleted` даёт и живое чтение** (коммит `cffa687`):
  право включено в круг `select`, иначе удалённые не достать (см.
  п. 3 — ограничение одной политики слоя). По принципу владельца
  это неверно; варианты: оставить как есть осознанно, вынести чтение
  удалённых в отдельную политику слоя (расширение `#lib/db`), либо
  показывать удалённые только `admin`/`server`.
- **A4. Связка на окончательное удаление неполная для живых строк.**
  `delete(id, { hard: true })` без гранта `readDeleted` целит только
  живые строки и физически удаляет живую запись: мягкая стадия
  обходится любым, кто в политике `delete`. Для `user.block` это
  значит: модератор может окончательно стереть **живую** запись
  блокировки, хотя удалённую — не может. Тест этапа 9 проверял
  `hard` только на уже удалённой строке и этого не ловил.
- **A5. У профиля и конфига мягкого удаления нет** — `delete` сразу
  физический. Для профиля это осознанно («удалится сразу»), для
  конфига `hard: true` в адаптере — мёртвый параметр.
- **A6. `demo.post`: `editor` правит, но не удаляет** — право записи
  в `delete` не продублировано (демо-модель, но как прецедент в
  китах она misleading).

## Статус исправлений (2026-10-29, по решениям владельца)

- **A4 — исправлено в слое**: `hard: true` без гранта `readDeleted`
  запрещён и на живой строке (`resource.ts`, `idWhere`); мягкая
  стадия не обходится. Заодно добавлено право `account.readDeleted`:
  у `auth` грант `readDeleted` и чтение удалённых убраны из
  `account.read`, описание права поправлено.
- **A3 — исправлено в слое**: политика `selectDeleted` — чтение с
  удалёнными может идти отдельным правилом (`rules.ts`, `where`,
  пути чтения/`count` в `resource.ts`); у блока право удалённых
  из живого `select` убрано, у auth заведено `selectDeleted`.
- **A6 — исправлено**: `editor` у `demo.post` добавлен в `delete`.
- **A1/A2 — отдельный план**: `docs/plan-auth-session-rights.md`
  (когда будем делать компоненты сессий).
- **A5 — без изменений**: профиль удаляется физически осознанно;
  мёртвый `hard: true` у конфига оставлен как есть.
