# План: узел `exists` в грамматике `Filter` (lib/db)

Заказ владельца (2026-10-28). Политика модели сегодня — функция
`контекст → Filter`, а `Filter` умеет условия только по своим
колонкам: «строка видна/изменяема, если в **другой модели** есть
связанная строка в нужном состоянии» слоем не выражается (профиль
по конфигу, аккаунт по сессии, список по наличию профиля — всё это
сейчас обошлось бы доменной резкой в памяти или зеркальными
колонками). Вводим общий узел `exists` в грамматику `Filter`.

Требования владельца:

- В узле указывается **конкретная модель** (объект ресурса), а не
  таблица и не строковый ключ: таблицу, поля, политику и мягкое
  удаление слой берёт из определения модели.
- Сразу поддержать **несколько** `exists`: любая композиция
  существующими `and`/`or`/`not`, несколько узлов в одной политике,
  вложенные `exists` (внутри `where` цели — свой `exists`, включая
  ссылку модели на себя).
- Механизм общий: любая пара моделей, любая операция, где `Filter`
  становится `WHERE`. Узких «проверок конфига» в слое не появляется;
  конфиг — первый потребитель, не повод.

## Форма узла (этап 1 фиксирует окончательно)

```ts
| { exists: {
    from: Resource;                              // модель, не таблица
    on: readonly (readonly [string, string])[];  // пары [своё поле, поле цели], ≥1
    where?: Filter;                              // условия по полям цели; вложенный exists допустим
    policy?: boolean;                            // default true — внутри действует select-политика цели
  } }
```

Правила узла:

- **Только серверный.** `filterSQL` допускает `exists` лишь в
  доверенных фильтрах (`trusted` — политики и именованные правила);
  клиентский фильтр с `exists` отклоняется (`forbidden`), как сегодня
  отклоняются поля без гранта на операцию. Существованием чужих
  строк клиент не зондирует ничего.
- **`policy: true` по умолчанию**: внутри подзапроса дополнительно
  действует `select`-политика цели (как в `linkSQL` ключей доступа),
  чтобы фактом существования нельзя было подсмотреть то, что читать
  нельзя. `policy: false` — осознанное исключение в объявлении
  (пример: профиль↔конфиг — гость конфиг не читает, но видимость
  профиля — правило самого профиля).
- **Мягко удалённые цели не считаются**: условие `deleted_at IS NULL`
  дописывается автоматически, как везде в слое.
- **Алиасы уникальны в пределах запроса**: `kit_exists_<n>` по
  счётчику сборки (не константа `kit_link`, как у ключей доступа:
  несколько и вложенных узлов в одном запросе обязаны сосуществовать,
  включая ссылку модели на себя).
- **Один SQL.** Узел — операнд единого `WHERE` (политика AND ключи
  доступа AND клиентский фильтр AND не удалённые), include — те же
  `LEFT JOIN LATERAL` в том же запросе; построчных запросов нет.
  Скорость обеспечивает индекс по полям `on` цели — ответственность
  объявления модели (`db.indexes`/`db.unique`).
- **Лимиты — существующие**: узел считается в `filterNodes`,
  вложенность — в `filterDepth`; новых квот не вводим.
- Значения — только параметрами (`fieldParam`/`param`), как весь
  `filterSQL`; имена полей и операторов валидируются по модели цели
  тем же кодом (рекурсивный `visit` по ресурсу цели).
- `insert` узла не касается (политика вставки — булева от контекста,
  черновика не видит — как было). `without(['policy'])`/`raw` узел
  гасят вместе с политиками — стандартная семантика слоя.

## Этап 1. Ядро в `lib/db`

1. `types.ts`: вариант узла в `Filter` (модель — объектом ресурса).
2. `query/sql.ts` (`filterSQL`): ветка `exists` — рекурсивный рендер
   `EXISTS (SELECT 1 FROM <таблица модели> AS kit_exists_<n> WHERE
   <пары on> AND <where> AND <политика цели при policy:true> AND
   <не удалена>)`; пары `on` — равенства колонок своей строки и цели;
   отказ недоверенному фильтру.
3. README слоя (`src/lib/db/README.md`) — раздел про узел: форма,
   серверность, `policy`, алиасы, лимиты; в том же коммите (контракт
   слоя меняется).
4. Тесты слоя (`src/lib/db/test/`, PGlite-фикстуры — две-три модели
   с связью по полю):
   - один `exists` в `select`-политике: видна/не видна строка;
   - **несколько**: `and` из двух `exists` по разным моделям;
     `or` из двух; `not exists` — отсутствие связанной строки;
   - **вложенный**: `exists`, чей `where` содержит `exists` по
     третьей модели; ссылка модели на себя;
   - составной `on` из двух пар; `exists` без `where` (чистое
     наличие);
   - `policy: true` прячет существование недоступной цели,
     `policy: false` — показывает (оба поведения заперты тестами);
   - мягко удалённая связанная строка существованием не считается;
   - клиентский фильтр с `exists` — `forbidden`; превышение
     `filterDepth`/`filterNodes` на вложенности — `validation`;
   - узел в `update`/`delete`-политике: запись разрешена/запрещена
     по связанной строке;
   - сгенерированный SQL — один запрос: `EXISTS` внутри единого
     `WHERE` (утверждение по тексту запроса, без замера плана).
5. Приёмка этапа: гейты `npm run check`, `layer-guard`, тесты слоя
   и полный vitest зелёны; чужие потребители слоя не сломаны
   (полный прогон обязателен — меняется общая грамматика).

## Этап 2. Перенос мест на `exists`

Каждое место со своим тестом; поведение для пользователя не меняется,
меняется уровень, на котором держится правило.

1. **Приватность профиля** (этап 8 плана seed-списка, потребитель №1):
   `select`-политика `user.profile` получает ветку
   `exists(user.config, on: [auth_id→auth_id], where: key =
   'profile.visibility' AND значение допустимо контексту,
   policy: false)`; доменная резка проекцией и зеркальная колонка
   не нужны — гарантия на уровне модели для любого читателя слоя.
   План этапа 8 правится ссылкой сюда в том же коммите.
2. **Список seed-юзеров — «профиль создан / не создан»**: различие
   переезжает с include и ручных срезов на `exists`/`not(exists)` по
   модели `user.profile` (`on: [id→auth_id]`) в доменном запросе
   списка; фильтр состояния профиля, если вводится в UI, — тот же
   узел.
3. **Конфиг-модель** (этап 10 плана seed-списка): удаление ключа
   умолчания при живых юзерских переопределениях проверяется
   `exists` по той же модели (`on: [key→key]`, строка юзера с тем же
   ключом) в конфиг-API; выборки «у кого ключ закреплён» для раздела
   управления — тот же узел от модели аккаунтов.
4. **Аккаунты по связанному состоянию** (образцы этапа, применяются
   при появлении потребителя — код под них сейчас не пишется):
   аккаунты с живой сессией (`exists` по модели сессий: не отозвана,
   срок не истёк), очереди «есть необработанная связанная запись»,
   `update`/`delete`-политики «только если связанная строка в
   состоянии S» — обобщённый преемник частных проверок ключей
   доступа там, где FK в самой строке нет.

Приёмка этапа: тесты домена по пп. 1–3 (политика профиля — на модели:
гость/юзер/владелец × три уровня видимости; список — создан/не создан
без include-раздувания; конфиг-API — отказ удаления умолчания при
живых переопределениях), гейты стандартные, README модулей — в тех
же коммитах.

## Не делаем

- `notExists` отдельным узлом (есть `not`), клиентский `exists`,
  агрегаты/`count` в узле, условия по вычисляемым выражениям —
  узел только про равенство пар полей и `Filter` цели.
- Не трогаем ключи доступа (`access`/`link`): они про FK-строку и
  именованные правила; `exists` их не заменяет и не дублирует.
