# Разбор плана ускорения тестов: что подтвердилось, что нет, где лучше

Проверка `docs/plan-test-speedup-2026-10-30.md` замерами на ветке `img` (`357fa80`), стенд — 2 vCPU /
1.9 ГиБ RAM, Node 22.23.4, Chromium через Playwright 1.63. Все цифры ниже сняты командой, а не оценены.

## Короткий вывод

План смотрит в верном направлении, но **неверно раскладывает бюджет времени** в главном файле и
недооценивает объём работы: он считает, что 165 s в `db-demo.mjs` + `paginate.mjs` — это сны,
`networkidle` и задержка демо-источника. Фактически **60 s из 93 s в `db-demo.mjs` — две проверки,
которые гарантированно ждут впустую до 30-секундного таймаута**. Без этой находки, честно выполнив
весь план, в его же критерий приёмки (35–45 s на два файла) не попасть.

При этом план **неполон по охвату**: он целится в два файла (163.9 s из 552.3 s, то есть 30 % набора),
а самые дорогие после них — `forms-a11y` (63.3 s, `axe-core`), `regressions` (61.4 s), `forms` (47.0 s),
`modals` (41.5 s), и в них лежит больше безусловных пауз, чем в целевых двух файлах.

### Где на самом деле уходит время в `db-demo.mjs`

Профиль по местам вызова (сумма ожиданий 92.0 s при стене 92.9 s — сходится):

```
   30.0 s ×  1  test/browser/db-demo.mjs:109 → textContent
   30.0 s ×  1  test/browser/db-demo.mjs:287 → innerText
    7.0 s ×  1  test/browser/db-demo.mjs:344 → waitForTimeout      (тот самый «7 s тиков»)
    3.9 s ×  1  test/browser/db-demo.mjs:321 → waitForFunction
    2.3 s ×  1  test/browser/db-demo.mjs:496 → waitFor
    1.5 + 1.5 + 1.2 s — остальные waitForTimeout
   остальное — 15 goto по 0.6–0.9 s и 10 waitForFunction по ~0.5 s
```

Две верхние строки — не «медленные проверки», а **дефект ожидания**: `textContent()`/`innerText()` у
ОТСУТСТВУЮЩЕГО узла не возвращает `null` сразу — Playwright ждёт появления узла весь свой таймаут
(по умолчанию 30 с) и только потом бросает исключение, которое `.catch()` молча превращает в `null`/`'нет'`.
То есть сьют 60 s из 93 ждал того, чего по условию проверки быть не должно.

## Что сделано (лучше, чем в плане) — и проверено

`test/browser/db-demo.mjs`: сначала `count()` (мгновенный), текст читается только у существующего узла
и с коротким таймаутом. Плюс устранена гонка «срез: возврат на 1-ю страницу…» (строки читались раньше
отрисовки; падало через раз как `back1Ids: []` — теперь ждём ожидаемое число строк).

Замер: **93.2 / 93.6 / 93.1 s → 33.1 / 33.5 / 33.5 / 32.9 s** (4 прогона, все зелёные), покрытие 1-в-1.
Это **60 s за 4 строки диффа** — столько план рассчитывал снять со всего файла ценой разбиения 525 строк
на секции, вычистки 13 `waitForTimeout` и переделки live-опроса на ожидание тиков.

## Что план упускает по охвату (и это дороже его целей)

1. **`waitForTimeout` — самая дорогая категория во всём наборе**, а не только в двух файлах:
   `forms` — 26.5 s / 43 вызова, `regressions` — 17.8 s / 64 вызова, `forms-a11y` — 16.7 s / 19 вызовов,
   `db-demo` — 12.5 s. Механическая замена «фиксированная пауза → ожидание факта» по всем сьютам даёт
   больше, чем построчный рефакторинг двух файлов.
2. **`forms-a11y` (63.3 s) почти весь — полезная работа `axe-core`**: из 60.7 s стены инструментарий
   видит только 18.4 s, остальное — `axe.run()` внутри `page.evaluate`. Ускорять там надо не паузы,
   а число прогонов axe на состояние (одна инъекция на страницу, а не на проверку).
3. **Процессная обвязка — не проблема, параллелизм — проблема.** 16 последовательных процессов стоят
   ~1 s на запуск каждый; выигрыш оркестратора из T4 — единицы секунд. Зато **параллельный запуск двух
   сьютов** (2 vCPU) даёт ~40–45 % от 552 s, и плана это не касается. Ограничение — память (ниже).
4. **`TEST_FILTER` — полезно, но дешевле делать это иначе**: сьюты и так запускаются по одному
   (`npm run test:browser:db-demo`), а внутри секционный фильтр нужен редко; вложение в `_harness.mjs`
   окупается только если им же заменить `networkidle` и паузы, то есть T1 и T3 — одна работа, не две.

## Ловушки окружения, которых в плане нет

- **Preview-сервер умирает по OOM** на 1.9 ГиБ: один прогон полного набора закончился `exit 137`
  (`Killed`) — PGlite в памяти + Chromium + node не влезают. Отсюда: оркестратор из T4, который держит
  ОДИН сервер на весь прогон, превращает это в единую точку отказа; сервер надо поднимать с
  `NODE_OPTIONS=--max-old-space-size=1000..1100` и перезапускать при падении.
- **Нельзя пересобирать проект при живом `vite preview`**: `npm run build` переписывает
  `.svelte-kit/output`, и сервер падает на `ENOENT` ассета (поймано на себе). В плане этого нет, а при
  отладке тестов соблазн большой.
- **`npm run check` падает по OOM** при дефолтном heap на этом стенде; с `--max-old-space-size=1400` —
  `0 errors, 0 warnings`. План рекомендует 1536 — сходится.
- **Разброс `vitest src/lib/db`**: 46.6 / 50.6 / 76.8 / 79.3 s на одном и том же коде (в один заход
  прогон с `--maxWorkers=1` упал с rc=1, в другой — прошёл). Любые «до/после» по этому пакету надо
  мерить сериями и сравнивать медиану, иначе вывод будет про шум.
- Playwright в песочнице требует `playwright install --with-deps chromium` (без `libnspr4` браузер не
  стартует), и версию браузера надо ставить из локального `node_modules` (1.63), а не глобально.

## Как выглядит исправленный план (по отношению «секунды / риск»)

1. **T0 — выжигания таймаутов** (сделано, 60 s): найти в сьютах `textContent/innerText/waitFor*` у
   заведомо отсутствующих узлов и убрать `.catch()`-маскировку. Проверять профилем по местам вызова,
   а не глазами.
2. **T1' — механическая замена пауз** во ВСЕХ сьютах (не только в двух): `waitForTimeout(n)` →
   `waitForFunction`/`waitForResponse`/`expect.poll`. Ожидаемо 60–70 s по `forms`, `regressions`,
   `forms-a11y`, `db-demo`.
3. **T2' — `networkidle` → детерминированное ожидание** (35 мест): измеренная экономия 16.7 s; делать,
   но последним из «ожиданий», потому что с `T1'` часть вызовов исчезнет сама.
4. **T3' — `DEMO_TRANSPORT_MS` через явный тестовый сигнал**, оставив 500 мс секциям скелетонов; при
   этом помнить, что затронутых секций меньше, чем «все, кроме двух» — точный список даёт прогон с
   задержкой 0 (падает на первой проверке скелетонов).
5. **T4' — параллелизм 2 сьюта, а не оркестратор**: `MAX_PARALLEL=2` с общим preview, лимитом heap и
   перезапуском сервера; профит ~40 % против единиц секунд от «один процесс вместо шестнадцати».
6. **T5' — `isolate: false` для `src/lib/db`** (10 холодных стартов PGlite → один на воркер):
   дешевле `dumpDataDir/loadDataDir`, но мерить медианой. Изолированный холодный старт сохранить для
   `db-sync*` и самопроверки `withTestDb`.

## Что осталось непроверенным

- Точная экономия от гейта `DEMO_TRANSPORT_MS`: требует правки самих секций (T3'), в этой проверке не
  реализована; верхняя граница видна по падению при `0`.
- `TEST_FILTER` ≤ 5 s: не реализован, оцениваю по времени старта сьюта (~1 s) + первая секция.
- Параллельный прогон 2 сьютов: не запускался — на 1.9 ГиБ есть риск OOM сервера, нужен прогон с
  замером памяти.
