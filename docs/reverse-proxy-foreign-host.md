# Reverse proxy с Host внешнего ingress

Некоторые ingress направляют запрос к приложению только если upstream `Host` совпадает с их доменом. Если браузер использует `https://edge.example`, а прокси отправляет запросы на `https://origin.example`, сохранение `Host: edge.example` может вернуть ошибку маршрутизации до приложения. Проверяйте это на конкретном ingress; не предполагайте, что все платформы ведут себя одинаково.

Для такой схемы можно передавать upstream `Host: origin.example`, оставляя браузерный `Origin` без изменений. При этом приложение видит origin запроса `https://origin.example`, а браузер присылает `Origin: https://edge.example`. Значит, внешний origin нужно **явно** разрешить в `KIT_TRUSTED_ORIGINS`:

* Укажите точный origin с правильной схемой и, если используется нестандартный порт, портом. Не разрешайте произвольные origin.
* Передайте значение и на **сборку**, и в **runtime**: SvelteKit формирует `csrf.trustedOrigins` при сборке, а проверки форм/WS приложения используют runtime-настройку. Изменение только runtime не исправит проверку CSRF внутри уже собранного SvelteKit.
* Сохраните прежние разрешённые origin, если они необходимы. Node `server.mjs` проверяет пришедший `Host` по `NF_HOSTS`, `ORIGIN` и `KIT_ALLOWED_ORIGINS`. Сам по себе `X-Forwarded-Host` не меняет вычисленный origin и не заменяет корректный upstream Host.
* Используйте HTTPS до ingress и проверку сертификата и имени upstream. Не включайте `tls_insecure_skip_verify`. Для Caddy проверьте документацию своей версии: поведение `Host` для HTTPS upstream менялось между версиями. Явная настройка не отменяет проверки реального маршрута и TLS.
* Адреса из заголовков прокси не следует считать настоящим IP клиента без отдельно проверенной цепочки доверенных peer, правил перезаписи и защиты от прямого обхода. `KIT_TRUSTED_ORIGINS` разрешает origin для проверок форм; он **не** аутентифицирует VDS и не делает безопасными произвольные `X-Forwarded-*`.
* Redirects, абсолютные ссылки и cookies тоже нужно проверить через внешний домен. Не предполагайте, что настройки успешного POST автоматически решают все маршруты и внешние интеграции.
* Caddy при смене конфигурации может закрывать открытые WebSocket. Вариант `stream_close_delay` лишь откладывает закрытие и требует отдельного выбора и тестирования; аварии и переключение на другой экземпляр им не решаются.

## Изолированная браузерная проверка

В demo-модуле есть `/upload-demo`. Специальный сценарий `test/browser/proxy-rewritten-host.mjs` проверяет SSR, настоящее отправление файла по WSS, побайтное скачивание, нативную форму без JavaScript и отказ POST/WS от чужого Origin. Он изменяет **память demo-сервиса**, поэтому запускайте его только на изолированном стенде или при явном согласии на тестовые записи.

Предварительно соберите demo, задав точный внешний origin в build-time и runtime `KIT_TRUSTED_ORIGINS`, и настройте прокси с переписанным upstream Host. После установки Playwright и браузера:

```sh
EDGE_TEST_BASE=https://edge.example \
EDGE_TEST_ALLOW_WRITES=yes \
node test/browser/proxy-rewritten-host.mjs
```

Для локального стенда с собственным недоверенным сертификатом дополнительно можно задать `EDGE_TEST_INSECURE_TLS=1`. Не используйте этот флаг для публичного подключения: в нём проверка TLS сертификата браузером и отрицательными HTTP/WS-запросами отключается.

Для настоящего деплоя дополнительно проверяйте TLS/SNI, правила и домены ingress, DNS, сертификат публичного домена, cookies, возможный прямой обход и доступ со стороны реального клиента. Локальный тест не подтверждает эти свойства.
