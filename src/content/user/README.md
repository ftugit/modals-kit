# `src/content/user` — модуль пользователя (вход по seed, сессии, профиль, ACL)

Автономный доменный модуль приложения: Ed25519-подпись `seed` по запечатанному challenge-токену (stateless, без серверного хранилища nonce), оба токена сессии в `HttpOnly`-куках, клиентское зеркало `access` в RAM (`vault`), таблицы аккаунтов/сессий/профилей в `#lib/db`, UI ACL на 21 экран и маршрутно-независимые формы компонентов через `#hooks/component-form`.

---

## Модуль приложения, а не библиотека

Папка в `src/content/` принадлежит предметной области «пользователь» (наравне с `demo-catalog/posts/posts.ts` и источниками каталогов), а не переиспользуемому слою `src/lib/`. В одном месте собраны ресурсы БД, чистые доменные функции, адаптеры портов, серверный фасад кук и самодостаточные UI-компоненты.

## Состав

| Путь | Назначение |
|---|---|
| `schema.ts` | Пять ресурсов `#lib/db`: `user_auth` (`AUTH_ACL`: владелец читает и мягко удаляет свою строку, создаёт только `server`; `seed`, времена + soft delete, соль подсетей), `user_profile` (неуникальный никнейм с запрещённым списком, `avatar_url`, пирамида `PROFILE_ACL` с расширением публичной видимости через `extend.select`), `user_session` (`SESSION_ACL`: владелец читает, меняет имя и мягко отзывает; `jti` и срок пишет только `server`; отзыв = soft delete), `user_config` (конфиг-модель: ключ/значение/`auth_id`/`schema`; уникальность пары — частичные индексы ручным SQL в `db.server.ts`; гранулярные права `assign`/`editUser`/`deleteUser`/`editDefault` живут в `ConfigKeySchema` строк умолчаний. **Исключение:** модель задана низкоуровневым `policy`, а не `acl: defineAcl(...)`, — см. «Единый слой прав»), `user_block` (блокировки на `BLOCK_ACL`: цель/сфера/причина/срок/автор; подотчётный `moderator` имеет `insert` + `update` только срока `until` + мягкое `softDelete` без права менять `reason` и без `hardDelete`). Шаг подтверждения двухрежимный: на странице — URL-ключ (`sessions-exit` у списка, `session.exit` у карточки; ключ списка не входит в семейство пагинатора `sessions.*`), в модалке — локальный хост шагов (`mode="modal"`), адрес носителя не читается и не пишется. Адрес журнала берётся из реестра (`sessionsJournalRoute`). Цель списка и фильтров — один `SessionsTarget` (`own|account|journal`); фильтры получают цель явными параметрами пары (`uid`, `journal`), а не разбирают адрес носителя `from`. Литералы пути и разбор журнала на месте держит страж `tooling/journal-path-guard`. |
| `profile.ts` | Профильный API отдельно от `auth.ts`: `profile` (чтение: строка + признак `notCreated` — владелец/права чтения отличают «не создан» от отказа), `updateProfile`, доменная проверка аватара по заголовку (`probeImageHeader`). | `ui/logout/` + `ui/LogoutModal.svelte` | Выход — пара `user.logout` (модалка; без JS — роут `/user/logout`). Шаг подтверждения на странице живёт в адресе (`?logout.step=confirm`), в модалке — локально (`mode="modal"`); чекбокс стоит на том же экране, что и отправка, — поэтому no-JS не теряет ни шаг, ни намерение. Удержание — только когда в наборе больше одной строки. Третий сценарий, локальный выход (`?/local`, `logoutLocal` гейтвея), снимает куки без отзыва: им можно выйти даже тогда, когда актора уже не прочитать (без него `load` отдаёт `canRevoke: false` и экран показывает только эту кнопку). Экшены наборов выносит общий хелпер `sessions-exit.server.ts`: куки снимает гейтвей и только когда в снятых есть текущая сессия. Адрес назначения задаёт сервер, а не страница-носитель: закрыл набор и текущую сессию — уводит на `doneHref` (`/user/auth`), закрыл чужие — возвращает к списку (`selfHref`). Отсюда же адрес POST: наборам нужны экшены конкретных роутов (`?/exit` у `/user/logout`, `?/others` у списков сессий), поэтому `ExitSteps` требует `action` пропом, а модалка выхода берёт адрес из реестра — относительный `./?/…` ушёл бы на страницу-носитель, где такого экшена нет. |
| `ui/UserPickerSteps.svelte` | Прототип админки на хосте шагов (`steps`, сценарий «удаление пользователя»): список с параметрной механикой строк — нажатие переключает id в `?picked=id,id` адреса (выбор читается из адреса, переживает шаги и переходы без состояния в компонентах); шаг «Выбранные» — тот же список со срезом `ids`; отказы списка носителю рисует этот компонент экраном `Acl`. Доказательство, что компонентам не нужна подача данных носителем, а механику меняет только фабрика атрибутов у списка. |
| `ui/blocks-list/`, `ui/block-form/`, `ui/block-delete/` | Система управления блокировками (`user.block`) на реактивном `useGrants`: пагинированный список `BlocksList` (по пользователю `/user/[id]/blocks` и глобальный `/blocks`, передающий активный фильтр `uids` за вычетом `vault.principal` в создание) с фильтрами `BlocksFiltersForm` и пикером `UserPicker`, единая карточка `BlockForm` (`create` по схеме `1 + 3` — `field.multiselect` `subjects` с предзаполнением из фильтра `uids` без `actor.id`, множественный `user.picker` под гейтом `useGrants([grants(auth).select, grants(block).insert])` и защита от случайного массового бана через `HoldButton` при `N > 1`; `edit` и read-only просмотр без отправки для читателей), `BlockDelete` с `HoldButton` и условным полным удалением `hard` по `grants(block).hardDelete`, а в `Profile.svelte` — кнопка перехода к `user.blocks` в обоих состояниях профиля (`profile` и `notCreated`). |
| `ui/BanNotice.svelte` / `ui/RestrictionsNotice.svelte` | Экраны полной блокировки (`scope: 'auth'`) и частичных ограничений аккаунта. |
| `ui/AuthWidget.svelte` | Тонкий координатор шагов потока входа (`auth.*` / `blocked` / `restrictions` / `profile`, адрес — `?stage=auth.restore`) + связка `formSteps`. |
| `ui/MenuBody.svelte` / `ui/MenuModal.svelte` / `ui/UserMenu.svelte` | Меню пользователя под `<Acl allow="user">` (аватар, никнейм из спеки при пустом, чтение своего профиля — модалка `user.profile`/роут `/user/<id>`, переход к `?stage=profile`, выход) и кнопка в шапке. На узкой ширине аватар открывает меню модалкой `user.menu`; на широкой — `Floating` без URL (без JS — страница `/user/menu`). |
| `index.ts` | Публичная точка входа доменного ядра. |

## Цепочка вызова

```
POST <любой маршрут> (__form_id = user-seed | user-profile)
  ─> componentFormsHandle (src/hooks/component-form/server.server.ts)
  ─> execute (ui/seed-form/seed.form.server.ts | ui/profile-form/profile.form.server.ts)
  ─> gateway auth(event) ─> core api (auth.ts / profile.ts) ─> факт { code, path?, args? }

любая страница (SSR): +layout.server.ts ─> resolveVault(event) ─> data.user + authStamp ─> vault
```

Ядро (`auth.ts`, `profile.ts`) не знает `Request` и `Cookies`: на входе данные и порты, на выходе результат или доменный факт.

## Выключение без секрета

Если `AUTH_SEAL_SECRET` не задан, подсистема входа мягко выключается без `500`: `<Acl enabled={false} />` показывает экран «Вход временно отключён», `resolveVault` возвращает `null`, а серверные обработчики отвечают `auth.disabled` (`503`) на все действия, кроме `logout`.

## Генерация `seed` при создании аккаунта

- **С JavaScript** — ключ генерируется локально в браузере (`generateKeyPair()` в `AuthWidget.svelte`) при переключении шага без обращения к серверу; приватный материал не попадает в HTML-ответ.
- **Без JavaScript / по прямой ссылке `?stage=auth.register`** — `registerSeed` создаёт сервер в `load`, и `SeedForm` показывает явное предупреждение, что ключ присутствовал в HTML ответа.

## Единый слой прав: `defineAcl`, `checkGrants` и `useGrants`

Все проверки прав в домене (`blocks.ts`, `accounts.ts`, `profile.ts`, `config-api.ts`) и в UI-компонентах (`Profile.svelte`, `BlocksList.svelte`, `BlockForm.svelte`, `BlockDelete.svelte`, модалки и фильтры) опираются на единственный источник истины — объявления моделей в `schema.ts`:

1. **Модели (`schema.ts`)** объявляют пирамиду прав через `defineAcl` (`BLOCK_ACL`, `PROFILE_ACL`, `CONFIG_ACL`):
   - `readDeleted` всегда конъюнктивен (`select` **И** `deleted`): сервисная роль чтения удалённых никогда сама по себе не открывает чтение живых или удалённых записей.
   - На `user_block` роль `moderator` — подотчётный исполнитель: входит в `insert`, `update` и `softDelete`, но **не** входит в `edit`. Поэтому модератор не может менять защищённое поле `reason` (`update: BLOCK_ACL.roles.edit`) и не может физически стереть улику из БД (`hard: true`), даже если ему дополнительно выдали `block.readDeleted` (`hardDelete` требует круг `edit` **И** `deleted`).
   - При инициализации `schema.ts` все ресурсы с `acl` проверяются стражем `validateResourceAcl` (с явными точечными исключениями `allowAnomalies` для системных ролей вставки `'server'`).
   - **`user_config` стоит на низкоуровневом `policy`, а не на `defineAcl`.** Для неё страж аксиом и генерация чтения из записи **не работают** (`expandAcl` отдаёт `enforceGuard: false`): `'admin'` и `'server'` попадают в чтение только потому, что вписаны в `policy.select` руками через `CONFIG_WRITERS`. Гранулярные права `assign`/`editUser`/`deleteUser`/`editDefault` живут в `ConfigKeySchema` строк умолчаний, а не в ACL модели. Инвариант «роль из записи входит в чтение» здесь держится на авторе, а не на механике — это единственная пользовательская модель-исключение в модуле.
2. **Домен (`blocks.ts`, `accounts.ts`, `profile.ts`)** вычисляет возможности синхронно через `checkGrants(actor, grants(resource), { ownerId })` без дублирования массивов ролей.
3. **Сессия и UI (`vault.permissions` + `useGrants`)**: короткоживущая кука `auth_tmp` несёт массив `perms`, который `readVault` / `vaultPayloadOf` отдают в `VaultSessionMeta.permissions` (`0` дополнительных запросов к БД). В компонентах `useGrants(...)` из `src/content/user/grants.svelte.ts` читает `{ id: vault.principal, permissions: vault.permissions }`:
   - на живой сессии (`vault.principal !== null`, включая SSR и клиент) `useGrants` является авторитетным реактивным источником и мгновенно перестраивает интерфейс при смене сессии/прав через `BroadcastChannel`;
   - при `vault.principal === null` (изолированные SSR-юнит-тесты с мок-пропсами `initial*` без `page.data.user`) компоненты безопасно опираются на переданные флаги данных.

## Эталон вызова компонента

Правило, по которому сверяются все списки и формы модуля. Оно нигде не было
сформулировано целиком, поэтому отдельные места от него отступают.

1. **Актор — только из куки.** Активный пользователь приходит из `HttpOnly`-куки
   через `guard()` (`g.sub`, `g.perms`) или на клиенте из `vault`. Из URL он
   не читается никогда.
2. **Цель — из пути, не из query.** Чей объект смотрят, задаёт сегмент пути
   (`/user/[id=uuid]/blocks`, `/user/[id=uuid]/sessions`) или аргумент серверного
   `load`, но не `searchParams`. Так цель нельзя подменить из адресной строки.
3. **Фильтры — из URL, но через whitelist и кламп.** Числа ограничиваются
   (`num(raw, 1, 1, 10_000)`), перечисления сверяются с закрытым списком
   (`BLOCKS_ORDERS.includes(...)`), списки id режутся по количеству (`.slice(0, 500)`).
   Ни одно значение из адреса не попадает в запрос напрямую.
4. **Права решает домен, компонент — только отрисовка.** Проверка живёт в доменной
   функции (`checkGrants` + ACL модели); компонент получает готовые флаги
   (`canSeeDeleted`, `canPickUsers`, `canCreate`) в ответе и по ним рисует UI.
   `useGrants(...)` в компоненте — тот же `grants(resource)`, но для показа/скрытия,
   а не дверь к данным.
5. **Фильтр, требующий права, без этого права не применяется.** Флаг возможности
   уходит наружу для отрисовки — но и сам фильтр тоже обязан проверяться.
   Отступление: `blocks.uids` в `blocks.ts` кладётся в запрос без `canPickUsers`
   (модель всё равно режет выдачу по ACL, так что утечки нет, но правилу место
   не соответствует).
6. **Всё, что домен умеет, имеет дверь в UI** — либо это зафиксировано как
   осознанное решение. Иначе возможность есть, а попасть в неё нельзя.

## Приватность профиля (этап 8)

Видимость чужого профиля — переопределение ключа `profile.visibility`
(`all`/`users`/`nobody`, bootstrap `nobody`) за владельцем. Строка профиля
видна чтению по `exists`-ветке select-политики (`on: [auth_id, auth_id]`
по конфигу, самоссылка — только `policy: false`): политики моделей не
меняются. Домен `publicProfile` отдаёт чужим публичную проекцию
(`nickname`, `avatarUrl`, `createdAt` — без `id`/`auth_id`/`updatedAt`)
и только при разрешённом уровне; фасад для публичного показа смотрит на
сырой `access()` — истёкший токен равен гостю. Владелец и держатели прав меняют и просматривают параметры компонентом
`ui/user-config/` (пара `user.config.edit` → `/user/config` и `/user/[id]/config`,
записи — конфиг-API: значение = умолчание строку не плодит; ключи только для
чтения показываются строками `read-only`). Носители (роут/модалка) показывают
публичный показ без ACL-экрана, отказ возможен только фактом запрета
конкретного показа.

## Приватность и известные ограничения

- Полный IP-адрес не сохраняется никогда: в сессии пишется только `SHA-256` подсети (`/24` для IPv4, `/48` для IPv6) с индивидуальной солью аккаунта и код страны.
- Аватары профилей никогда не сериализуются в `base64` ни в БД, ни в куку `auth_tmp`: `user_profile.avatar_url` хранит короткую неизменяемую ссылку `/api/storage/avatars/…` в боевом хранилище `appStorage` (`src/server/app-storage.server.ts`), а при замене аватара или удалении профиля старый объект немедленно удаляется через `storage.remove`.
- Исполнитель окончательной зачистки `sweepDeletions` реализован в `auth.ts`; подключение к внешнему планировщику остаётся на усмотрение боевого окружения.

Пакетный отзыв (`revokeBulkSessions`) принимает серверный срез `where` (тот же построитель `sessionsWhere`, что у списка), исключения `except` и флаг `includeCurrent`. Предел исключений — `SESSIONS_BULK_IDS_LIMIT` (одно объявление в `types.ts`): больше — отказ `auth.limit`, а не усечение. Пустой срез — `session.nothing-to-close`. Экран выхода (`onlyCurrent`) закрывает одну текущую сессию, id сервер знает из куки.

Экран своих сессий показывает по 30 записей; ссылки страниц ведут на `/user/sessions?page=…` и работают без JavaScript (из модалки открывается страница). Статус активности обновляется раз в 30 секунд.
