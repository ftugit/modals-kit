# План исправления

Что чинится: места, где разработчик вынужден править саму библиотеку, и показ ошибок.

Основной приём: знание принадлежит тому, кто им обладает. Центральная таблица, которая
перечисляет чужие свойства, заменяется свойством, объявленным владельцем.

---

## Этап 1. Открытые ключи вместо замкнутых объединений

**Сейчас.** `ValueKind`, `InputMode`, `RuleName` — литеральные объединения.
`registerFieldType` есть, но бесполезен: таблицы типизированы этими объединениями,
и новый ключ в них не положить.

**Становится.** Ключи — строки, типизация возвращается расширением интерфейса
на стороне приложения.

```ts
// библиотека
export interface FieldValues { }              // пусто, расширяется потребителем
export type ValueKind = keyof FieldValues & string

// приложение
declare module '$lib/form' {
  interface FieldValues { rating: number | null }
}
registerFieldType({ kind: 'rating', /* … */ })
```

То же для правил. Встроенные типы и правила объявляют свои записи тем же способом.

**Готово, когда:** приложение добавляет тип поля и правило, не меняя ни одного файла
в `src/lib/form`. Проверяется тестом, которому доступен только публичный экспорт.

## Этап 2. Словарь ограничений вместо таблиц

**Сейчас.** `COMPAT` (матрица правило × тип) и `ATTR_TABLE` (правило → атрибут) —
литералы в ядре, плюс один `switch` с восемью причинами отказа.

**Становится.** Три связи — применимость, проекция в разметку, причина отказа —
не живут ни в центре, ни целиком в типе, ни целиком в правиле. Посредник — **словарь
абстрактных ограничений**.

- Правило говорит, к какому виду ограничения оно относится: «нижняя граница величины»,
  «набор допустимых значений», «формат строки».
- Тип значения говорит, какие виды умеет проецировать в разметку и как.

```ts
// правило относит себя к виду ограничения
fn.describe = () => [{ constraint: 'minBound', value: n, safeAsAttr: !exclusive }]

// тип умеет проецировать известные ему виды
registerFieldType({
  kind: 'number',
  inputs: ['number', 'range'],
  constraints: {
    minBound: (c) => ({ min: c.value }),
    maxBound: (c) => ({ max: c.value }),
    step:     (c) => ({ step: c.value }),
  },
})
```

Правило, чей вид тип не знает, просто не даёт атрибута — с названной причиной,
а не молча. Валидатор без `describe` не даёт атрибута вовсе: честно, без догадок.

Матрица и таблица не исчезают как **отчёт**: строятся обходом реестра для панели
и для тестов. Источник — реестр, не литерал.

**Цена, которую принимаем.** Словарь видов ограничений становится новым общим местом.
Технически он открыт, но договариваться о смысле нового вида приходится людям. Правила
вроде «не раньше чем через два рабочих дня» в словарь не лягут — это календарь, а не
упорядоченность; такие проверяются только на сервере и в браузере со скриптом.

**Признак, что словарь перестал справляться:** в отчёте растёт доля правил, не давших
ни одного атрибута, и растёт число причин «вид ограничения неизвестен типу».

**Готово, когда:** `attrs.ts` и `COMPAT` удалены; таблица на странице строится обходом
реестра и совпадает с прежней.

## Этап 3. Реестры на конфигурацию, а не на модуль

**Сейчас.** Реестры типов и валидаторов — `Map` на уровне модуля. На сервере
регистрации копятся между запросами, два приложения в одном процессе делят их,
повторная регистрация молча перетирает чужую.

**Становится.** `createRegistry()`, передаётся в настройку. Умолчательный реестр
остаётся для краткости. Повторная регистрация того же ключа — ошибка, а не тихая замена.

**Готово, когда:** два реестра в одном процессе не видят регистраций друг друга.

---

## Этап 4. Константы — в политику

**Сейчас** зашиты без переопределения: белый список шаблонов (и нет функции
регистрации), правило имён, пределы, имена ключей конверта, канонические статусы,
правило разбора числа, интерполяция сообщений.

**Становится.** Один объект политики с умолчаниями, передаётся в настройку;
`registry.registerPattern(...)` добавляет шаблон.

**Готово, когда:** приложение меняет имена ключей конверта и добавляет шаблон,
не трогая библиотеку.

## Этап 5. Ошибки: два места и один обработчик

Самая большая правка. Нынешняя схема — места показа, доступность среды, маршрутизация
с перехватчиками — убирается целиком.

### 5.1 Библиотека знает ровно два места

**Общие** — «регистрация отключена», «запись не создана». **Поля** — «не заполнено»,
«не более N символов». Всё остальное — всплывающее уведомление, системное уведомление,
сообщение в мессенджер — библиотеку не касается: разработчик забирает такие ошибки себе
и обратно не возвращает.

Поэтому исчезают: реестр мест, признак доступности среды, каскад запасных, владение
местом, `errorAt` у поля, деградация уведомлений.

### 5.2 Факт и показ — разные списки

```
факт  — массив ошибок как он есть
показ — то, что вернул обработчик. Отсюда берутся ТЕКСТЫ.
```

Разработчик может забрать все ошибки себе: тексты не покажутся нигде, но поля
по-прежнему знают, что были невалидны, и подсвечиваются.

### 5.3 Откуда берётся «поле невалидно»

У поля есть признак `has`. По умолчанию он считается **по факту**: ошибка была —
поле подсвечено, даже если текст забрали. Это переключается.

```ts
invalidFrom: 'fact' | 'shown'
// 'fact'  — по наличию ошибки (умолчание)
// 'shown' — только по тому, что вернул обработчик
```

Настройка задаётся на четырёх уровнях, побеждает самый узкий:

| уровень | где | зачем |
|---|---|---|
| ошибка | пометка на самой ошибке | «эта не дошла текстом и подсветку не даёт» |
| поле | описание поля | одно поле ведёт себя иначе, чем остальные |
| форма | связывание формы | политика одного экрана |
| библиотека | настройка проекта | умолчание на всё |

Порядок разрешения: **ошибка → поле → форма → библиотека**.

Отдельный случай — ошибка, которую обработчик оставил, но без текста. Тогда у неё три
исхода, и все три выражаются одним массивом:

| что сделал обработчик | текст | подсветка |
|---|---|---|
| вернул как есть | есть | есть |
| вернул без текста | нет | есть |
| не вернул | нет | по `invalidFrom` |

`invalidFrom` — статическая настройка, а не вычисляемое значение: иначе одно и то же
состояние давало бы разную подсветку в разных отрисовках.

### 5.4 Обработчик — преобразование массива

```ts
onErrors?: (errors: readonly FormError[], ctx: ErrorContext) => readonly FormError[]

interface ErrorContext {
  from: 'action' | 'fetch'   // как пришёл результат
  intent: string
  outcome: Outcome
}
```

Обработчик проходят **оба пути, без исключений**:

| путь | как пришло | где выполняется обработчик | что доступно |
|---|---|---|---|
| `action` | обычный POST формы, страницу рисует сервер | на сервере | вырезать, переписать, стереть `path` |
| `fetch` | тот же адрес из `action`, запрошен JSON | в браузере | то же плюс внешние каналы: тост, sms |

Отсюда требование: обработчик **изоморфен**. Браузерные вызовы в нём допустимы только
под проверкой `ctx.from === 'fetch'`.

`from` — факт о том, как пришёл результат, а не догадка о среде. Результат, полученный
из `action`, помечен `action` навсегда: повторная отрисовка на клиенте не пересчитывает
его с другим значением, поэтому показ не меняется после оживления.

Сценарии, все внутри одного обработчика:

```ts
// вернуть как есть
(errors) => errors

// режим одного блока: стереть имена полей — всё уедет в общие
(errors, ctx) => ctx.from === 'action'
  ? errors.map((e) => ({ ...e, path: undefined }))
  : errors

// не показывать конкретную ошибку
(errors) => errors.filter((e) => e.code !== 'E123')

// увести во внешний канал и не возвращать
(errors) => errors.filter((e) => e.code !== 'PAYMENT_HOLD')
```

Что вернулось — то и показывается, без доработки со стороны библиотеки.

**Обработчик обязан быть чистым.** Его зовут не только при отправке, но и для
предпросмотра, и повторно при перерисовке. Сама отправка во внешний канал —
побочное действие, и живёт отдельно, рядом с результатом. Иначе предпросмотр
разошлёт сообщения, а реактивные движки запретят вызов вовсе.

### 5.5 Разделение на общие и поля — после обработчика

Есть `path` → ошибка поля. Нет `path` → общая. Других правил нет.

### 5.6 Гарантия понижается честно

Прежнее «ни одна ошибка не теряется» больше не выполнимо: разработчик удаляет ошибки
сознательно. Остаётся наблюдаемость — предупреждение при разработке: «обработчик удалил
N ошибок из M». Это честнее каскада, который возвращал ошибку туда, куда её не просили.

**Готово, когда:**
- стирание `path` в обработчике переводит все ошибки в общий блок;
- фильтрация по коду убирает ошибку из показа, но поле остаётся подсвеченным;
- `invalidFrom: 'shown'` на поле гасит подсветку этого поля, не трогая остальные;
- пометка на одной ошибке перебивает настройку поля, формы и библиотеки;
- `ctx.from` различает `action` и `fetch`, и результат сохраняет своё значение
  при повторных отрисовках;
- обработчик выполняется на обоих путях, в том числе на сервере;
- в коде библиотеки нет ни одного упоминания конкретного вида интерфейса.

## Этап 6. Чужие службы: нормализация до обработчика

Инструкция разбора приводит чужой ответ к общему виду **прежде**, чем его увидит
разработчик. Иначе ему пришлось бы разбирать чужой формат второй раз.

```
сырой ответ (свой сервер или чужой REST)
      ↓   инструкция: parse → aliases → codeAliases → messages
единый массив ошибок                      ← ФАКТ
      ↓   обработчик разработчика
массив к показу                           ← ПОКАЗ
      ↓
общие / поля
```

Инструкция регистрируется и описывает только чужой формат:

```ts
registerErrorInstruction({
  id: 'external-api',
  parse: ({ status, body }) => /* сырое → { code, field, message }[] */,
  aliases: { user_email: 'email' },          // имя поля службы → наше
  codeAliases: { EMAIL_TAKEN: 'email' },     // код → поле, если поле не названо
  messages: { EMAIL_TAKEN: 'Этот адрес уже занят' },
})
```

Нормализованная ошибка сохраняет ссылку на исходное — иначе манипулировать нечем:

```ts
{ code: 'EMAIL_TAKEN', path: 'email', message: '…', source: { kind, target, detail } }
```

Не нашёлся alias — `path` пустой, ошибка просто общая. Обработчик при желании
распорядится ею сам.

**Готово, когда:** ответ в чужом формате доходит до обработчика уже нашими именами;
`source` позволяет отличить службу, не разбирая тело заново.

## Этап 7. Политика адаптера — наружу

Зашито и не настраивается: идентификатор поля, состав `aria-describedby`, правило
эскалации живой проверки, сборка `value`/`checked`, формат намерения. Всё переезжает
в политику с текущими умолчаниями.

**Готово, когда:** демонстрация подменяет идентификаторы полей и правило эскалации
из настройки проекта.

---

## Этап 8. Демонстрация

- переключатель **обработчика ошибок**: как есть · всё в общий блок · без кода `E123` ·
  увести во внешний канал. Видно, что поля остаются подсвеченными, когда текстов нет;
- переключатель **пути**: `action` против `fetch` — видно, что обработчик проходят оба
  и что показ не меняется после оживления;
- переключатель **источника подсветки**: по факту против по показу — на всю форму
  и отдельно на одном поле, чтобы был виден порядок разрешения;
- кнопка **«зарегистрировать тип `rating`»** — поле появляется, атрибуты приходят
  из регистрации, отчёт обновляется сам;
- кнопка **«добавить правило»** в двух вариантах: с `describe` (атрибут выводится)
  и без (не выводится, причина названа);
- форма с ответом **чужой службы** в её формате: видно сырой ответ, нормализованный
  массив и то, что вернул обработчик.

**Готово, когда:** всё перечисленное делается кодом страницы, а `src/lib/form`
не меняется.

## Что не меняется

- Единая точка входа, контракт результата, семантика исхода.
- Работа без скрипта и совпадение двух путей отправки.
- Граница «разметка — данные»: библиотека не создаёт элементов.
- Правило «если приложение может забыть и этим сломать — это не его решение».
  Оно и привело к тому, что обработчик ошибок теперь один и не обязателен:
  не задал — работает стандартная схема.

## Сделано

Этапы 1–8 выполнены, плюс закрыты пробелы, остававшиеся от большого плана:
серверные слои, асинхронные проверки, внешние схемы, операции над набором
полей и повторяемые группы, поля из рантайма, источник описания и протокол
устаревания, продолжение с деградацией носителя, исход `queued`, стратегия
файлов, отчёт для разработки.

Проверяется: `npm run check` (0 ошибок), `npx vitest run src/lib/form`
(51 модульный тест), `node test/browser/forms.mjs` против работающего
сервера (25 проверок, включая прогон с выключенным скриптом, сравнение двух
путей, идемпотентность и отказ слоя имён), `node test/browser/a11y.mjs`
(axe по ключевым экранам) и `npm run test:budget` (gzip-бюджеты клиентской
сборки и начальной загрузки маршрутов).

Дефекты, найденные при проверке, и их причины:

- обработчик вызывался и для предпросмотра, поэтому побочное действие внутри
  него запрещено — отправка во внешний канал вынесена наружу;
- продолжение поднималось в эффекте, а при серверном рендере эффектов нет:
  без скрипта ошибки не попадали в разметку. Поднимается при связывании;
- копия настроек через `{...opts}` превращает ленивое чтение в снимок,
  и переключатели перестают работать на лету;
- строгий запрет повторной регистрации ломал горячую замену: теперь повторное
  объявление того же значения допустимо, другого — ошибка в сборке
  и замена с предупреждением при разработке;
- сравнение валидаторов через сериализацию всегда давало «равны»: функция
  сериализуется одинаково. Сравниваются ОГРАНИЧЕНИЯ — они данные;
- признак «идёт проверка» поднимался у полей без асинхронных проверок
  и больше не опускался.

## Как вести правку

Файлы переписываются целиком либо заменяются целыми функциями. Частичная правка
запрещена: от прежней библиотеки не должно остаться ни переменных, ни полей структур,
ни веток, которые «пока пригодятся».

Признак, что правило нарушено: в файле соседствуют два способа делать одно и то же —
старая таблица и новый реестр, `place` и `path`, доступность среды и `ctx.from`.
Такой файл дописывать нельзя, его надо переписать.
