# lib/fetch — `fetch` для обращений к чужим сервисам

Обёртка над `fetch` со стандартным набором для сети: таймаут попытки, свой `signal`,
повторы с паузами и `Retry-After`, лимит запусков на хост, склейка одинаковых
одновременных запросов, одна ошибка с кодом. Вызов и ответ — как у `fetch`: та же
сигнатура, тот же `Response`.

Без фреймворка и без зависимостей. Нужны `fetch`, `AbortSignal.timeout` и
`AbortSignal.any` (Node 20+, современные браузеры). Кэша нет: что и сколько
хранить, решает тот, кто знает данные (транспорт, через `#lib/cache`).

## 1. Быстрый старт

```ts
import { createFetch, readJson, FetchError } from '#lib/fetch/index.js'

const upstream = createFetch({
  hosts: { 'api.example.com': { rps: 4, rpm: 80, headers: { 'User-Agent': 'my-app/1.0' } } },
})

const res = await upstream('https://api.example.com/items?page=2', { signal })
const items = await readJson<Item[]>(res)          // код проверен, тело разобрано
```

В приложении экземпляр один: `src/lib/server/fetch.ts` (`upstream`). Транспорты
получают его явно (`deps.fetch`, по умолчанию — он). Глобальный `fetch` не
подменяется: `lib/db` ходит через него к прокси базы, и повтор записи там недопустим.

## 2. Что делает каждый вызов

1. Собирает заголовки: заголовки хоста по умолчанию, поверх — заголовки вызова.
2. Если для хоста заданы лимиты — ждёт своей очереди (порядок запусков = порядок вызовов).
3. Запускает попытку с таймаутом (`timeoutMs`, вместе с чтением тела).
4. Ответ из списка повторяемых или сетевой сбой — пауза и следующая попытка (если
   запрос безопасно повторить и попытки остались).
5. Возвращает `Response`. Негодный код после всех попыток — тоже `Response`, как у
   `fetch`: решает вызывающий (или `readJson` / `ensureOk`).

## 3. Настройки

```ts
createFetch({
  fetch,          // нижний fetch; по умолчанию globalThis.fetch в момент вызова
  timeoutMs,      // таймаут одной попытки, 10 000
  retry,          // { attempts: 3, baseDelayMs: 300, maxDelayMs: 5000, statuses: [408,425,429,500,502,503,504] } | false
  hosts,          // { 'host': { rps?, rpm?, headers? } } — по URL.hostname
  dedupe,         // склейка одинаковых одновременных запросов, true
  clock,          // { now, sleep, random } — для тестов
})
```

Поля вызова поверх `RequestInit`:

| Поле | Что делает |
|---|---|
| `signal` | Прерывает ожидание сразу: в очереди, в попытке, в паузе. Отказ — `AbortError` (как у `fetch`), без повторов. |
| `timeoutMs` | Таймаут попытки для этого вызова. |
| `retry` | Поля поверх общих или `false`. |
| `idempotent` | Запрос безопасно повторить. По умолчанию — по методу: GET, HEAD, OPTIONS, PUT, DELETE. POST, который ничего не меняет (запрос GraphQL), помечается `idempotent: true`. |
| `dedupe` | `false` — не склеивать этот вызов. |

## 4. Повторы

- Повторяется: сетевой сбой, таймаут попытки, коды из `statuses`.
- Не повторяется: запрос, который нельзя повторить (POST без `idempotent`), прерывание
  своим `signal`, коды вне списка (4xx, кроме 408/425/429).
- Пауза: `Retry-After` (секунды или HTTP-дата), иначе экспонента с полным разбросом —
  случайно от 0 до `baseDelayMs · 2^(n-1)`, не выше `maxDelayMs`.
- Сервис просит ждать дольше `maxDelayMs` — повтора нет, вызывающий получает ответ
  (обычно 429) сразу, а не висит минуту.
- 429/503 с `Retry-After` ставят паузу всему хосту: следующие запросы к нему ждут её,
  даже если сами ничего не получали.
- Тело брошенного ответа отпускается (`body.cancel()`).

## 5. Лимиты хоста

`rps` и `rpm` — скользящие окна: в ЛЮБОЙ секунде (минуте) запусков не больше лимита.
Это строже фиксированного окна сервиса: если у нас не больше 5 запусков в любой
секунде, то и в любой его календарной секунде не больше 5. Повторы идут через ту же
очередь. Прерванный в очереди вызов уходит из неё и не задерживает следующих. Хосты
вне `hosts` идут без очереди.

Очередь — память процесса. Несколько инстансов делят лимит сервиса между собой
только приблизительно (почему так и чем это закрыто — `docs/design/instance-coordination-research.md`).

## 6. Склейка одинаковых запросов

Одновременные одинаковые запросы уходят в сеть один раз. Одинаковые — это метод,
адрес и заголовки, а у `idempotent: true` со строковым телом ещё и тело. Склеиваются
GET/HEAD без тела и такие безопасные запросы с телом.

- Каждый ожидающий получает свою копию ответа: тело читается в память один раз.
  Для потоков и больших файлов склейку выключают (`dedupe: false`).
- Свой `signal` прерывает только своё ожидание: общий запрос доходит до конца для
  остальных. Сверху его держит таймаут попытки.
- После ответа запись склейки удаляется: следующий вызов — новый запрос (кэш — не здесь).
- `Response.url` у копии пустой.

### Почему вызов ждёт: `onWait`

```ts
await f(url, { onWait: (wait) => show(wait) })
// { reason: 'queue', host: 'shikimori.io', ahead: 2 }           — впереди два вызова
// { reason: 'queue', host: 'shikimori.io', ahead: 0, waitMs: 750 } — пауза лимита до запуска
// { reason: 'retry', attempt: 2, attempts: 3, waitMs: 400 }       — пауза перед повтором
```

Склеенный вызов получает ожидания общего запроса, включая последнее, случившееся до
него. Слов для человека пакет не выбирает: в приложении их ставит `server/fetch.ts`.

## 7. Ошибки

Одна ошибка — `FetchError`, по коду видно, что случилось:

| `code` | Когда | `status` |
|---|---|---|
| `fetch.timeout` | таймаут попытки (после всех повторов), в том числе во время чтения тела | 504 |
| `fetch.network` | соединение не удалось (после всех повторов) | 504 |
| `fetch.status` | негодный код ответа (`readJson`, `readText`, `ensureOk`) | 502 |
| `fetch.parse` | обещан JSON, пришло другое | 502 |
| `fetch.rejected` | ответ разобран, но по смыслу отказ (`errors` в GraphQL) — бросает вызывающий | 502 |

- `message` — наш текст без адресов и подробностей, его можно показать клиенту.
- `status` — каким кодом отвечать НАШЕМУ клиенту; `upstreamStatus` — что ответил сервис.
- Адрес, метод и исходная ошибка — только в `cause`, для лога.
- Прерывание своим `signal` — не `FetchError`, а `AbortError` (`isAbortError(e)`).

```ts
try {
  return await readJson(await upstream(url, { signal }))
} catch (e) {
  if (isAbortError(e)) throw e                     // клиент ушёл
  if (e instanceof FetchError && e.code === 'fetch.timeout') { /* … */ }
  throw e
}
```

В приложении ошибка становится ответом маршрута в одном месте —
`src/lib/server/api-error.ts` (`apiFailure`): тело `{ error, code }`, формат —
`src/lib/api-error.ts`. Там же инструкция `lib/form` (`apiErrorInstruction`), чтобы
форма показала отказ маршрута как обычную ошибку.

## 8. Чтение ответа

```ts
await readJson<T>(res, { accept? })   // код проверен, JSON разобран
await readText(res, { accept? })      // код проверен, текст
await ensureOk(res, { accept? })      // только код
```

`accept(status)` — какие коды считать годными, когда «плохой» код — это данные: 404
«ничего не найдено» у REST Rick and Morty, 422 со списком значений у пробы Shikimori
(`accept: () => true`).

### Ход долгой операции в ответе: `readTaskStream`, `fetchWithTask`

Сервер, который ждёт долгую операцию (запуск базы, очередь лимита), может ответить
строками NDJSON — сначала ход, последней строкой сам ответ. Строки приходят, только если
запрос их попросил и сервер правда ждал; иначе ответ обычный.

```ts
import { readTaskStream, TASK_STREAM_ACCEPT } from '#lib/fetch/index.js'

const raw = await fetch('/api/db-posts?page=2', { headers: { accept: TASK_STREAM_ACCEPT }, signal })
const res = await readTaskStream(raw, (task) => (state.task = task)) // ход: { status: 'pending', scope, label?, progress? }
if (!res.ok) throw …            // код, заголовки и тело — как без строк
const page = await res.json()
```

- строка `{"result":{"status","headers","body"|"text"}}` превращается в обычный `Response`:
  код ошибки, пришедшей после начала строк, тот же, что без них;
- обычный ответ с `Content-Length` (без сжатия) читается здесь и сообщает ход байтами;
- поток оборвался до результата — `fetch.network`, кривая строка — `fetch.parse`;
- серверная сторона в приложении — `src/lib/server/task-stream.ts` (`taskResponse`).

Короче то же самое — `fetchWithTask`: с `onTask` просит строки и читает их, без него —
обычный `fetch`:

```ts
const res = await fetchWithTask(`/api/db-posts?${q}`, { signal: look.signal, onTask: look.report })
```

## 9. Тесты

`clock` подменяет время: `sleep` двигает его мгновенно, паузы и лимиты проверяются
точными числами без настоящего ожидания (`create.test.ts`). Тесты транспортов берут
`makeUpstream(нижний, clock)` из `server/fetch.ts` — те же правила хостов, что в бою,
на поддельной сети.

## 10. Чего здесь нет

- Кэша — он у транспортов (`#lib/cache`).
- Ограничения числа одновременных запросов на хост — хватает лимита запусков.
- Подмены глобального `fetch` — экземпляр передаётся явно.
- Повторов не-идемпотентных запросов по умолчанию.
