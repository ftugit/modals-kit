# Хост стопки: устройство через адаптеры

Хост говорит с миром **только** через `ChainAdapter`. Других каналов у него нет.
Адаптер отвечает сразу за две вещи, которые обычно путают: **как стопка
читается** и **как она хранится**.

## Слои

```
types.ts         модель записи и контракты — 0 импортов фреймворка
core.ts          чистый TS: кодек адреса, геометрия хвостов, блокировки
store.ts         состояние + подписки, без реактивности фреймворка
   ↑
adapter.ts       контракт транспорта
   ↑
adapters/        url.ts (ядро кодека + истории, тестируется без браузера)
                 ├── sveltekit.ts   обвязка $app/* — первый адаптер
                 ├── local.ts       localStorage + синхронизация вкладок
                 └── memory.ts      SSR, тесты, встраивание
   ↑
svelte/          store.svelte.ts — ЕДИНСТВЕННОЕ место с реактивностью
```

Цель — **одно ядро, много фреймворков**. Svelte здесь первый, а не
единственный: добавить React или Vue = добавить два файла рядом, ядра
не касаясь.

```
adapters/<фреймворк>.ts   обвязка роутера     ← знает фреймворк
<фреймворк>/              реактивность и вид  ← знает фреймворк
всё остальное                                 ← чистый TypeScript
```

Граница не декларативная, а проверяемая: `tooling/core-purity.mjs` роняет
`npm test`, если в ядре появился импорт фреймворка **или** импорт слоя
фреймворка (зависимость направлена только вниз). Страж не пустой — при
временной вставке `import 'svelte'` в `core.ts` он падает:

```
not ok - ядро модалок не зависит ни от одного фреймворка
    [core-purity] core.ts
        импорт: svelte
        • реактивность и разметка → src/lib/modals/<фреймворк>/
```

### Оформление: утилиты, а не CSS-файл

Всё, что рисует система, собрано из атомарных утилит UnoCSS:

| Где | Что |
|---|---|
| `svelte/classes.ts` | классы хоста: фон, сцена, оболочка, хвост, скелетон, ошибка, спиннер, кадры входа/выхода |
| `ui/modals/variants.ts` | CVA-наборы: `modalBackdropVariants`, `modalPopupVariants`, `modalButtonVariants`, `modalTriggerVariants` |
| `src/app.css` | **только токены тем** — цвета и радиус; ни одного правила оформления |
| `src/app.html` | база документа классами: фон, шрифт, размер, выделение, курсор кнопок |

Своего CSS у системы нет вовсе, и своих кадров тоже: анимации берутся
встроенные — `animate-[pulse_…]` у скелетона, `animate-[spin_…]` у спиннера,
`flash` у каретки OTP (период тот же, что был у своих кадров), а раскрытия
панелей — переходы из `@starting-style` (вариант `starting:`), у которых
первый кадр ровно тот же, что был у прежних `@keyframes`.

Маркер-классов тоже больше нет: снаружи система и её примитивы видны
**только по data-атрибутам и id** — `data-modal-backdrop`, `data-modal-popup`,
`data-modal-stage`, `data-modal-layer`, `data-modal-tail`, `data-modal-btn`,
`data-modal-trigger`, `data-modal-skeleton`, `data-modal-error`,
`data-modal-spinner`, `data-select-*`, `data-fe-sidebar-*`, `data-sidebar-zone`.
Их ставят компоненты, по ним ходят тесты и внешние стили. Следит за этим
`probes/classes-audit.mjs`: он ищет маркеры и утилиты, для которых нет правил.

**Грабли, на которые легко наступить заново.** UnoCSS собирает классы из
разметки: по умолчанию (`content.pipeline.include`) сканируются только
`.svelte`, `.html`, `.vue`, `.tsx`. Обычный `.ts`-модуль со строками классов
не сканируется — классы остаются строками в JS, а CSS для них не генерируется.
Модалки при этом открываются, но без фона, теней и переходов. Поэтому у
`classes.ts` и `variants.ts` в первой строке стоит пометка:

```ts
/* @unocss-include */
```

Проверить, что все классы действительно собрались, можно без браузера:

```
node probes/classes-audit.mjs     # маркеры + токены, для которых нет правил
node probes/uno-probe.mjs 'z-200' 'animate-[pulse_1.4s_ease-in-out_infinite]' 'starting:opacity-0'
```

Соответствие утилит и прежних правил держит `test/browser/modals.mjs`:
он читает `transition-property` и первый кадр раскрытия у `[data-modal-reveal]`,
`animation-name` скелетона (встроенный `pulse`), сквозной z-index фона и
сцены и поведение при `prefers-reduced-motion`.

### Существование маршрута — дело адаптера, а не наше

Проверка «ведёт ли `route` на настоящую страницу» прошла две правки,
и обе поучительные.

Сначала я написал в общем транспорте `matchRoute` с шаблонами `[id]`
и `[...rest]`. Это синтаксис SvelteKit и Next — у Vue, Angular и React
Router маршруты пишутся `:id`. Транспорт не должен знать ни того, ни другого.

Затем я перенёс сопоставление в обвязку и собирал таблицу маршрутов через
`import.meta.glob`. Это тоже неверно: **SvelteKit знает свои маршруты сам**,
и ответ у него сильнее рантайм-проверки —

```ts
export function resolve<T extends RouteId | Pathname>(...args: ResolveArgs<T>): ResolvedPathname
```

`RouteId` — сгенерированный union настоящих маршрутов. Опечатка в
`resolve('/films/[id]', { id })` **не компилируется**; блокировать кнопку
в рантайме уже незачем. (`resolveRoute` помечен deprecated в пользу `resolve`.)

Поэтому адаптер SvelteKit **не реализует `resolves`** — и своего
сопоставления шаблонов в проекте не осталось вовсе.

В контракте `resolves?` при этом сохранён: он нужен транспортам, которые
знают свои маршруты только в рантайме (как роутер FastEdge оригинала
с его `useResolves()`). Возможность остаётся в контракте, даже когда
конкретному фреймворку она не нужна, — в этом и смысл переговоров
по наличию метода.

Так же устроен `lib/paginate` в этом же проекте: `core.ts` чистый,
`adapter-*.ts` чистые, весь фреймворк — в `solid.tsx`.

## Переговоры о возможностях

Хост **никогда** не спрашивает «ты какой адаптер?». Он спрашивает, что
адаптер умеет — по наличию метода:

```ts
const hasHistory = typeof adapter.back === 'function'
```

Метода нет → возможности нет, и хост честно деградирует:

| Нет метода | Поведение хоста |
|---|---|
| `back` | закрытие делает `write(replace)`, «Вперёд» не сохраняется |
| `subscribe` | внешние изменения не отслеживаются (память, SSR) |
| `hrefFor` | триггер рисует кнопку вместо ссылки — без JS работать не будет |
| `resolves` | битый `route` не ловится до клика, даст 404 |
| `preload` | данные берутся только из `definition.loader` |
| `bind` | роутер не нужен |

То, что нельзя выразить наличием метода, лежит в явном `capabilities`:

```ts
capabilities: {
  addressable: boolean   // записи переживают F5 и передаются ссылкой
  transient:   boolean   // записи без адреса, но со своей записью истории
  history:     boolean   // Назад/Вперёд существует
}
```

## Реестр с областью видимости

В оригинале реестр — одна глобальная `Map`. Но глобальной она была только
**по хранению**: `<ModalHost>` монтируется на странице (свой в `ModalsDemo`,
свой в `ShikimoriPage`), `registerModal()` вызывается побочным эффектом
импорта лениво загружаемого чанка страницы, а глобального импорта
определений в проекте нет вообще.

Отсюда три проблемы, которые снимает область видимости:

| Было | Стало |
|---|---|
| имя уникально на всё приложение; коллизия перезаписывает **молча** | имя уникально внутри области; повторное объявление — ошибка |
| момент регистрации непредсказуем → понадобился `registryVersion` | объявление статично, опрос не нужен |
| холодный запуск работает потому, что чанк-регистратор = чанк хоста | область принадлежит роуту явно |

Порядок разрешения повторяет разрешение layout-ов SvelteKit — своя область,
затем родительские, затем глобальная:

```ts
const app   = globalScope.define([auth, settings])   // видно отовсюду
const shop  = app.child('/shop').define([cart])
const item  = shop.child('/shop/[id]').define([gallery])

item.resolve('gallery') // → своя
item.resolve('cart')    // → родительская
item.resolve('auth')    // → глобальная
```

Вниз реестр не смотрит: модалки `/users` из `/films` не видны, поэтому
одноимённые `card` в разных роутах спокойно сосуществуют, а ближняя
перекрывает дальнюю — как layout.

Ошибка при этом обязана объяснять, а не просто отказывать:

> Нет модалки «profile». Искали в областях: /films → global.
> Такое имя объявлено в: /users — эта область отсюда не видна.
> Либо перенесите объявление в общего родителя, либо объявите её здесь.

`registerModal()` остался и кладёт в глобальную область — совместимость
не сломана.

## Два вида записей

### Простыми словами

**`declared`** — обычная модалка: заранее объявлена в реестре, открывается
по имени, живёт в адресе.

```ts
modals.open('card', { params: { id: 7 } })   // → /films?modal=card&modal.0.id=7
```

**`transient`** — разовый слой, собранный прямо в коде. Имени в реестре нет,
содержимое передаётся тут же, в адрес не попадает.

```ts
modals.openLayer({ content: confirmSnippet })   // адрес не меняется
```

### Зачем он нужен

Возьмите «Удалить запись?». Как `declared` это значит: придумать имя,
зарегистрировать его, а текст вопроса протащить через параметры —
и параметры обязаны быть сериализуемы в адрес. На каждое разовое окно.

Как `transient` — просто отдать содержимое.

Типичные случаи: подтверждение действия, показ результата операции,
предпросмотр из локальных данных и **список опций мобильного `select`**
(он не зарегистрированная модалка, а слой с собственной разметкой —
см. решение D16).

### Почему не в адресе

Содержимое — ссылка на компонент или сниппет, то есть кусок памяти.
В строку его не превратить. Ссылка вида `?modal=layer-7` у другого
человека открыла бы пустоту, поэтому `hrefFor` для такого слоя честно
возвращает `null`, а не выдуманный адрес.

### Но запись истории у него ЕСТЬ

Это главное. Для пользователя transient — обычный слой: Escape закрывает,
Назад закрывает, Вперёд возвращает, стопка и хвосты работают. Не работает
ровно одно — поделиться ссылкой.

| | `declared` | `transient` |
|---|---|---|
| открывается | по имени из реестра | содержимым из кода |
| в адресе | ✅ | ❌ |
| Назад / Вперёд | ✅ | ✅ |
| переживает F5 | ✅ | ❌ |
| можно дать ссылку | ✅ | ❌ |
| место в стопке | любое | только вершина |

### Чем за это платим

**Не переживает перезагрузку.** Содержимое было в памяти — после F5 его нет.
Запись истории остаётся, поэтому слой считается закрытым, а глубина
подчищается.

**Только на вершине.** Не вкусовщина: адрес кодирует параметры позиционно
(`modal.0.id`, `modal.1.id`). Несериализуемая запись в середине сдвинула бы
индексы всех записей правее.

### Когда transient НЕ нужен

Если на слой можно дать ссылку и он переживает перезагрузку — это
`declared`, объявляйте в реестре. Transient — для того, что по своей
природе одноразовое.

## Два вида записей — формально

| | `declared` | `transient` |
|---|---|---|
| откуда | реестр, по имени | код, со своим содержимым |
| в адресе | да | **нет** |
| переживает F5 | да | нет |
| Назад/Вперёд | да | **да** |
| где в стопке | где угодно | **только на вершине** |

Ограничение «только на вершине» — не вкусовое. Адрес кодирует параметры
позиционно (`modal.0.id`, `modal.1.id`); несериализуемая запись в середине
сдвинула бы индексы всех записей правее. Правило закреплено одной функцией
`assertTransientOnTop()` и покрыто тестом, который проверяет, что сообщение
об ошибке **называет причину**, а не просто запрещает.

## Загрузчик адаптера не требует

`loader.ts` фреймворк не зовёт: `definition.loader(params, signal)` — это код
**потребителя**, а `AbortSignal` — веб-стандарт. Единственный импорт Solid
в оригинале — `import type { Accessor }`, то есть только тип. Кеш, дедупликация
одинаковых запросов и отмена — чистый TS.

Но одна вещь у загрузки всё же зависит от фреймворка, и она в контракте есть.
У модалки с `route` данные сегодня добываются **дважды**: загрузчиком страницы
(чтобы работало без JS) и `definition.loader` (для модалки). В демо оригинала
это прямо записано в тексте карточки: *«В модалке те же данные приходят через
loader»*.

Необязательный `preload(href)` это закрывает: транспорт исполняет загрузчик
**самого маршрута** (в SvelteKit — `preloadData`, канонический приём shallow
routing). Тогда модалке с `route` собственный `loader` не нужен вовсе — одна
реализация данных обслуживает и страницу, и модалку.

## Сборка: модалка(движок(хранилище), опции)

```ts
createModals(svelteKitEngine(), urlStorage())        // цепочка в ?modal=
createModals(svelteKitEngine(), localStorageChain(localStorage))  // адрес чистый
createModals(memoryEngine(),    urlStorage())        // SSR: адрес есть, истории нет
```

| Что | За что отвечает |
|---|---|
| **движок** | адрес, история, предзагрузка — всё, что от фреймворка |
| **хранилище** | где лежит объявленная часть цепочки |
| **опции** | `lookup` (область видимости имён), `stateKey` |

Имя транспорта собирается само и читается как формула: `sveltekit(url)`,
`history(local)`, `memory(memory)`.

### Возможности не объявляются, а выводятся

| Источник | Что даёт |
|---|---|
| движок с `go` | `history: true` и метод `back` |
| движок без `go` | `back` отсутствует, закрытие через `replace` (случай SSR) |
| движок с `onPopState` | внешние изменения отслеживаются |
| движок с `preload` / `resolves` | данные маршрута / проверка битого маршрута |
| хранилище `addressable` | `hrefFor`, то есть работа без JS |

Отсюда SSR не требует отдельного адаптера: `svelteKitEngine()` на сервере
не отдаёт ни `go`, ни `onPopState` — транспорт сам становится «без истории».

### Чего вложение стоило: зеркало в записи истории

Замысел «localStorage + живые Назад/Вперёд» сначала не заработал, и тест
это поймал: `go(-1)` шагает по истории, но localStorage **вне истории**
и назад не откатывается — получался шаг без смены содержимого.

Навигация восстанавливает только то, что лежит **в самой записи**: адрес
или её состояние. Поэтому для неадресуемого хранилища цепочка держится
в двух местах:

| Где | Зачем |
|---|---|
| состояние записи истории | чтобы работали Назад/Вперёд |
| носитель (localStorage) | чтобы пережить перезагрузку |

При чтении приоритет у записи истории — она знает, где мы сейчас;
носитель подхватывает после перезагрузки, когда состояние потеряно.
У адресуемого хранилища дублирования нет: адрес уже и есть запись истории.

### Чего сочетать нельзя

Поэлементно смешивать носители («эта модалка в адрес, та в localStorage»)
нельзя: цепочка — одна упорядоченная величина, и владелец порядка у неё
обязан быть один, иначе `back()` не знает, чей это шаг.

Разделение внутри одного транспорта есть, но **по видам записей**:
`declared` уходит в носитель, `transient` живёт в состоянии записи истории
и перезагрузку не переживает.

## Несколько источников

Ядро принимает не одно хранилище, а именованный набор. Модалка
закрепляется за источником — это **размещение**, то есть куда её класть:

```ts
const core = svelteKitCore({
  url:    urlStorage(),
  local:  localStorageChain(localStorage),
  memory: memoryStorage(),
})

createRegistry('app').define([
  { name: 'card',   component: Card },                         // источник по умолчанию (первый)
  { name: 'wizard', component: Wizard, source: 'local' },
  { name: 'debug',  component: Debug,  source: ['memory', 'local'] },  // пишется в первый доступный
])

modals.open('card', { source: 'memory' })   // явное указание перебивает объявление
```

### Порядок стопки — по времени, а не по порядку источников

Это единственное жёсткое правило. Если склеивать источники «по порядку
объявления», только что открытая модалка уедет **под** старую.

Поэтому **порядок живёт в одном месте** — в состоянии записи истории,
а источники хранят только содержимое:

| Что | Где |
|---|---|
| порядок записей | состояние записи истории |
| содержимое записи | свой источник |

### Долговечность выбирается на запись

```ts
modals.open('wizard')   // source: 'local'  → переживёт F5, адрес чистый
modals.open('card')     // source: 'url'    → в адресе, делится ссылкой
modals.open('debug')    // source: 'memory' → исчезнет с перезагрузкой
```

### Размещение, а не разрешение

Запись, найденная в «чужом» источнике, всё равно показывается. Фильтр
«разрешено ли имя здесь» был, но конфликтовал с явным
`open(name, { source })` и молча ронял такую запись. Молчаливая пропажа
хуже чужой записи, тем более что источники наполняет наш же код.

### Тонкость недолговечных источников

Шаг назад по истории **не откатывает содержимое памяти** — она мутируется
глобально. Поэтому после первой же записи недолговечный источник читается
только из зеркала в истории; своё содержимое он отдаёт лишь до первой
записи (начальное наполнение). Иначе после `closeAll()` возвращалась
устаревшая запись — на этом и ловилось.

## Готовые сочетания

| Движок | Хранилище | addressable | history | Назначение |
|---|---|:-:|:-:|---|
| `svelteKitEngine()` | `urlStorage()` | ✅ | ✅ | боевой: ссылки, `preload` |
| `svelteKitEngine()` | `localStorageChain()` | ❌ | ✅ | ⚠️ пример второй реализации, не рекомендуемый режим |
| `memoryEngine()` | любое | — | ❌ | тесты |

⚠️ **Для SSR отдельное ядро не нужно.** На сервере `svelteKitCore()`
читает `page.url` и работает обычным адресным хранилищем.

### Что класть в цепочку, а что нет

В цепочке — **идентичность слоя и минимальные аргументы**, по которым его
можно восстановить: `?modal=account&modal.0.id=42&modal.0.tab=profile`.

Всё, что по этим аргументам **выводится** — заголовок, черновик,
загруженные данные — хранится отдельно. Не ради чистоты: у отдельного
хранилища ключ составляется из тех же аргументов
(`draft:user:42:category:7`), то есть получается **изоляция по
пользователю и сущности**, которой в цепочке быть не может — она одна
на адрес.

⚠️ Значение, не выразимое плоскими ключами, кодек упакует в `pack`
(JSON в адресе). Это работает, но регулярное попадание в `pack` —
признак того, что в цепочку кладут содержимое.

⚠️ **Прежде чем брать `localStorageChain`,** проверьте, точно ли нужна
долговечность **цепочки**, а не содержимого. Черновик формы, прогресс
мастера и т.п. — это содержимое: его хранит своё хранилище, а загрузчик
модалки читает. Цепочка при этом остаётся в адресе и делится ссылкой.

Сокращение для частого случая: `createSvelteKitModals()`.

`memory` существует не для галочки: абстракция с единственной реализацией
ничего не доказывает. Весь набор сценариев в `adapter.test.ts` прогоняется
по обоим транспортам.

## Как написать свой

```ts
const myAdapter: ChainAdapter = {
  name: 'my-transport',
  capabilities: { addressable: false, transient: true, history: false },
  read: () => chain,
  write: (next) => { chain = next; notify() },
  // остальное — по желанию; чего нет, того хост не потребует
}
```

Обязательны только `name`, `capabilities`, `read`, `write`.

## Чего писать НЕ надо: это берёт на себя Ark

Проверено по типам `@zag-js/dialog` → `DialogProps`:

| Соблазн написать руками | Проп машины |
|---|---|
| сохранить активный элемент и вернуть ему фокус | `restoreFocus`, `finalFocusEl` |
| навести фокус на слой при открытии | `initialFocusEl` |
| `body.style.overflow = 'hidden'` | `preventScroll` |
| перехват `Tab` для ловушки фокуса | `trapFocus` |
| `setAttribute('aria-hidden')` на соседях | `modal` |
| фильтр «`focusin` — не клик по фону» | **`persistentElements`** |
| `role="dialog"` в разметке | `role` |

Это не памятка, а проверка: `tooling/ark-owns.mjs` сканирует `src/lib/modals`
и роняет `npm test`, если что-то из списка появилось. Отключение — по месту:

```ts
preOpenEl.focus() // ark-owns-ok: причина
```

Страж не выдуман: на настоящем `host.tsx` оригинала он находит **7 мест** —
пять вокруг ручного возврата фокуса, одно про наведение фокуса на сцену
и одно про эвристику `focusin`, которой штатная замена — `persistentElements`.
