# paginate/filters — фильтры каталога

Схема фильтров источника даёт параметры полям формы `lib/form` (саму форму описывает
приложение), правила проверки и адрес `?page.filters.<поле>[.<режим>]`. Модуль изоморфный, без фреймворка: один и тот же код работает
в серверной зоне схемы, в клиентской форме и в транспорте источника. О конкретном каталоге он
ничего не знает: источник приходит схемой (`CatalogFilterSchema`).

## 1. Схема

```ts
const schema: CatalogFilterSchema = {
  source: 'shikimori',          // ключ источника: по нему схема и помнится (§5)
  version: 1,
  builtAt: '2026-10-12T10:00:00.000Z',  // когда справочники прочитаны живьём
  fields: [
    { key: 'kind', label: 'Тип', type: 'select', options: [{ value: 'tv', label: 'TV' }] },
    { key: 'studios', label: 'Студии', type: 'multiselect', modes: ['and', 'not'],
      options: [{ value: '858', label: 'Wit Studio', count: 2 }, /* …все ~2000 */] },
    { key: 'score', label: 'Оценка', type: 'number', min: 1, max: 10, bounds: ['min'] },
  ],
  rules: [/* связки: что нельзя сочетать, с причиной для интерфейса */],
}
```

- `validateCatalogFilterSchema(input)` — проверяет схему. Невалидную схему нельзя отдавать
  клиенту, поэтому сборщик схемы источника прогоняет её через этот же валидатор.
- `label` поля схемы — данные источника (им называют поле журнал и сервер). В интерфейсе
  подписи пишет описание формы приложения (§2).
- `count` у опции — частота в популярной части каталога. Она задаёт порядок длинного списка (§3).

## 2. Форма фильтров: описание приложения + параметры схемы

Фильтры — обычная форма `lib/form`. Какие поля есть, в каком порядке и с какими подписями,
решает приложение — своё описание и свой компонент под каждую схему. Из схемы приходит то, что
знает только источник: варианты, границы значений, пределы, связки и правила между полями.

**Описание** — функция приложения, одна на браузер и сервер (`src/content/shikimori-filters.ts`):

```ts
export function shikimoriFilterForm(schema: CatalogFilterSchema, opts?: CatalogFilterFormOptions) {
  const filter = formParams(schema, opts)
  return defineForm({
    id: 'shikimori-filters',
    policy: filter.policy,               // предел вариантов поднят до предела схемы (5000)
    fields: filter.fields({
      'genres.and': field.multiselect({ label: 'Жанры · все из', placeholder: 'Не выбрано', ...filter.genres.and }),
      'genres.not': field.multiselect({ label: 'Жанры · кроме', placeholder: 'Не выбрано', ...filter.genres.not }),
      status: field.select({ label: 'Статус', placeholder: 'Любое', ...filter.status }),
      'year.min': field.number({ label: 'Год · от', ...filter.year.min }),
      'year.max': field.number({ label: 'Год · до', ...filter.year.max }),
    }),
  })
}
```

Свои ключи пишутся **после** развёртки, иначе развёртка их перекроет. Свой валидатор — рядом с
выданными: `validate: [...filter.year.min.validate, v.integer()]`.

**Что даёт `formParams(schema, { prefix })`** — по ключу схемы и его режиму/границе:

| Параметр | Откуда |
|---|---|
| `options` | варианты схемы (подписи и `disabled` сохраняются) |
| `validate` | `minValue`/`maxValue` (края базы), `maxCount`, список допустимых при полном списке; `v.notAbove(…max)` у «от»; `v.noOverlap(…and)` у «кроме» |
| `placeholder` | у числа — край базы («Оценка · от» пустое, подсказка «1») |
| `disabledWhen` | связки схемы; поле и виновника `filter.fields` называет подписями описания |

`filter.fields({...})` переводит короткие ключи (`'genres.and'`) в имена формы
(`page.filters.genres.and` в браузере, `filters.genres.and` на сервере) и убирает поля,
которых у источника нет (студии у GraphQL), — одно описание годится для всех версий API.
Неизвестный ключ даёт пустые параметры (`{ validate: [] }`). Развёртка чужого ключа
(`'genres.not': ...filter.genres.and`) в разработке даёт предупреждение в консоль.

**Ошибки между полями** — валидаторы формы, тексты — её словаря (`form/README.md`, каталог):

| Сочетание | Код | Где ошибка |
|---|---|---|
| одно значение в «все из» и в «кроме» | `noOverlap` | у «кроме» |
| «от» больше «до» | `notAbove` | у «от» |
| связка задела заполненное поле | `link.blocked` | у снятого поля |

Ошибка любого поля отклоняет набор целиком — и в браузере (до отправки), и на сервере.

**Компонент** — свой у каждой схемы, поля расставлены руками
(`src/routes/(site)/(app)/paginator/ShikimoriFilters.svelte`):

```svelte
<script lang="ts">
  let props: FilterFormProps = $props()
  const filters = bindFilters(() => props)
</script>

<Form form={filters.form} hiddenFields={props.hidden}>
  <Field of={filters.f['genres.and']} />
  <Field of={filters.f['genres.not']} />
  <div class="grid grid-cols-2 gap-3">
    <Field of={filters.f['year.min']} />
    <Field of={filters.f['year.max']} />
  </div>
  <FilterActions resetHref={props.resetHref} />
</Form>
```

`Field` — тот же, что у остальных форм приложения. Поля, которого у источника нет,
`filters.f[...]` не даёт, и `Field` ничего не рисует. `bindFilters`
(`#components/paginator/index.js`) — `bind` формы с адресным контуром: набор применяется
целиком по «Применить», без JS форма уходит обычным GET. Связка гасит контрол только с JS: без
него выключенное поле браузер не отправил бы и значение из адреса пропало бы молча; причина под
полем видна и без JS.

**Панель** (`FiltersPanel`) — рамка: заголовок, раскрытие, чипы, нарушения применённого набора.
Ей передают описание и компонент схемы:

```svelte
<FiltersPanel {name} {schema} {extra} describe={shikimoriFilterForm} form={ShikimoriFilters} />
```

Адресов фильтры не строят (ход 247): чип и «Сбросить» несут патч extra, а ссылку на него даёт
адаптер пагинатора — `linkFor(name, { page: 1, patch })`; скрытые поля формы без JS — его же
`carryFields(search, ['filters.*'])`. Ссылки нет (хранилище без адреса) — UI рисует кнопку, как `PageLink`.
Срез адреса для ссылок панель берёт живой; приложение может передать свой (`search`), например без
открытой модалки.

Подписи чипов берутся из описания: поля, которого в описании нет, нет и в чипах. Нарушения над
панелью — ошибки той же формы над применённым набором (`catalogFilterViolations`) плюс
сработавшие связки при пустом поле: без JS человек видит причину, не раскрывая форму.

## 3. Длинные списки: с JS — все, без JS — топ-200

Решение владельца: «JS-форма за счёт поиска будет иметь все студии, no-JS — только
ограниченный список».

| | С JavaScript | Без JavaScript |
|---|---|---|
| Что в списке | все значения схемы (студий 1934) | первые 200 плюс всё уже выбранное |
| Как найти | поле поиска в списке ищет по всем, по подписи и значению | нативный `<select>` из серверной разметки, быстрый набор по началу имени |
| Пояснение под полем | нет | «Без JavaScript в списке первые 200 из N; поиск по всем работает с JavaScript.» |
| Значение не из первых 200 | выбирается поиском | приходит адресом (ссылкой); показывается 201-м и выбранным |

Числа и функции:

| Что | Значение | Где |
|---|---|---|
| `CATALOG_FILTER_NOJS_OPTIONS` | 200 — показ без JS | `schema.ts` |
| `CATALOG_FILTER_OPTIONS_LIMIT` | 5000 — защита от гигантских форм, не размер показа | `schema.ts` |
| `capCatalogFilterOptions(schema)` | поле длиннее 200 упорядочивает по частоте, при равной — по подписи; поле длиннее 5000 обрезает (аварийно) и пишет `optionsTruncated` | `schema.ts` |
| `nativeLimit` у `Select` | сколько опций нативный `<select>` показывает до гидратации (0 — все) | `#components/ui/select/Select.svelte` |

**Почему первые 200 — нужные.** Порядок задаёт сборщик схемы: частые первыми. Без частот в
первые 200 попали бы студии по алфавиту, и популярной «Wit Studio» там могло бы не оказаться.
Частоты Shikimori считаются по выборке из трёх страниц популярности (`shikimori-schema.ts`).

**Почему выбранное показывается сверх 200.** Нативный `<select>` отправляет только то, что в нём
есть. Если бы выбранной студии из хвоста не было среди опций, выбор пропал бы при следующей
отправке формы.

**Где это включено.** Поле выбора демо-форм (`#components/form/SelectField.svelte`) — то же
для фильтров и остальных форм:

```svelte
<Select
  options={f.options}
  config={{ nativeList: long ? 'value' : 'all', nativeLimit: 200 }}
/>
```

Порядок `options` и есть порядок показа: `nativeLimit` берёт первые N. Длинный список
(больше 200) после оживления держит в нативном контроле только значение, короткий — весь.
Пояснение под полем и ссылка на него в `aria-describedby` есть только до оживления. Если
источник прислал не все варианты (`optionsTruncated`), это пишет компонент схемы своим текстом
(`filters.truncated('studios')`).

**Вес.** Страница каталога (`/paginator?page.src=animes`, 2026-10-12): HTML 234 KiB
(43 KiB в gzip). В нём все 1934 студии для JS и по 200 в двух нативных списках («и» и «не»).
До изменения было 242 KiB: 1000 студий в данных и по 1000 в каждом нативном списке.

## 4. Проверка выбора

- Список допустимых значений строится по **всем** опциям поля
  (`catalogFilterOptionsAreComplete` → `true`). Студия из хвоста законна, чужой id отклоняется
  с кодом `oneOf`: и в браузере, и на сервере (`validateCatalogFilterValues(schema, data, describe)`
  — тем же описанием, что рисует форму; поле, которого в описании нет, не применяется).
- Только у поля с `optionsTruncated` (справочник длиннее 5000) список неполный. Тогда
  проверяется синтаксис значения, а решает источник: он отвечает списком `dropped`.
- Окончательно выбор всегда проверяет сервер по своей текущей схеме. Поэтому старая схема в
  долгоживущей вкладке (§5) не опасна.

## 5. Схема в памяти вкладки

Решение владельца: схема, однажды пришедшая в браузер, хранится в оперативной памяти, пока
человек не ушёл с сайта или не перезагрузил страницу. Не localStorage: перезагрузка — законный
способ получить свежую схему.

```ts
import { catalogFilterSchemas } from '#lib/paginate/filters/index.js'

catalogFilterSchemas.remember(schema)           // под schema.source
catalogFilterSchemas.recall('shikimori')        // схема или null
```

- **Ключ — `source`:** так помнится схема любого источника, не одного.
- **На сервере память выключена:** переменная модуля там общая для всех запросов и
  пользователей, и схема одного запроса не должна стать ответом другому. `remember` на сервере
  ничего не делает, `recall` отвечает `null`.
- `createCatalogFilterSchemaMemory(enabled)` — своя память (тесты, другой жизненный цикл). По
  умолчанию `enabled = BROWSER` из `esm-env`.
- **Без JS** сохранить нечего: такому клиенту схема приходит с каждой страницей.

Как это использует демо каталога:

| Запрос | Схема с данными страницы | Откуда берёт браузер |
|---|---|---|
| Первый заход, перезагрузка, любой запрос без JS | да: нужна разметке без JS и гидратации | со страницы, сразу в память |
| Переход внутри сайта (`event.isDataRequest`) | нет | из памяти; если там пусто — один раз роутом (§6) |
| Смена фильтров, страниц, источника в панели | загрузка страницы не перезапускается | из памяти или роутом |

После перехода с каталога на главную и обратно данные страницы весят 10 KiB вместо 83 KiB.

## 6. Откуда браузер берёт схему

`GET /api/shikimori/filters` (`src/routes/api/shikimori/filters/+server.ts`) нужен, только когда
схемы нет ни в странице, ни в памяти:

- источник переключили в панели (адрес меняется без серверной загрузки);
- пришли на каталог переходом внутри сайта, а в памяти схемы ещё нет;
- сервер не собрал схему при отрисовке (Shikimori недоступен), и человек нажал «повторить».

Роут отвечает только страницам этого сайта: `Sec-Fetch-Site: same-origin`, иначе 403 без тела.
В dev по http запрос без заголовка пропускается (`sameOriginFetch` в
`src/server/trusted-origins.ts`). От парсеров это не защищает, заголовок подделывается
одной строкой. Данные те же, что и в HTML страницы. В Shikimori роут не ходит: схема собирается
раз в 30 минут, одна сборка на всех.
