- RLS (`SET LOCAL role`) — вне пакета, зона схемы и миграций приложения.

## Список БД и пагинатор

### Наблюдения 14.10.2026 (замер — браузер + счёт запросов, сид 500 записей; устранены — см. ниже)

Претензия владельца: «после добавления записи список обновляется постоянно; фейковая карточка
должна получать обновление, а не весь список; курсор + „следить за новыми“ — постоянное
обновление пагинатора». Подтверждено, причины найдены:

| сценарий | что видно | запросы |
|---|---|---|
| страницы, добавление | карточка подтверждается строкой из ответа, и **сразу же** весь список перезапрашивается | POST + `GET /api/db-posts` |
| страницы + слежение, добавление | список перезапрашивается **дважды**: `onApplied → reset`, затем опрос видит новый ETag → ещё `reset` | POST + 4 GET за 4,5 с |
| курсор + слежение, простой 10 с | накопленные 15 строк схлопываются до 5, и так **каждый тик** | 10 GET за 10 с (опрос + `reset`) |

1. **Добавление = перезапрос всего окна.** `db-demo/+page.svelte` отдаёт формам
   `onApplied={refreshList}` → `list.reset()`. При этом `CreateForm` уже получил строку
   (`Result.data.created`) и вызвал `optimistic.confirm(tmpId, row)` — карточка обновлена
   сама, `reset` поверх неё лишний.
2. **Курсор + слежение = `reset` каждые 2 с.** Ответ курсорного режима несёт `extra.after` —
   подписанный токен с `exp` = «сейчас + TTL». Сервер переподписывает его на каждом запросе,
   поэтому тело, а с ним ETag (`fingerprint(body)`) другие на каждом тике, хотя строки те же.
   `live.svelte.ts` считает это «изменилось» → `onFresh` → `actions.reset()`: накопленные окна
   теряются, а сам `reset` идёт ещё одним GET.
3. **`onFresh` не различает режимы.** При `scrollY ≤ 100` — `reset`, иначе пилюля; одинаково
   для страниц и курсора. Запись в `LIVE-APPEND.md` §5 «в курсорном режиме — пилюля» с кодом
   расходится.
4. **304 при одном зрителе не бывает.** Память условного GET (`live-cache.ts`) живёт 1500 мс,
   опрос — раз в 2000 мс: к следующему тику запись уже истекла, и каждый тик читает базу.
   Замер: `If-None-Match` через 0,5 с и 1 с → 304, через 2 с → 200.
5. **Своя запись не отличается от чужой.** Опрос видит «изменилось» и после собственной
   вставки: карточка уже показала строку, но список всё равно пересобирается.
6. **Сид давал одинаковое `created_at`** (`DEFAULT clock_timestamp()` в одном `INSERT`) —
   порядок «Как в слое» был произвольным. Исправлено: шаг `demo-post-seed-500`, 500 записей
   с шагом в минуту (`src/lib/server/db.ts`). На уже развёрнутой БД с записями шаг не делает
   ничего (`WHERE NOT EXISTS`).

### Что выбрано и сделано (14.10.2026)

Все пять причин выше устранены; `reset` остался только за сменой фильтра/порядка/режима и за
кликом по пилюле в постраничном режиме.

- **ETag по данным, без токена; память 304 — 5 с** (`server/live-cache.ts`: `stableText`,
  `LIVE_CACHE_TTL_MS`). Отпечаток не включает переподписываемый `extra.after`; TTL — 2,5
  интервала опроса, при котором два тика из трёх без изменений обходятся без базы (304 срок
  не продлевает — устаревание на соседнем инстансе ограничено 5 с). Причины 2 и 4.
- **Локальные правки окна в ядре — `patchItems`** (`paginate/core.ts`, действие
  `patchItems` у `usePaginatorActions`): `{ insert, at: 'head' | 'tail' }`, `{ update }`,
  `{ remove: id }`. Окно правится на месте, `totalItems`/`totalPages`/`hasNext` сдвигаются,
  предзагруженные соседи сбрасываются. Идентичность — паспорт записи источника
  (`adapter.recordFor`, тот же `record.id`, что у поиска и ключей списка); без паспорта
  правка отказывает. Формы демо вызывают её вместо `reset`; место своей строки известно без
  сервера только при порядке по `created_at` и без фильтра (`ownRowPlacement`), иначе
  подтверждённая карточка остаётся карточкой до следующей загрузки. Причины 1 и 5;
  удаление строки не с первой страницы больше не выбрасывает на первую.
- **Слежение — вопрос «что появилось», а не переспрос окна**: `GET /api/db-posts?since=<ISO>`
  (+ `flt` выдачи) → строки новее отметки, свежие первыми, не больше 50; `since=` пусто →
  сама отметка (`created_at` и `id` самой свежей строки). Условие соединяется с фильтром
  пользователя через `and` языка слоя (оператор `gt` у `created_at` объявлен ресурсом);
  смешивание с ключами страницы — 422. Разворот порядка (Р2) не понадобился: вопрос не про
  страницу. Список (`db-list/fresh.ts`, `DbPostsList.svelte`) отсеивает строку-отметку,
  показанные и свои строки (`optimistic.own`). Курсор + порядок «новые сверху» + читатель у
  начала (≤ 100 px) — строки встают в голову окна через `patchItems`; иначе — пилюля
  «↑ N новых записей — показать» (потолок — «50+»): в курсорном режиме клик вставляет и
  поднимает к началу, в постраничном — `reset` на первую. Причины 2, 3 и 5.

Мерка: `patch-items.test.ts` (8), `fresh.test.ts` (4), `live.test.ts` (8),
`optimistic.test.ts` (9), `live-cache.test.ts` (8); HTTP-проверка — 38 (курсорный повтор → 304,
`since`: отметка/новые/фильтр, 422 на смешанный адрес); браузер — 22 (после записи и удаления
ни одного запроса страницы, своя запись не даёт пилюли, чужая — пилюля в постраничном режиме
и строка сверху в курсорном).

Граница, названная честно: строка, созданная между загрузкой списка и запросом отметки (один
сетевой круг после включения слежения или сброса), пилюлей не покажется — её покажет
следующая загрузка. **Открыто — Г, `refresh({ keepWindow: true })`**: правки чужими руками
внутри окна опрос «что появилось» не видит.

### Прочее

- Чат-режим в списке БД не сделан сознательно: `/db-demo` — витрина «номера страниц +
  курсор», чат показан в демо-пагинаторе.
- Опрос новых записей и форма считают сбои раздельно (два backoff'а) — не ошибка, но при
  развитии живого режима это надо свести.
- Поиск без учёта регистра в демо: ресурс объявляет `eq/contains/startsWith`, поэтому
  `icontains`/`istartsWith` отклоняются (deny-safe работает как задумано). Включается одной
  строкой в `field.filters`, если демо это понадобится.

## Безопасность хоста (задача оператора)

- Кластер, на котором мерили, был без TLS и с `trust`; в production — TLS, пароль/SCRAM,
  роль приложения без `SUPERUSER`/`BYPASSRLS`.
