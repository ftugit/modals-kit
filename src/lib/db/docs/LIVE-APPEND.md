# T8. Живая выдача: «режим чата» и оптимистичная карточка

Постановка заказчика (10.10.2026), дословно значимое:

> «в зависимости от сортировки новые посты будут появляться либо с конца либо в
> начало пагинатора. Автоматически. По идее в режиме чата это будет всегда курсор,
> тут ты должен уже сам исследовать»; «сразу после отправки формы, если она прошла
> валидацию, создаётся card в поток за последним id… когда REST/БД ответит, данные у
> card перезаписываются… фэйковый card должен быть немного прозрачным. Если сервер
> вернул неудачу — в зависимости от опции card либо удаляется, либо можно повторить
> отправку»

Здесь разбор и решения. Код — за ним, но только в том объёме, который доказан этим
разбором: правка ядра пагинатора без измерения UX-проблемы была бы «ещё один API на
всякий случай».

## 1. Что есть в слое и чего в нём нет

| Есть | Где | Чего не хватает для T8 |
|---|---|---|
| `EdgeTrigger = off\|direction\|edge\|chat\|manual` | `src/lib/paginate/types.ts:207` | `chat` описывает **жест** (грузить только в сторону движения), а не источник новых строк |
| `LoadMoreLink` + `EdgeSentinel` + `prependBehavior` | `src/components/paginator`, `PaginatorHost.svelte` | строки, которой нет ни в одном ответе источника |
| `pending` | `core.ts:308` | только слоты-скелетоны по числу ожидаемых записей; «данные есть, ответа ещё нет» там выразить нечем |
| `mode: accumulate\|single`, `extra` в адресе, `?page.after` (keyset) | ядро + `adapter-url.ts`, демо-источник (папка роута `/db-demo`) | точки «переспросить ТЕКУЩЕЕ окно, не сбрасывая его» (T6.2 `refresh`) |
| возможности источника (`capabilitiesFor`) | `source.ts` | источника, который умеет расти без перезапроса страницы |

Вывод из таблицы один: **две независимые вещи** — «доставить новые строки» (ядро +
адрес) и «показать строку до ответа сервера» (состояние списка). Их нельзя решить
одним пропом в разметку, иначе оптимистичная карточка станет частью навигации.

## 2. Как это делают снаружи (изучение 10.10.2026)

### 2.1 Оптимистичная запись

Жизненный цикл, общий у TanStack Query и у всего, что делает это вручную
([optimistic updates guide](https://www.mintlify.com/TanStack/query/guides/optimistic-updates),
[разбор с паттернами](https://oneuptime.com/blog/post/2026-01-15-react-optimistic-updates-react-query/view)):

1. **отменить/заблокировать идущие запросы** перед записью в состояние — иначе
   фоновый refetch прилетит ПОСЛЕ оптимистичной записи и сметёт её (это и есть
   классический «строка мигнула, пропала, появилась снова»:
   [troubleshooting](https://nerdleveltech.com/tanstack-query-optimistic-updates-rollback-tutorial));
2. **снимок предыдущего состояния** → его же возвращаем контекстом для откатa;
3. запись ожидаемых данных (для постраничной выдачи — **в нужную страницу**, а не
   «в конец массива»: `pages[i].items` — см.
   [Paginated Data](https://oneuptime.com/blog/post/2026-01-15-react-optimistic-updates-react-query/view));
4. `onError` → откат по снимку; `onSettled` → инвалидация (приведение к серверу),
   **не** `onSuccess`: ошибка тоже обязана привести состояние в порядок.
5. Временный id обязателен и обязан быть **заменён** серверным, а не добавлен
   рядом («Use temporary IDs for new items and replace them with server-generated
   IDs on success»).

Границы применимости те же, что у школы: оптимизм уместен при высокой доле успеха,
заметной задержке и обратимости; не уместен, когда операция необратима или данные
критичны к точности. Наш `create` подходит по задержке и обратимости, НО первое
измерение здесь же и поправило сам документ: **уникальности по `title` в демо нет**
(в `src/server/db.server.ts` только `demo_post_page` — индекс порядка; `title` держит
`CHECK (length BETWEEN 3 AND 120)`). Практических следов два, и оба жёсткие:
   • «дубль заголовка» как способ получить отказ непригоден — он проходит;
     проба моделирует отказ отменой запроса (`page.route(..., abort)`), что и есть
     тот случай, ради которого карточка существует;
   • дедуплицировать карточку по тексту нельзя: два одинаковых заголовка — две
     законные строки, и «умное» сопоставление молча съедало бы вторую вставку.

Отдельно про форму при неудаче: значение из поля **нельзя** очищать — его возвращают
обратно вместе с откатом, иначе пользователь печатает заново
([обсуждение и ответ maintainer'а](https://github.com/TanStack/query/discussions/1268));
это ровно то, что заказчик назвал «в зависимости от опции card либо удаляется, либо
можно повторить отправку» — у нас это становится третьим тумблером панели, а не
развилкой в голове автора.

### 2.2 Живая выдача и «чат»

* Ось в чате инвертирована: «страница 1» = свежие, «следующая страница» = **старее**
  ([Messenger on Paginator](https://medium.com/@aliev.djamal.2000/messenger-on-paginator-real-world-tasks-732a6ddb3dae)).
  Значит «дальше» и «новые» — разные направления, и путать их нельзя: новые строки —
  это НЕ `after`-шаг, а пересборка головы окна.
* Держать дно: `flex-direction: column-reverse` даёт «приклеенное дно» средствами CSS
  ([Kitty Giraudel](https://kittygiraudel.com/2024-02-26/css-only-bottom-anchored-scrolling-area/)),
  но «CSS-only решения, которое сохраняет дно при добавлении элементов, нет» — JS всё
  равно нужен ([обсуждение](https://www.reddit.com/r/webdev/comments/1nrqwof/is_there_really_no_easy_way_to_make_the_scroll/)).
* Автоскролл — **только если пользователь уже у дна** (порог ~100 px), иначе — ничего,
  а вместо прыжка появляется счётчик новых записей
  ([паттерн](https://stackoverflow.com/questions/25505778/automatically-scroll-down-chat-div),
  [формулировка требований с пилюлей «N novas mensagens»](https://github.com/tprei/dividimos/issues/889)).
  Там же зафиксировано, почему нельзя считать «новые» по `length`: prepend старой
  истории увеличивает длину так же, как append новых строк.
* Препенд старой истории не должен двигать то, что читатель видит: `overflow-anchor`
  браузера — первая линия защиты, ручная компенсация `scrollTop` — только если её
  мало ([preserveScrollOnPrepend](https://ui.shadcn.com/docs/components/base/message-scroller),
  [компенсация на iOS](https://github.com/jessesquires/JSQMessagesViewController/issues/1838)).
* Список обязан быть **ключеванным** (`id` строки), иначе перерисовка всего окна
  сбрасывает скролл наверх
  ([пример с `TrackByFunction`](https://stackoverflow.com/questions/75438808/sending-receiving-a-new-message-takes-me-to-top-of-the-screen-on-chat-app)).
  У нас роль ключа уже играет `data-id`/`catalogTestId` — важно не потерять его при
  вставке оптимистичной строки.
* Уважать `prefers-reduced-motion`: `smooth` без проверки — дефект
  ([dividimos #889](https://github.com/tprei/dividimos/issues/889)).

### 2.3 Чем спрашивать сервер: опрос против выталкивания

Этикет опроса, повторяющийся во всех источниках:

* условный `GET` с `If-None-Match`/ETag: «ничего не изменилось» должен стоить 304 без
  чтения данных ([паттерн](https://medium.com/tech-pulse-by-collatzinc/modern-javascript-polling-adaptive-strategies-that-actually-work-part-1-9909f5946730),
  [и то, что без ETag 304 принципиально невозможен](https://github.com/vachekcz/vizlinx.com/issues/42));
* пауза на скрытой вкладке (`visibilitychange`) и замедление (в 4 раза) на
  неактивных поверхностях, полный останов в терминальных состояниях
  ([PollGate](https://github.com/rouderz/coucou/pull/67));
* экспоненциальный backoff на ошибках (3 → 6 → 12 → 30 → 60 с), сброс после успеха,
  учёт `Retry-After`;
* запросы не должны накладываться (не начинать новый, пока «в полёте» предыдущий) и
  обязаны иметь `AbortSignal.timeout`;
* `Prefer: wait=…` (long-poll-подсказка) — способ получить «почти SSE» без новой
  протокольной ветки ([Fanout](https://blog.fanout.io/2016-11-21/moving-from-polling-to-long-polling/));
* SSE оправдан, когда события частые и latency важнее интервала; у SSE есть
  автопереподключение и `Last-Event-ID`, но нужны heartbeats и отдельный путь на
  сервере ([сравнение](https://coreconceptlearning.com/blog/websocket-vs-sse-vs-long-polling)).
  Для одного пользователя демо честнее 1–2 с опрос: шины событий у нас нет, а
  «WS на Vercel» — ложная экономия (см. `docs/TRANSPORTS.md`).

## 3. Решения (мои — потому что заказчик просил исследовать и решить)

**Р1. В режиме чата навигация всегда курсорная.** Обоснование: offset при появившихся
сверху строках сдвигает границы страниц — строка либо дублируется на двух страницах,
либо исчезает; keyset-токен привязан к значению сортируемого ключа (`values` +
`scope` порядка) и дыру не теряет. `PageNav` в этом режиме не имеет смысла (номера
меняются на глазах), и `withDbCursor` уже снимает `totals` — разметка гасит их сама.

**Р2. «Вверх по истории» делаем разворотом порядка, а не новым `before`-токеном.**
Слой умеет только вперёд (`api.cursor` отдаёт `nextCursor`), и вводить `before` —
значит менять контракт токена и его scope. Разворот `order` (`created_at ASC`) даёт
свой подписанный токен в том же механизме, то есть «назад» = «вперёд по обратной
сортировке». Это же снимает соблазн хранить в адресе два указателя.

**Р3. Оптимистичная строка — не часть источника, а часть окна.** Она не участвует в
`totalItems`, не попадает в `after`-шаг (иначе серверный курсор «перепрыгнул» бы её)
и обязана вставляться **по порядку сортировки**: `created_at DESC` → голова окна,
`ASC` → хвост. Ключ — временный (`tmp:<crypto.randomUUID()>`), поле `id` у неё
отсутствует; `DbPostRow` обязан это пережить (у нас `item.id.slice(0, 8)` → нужен
`id ?? '—'`, иначе белое окно на 200 мс — реальный риск, а не теория).

**Р4. Примирение (reconcile) — по alias, а не по «похожести».** Коммит обязан вернуть
строку: `POST /db-demo/submit` теперь отдаёт в `Result.data.created` `{ id, title,
created_at }` — единственное, чего клиент знать не может. По нему временная запись
**заменяется на месте** (тот же элемент массива, только с `row`), значит без удаления,
без вставки и без скачка; `data: { message }` для этого не хватало в одну строку.
Сопоставление карточки с окном — **только по `id`** (`isAbsorbed`): пока серверного id
нет, «похожая» строка карточку не отменяет. Цена, названная честно: если опрос принёс
запись раньше ответа формы, одна лишняя полупрозрачная копия живёт до `confirm` —
уникальности по заголовку, которая сделала бы это невозможным, в схеме нет.

**Р5. Неудача — опция, а не поведение.** `onFailure: 'remove' | 'retry'`: `remove` =
откат по снимку (строка исчезает, форма остаётся заполненной), `retry` = строка
остаётся полупрозрачной с кнопкой «повторить» и исходными значениями. Панельный
третий тумблер (или select из двух значений — select, **не** чекбокс, потому что
«пустое = не трогаем» и здесь сыграло бы злую шутку, см. `compile.ts:toPatch`).

**Р6. Автоподгрузка = условный опрос текущего окна, а не «`page=1` ещё раз».** *(Реализовано иначе —
три раздельных запроса вместо переспроса окна: новые у края, изменённые и удалённые в границах
видимой порции; см. `src/routes/(site)/(app)/db-demo/live.svelte.ts`, `src/routes/(site)/(app)/db-demo/fresh.ts`
и `src/server/live-cache.server.ts`.)*
Ядру нужна точка `refresh({ keepWindow: true })` (T6.2): переспрашиваются те же
ключи, включая `?page.after` головы, ответ склеивается по ключам. Правила опроса —
из §2.3: `If-None-Match` на `/api/db-posts` (+ `ETag` из `max(created_at)`/счёта),
пауза на скрытой вкладке, backoff на ошибке, незаходящие друг друга запросы,
`AbortSignal.timeout`. Интервал по умолчанию 2 с, в панели — «обновлять: выкл / 2 с /
5 с» (select).

**Р7. Держать дно = «был у дна → остаётся у дна; не был → пилюля «N новых».**
Порог 100 px; длина списка как сигнал — не годится (см. §2.2); авто-скролл с
`behavior` по `prefers-reduced-motion`.

## 4. Порядок работ (и почему он такой)

**T8.1 — демо без правки ядра (доказательство UX).**
1. `src/routes/(site)/(app)/db-demo/optimistic.svelte.ts`: `pending` (массив
   `{ tmpId, row, state: 'pending' | 'failed' }`), `begin()/confirm()/fail()`,
   снимок для отката, `begin(title, reuseId)`.
2. `DbPostsList`: `PageList` + до/после него (по порядку сортировки) — строки из
   `pending`; класс `opacity-60` + `aria-busy`; `DbPostRow` принимает запись без `id`.
3. `CreateForm`: после валидации — `begin()` **до** fetch; `confirm(real)` по
   ответу; `fail()` по ошибке/403; при `retry` — кнопка повтора в строке.
4. `live.svelte.ts`: опрос текущего окна по R6 (в `onMount`/`unmount`, `visibilitychange`,
   backoff), `ETag`-заголовок на `/api/db-posts` + `Cache-Control: no-store` как есть.
5. Пробы: HTTP-проверка `ETag → 304`, `size`/`after` не меняются; браузерная —
   «строка появилась до ответа» (метка на `window` + `performance.mark`), «нет скачка
   при примирении» (снимка `scrollTop` до/после confirm), «откат удаляет / retry
   оставляет», «скрытая вкладка не спамит» (счётчик запросов).

Если T8.1 показывает, что слияние «pending + окно» требует знания окон и якорей —
тогда и только тогда **T8.2**: примитив ядра (`state.shadow: T[]` +
`core.setShadow()`, ключ-слияние по `record.id`, участие в `pending`-счёте и в
`preserveScrollOnPrepend`) и `refresh({ keepWindow: true })` в `core.ts`/
`adapter-url.ts` с тестами в `paginate.test.ts`. Право на это решение — за меркой из
T8.1, а не за желанием иметь красивый API.

**Что остаётся открытым (нужно от заказчика, а не от меня):**

1. Интервал автоподгрузки по умолчанию: 2 с (отзывчиво, шумно) или 5 с (демо-скромно)?
   Я ставлю 2 с с паузой на скрытой вкладке и прошу подтвердить.
2. Должна ли оптимистичная строка участвовать в «всего записей» (`totalItems`): моё
   решение — нет (счётчик сервера, а не домысел клиента); если нужно «+1 сразу»,
   это отдельная опция панели.
3. Нужен ли «длинный» путь (`Prefer: wait=` на `/api/db-posts`, ~30 строк на сервере
   и ни одного нового протокола); по умолчанию — нет, пока опрос отвечает
   304 за ~1 мс.

ядра на самом деле — так это `refresh({ keepWindow: true })` (сейчас автообновление
в курсорном режиме означает `reset`, то есть потерю накопленных окон). Обновление 14.10.2026: переспрос окна заменён
опросом «что появилось» (`?since=`), своя запись правит окно через `patchItems` ядра, а
`reset` после записи и на тике ушёл — см. §6 ниже, «Что выбрано и сделано».
Вводить `state.shadow` ради одной демо-страницы — значит отдать половину `core.ts`
за поведение, которое сегодня стоит 120 строк в демо-странице.

**Три вопроса закрыты моими же решениями, ждут подтверждения заказчика:**
интервал 2 с (пауза на скрытой вкладке, backoff до 60 с); `totalItems` оптимистичной
строкой НЕ двигается (счётчик сервера); `Prefer: wait=` не добавлялся — тик — это
`304` за ~1 мс (память 5 с = 2,5 интервала), а long-poll держал бы воркера и ничего не дал бы демо.

Честные границы того, что здесь «живое»: это опрос, а не push (задержка ≤ интервал);
память условного GET — на процесс (несколько инстансов = чуть больше 200-х, ошибок
не даёт); первый запрос после включения слежения — отметка (`since=` пусто), а не
«изменение».

## 6. Список БД и пагинатор: лишние перезапросы (14.10.2026)

### Наблюдения 14.10.2026 (замер — браузер + счёт запросов, сид 500 записей; устранены — см. ниже)

Претензия владельца: «после добавления записи список обновляется постоянно; фейковая карточка
должна получать обновление, а не весь список; курсор + „следить за новыми“ — постоянное
обновление пагинатора». Подтверждено, причины найдены:

| сценарий | что видно | запросы |
|---|---|---|
| страницы, добавление | карточка подтверждается строкой из ответа, и **сразу же** весь список перезапрашивается | POST + `GET /api/db-posts` |
| страницы + слежение, добавление | список перезапрашивается **дважды**: `onApplied → reset`, затем опрос видит новый ETag → ещё `reset` | POST + 4 GET за 4,5 с |
| курсор + слежение, простой 10 с | накопленные 15 строк схлопываются до 5, и так **каждый тик** | 10 GET за 10 с (опрос + `reset`) |

1. **Добавление = перезапрос всего окна.** `db-demo/+page.svelte` отдаёт формам
   `onApplied={refreshList}` → `list.reset()`. При этом `CreateForm` уже получил строку
   (`Result.data.created`) и вызвал `optimistic.confirm(tmpId, row)` — карточка обновлена
   сама, `reset` поверх неё лишний.
2. **Курсор + слежение = `reset` каждые 2 с.** Ответ курсорного режима несёт `extra.after` —
   подписанный токен с `exp` = «сейчас + TTL». Сервер переподписывает его на каждом запросе,
   поэтому тело, а с ним ETag (`fingerprint(body)`) другие на каждом тике, хотя строки те же.
   `live.svelte.ts` считает это «изменилось» → `onFresh` → `actions.reset()`: накопленные окна
   теряются, а сам `reset` идёт ещё одним GET.
3. **`onFresh` не различает режимы.** При `scrollY ≤ 100` — `reset`, иначе пилюля; одинаково
   для страниц и курсора. Запись в `LIVE-APPEND.md` §5 «в курсорном режиме — пилюля» с кодом
   расходится.
4. **304 при одном зрителе не бывает.** Память условного GET (`live-cache.ts`) живёт 1500 мс,
   опрос — раз в 2000 мс: к следующему тику запись уже истекла, и каждый тик читает базу.
   Замер: `If-None-Match` через 0,5 с и 1 с → 304, через 2 с → 200.
5. **Своя запись не отличается от чужой.** Опрос видит «изменилось» и после собственной
   вставки: карточка уже показала строку, но список всё равно пересобирается.
6. **Сид давал одинаковое `created_at`** (`DEFAULT clock_timestamp()` в одном `INSERT`) —
   порядок «Как в слое» был произвольным. Исправлено: шаг `demo-post-seed-500`, 500 записей
   с шагом в минуту (`src/server/db.server.ts`). На уже развёрнутой БД с записями шаг не делает
   ничего (`WHERE NOT EXISTS`).

### Что выбрано и сделано (14.10.2026)

Все пять причин выше устранены; `reset` остался только за сменой фильтра/порядка/режима и за
кликом по пилюле в постраничном режиме.

- **ETag по данным, без токена; память 304 — 5 с** (`server/live-cache.ts`: `stableText`,
  `LIVE_CACHE_TTL_MS`). Отпечаток не включает переподписываемый `extra.after`; TTL — 2,5
  интервала опроса, при котором два тика из трёх без изменений обходятся без базы (304 срок
  не продлевает — устаревание на соседнем инстансе ограничено 5 с). Причины 2 и 4.
- **Локальные правки окна в ядре — `patchItems`** (`paginate/core.ts`, действие
  `patchItems` у `usePaginatorActions`): `{ insert, at: 'head' | 'tail' }`, `{ update }`,
  `{ remove: id }`. Окно правится на месте, `totalItems`/`totalPages`/`hasNext` сдвигаются,
  предзагруженные соседи сбрасываются. Идентичность — паспорт записи источника
  (`adapter.recordFor`, тот же `record.id`, что у поиска и ключей списка); без паспорта
  правка отказывает. Формы демо вызывают её вместо `reset`; место своей строки известно без
  сервера только при порядке по `created_at` и без фильтра (`ownRowPlacement`), иначе
  подтверждённая карточка остаётся карточкой до следующей загрузки. Причины 1 и 5;
  удаление строки не с первой страницы больше не выбрасывает на первую.
- **Слежение — вопрос «что появилось», а не переспрос окна**: `GET /api/db-posts?since=<ISO>`
  (+ `flt` выдачи) → строки новее отметки, свежие первыми, не больше 50; `since=` пусто →
  сама отметка (`created_at` и `id` самой свежей строки). Условие соединяется с фильтром
  пользователя через `and` языка слоя (оператор `gt` у `created_at` объявлен ресурсом);
  смешивание с ключами страницы — 422. Разворот порядка (Р2) не понадобился: вопрос не про
  страницу. Список (`db-list/fresh.ts`, `DbPostsList.svelte`) отсеивает строку-отметку,
  показанные и свои строки (`optimistic.own`). Курсор + порядок «новые сверху» + читатель у
  начала (≤ 100 px) — строки встают в голову окна через `patchItems`; иначе — пилюля
  «↑ N новых записей — показать» (потолок — «50+»): в курсорном режиме клик вставляет и
  поднимает к началу, в постраничном — `reset` на первую. Причины 2, 3 и 5.

Мерка: `patch-items.test.ts` (8), `fresh.test.ts` (4), `live.test.ts` (8),
`optimistic.test.ts` (9), `live-cache.test.ts` (8); HTTP-проверка — 38 (курсорный повтор → 304,
`since`: отметка/новые/фильтр, 422 на смешанный адрес); браузер — 22 (после записи и удаления
ни одного запроса страницы, своя запись не даёт пилюли, чужая — пилюля в постраничном режиме
и строка сверху в курсорном).

Граница, названная честно: строка, созданная между загрузкой списка и запросом отметки (один
сетевой круг после включения слежения или сброса), пилюлей не покажется — её покажет
следующая загрузка. **«Открыто — Г» ЗАКРЫТО**: `refresh({ keepWindow: true })` не понадобился.
Правки чужими руками внутри окна теперь видны — вопросом «что изменилось новее отметки» по
границам видимой порции, а не переспросом окон (`src/routes/(site)/(app)/db-demo/live.svelte.ts`,
`src/routes/(site)/(app)/db-demo/fresh.ts`). `loadMore`/`reset` ядра не тронуты: применение — `patchItems({ update })` и
`{ remove }` по `id`.
