# lib search

Поиск как **перехват пагинатора**: lib/search подключается к источнику
декоратором `withLibSearch` (тот же путь и в `defineSearch`, который
регистрирует пагинатор на URL-адаптере). Источник — АДАПТИРОВАННЫЙ
(`$lib/paginate/source`): паспорт записи (`id`/`title`/`texts`), словарь и
размер батча lib/search берёт у него, а не у потребителя. Своего ядра состояния у поиска нет — страницы, гонки,
SSR-снапшоты, back/forward, ссылки без JS делает lib/paginate; запрос `q` —
обычный ключ extra пагинатора (`reloadKeys: ['q']`).

Поведение перехваченного пагинатора:

- **запрос пуст** → сквозной проход: базовый источник отдаёт обычные страницы
  каталога — пагинатор работает так, как будто поиска нет;
- **SSR/no-JS с запросом** → тот же базовый источник: серверное сужение точной
  подстрокой по сырому `q` (fuzzy на сервере не исполняется никогда);
- **клиент с запросом** → поиск забирает у источника данные первой страницы
  (батчем) и подгружает следующие, если надо: со словарём — коррекция опечаток
  и серверное сужение исправленным запросом, без словаря — сканирование.

## Состав

| Файл | Роль |
| --- | --- |
| `index.ts` | Публичная поверхность framework-neutral части. Svelte-обвязки здесь нет намеренно — см. ниже |
| `types.ts` | Контракты: `SearchConfig` (вход `defineSearch`), `SearchInstance` |
| `registry.ts` | Реестр по имени (deny by default), `defineSearch` (перехват + регистрация пагинатора), `searchAddressSpec` для validateSearch роута |
| `core.ts` | Vanilla-действия: `setSearchQuery` / `clearSearchQuery` / `resyncSearch` (обёртки над `setExtra`/`goToPage`) |
| `accumulator.ts` | `withLibSearch` — подключение fuzzy-контура к адаптированному источнику (нужно `scan` в спеке); `createAccumulatingSource` — механика бюджета и виртуальных страниц без средовых гардов |
| `fuzzy.ts` | Изоморфное ядро: foldKey, взвешенный Дамерау-Левенштейн, словарь терминов, скоринг |
| `dictionary.ts` | Клиент: разбор артефакта `display\tdf`, биграммный индекс, корректор запроса |
| `svelte/` | Svelte 5-вход `$lib/search/svelte`: хук `useSearchCorrection` (подпись «искали X → показываем Y»). Устроен как `$lib/paginate/svelte`: ядро о фреймворке не знает, обвязка живёт отдельной точкой входа — поэтому `$lib/search` остаётся импортируемым из node-тестов |

Самой формы поиска в библиотеке нет: поле запроса — обычное поле lib form
(`<Form method="get">` + поле), транспорт — GET-форма, композицию собирает
приложение. Связь тонкая: `commit` — это `setSearchQuery`, ресинк deep-link'а —
`resyncSearch` при монтировании хоста результатов.

## Подключение (три шага)

```ts
// 1. Регистрация (общий модуль клиента и сервера — как definePaginator).
//    source — базовый источник страниц; ОБЯЗАН понимать extra.q на сервере
//    как подстрочное сужение (отдельным полем транспорта, не в фильтрах!).
defineSearch<Record>({
  name: 'my-search',        // имя пагинатора
  pageParam: 'search',      // адрес: ?search=N, ?search.q=строка
  source: baseSource,
  fuzzy: { id, texts, correct, onCorrection },  // клиентское усиление
})

// 2. Роут: спецификации ВСЕХ пагинаторов страницы массивом
export const load = ({ url }) => /* … */ void url
// validateSearch: paginatorSearch([
//   { pageParam: 'page', extra: CATALOG_EXTRA },
//   searchAddressSpec('search'),
// ])
// loader: initServerPaginator(store, 'my-search', { url }) — SSR-снапшот
// (пустой q = обычная страница каталога, с q = страница результатов)
```

```svelte
<!-- 3. Страница: обычный хост single + PageNav, ВСЕГДА видимый, форма над ним. -->
<form method="get" action="/my-page">
  <input name="search.q" value={q} />
</form>

<PaginatorHost name="my-search" snapshot={data.snapshot} mode="single"
  topTrigger="off" bottomTrigger="off" extraDefaults={{ q: '' }}>
  {#snippet children()}
    <!-- items… -->
    <PageNav name="my-search" />
  {/snippet}
</PaginatorHost>
```

```svelte
<!-- Подпись коррекции — из Svelte-входа -->
<script lang="ts">
  import { useSearchCorrection } from '$lib/search/svelte'
  const correction = useSearchCorrection('my-search')
</script>
{#if correction()?.changed}
  <p>Искали «{correction()!.query}» — показываем «{correction()!.corrected}»</p>
{/if}
```

**Несколько поисков на странице** — несколько `defineSearch` с разными
`name`/`pageParam` и все спецификации в массиве `paginatorSearch`. Каждый ключ
адреса принадлежит ровно одному пагинатору.

### Второй способ: пагинатор + перехватчик (как в демо)

Когда пагинатор уже определён сам (свой URL-адаптер, `pageSizes`, опции панели)
и один источник обслуживает несколько входов, поиск подключается НИЖЕ уровня
реестра — тем же перехватчиком, которым пользуется `defineSearch`:

```ts
// Клиент и сервер: пагинатор с источником-диспетчером.
const base = defineSource<Item>({
  name: 'items',
  record: { id: (r) => String(r.id), title: (r) => r.title, texts: (r) => [r.title] },
  search: { minLength: 2 },   // родной поиск источника (q → параметр API)
  scan: { batchSize: 50 },    // разрешение сканирования для fuzzy-контура
  dictionary: () => loadTerms(),   // словарь коррекции — свойство ИСТОЧНИКА
  data: (look, input) => loadPage(look, input),
})
// lib/search: fuzzy + коррекция; тумблер потребителя — ключ extra `ls`.
const source = withLibSearch(base, {
  gate: 'ls',
  onCorrection: (info) => reportSearchCorrection(name, info), // канал реестра
  onStats: (stats) => publishStats(name, stats),              // канал потребителя
})

definePaginator({ name, source, reloadKeys: ['q', 'ls'],
  adapter: createUrlAdapter({ name, source, pageSizes, extraSearch: { q: qValidator } }) })
```

Подключение к источнику без `scan` — ошибка разработчика (`withLibSearch`
бросает): «включено, но молча ничего не делает» слой не допускает.

Отличия от `defineSearch` ровно два, и оба — про отсутствие экземпляра поиска
в реестре: запись запроса делается штатным `setExtra(store, name, { q })`
(нормализация — `normalizeSearchQuery`), а перезапрос текущей страницы после
гидратации deep-link'а — `goToPage(store, name, state.page)` (в single-семантике
это REPLACE через перехватчик) вместо `resyncSearch`. Подпись коррекции
(`useSearchCorrection`) и `hasSearch/getSearch` при этом работают как обычно.

## Что lib search НЕ делает

lib search — **не хранилище и не транспорт**. Адрес (`?<pageParam>`,
`?<pageParam>.q`), состояние, SSR-снапшоты и persist принадлежат пагинатору и
его URL-адаптеру; источник свою работу не меняет. Вся разница после перехвата:
пагинатор просит страницы у lib search, а lib search внутри запрашивает
страницы у источника (с первой и дальше). У lib search есть только
оперативный буфер ранжирования в памяти клиента — он не переживает
перезагрузку и никуда не сохраняется.

## Фильтры источника проходят сквозь перехват

Фильтры принадлежат ИСТОЧНИКУ, а не lib search: перехват цепочку не рвёт —
источник фильтрует, lib search просит у него страницы. `defineSearch`
принимает `extraSearch` (ключи адреса вида `?<pageParam>.filters.*`) и
`reloadKeys` (их смена перезагружает выдачу, как смена запроса) и передаёт их
адаптеру пагинатора; перехватчик кладёт ВСЕ ключи extra, кроме `q`, в каждый
запрос к источнику. Отпечаток буфера включает эти ключи: другой набор
фильтров — другая выдача источника, буфер строится заново, замороженные
страницы старого набора не смешиваются с новым.

## Поделённый адрес (deep-link) с запросом

Сервер рендерит такую страницу данными ИСТОЧНИКА (подстрока по сырому q). С JS
страница при монтировании хоста вызывает `resyncSearch`: lib search просит
источник с ПЕРВОЙ страницы, в фоне добирает данные на нужное число страниц и
показывает именно запрошенную страницу — не продолжая от перехваченных
серверных данных. Адрес не меняется. Данные lib search и источника для одной и
той же страницы могут различаться — осознанный компромисс шаринга адреса,
не баг. Без JS механизм не работает (остаётся серверная выдача источника).

## Статусы во время загрузки

Пока lib search добирает страницы у источника, запрос пагинатора «в полёте» —
`status='loading'` держится до полного ответа перехватчика (сколько бы фоновых
обращений к источнику тот ни сделал). Статусы UI обязаны читаться из STATE
пагинатора, а не из фактических данных: `EmptyState` («ничего не найдено») и
`EndRow` («конец») показываются ТОЛЬКО в `status='idle'`; во время загрузки
видна строка «Загрузка страницы…» (replace-pending группа). Пагинатор никогда
не решает «данных нет» на основании пустого списка, пока lib search ещё грузит.

## Правила (из принятых решений 2026-09-29)

- **Запрос — отдельное поле, никогда не в filters**: значения фильтров идут
  через схему и точное сравнение, произвольный ключ там даёт пустую выдачу.
  Серверный транспорт принимает `q` рядом с фильтрами.
- **Fuzzy никогда на сервере**: SSR/no-JS — сквозной вызов базового источника
  с сырым `q`, fuzzy-контуры включаются только в браузере.
- **Адрес хранит сырой q**; исправленный запрос — только подпись в UI
  (`useSearchCorrection`).
- **`mode="single"`** — условие перехвата: накопительная лента с fuzzy-порядком
  дала бы «шов» сортировки между порциями. `totalItems` перехват не отдаёт
  НИКОГДА: число страниц непредсказуемо, PageNav автоматически остаётся на
  стрелках; номерная навигация живёт только у неперехваченного источника
  (пустой запрос / no-JS), если тот отдаёт totalItems.
- **fuzzy — это метод** (сопоставление и ранжирование, `fuzzy.ts`); страницы
  добирает сама lib search: наполняет страницу пагинатора до pageSize,
  избыток переносит на следующую и добирает дальше.
- **Позиция чтения источника не попадает в адрес**: в URL только номер
  виртуальной страницы; перехватчик строит страницы «водяным знаком» (повтор
  шагов 1..p), выданные id заморожены — deep-link ≡ проходу кликами, без
  дублей и потерь.
- `extraDefaults={{ q: '' }}` на хосте обязателен: back/forward на адрес без
  `.q` должен сбросить запрос (diff externalRestorable сравнивает только
  присутствующие ключи).

## Известное ограничение v1

Перехваченный пагинатор независим от фильтров каталога: сквозной проход и
поиск идут по всему каталогу, а «Применить фильтры» (канонический redirect
серверной формы) сбрасывает ключи `?search*` из адреса. Сохранение q при
applyUrl серверной формы — отдельная задача (v2).

## Происхождение

Библиотека перенесена из исходника SolidHono (`src/lib/search`) — логика,
контракты и правила сохранены без упрощений; отличия порта ровно два:
импорты смотрят на `$lib/paginate`, а Solid-хук `useSearchCorrection` заменён
Svelte 5-обвязкой в `$lib/search/svelte`. Единственный файл канона, который
сюда не переносился, — `catalog-filter.ts` (схема фильтров каталога → форма →
адрес): он построен на form-API канона (`@/lib/form/core`: `defineForm`,
`field`, `safeName`, `validators`), которого в порте форм нет, и принадлежит
витрине каталога, а не механике поиска. Если он понадобится, это отдельная
задача с адаптацией под `$lib/form`.
