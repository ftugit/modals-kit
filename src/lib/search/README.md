# lib search

> Порт из исходника (SolidHono, `src/lib/search/`) на SvelteKit-репозиторий modals-kit.
> Ядро (fuzzy, dictionary, accumulator, registry, core) — изоморфное, перенесено 1:1;
> слой фреймворка — `svelte/correction.svelte.ts` (порт хука) и `solid.tsx` (референс
> исходника). Отличия порта и состав — в § «Порт» в конце файла.

Поиск как **перехват пагинатора**: `defineSearch` подменяет источник
пагинатора обёрткой (`createSearchInterceptor`) и регистрирует его на
URL-адаптере. Своего ядра состояния у поиска нет — страницы, гонки,
SSR-снапшоты, back/forward, ссылки без JS делает lib/paginate; запрос `q` —
обычный ключ extra пагинатора (`reloadKeys: ['q']`).

Поведение перехваченного пагинатора:

- **запрос пуст** → сквозной проход: базовый источник отдаёт обычные страницы
  каталога — пагинатор работает так, как будто поиска нет;
- **SSR/no-JS с запросом** → тот же базовый источник: серверное сужение точной
  подстрокой по сырому `q` (fuzzy на сервере не исполняется никогда);
- **клиент с запросом** → поиск забирает у источника данные первой страницы
  (батчем) и подгружает следующие, если надо: со словарём — коррекция опечаток
  и серверное сужение исправленным запросом, без словаря — сканирование.

## Подключение (три шага)

```ts
// 1. Регистрация (общий модуль клиента и сервера — как definePaginator).
//    В порте импорты идут через `$lib/search` / `$lib/paginate`.
//    source — базовый источник страниц; ОБЯЗАН понимать extra.q на сервере
//    как подстрочное сужение (отдельным полем транспорта, не в фильтрах!).
defineSearch<Record>({
  name: 'my-search',        // имя пагинатора
  pageParam: 'search',      // адрес: ?search=N, ?search.q=строка
  source: baseSource,
  fuzzy: { id, texts, correct, onCorrection },  // клиентское усиление
})

// 2. Роут: спецификации ВСЕХ пагинаторов страницы массивом
validateSearch: paginatorSearch([
  { pageParam: 'page', extra: CATALOG_EXTRA },
  searchAddressSpec('search'),
])
// loader: initServerPaginator(store, 'my-search', { url }) — SSR-снапшот
// (пустой q = обычная страница каталога, с q = страница результатов)

// 3. Страница: обычный хост single + PageNav, ВСЕГДА видимый, форма над ним.
//    Поле запроса — через lib form (все поля приложения идут через валидатор):
//    commit = setSearchQuery, значение из адреса = useSearchQuery, ресинк
//    deep-link'а — onMount(() => resyncSearch('my-search')).
<!-- композицию формы собирает приложение (в исходнике — features/search): -->
<SearchQueryForm path="search.q" action="/my-page"
  current={useSearchQuery('my-search')}
  commit={(v) => void setSearchQuery('my-search', v)} />
<PaginatorHost name="my-search" snapshot={...} mode="single"
  topTrigger="off" bottomTrigger="off" extraDefaults={{ q: '' }}>
  …items… <PageNav />
</PaginatorHost>
```

**Несколько поисков на странице** — несколько `defineSearch` с разными
`name`/`pageParam` и все спецификации в массиве `paginatorSearch`. Каждый ключ
адреса принадлежит ровно одному пагинатору.

## Что lib search НЕ делает

lib search — **не хранилище и не транспорт**. Адрес (`?<pageParam>`,
`?<pageParam>.q`), состояние, SSR-снапшоты и persist принадлежат пагинатору и
его URL-адаптеру; источник свою работу не меняет. Вся разница после перехвата:
пагинатор просит страницы у lib search, а lib search внутри запрашивает
страницы у источника (с первой и дальше). У lib search есть только
оперативный буфер ранжирования в памяти клиента — он не переживает
перезагрузку и никуда не сохраняется.

## Фильтры источника проходят сквозь перехват

Фильтры принадлежат ИСТОЧНИКУ, а не lib search: перехват цепочку не рвёт —
источник фильтрует, lib search просит у него страницы. `defineSearch`
принимает `extraSearch` (ключи адреса вида `?<pageParam>.filters.*`) и
`reloadKeys` (их смена перезагружает выдачу, как смена запроса) и передаёт их
адаптеру пагинатора; перехватчик кладёт ВСЕ ключи extra, кроме `q`, в каждый
запрос к источнику. Отпечаток буфера включает эти ключи: другой набор
фильтров — другая выдача источника, буфер строится заново, замороженные
страницы старого набора не смешиваются с новым.

## Поделённый адрес (deep-link) с запросом

Сервер рендерит такую страницу данными ИСТОЧНИКА (подстрока по сырому q).
С JS страница при монтировании хоста вызывает `resyncSearch`: lib search просит
источник с ПЕРВОЙ страницы, в фоне добирает данные на нужное число страниц и
показывает именно запрошенную страницу — не продолжая от перехваченных
серверных данных. Адрес не меняется. Данные lib search и источника для одной
и той же страницы могут различаться — осознанный компромисс шаринга адреса,
не баг. Без JS механизм не работает (остаётся серверная выдача источника).

## Статусы во время загрузки

Пока lib search добирает страницы у источника, запрос пагинатора «в полёте» —
`status='loading'` держится до полного ответа перехватчика (сколько бы
фоновых обращений к источнику тот ни сделал). Статусы UI обязаны читаться из
STATE пагинатора, а не из фактических данных: `EmptyState` («ничего не
найдено») и `EndRow` («конец») показываются ТОЛЬКО в `status='idle'`; во время
загрузки видна строка «Загрузка страницы…» (replace-pending группа). Пагинатор
никогда не решает «данных нет» на основании пустого списка, пока lib search
ещё грузит.

## Правила (из принятых решений 2026-09-29)

- **Запрос — отдельное поле, никогда не в filters**: значения фильтров идут
  через схему и точное сравнение (`matchesMapFilters`), произвольный ключ там
  даёт пустую выдачу. Серверный транспорт принимает `q` рядом с фильтрами.
- **Fuzzy никогда на сервере**: SSR/no-JS — сквозной вызов базового источника
  с сырым `q`, fuzzy-контуры включаются только в браузере.
- **Адрес хранит сырой q**; исправленный запрос — только подпись в UI
  (`useSearchCorrection`).
- **`mode="single"`** — условие перехвата: накопительная лента с fuzzy-порядком
  дала бы «шов» сортировки между порциями. `totalItems` перехват не отдаёт
  НИКОГДА: число страниц непредсказуемо, PageNav автоматически остаётся на
  стрелках; номерная навигация живёт только у неперехваченного источника
  (пустой запрос / no-JS), если тот отдаёт totalItems.
- **fuzzy — это метод** (сопоставление и ранжирование, `fuzzy.ts`); страницы
  добирает сама lib search: наполняет страницу пагинатора до pageSize,
  избыток переносит на следующую и добирает дальше.
- **Позиция чтения источника не попадает в адрес**: в URL только номер
  виртуальной страницы; перехватчик строит страницы «водяным знаком» (повтор
  шагов 1..p), выданные id заморожены — deep-link ≡ проходу кликами, без
  дублей и потерь.
- `extraDefaults={{ q: '' }}` на хосте обязателен: back/forward на адрес без
  `.q` должен сбросить запрос (diff externalRestorable сравнивает только
  присутствующие ключи).

## Известное ограничение v1

Перехваченный пагинатор независим от фильтров каталога: сквозной проход и
поиск идут по всему каталогу, а «Применить фильтры» (канонический redirect
серверной формы) сбрасывает ключи `?search*` из адреса. Сохранение q при
applyUrl серверной формы — отдельная задача (v2).
