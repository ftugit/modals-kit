# Аудит modals-kit: ветки img и demo

## Область и итог

Проверена история последних 40 коммитов `img` — от `51a63ae` до `d35a173` — и все пять коммитов `demo/storage-server-form` до `b211e8b`. Глубоко проверены наиболее рискованные участки, но не все 231 изменённый файл: это не исчерпывающий аудит.

Работа в основном направлена на объединение существующих механизмов: появилась общая оболочка списков, фильтры вынесены в sidebar, переиспользованы формы и модальные поверхности, добавлен экран своих сессий. Исправлялись сборка и доверенный IP за прокси. В демо синхронизировали код с ядром, добавили общую форму сервера, фильтры и всплывающие поверхности.

**Оценить работу как качественно проверенную пока нельзя.** Найдены несовместимость ядра с демо, неполный экран сессий и сломанный проектный guard. Есть архитектурное решение, похожее на костыль по определению заказчика: общий поиск требует отдельного ручного перечисления экранов для работы без JS.

## Находки

### 1. `img` и демо несовместимы по API поиска — высокий приоритет

В `img` компонент [`SearchBar`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/paginator/ui/SearchBar.svelte#L10-L16) получил обязательные параметры `pageParam` и `from`. Но его вызов в [демо-каталоге](https://github.com/ftugit/modals-kit/blob/b211e8b/modules/demo/files/src/routes/%28site%29/%28app%29/paginator/CatalogDemo.svelte#L485-L492) их не передаёт.

Последствия:

- статическая проверка типов должна обнаружить отсутствующие пропсы;
- no-JS поиск не получает адрес и параметр пагинатора, необходимые для POST и редиректа;
- серверный обработчик поиска [явно регистрирует только списки пользователей и блокировок](https://github.com/ftugit/modals-kit/blob/51a63ae/src/content/user/ui/search.form.server.ts#L12-L19), поэтому одна передача пропсов ещё не решит интеграцию демо.

Вывод основан на коде; сборка с подключённым демо не запускалась. Тег `modules` указывает на проверенный `b211e8b`, то есть проблема относится к текущей связке по умолчанию.

### 2. Экран сессий показывает только первые 30 устройств — высокий приоритет

Маршрут [`/user/sessions`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/routes/%28site%29/%28app%29/user/sessions/%2Bpage.server.ts#L25-L36) вызывает `listSessionsPage()` без параметров. Сервер по умолчанию возвращает [первую страницу по 30 записей](https://github.com/ftugit/modals-kit/blob/51a63ae/src/content/user/sessions.server.ts#L199-L220), а [`SessionsView`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/content/user/ui/SessionsView.svelte#L79-L117) не содержит пагинации.

Если активных сессий больше 30, остальные нельзя просмотреть и отозвать по одной; текущая сессия тоже может отсутствовать в видимой порции. Массовый отзыв остальных при этом предусмотрен. В плане фильтры и другие возможности названы незавершёнными, но ограничение списка существенно и для уже предоставленного экрана.

### 3. После ошибки загрузки модальную ссылку нельзя повторить — средний приоритет

В [`modal-link.svelte.ts`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/hooks/links/modal-link.svelte.ts#L164-L168) клик запускает открытие только при `status === 'idle'`. При ошибке preload статус становится [`error`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/hooks/links/modal-link.svelte.ts#L214-L219), а возврата в `idle` для этого случая нет.

Сценарий: временный сетевой сбой → ошибка на ссылке → повторный обычный клик не пробует загрузить модалку. Это существовавшая ранее проблема, не обязательно регрессия последнего коммита; последний коммит расширил использование preload и потому делает её актуальнее.

### 4. Проектный guard падает на чистом `img` — подтверждено запуском

Команда `node --test tooling/source-schema-guard.test.mjs` дала **18 успешных тестов и один ошибочный**. Проверка жалуется на `filters.range`, `filters.size`, `filters.value` в формах фильтров пользователей и блокировок.

Важно не перепутать причину с сообщением теста: например, [`filters.range` и `filters.value`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/content/user/ui/seed-users/filters-form.ts#L18-L22) — это коды сообщений об ошибках, а не обязательно вручную продублированные ключи фильтра. Похоже на ложные срабатывания guard. Проверка архитектуры не зелёная, и её нельзя надёжно использовать для выявления настоящих нарушений.

### 5. Общий поиск зависит от ручного списка конкретных экранов — архитектурный долг

Общий компонент поиска оформлен как переиспользуемый, но для no-JS режима каждый новый список нужно вручную добавить в `ensure()` в пользовательском модуле. Это [прямо указано в коде](https://github.com/ftugit/modals-kit/blob/51a63ae/src/content/user/ui/search.form.server.ts#L1-L19).

По определению заказчика это похоже на **костыль**: одинаковое действие — поиск по пагинатору — в JS работает через общий механизм, а на сервере требует отдельного знания о каждом экране. Ошибка интеграции демо выше показывает практический риск такого подхода. Стоит рассмотреть регистрацию серверных пагинаторов через уже существующий механизм регистрации источников и модулей, не создавая ещё один ручной реестр.

### 6. Массовый отзыв `others` не защищён от отсутствующего ID текущей сессии — риск API

В [`revokeBulkSessions`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/content/user/sessions.server.ts#L305-L321) текущая сессия исключается только если `actor.sessionId` задан. Если вызвать функцию с `scope: 'others'` и без него, исключения не будет и функция отзовёт все подходящие сессии.

Тип `SessionActor` допускает отсутствие `sessionId`. При этом текущий gateway, судя по коду, передаёт его, поэтому **для нового UI эксплуатация этого сценария не подтверждена**. Но публичный контракт функции опасен: для `others` безопаснее явно отказывать при неизвестной текущей сессии.

## Что выглядит хорошо

- Сессии читаются через модель и ACL, а в клиентскую проекцию намеренно не попадают `jti` и версия.
- Для списков и форм есть попытка переиспользовать существующие `Listing`, `Form`, `Field`, `Surface`, а не собирать каждый экран заново.
- Для IP за доверенным прокси описана граница доверия, есть проверки токена и отдельные тесты.
- Добавлены тесты и документация. Однако SSR-тест экрана сессий не заменяет проверку входа и отзыва в браузере; предыдущий чеклист также отмечает, что живой сценарий вошедшего пользователя не проверялся.

## Проверки и ограничения

Исходники при аудите не изменялись, новых коммитов и чеклиста не создавалось. Playwright не запущен: пакет и браузер в текущем окружении не найдены. Системный Node `20.20.2`, тогда как проект требует `>=22.17 <25`; зависимости не устанавливались. Поэтому сборка, `svelte-check`, полный тестовый набор и браузерные сценарии не проверены. Репозиторий был клонирован до baseline окружения — в нарушение порядка из приложенного промта.

- **GIT:** `git -C /home/user/img log --oneline -3` → `51a63ae feat(user): свои сессии в шапке и блокировка`; `5211237 refactor(db): сброс сборки читает только DATABASE_URL`; `1a7b6cc chore: пустой прогон сборки preview`.
- **GATES:** `node --test tooling/source-schema-guard.test.mjs` → `# fail 1`; `node tooling/public-api.mjs` → `[public-api] входы объявлены и соблюдены: пакетов 11, входов 40`.
- **SKIPPED:** полная проверка изменённых файлов, сборка, typecheck, полный набор тестов и браузерная проверка — по указанным выше ограничениям; фазу проверки среды до клонирования выполнить задним числом невозможно.

## 8. Два реестра блоков фильтров — подтверждённая параллельная реализация

В [`filter-blocks.svelte.ts`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/paginator/filters/filter-blocks.svelte.ts#L17-L29) существует контекстный реестр панели, а в [`filter-registry.svelte.ts`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/paginator/filters/filter-registry.svelte.ts#L24-L32) — глобальный реестр по имени списка. Оба хранят блоки, открытый ключ и слот, реализуют захват, освобождение и возврат блока. [`FilterBlock.svelte`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/paginator/filters/FilterBlock.svelte#L99-L112) выбирает один из них через ветвление.

Правила уже расходятся: [контекстный `claim`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/paginator/filters/filter-blocks.svelte.ts#L61-L69) не заменяет другой блок с тем же ключом, а [глобальный](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/paginator/filters/filter-registry.svelte.ts#L62-L76) допускает замену отсоединённого узла. Разные области видимости объясняют потребность в двух способах доступа, но не требуют обязательно дублировать саму логику. Это подходящий кандидат для объединения механизма с разными адаптерами области видимости. Реальный пользовательский сбой именно от различия `claim` отдельно не воспроизводился.

## 9. Привязка портированных полей к форме продублирована — подтверждено кодом

[`FilterBlock.svelte`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/paginator/filters/FilterBlock.svelte#L51-L84) и [`PopupSteps.svelte`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/steps/PopupSteps.svelte#L101-L132) отдельно находят форму, при необходимости создают ID, назначают контролам атрибут `form` и отслеживают новые узлы через `MutationObserver`.

Поведение различается: `PopupSteps` дополнительно запускает `requestAnimationFrame`, а `FilterBlock` очищает назначенные атрибуты при завершении. Это подтверждённое дублирование и риск расхождения; само по себе оно не доказывает пользовательский баг. Общий helper или attachment стоит проектировать с учётом различий жизненного цикла и проверки существующих `form`-атрибутов.

## 14. `npm run check` требует `KIT_ADAPTER`, хотя документация описывает его для сборки — воспроизведено

При установленном Node 22 и зависимостях команда `env -u KIT_ADAPTER npm run check` завершается с кодом 1 ещё на `svelte-kit sync`:

```text
задайте KIT_ADAPTER=node, vercel или cloudflare
```

[README](https://github.com/ftugit/modals-kit/blob/51a63ae/README.md#L65-L67) описывает обязательный выбор адаптера для сборки, но это требование затрагивает и проверку типов. С `KIT_ADAPTER=node` в предыдущей сверке получены собственно шесть ошибок typecheck. Это подтверждённая проблема удобства разработки и документации; считать единственно правильным решение «выбрать адаптер автоматически» нельзя, поскольку явный выбор может быть архитектурным требованием. Можно как минимум документировать переменную для `check` и других затронутых команд.

## 15. Парсер ключа шифрования не проверяет заявленную печатность — воспроизведено на уровне функции

[`parseStorageServerEntry`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/hooks/storage-server-form/parse.ts#L96-L98) сообщает об ограничении «от 8 до 256 печатных символов», но проверяет только длину после `trim()`. Прямой вызов парсера в режиме редактирования со строкой `abcdefgh\u0001` вернул:

```json
{"ok":true,"keyHasControl":true,"issues":[]}
```

Это подтверждает расхождение текста и проверки на уровне парсера. Оно не доказывает, что такое значение проходит все уровни реальной отправки и сохраняется: полный UI/HTTP-путь не проверен. Нужно уточнить желаемый контракт: проверять допустимые символы либо изменить формулировку. Не следует называть это подтверждённой уязвимостью шифрования.

## 16. Статус сессии не имеет собственных живых часов — подтверждено кодом

[`SessionsView.svelte`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/content/user/ui/SessionsView.svelte#L42-L45) определяет «Активна»/«Истекла» через `Date.now()` при вычислении отображения, но не заводит таймер для обновления этого статуса. Если страница остаётся открытой после истечения сессии и список не обновляется по другой причине, метка может оставаться прежней. Это анализ кода, не браузерное воспроизведение; другое обновление данных может пересчитать метку.

В проекте уже есть [`TimeAgo`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/ui/time/TimeAgo.svelte#L24-L36) с периодически обновляемыми часами. Перед добавлением отдельного таймера стоит проверить возможность использовать имеющийся подход или общий источник времени, не предполагая, что сам компонент `TimeAgo` напрямую подходит для статуса.

## 17. `mergeSlot` маскирует объект под массив — подтверждённый типовой костыль

[`mergeSlot`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/shell/page.svelte.ts#L70-L96) фактически возвращает объект-маркер `MergeMarker`, приведённый через `as unknown as SlotItem[]`. Снаружи это объявлено как массив, хотя проверка `isMergeSlot` специально распознаёт не-массив. Текущий код, обрабатывающий маркер, может работать корректно, но тип контракта вводит потребителей в заблуждение: операции массива на таком значении потенциально упадут. Явный union для массива и маркера сделал бы контракт честным; необходимость и влияние на публичный API нужно оценить перед изменением.

Числа `888` и `999` действительно используются для упорядочивания слотов. Их наличие — вопрос поддерживаемости, не доказанный баг; одинаковые значения в разных зонах сами по себе не означают конфликт. Назначение именованных приоритетов и политика коллизий могут снизить риск случайного перезаписывания внутри одной зоны.

## 18. Уточнения к другим выводам приложенного отчёта

- **`fail()` и `r.value`.** Подтверждено по [`form/server.ts`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/lib/form/server.ts#L774-L787): переданная в `execute` функция `fail` бросает `ExecuteFailure`. Поэтому описанные две ошибки сужения типов не означают, что выполнение штатного обработчика после `fail` доходит до `r.value`.
- **Select без `ModalHost`.** [`Select.svelte`](https://github.com/ftugit/modals-kit/blob/51a63ae/src/components/ui/select/Select.svelte#L795-L837) действительно имеет ветки общего `Floating` и собственного inline fallback. Это два способа позиционирования, но fallback предназначен для отсутствующего хоста. Без проверки требований к автономному использованию и доступности нельзя назвать сам fallback ошибкой или рекомендовать его удаление.
- **Сброс БД.** Коммит `5211237` действительно удалил `DATABASE_RESET_ADMIN_URL` и сравнение назначения двух подключений. При текущем контракте используется один `DATABASE_URL`, поэтому старая проверка соответствия **двух** URL больше не применима. Риск появится, если отдельное reset-подключение вернут без эквивалентной проверки; самостоятельный текущий баг из удаления проверки не доказан. Причину архитектурного решения по одному только отсутствию текста в коммите установить нельзя.
- **Формальные нарушения README/коммитов.** Конкретные подсчёты из приложенного отчёта (15 из 40 и 6 из 40) не пересчитывались и не добавляются как независимо подтверждённые факты: необходимо учитывать действующие правила, область ближайшего README и тип изменения на момент каждого коммита.
- **Граница окна, полный vitest и внешние площадки.** Результаты тестов на `0cb1b5c`, полный vitest и развёртывания из приложенного документа в этой сверке не повторялись; соответствующие заявления остаются данными приложенного отчёта, а не самостоятельным воспроизведением.
